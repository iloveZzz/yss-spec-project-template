# 研发文档中文写作规范

起草或修订生命周期文档时，先读本规范的共用写法，再按阶段查阅第 3 节；发送进度与会签提示时读取第 4 节。按当前写入范围应用，正文、摘要和结构化信息应保持同一语义。

[Plan、Spec、Ticket、PR / MR 与复盘写作对照](../templates/examples/lifecycle-writing-examples.md)提供同一事实输入下的改写样例；示例不构成真实需求、执行证据或批准。

## 1. 适用范围与保留项

适用于研究结论、Plan、Spec、产品设计说明、工程契约的解释正文、Ticket、审查、PR / MR 描述、发布和复盘。聊天中的进度通知按第 4 节处理。

本文件是生命周期文档的共用写作规范。生命周期身份、门禁、资产所有权、批准和状态由根 `AGENTS.md` 指定的权威资产决定；标准术语消费根 `CONTEXT.md`。本规范约束表达，不新增阶段、审批或业务规则。

写作调整应保留这些内容的原意：主体、触发条件、规则、例外、量词、范围、非目标、数值及单位、证据引用、未决项、责任人、时点和依赖。稳定 ID、API 标识、schema、metadata、版本及批准记录按原合同保存。已经冻结的内容若需要改变行为，应回交资产所有者处理，不作为润色顺手修改。

## 2. 共用写法

### 先回答读者当前需要判断的问题

开头说明业务问题、本次结论或交付行为。必要背景紧接其后，让读者知道结论为什么成立。正式模板要求的 metadata 和身份信息仍保留；表达顺序的建议不能自行覆盖校验器要求的结构。

只在内容较长或需要导航时添加摘要。摘要引用正文，不另写一套范围和状态；维护时检查二者一致。

### 用主体、条件和结果表达需求

把“提升效率”“完善体验”等目标落实到具体场景：谁在什么情况下做什么，系统产生什么可观察结果。保留支持判断的业务动机，不把所有文字都拆成短句或编号。

输入没有规则时，记录待确认问题；不要为了让句子具体而补出时限、阈值、错误码或默认行为。重要缺口交回拥有该决定的工作单元。非阻断细节按既有流程记录责任人、解决时点和接收方。

### 让确定程度与证据一致

事实给出处；推断说明依据；方案使用建议语气；假设写明如何验证。章节开头已明确整段是假设或建议时，无须每句重复标签。

保留表达真实不确定性的“尚未确认”“可能”“取决于”。只有测试失败现象时，报告现象和下一项诊断，不编造原因；只有期望收益时，写目标和验证方法，不写成已实现收益。估算需有执行者、依据、范围和条件；无依据时不填精确工期。

### 让每段承担一项用途

一段解释一个问题、一项规则或一个取舍。顺序动作使用编号；同类规则、状态或选项比较使用表格；因果和取舍使用连贯段落。列表长度、段落数量和总字数按内容决定。

删除只有态度、没有事实或决定的修饰句。技术术语、业务术语和必要限定词保持准确，不使用同义词轮换制造变化。评价文档看它是否明确、可信和可执行，不追求模拟人的口头习惯或降低 AI 检测分数。

### 复用上游事实，交代本阶段新增内容

引用上游规则的可定位位置和必要版本，本阶段写新增细化、适用范围和交接。直接决定本地验收的条件可以在场景中重述，并绑定同一规则 ID；以一致性核验控制漂移。

不要用“详见相关文档”代替必要信息。引用不可读或版本不明时按现有合同处理。条件项只在流程允许时记录带原因的 `not-applicable`；命中的要求和必要异常场景应完整展示。

## 3. 各阶段怎么写

| 阶段 | 正文优先回答 | 本阶段需要写具体的内容 |
|---|---|---|
| 研究 | 已知什么，证据支持到哪里？ | 结论与来源、反证、限制分开；建议与事实区分 |
| Plan | 谁遇到什么问题，本期为什么这样取舍？ | 业务故事、MVP / 非目标、优先级依据、成功标准的确认情况、关键未决项 |
| Spec | 什么条件下，系统必须怎样表现？ | 规则与验收对应；按影响面覆盖成功、拒绝、边界、状态变化和恢复 |
| 产品设计 | 用户如何完成任务，失败后如何继续？ | 入口、操作、反馈、状态和恢复路径；引用 Spec，保留设计待确认项 |
| 工程契约 | 实现必须遵守什么，哪些地方有取舍？ | 精确协议与解释正文配合；标识、版本、范围及约束保持可核验 |
| Ticket | 本切片交付什么，如何证明完成？ | 窄而完整的行为、依赖、验收、公共测试 seam、当前合同及验证证据 |
| 审查 | 哪个具体条件下存在什么问题？ | 定位、触发条件、影响、依据与修复建议；推测和已复现问题分开 |
| 发布 / 复盘 | 验证了什么，还剩什么风险或决定？ | 实际验证范围、未覆盖部分、发布决定或失误机制与改进行动 |

这些指引帮助填写既有模板，不新增必填字段、阶段或门禁。Plan 不提前承诺详细 API 和工程实现；Spec 的例子不代替完整规则；Ticket 不重新设计已冻结行为。

### PR / MR 描述

用户要求起草或修订 PR / MR 描述时，按最终改动组织以下四部分。小改动可以写成四个短段落，复杂改动可用已有 PR / MR 模板；不要求新增模板文件或结构化字段。

1. **问题与 Before / After**：说明谁在什么条件下遇到什么问题，以及当前候选改变了什么可观察行为。已复现的原行为、候选目标与实际验证结果分别表达；未验证的 After 写成待验证目标。背景只保留解释本次改动所需的信息。
2. **范围与合同**：描述最终修改的范围，引用适用的现行 Spec、Ticket、工程契约或模板维护任务及其版本。交代影响判断所需的边界和依赖；不把未完成的依赖、草案或历史批准写成当前就绪。标题与正文围绕最终改动，不沿用已放弃方案的描述。
3. **实际验证与限制**：写明已执行命令的工作目录、退出码、对应结果及可定位证据。失败检查保留实际失败现象；未执行或未覆盖的检查说明原因和剩余限制，不能与通过项合并成“全部通过”。验证证据支持到哪里，结论就写到哪里。
4. **风险与回滚**：按实际影响说明剩余风险、依赖、阻塞及恢复方式。可逆改动引用已知回滚点和可执行恢复步骤；恢复尚未验证时明确说明。数据迁移、外部副作用或其他难以恢复的变化如实说明限制，不凭空承诺可以回滚。

起草或修订描述本身不授予 `git commit`、`git push`、远程创建 PR / MR、合并或发布权限。这些动作继续消费既有授权范围；描述、测试通过或自检结论不替代现行审查、批准和 Fresh Verification。

### 复盘中的改进与沉淀

先根据触发条件、实际影响和执行证据区分事实、已确认机制与待验证假设。检查已经存在但未接入实际执行路径，或本次没有执行时，优先修复接入与执行并引用执行证据。对重复出现、可机械判定的不变量，确认既有检查没有覆盖后，再提出能够检测该情形的最小检查和失败反例；无法机械判定的事项说明人工验证的方法、依据和结果记录位置。

改进动作及关闭状态继续由既有待办 / 工作项持有。复盘引用事实源、Skill、模板或检查的修订去向和实际验证结果；只有计划、建议或尚未执行的验证时保持待处理。单次现象先验证其机制和适用范围，不直接沉淀为通用禁令。

## 4. 进度与会签提示

### 将流程编号转成读者能理解的说明

面向用户的正文先写中文名称和具体动作。名称读取当前项目的生命周期注册表（`public_name` 优先，其次 `name`），角色读取 `digital-human-roles.yaml` 的 `name`；输入、产出和完成条件同样优先使用对应 `public_*` 字段。可以消费查询结果的 `presentation.names`，不得另建手工翻译表。

`stage.*`、`work-unit.*`、`gate.*`、`check.*`、`artifact.*`、`evidence.*`、`role.*` 属于追踪编号。聊天正文不直接串接这些编号；需要追踪时放在名称后的括号、详情或证据引用里。JSON / YAML 字段、命令参数、路径、批准记录仍保存原值；阅读视图可用“名称（编号）”逐项对照。未知编号写“名称未识别”并保留原值，不能猜名称、静默省略或改写旧资产。

说明应回答“目前什么情况、谁负责、接下来做什么、形成什么材料”。状态必须来自当前登记及验证，编号以 `approved` 结尾只表示检查身份；不能据此写“已批准”。负责人未登记时明确写出缺口，不能把角色候选当作实际指派。待核验、草案、批准、可实现分别表达，所有实质阻塞都要保留。

例如，只有已登记需求经理负责且检查状态待核验时，才可表述：“方案决策包评审状态待核验。下一步由需求经理汇总已确认的规划、业务边界和商业约束，形成供评审和后续 Spec 使用的方案决策包。”具体材料的版本、证据和批准状态继续引用原资产。不能把这个例子当成真实项目状态。

状态阅读可用 `scripts/lifecycle-status --root <项目> --checkpoint <ref> --format text`；默认 JSON 继续供工具读取。该查询及其中文展示均不授予执行或批准权限。

生命周期主控每轮返回或暂停，以及用户询问状态、恢复、阶段切换或出现阻塞时，简短说明：**当前阶段与本轮结果、下一阶段或单元及进入条件、问题与阻塞、谁处理及如何解除、下一动作**。依具体内容用连贯短段落或列表，不强制表格或固定行数；输出检查以当前编排合同的 `user_progress_report` 为准。普通问题直接回答；其他进度更新只说明本轮有意义的变化，状态未变时不重复整套说明。

状态读取已有 checkpoint 和适用验证结果，不建立或要求用户填写另一套状态文件。未核验的阶段或阻塞情况写“待核验”；只有当前适用证据支持时才能写“无阻塞”。证据过期应明确指出过期输入及恢复动作，不能沿用历史通过结论。责任人按已有登记填写，缺失写“未登记”，不自行指派；下一动作说明如何补齐登记或核验。

下一单元仍属当前阶段时说明剩余工作；拟进入的下一阶段附进入条件，不把目标写成已获准流转。阻塞逐项说明影响、来源、责任方、处理动作、解除证据和恢复检查；未决项与建议按实际影响表达。只读查询的未发现不等于已核验无阻塞，缺少下一路由不等于完成。模板源展示维护步骤和验证目标，阶段、批准和完成结论仍由原权威合同裁决。

默认只展示当前需要处理的事项，证据路径按需展开。查看状态本身不改文件，也不触发全套验证；推进阶段时仍执行原有适用校验。已授权且 Agent 可以完成的动作继续执行，避免把操作转交用户。

请求决定时展示当前版本、推荐方案及理由、实质选项和取舍、风险、批准范围与后续动作，遵守既有用户决定协议。可以突出当前最重要的问题，但所有影响决定的阻塞和选项都应可见。一次回复需要多个相互独立的决定时，分别说明各自影响。

示例：“规则说明已补齐。成功标准仍缺统计口径，负责人需在 Plan 进入 Spec 前确认；当前材料尚不能支持流转。”这类表述需要实际资产支持，不能成为固定的完成话术。

## 5. 起草与修订时的检查

1. 确认文档读者、当前阶段、权威输入和允许改动的范围；区分从事实起草与对既有正文作等义改写。
2. 起草时按本阶段的问题组织内容；修订时先列出必须保留的规则和约束，再调整文字。
3. 对照输入检查有无新增承诺、规则丢失、范围扩大、责任转移或不确定性被抹去。发现源资产冲突时记录并回交，不自行选一个版本。
4. 检查正文、摘要、表格和状态是否一致；验证适用的引用、结构和合同。自检结论不代替独立审查或批准。

规则、例外、证据或状态变化属于实质差异，不能被“字数减少”抵消。不要只用禁用词扫描或模型给自己的分数判断效果。

生成阅读材料使用 [合同阅读入口](contract-reading.md)。业务解释写入权威资产或人工 Markdown；不要手改 `reading/*.review.md`、manifest 或 map 的工具标记块。源编辑完成后更新已启用的阅读包，批准仍引用原资产及其摘要。
