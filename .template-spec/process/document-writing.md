# 研发文档中文写作规范

起草或修订研发文档时，先读本规范的共用写法，再按文档类型查阅第 3 节；发送进度与批准提示时读取第 4 节。按当前写入范围应用，正文、摘要和结构化信息应保持同一语义。

[Plan、Spec、Ticket、PR / MR 与复盘写作对照](../templates/examples/lifecycle-writing-examples.md)提供同一事实输入下的改写样例；示例不构成真实需求、执行证据或批准。

## 1. 适用范围与保留项

适用于研究结论、Plan、Spec、产品设计说明、工程契约的解释正文、Ticket、审查、PR / MR 描述、发布和复盘。聊天中的进度通知按第 4 节处理。

共用的事实、约束与未决项保留规则见 [技能内共用规范](../../.agents/skills/i-have-adhd/references/document-writing.md)。

## 3. 各类文档怎么写

| 文档类型 | 正文优先回答 | 需要写具体的内容 |
|---|---|---|
| 研究 | 已知什么，证据支持到哪里？ | 结论与来源、反证、限制分开；建议与事实区分 |
| Plan | 谁遇到什么问题，本期为什么这样取舍？ | 业务故事、MVP / 非目标、优先级依据、成功标准的确认情况、关键未决项 |
| Spec | 什么条件下，系统必须怎样表现？ | 规则与验收对应；按影响面覆盖成功、拒绝、边界、状态变化和恢复 |
| 产品设计 | 用户如何完成任务，失败后如何继续？ | 入口、操作、反馈、状态和恢复路径；引用 Spec，保留设计待确认项 |
| 工程契约 | 实现必须遵守什么，哪些地方有取舍？ | 精确协议与解释正文配合；标识、版本、范围及约束保持可核验 |
| Ticket | 本切片交付什么，如何证明完成？ | 窄而完整的行为、依赖、验收、适用公共接口、真实约束与实际验证限制 |
| 审查 | 哪个具体条件下存在什么问题？ | 定位、触发条件、影响、依据与修复建议；推测和已复现问题分开 |
| 发布 / 复盘 | 验证了什么，还剩什么风险或决定？ | 实际验证范围、未覆盖部分、发布决定或失误机制与改进行动 |

### 解释历史编号与实际状态

正文先说明具体对象、当前情况、负责人和下一动作。需要解释历史编号时，依据实际可读的原文说明名称和含义，保留原 ID、版本及来源；资料不足就明确无法确认，不猜名称或改写旧资产。普通写作不依赖生命周期注册表或角色登记。

状态依据当前事实和用户的真实决定；编号含 `approved` 不代表已经批准，候选负责人不等于实际指派。区分草案、已完成、待验证和待决定，保留影响当前任务的真实缺口，不从历史阶段推导执行资格。

## 4. 进度与决定

说明当前实际结果、未完成事项和下一动作；已有授权的独立工作继续。查看状态本身不改文件或触发全套验证，不从历史阶段编号推断当前资格。

需要真实决定时展示具体对象、推荐项、取舍与影响，复用用户已给的决定和授权。常规实现选择不另设确认；新范围或动作缺权限时只暂停依赖部分。

## 5. 起草与修订时的检查

按 [共用检查](../../.agents/skills/i-have-adhd/references/document-writing.md#起草与修订时的检查) 核对原意、范围、引用与正文一致性；自检不代表业务批准。保留历史记录和用户内容，不为普通文档新建阅读包、manifest、阶段检查或证据资产。
