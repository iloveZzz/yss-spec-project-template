# 阶段接入与产物复用使用手册

已有需求、设计、冻结接口或交付包时，可以让 `yss-product-lifecycle` 核验这些产物，从最近可信阶段继续。有效的上游成果可以复用；缺失或过期的部分按依赖补齐，不需要默认从 Plan 重做。

本手册面向项目负责人和后端交付人员，重点演示如何复用已有产物接续后端交付。本文是现行规则的操作说明，不新增阶段或批准入口；规则以[生命周期注册表](../process/lifecycle-registry.yaml)和[流程裁剪规则](../process/harness-process-tailoring.md)为准。

## 1. 先确认在哪个项目操作

在承载实际业务的 `project-instance` 中开始，读取本地 `yss-project.yaml`、`AGENTS.md`、根 `CONTEXT.md` 和适用 profile。当前主模板仓库是 `template-source`，用于维护流程和手册，不能在这里生成真实业务 Spec、切片或实现合同。

| 你所在的项目 | 可以接着做什么 |
|---|---|
| 综合项目实例 | 由 `yss-product-lifecycle` 核验上游，继续设计、工程契约、Ticket、实现或验证 |
| 专职后端项目实例 | 消费批准的上游资产，完成后端技术设计、实现与交付 |
| 尚未初始化或接管的代码仓 | 先按[用户手册](用户手册.md)初始化或接管，并登记实现仓库 |

专职项目使用本地已安装的技能与职责规则；不要从主模板复制一个主控 Skill 来替换本地入口。治理仓与代码仓可以分离，代码写入已登记的实现仓及允许路径。

## 2. 最快开始：给 Agent 一段完整指令

把下面尖括号中的内容替换为真实信息。没有的资料写“缺失”，不知道的状态写“待核验”，不必为了开始咨询先填写整套合同。

```text
使用 yss-product-lifecycle，从已有产物接入本功能。

目标：<本次希望完成的业务行为>
治理项目根：<project-instance 的绝对路径>
目标实现仓：<代码仓绝对路径或现有登记引用>
已有产物：<Spec、设计、交付包、合同等路径>
批准与验证证据：<可读取引用；没有则写缺失>
父 Ticket / 切片 / checkpoint：<现有引用；没有则说明>
希望开始的位置：<工程设计、实现或验证>
本次范围：<功能、页面、切片及不包含的内容>

先只读判断最近可信阶段，给出可以复用的资产、阻塞项和下一工作单元。
核验上游版本、批准范围及当前证据，不把文件存在视为阶段通过。
暂不写文件或代码。
```

如果已决定推进，可以把最后一句替换为：

```text
完成核验后，在本次范围内继续可执行的工作单元，只补齐缺失项。
优先核验并延续已有授权；遇到实质变化、必要输入缺失或适用人工决定时，
展示当前资产、差异与下一动作。满足 ready-for-agent 后才实现代码。
```

自然语言即可表达入口意图，不要求记忆模式关键字。`route` 表示只读路由，`audit` 表示只读审计，`orchestrate` 表示有界推进，`resume` 表示重建状态后恢复。模式语义见[主控编排说明](../../.agents/skills/yss-product-lifecycle/references/orchestration.md)。指定“从实现开始”只是期望入口，最终仍由当前证据决定。

### 同一功能从短目标继续

在完整 Spec 主控中，如果上次已完成 `spec-approved` 或 `product-design-completed`，明确说“继续同一功能 `<feature_id>`，本次目标改为 `<新目标>`”。主控沿用原 checkpoint 和有效批准，先设置新目标并复验，再推进首个合法未完成工作单元。不要新建功能来绕过原阻塞，也不要把短目标达到改写为业务整体完成。可复制指令见[用户手册](用户手册.md#先完成-spec再继续设计与交付)，命令见[目标配置步骤](unified-cli.md#正式功能的可续推目标)。

## 3. 根据手里的产物选择入口

| 已有材料 | 可以请求的下一动作 | 进入下一步前重点核验 |
|---|---|---|
| 已批准 Plan / 战略输入 | 继续 Spec | 当前范围、关键未决项、Plan → Spec 入口审阅及真实批准 |
| 已批准 Spec | 继续产品设计或适用工程分析 | 验收标准、影响面、上游新鲜度；有产品设计影响时完成对应设计 |
| 已批准页面方案或原型 | 继续工程契约与实现准备 | 页面、状态、权限体验与 Spec 一致；适用技术和接口契约完整 |
| 冻结接口及工程设计 | 继续 Ticket 与合同准备 | 工程批准、实现仓接入、切片范围及相关 UI 输入 |
| 已实现代码及当前合同 | 继续审查与验证 | 实际改动与批准范围一致、当前验证证据；已有代码不能补作批准证明 |

这些是常见入口，不是凭材料名称自动流转的对照表。上游资产需要同时满足内容、审查、批准和新鲜度要求。某项确实未命中时，按现行规则记录有原因和证据的 `not-applicable`；某项适用但未完成时，保留阻塞。

## 4. 后端交付

本节的正式目录包、ZIP 和导入步骤用于独立工程交接。同一个 Spec 主控内推进时，直接消费本功能批准的接口和工程资产，核验当前本地后端交付证据；不将资产自导自入，也不生成外部 Receipt。本地后端终点记录见[推进目标协议](../process/lifecycle-progression.md)。

### 4.1 后端准备什么

请后端提供由正式工具导出的 Backend Delivery 目录或 ZIP，以及目标环境和必要的访问条件。交付包应绑定当前窄业务切片、战略快照、规则和场景、冻结 OpenAPI、后端 Slice Contract、批准引用、构建部署身份与验证证据。包内不放运行时凭据。

后端可以使用以下指令：

```text
请为切片 <slice-id> 准备后端交付。
复用当前批准的战略基线、冻结接口和后端 Slice Contract。
核验构建、部署、测试数据和成功/失败场景证据，按现有协议准备交付描述。
从正式 backend-delivery 入口导出目录包及 ZIP，并报告导出路径、版本和摘要。
缺少源批准、部署身份或预检清单时列出缺口，不伪造记录。
```

只有 Swagger 链接、源码或接口截图时，先做缺口分析。它们不能单独证明业务范围、UI 输入和当前批准已齐备。

## 5. 需要手动操作时的命令

以下命令供交付维护人员和 Agent 使用。普通用户可以直接使用第 2、4 节的指令，让 Agent 操作并报告结果。命令中的 `scripts/` 来自当前已安装相应工具的治理项目；不要在未核对 profile 和工具版本时混用其他项目的脚本。

尖括号表示需替换的参数，不要原样粘贴执行。`--source-root`、`--target-root`、`--root` 指向治理项目根；交付描述、预检和接收记录中的引用按各自协议相对该治理根解析。新建后端交付输出目录必须尚不存在。

### 后端导出

在后端治理项目准备好真实交付描述后运行：

```sh
scripts/backend-delivery export \
  --source-root <后端治理根绝对路径> \
  --delivery <相对后端治理根的交付描述路径> \
  --output <新的交付输出目录绝对路径> \
  --zip
```

**既有后端工程身份为 v2 时，必须增加 `--preflight-input <预检清单绝对路径>`。**清单使用 `delivery_kind: backend-delivery`，绑定本次源交付描述和当前摘要；准备方法见[只读交付预检](../process/delivery-preflight.md)。预检失败时按返回的 `recovery` 补证，再从正常导出入口重试。

### 验包与导入

在目标治理项目运行：

```sh
scripts/backend-delivery verify --bundle <交付目录或ZIP绝对路径>

scripts/backend-delivery import \
  --bundle <交付目录或ZIP绝对路径> \
  --target-root <目标治理根绝对路径>
```

验包成功输出 `result: verified`，并明确 `live_service_checked: false`。记下导入命令返回的真实收据和草案路径；不要自行推测文件名或把草案状态直接改成已批准。

如果当前只有战略包，可先独立验证和导入：

```sh
scripts/strategic-handoff verify --bundle <战略交付目录或包绝对路径>
scripts/strategic-handoff import \
  --bundle <战略交付目录或包绝对路径> \
  --target-root <目标治理根绝对路径>
```

后端包已经带入同一战略版本时，无需重复做手工导入。不通过修改 schema 版本来绕过检查。

### 只读查看主控规则

综合项目可以查询实现入口的确定性合同投影：

```sh
scripts/query-lifecycle-context \
  --mode route \
  --work-unit work-unit.slice-implementation \
  --include modes
```

此命令只展示规则与路由，不读取业务资产来代替完整就绪判定，也不会批准或执行实现。可用阶段、工作单元和查询键以本地注册表及工具支持为准。

## 6. 已有合同或中断后如何恢复

已有完整 Slice 合同，可以直接提出恢复请求：

```text
使用 yss-product-lifecycle 恢复切片 <slice-id>。
checkpoint：<路径>
Slice Contract：<路径>
目标实现仓：<登记引用>

重新核验当前合同批准、上游摘要、Ticket、实现计划和允许路径。
前提仍满足时，从第一个未完成且未阻塞的工作单元继续。
复用未变化的有效资产，不重做已完成的需求和设计；
发现过期或新影响时，只回到受影响的资产与工作单元处理。
```

新会话、新机器或新目录不会使旧结论自动有效。恢复必须能读取原始资产与证据；相关输入变化后，先更新接收和依赖合同，再恢复。不同切片使用各自交付身份，避免不相关工作相互阻塞。

## 7. 常见阻塞怎么处理

| 现象 | 应采取的动作 |
|---|---|
| 当前仓是 `template-source` | 切换到真实项目实例；不要手改身份字段把模板源伪装成产品仓 |
| 只有接口文档，没有战略或业务验收 | 请来源方补交业务规则、范围和批准依据，先完成缺口分析 |
| 交付包导入成功，但仍不能编码 | 查看接收检查、Ticket、合同批准和就绪缺口 |
| 目标词汇与源包冲突 | 完成目标根 `CONTEXT.md` 对账；业务规则冲突回交来源方 |
| UI 基线缺失或不匹配 | 补适用产品设计；既有 UI 基线仅按其限定条件使用，截图不能自行成为批准 |
| `preflight-required` | 按只读交付预检合同准备当前源资产清单，并传入 `--preflight-input` |
| API、包摘要或部署身份不一致 | 核对交付版本，向后端补取同一基线的冻结接口、部署与证据 |
| 导入了新的同身份后端版本 | 重新接收当前版本，更新绑定并重编译受影响的合同 |
| 合同出现 `stale`、`drift` 或 `new_impacts` | 停止依赖旧合同的实现，回到受影响的设计、接收或合同编译环节 |
| 工具缺失、profile 或 schema 不支持 | 按[用户手册](用户手册.md)核对实例固定版本与同步路径，保留现有资料，不混拷脚本或静默降级 |

## 8. 如何判断这次接入已达到目标

要求主控用当前资产报告：复用了哪些上游内容、从哪个工作单元接入、哪些缺口已补齐、还剩哪些阻塞，以及下一动作。需要编码时，必须明确报告目标切片、当前合同和 `ready-for-agent` 结论；需要交付时，另提供实际测试及独立审查结果。最终业务验收需绑定同一战略、API 和后端部署版本。Git 提交、推送、合并与发布仍各自遵守授权边界。
