# 从这里开始

第一次使用 YSS 只读本页即可完成第一个任务；其余手册按需查阅。

## 1. 安装并核对 CLI

按[安装、接管、升级与恢复](cli/install-and-verify.md)取得固定版本的 `yss`，再运行 `yss version --json` 核对版本与 Bundle 来源。新项目用 `yss init`，已有工程用 `yss attach`，选型见[用户手册](用户手册.md#选择项目家族)。

## 2. 第一个任务：先走日常路径

大多数改动只需要一张任务单（Ticket 或 PR）。先让 Agent 判断这次改动能不能走日常路径，能走就不用准备阶段文档。

1. 在项目实例里写下这次改动的目标、验收标准、要改的仓库，以及怎么回滚。
2. 让 Agent 运行路径判定：

   ```sh
   yss lifecycle route --root <项目目录> --task <任务单> --implementation-root <实现仓> --base <完整提交 SHA> --view agent --json
   ```

   较新版本的 yss（该功能已合入 yss-cli 主干，随下一个 CLI 发行版提供）去掉 `--view agent --json` 后会直接输出几行中文摘要：路径、原因、当前改动数和下一步命令；`--json` 输出保持不变。当前固定版本仍输出完整字段。
3. 看结论：
   - `daily`：按“需求验收 → 实现 → 测试 → 独立审查”推进，所有记录写在同一张任务单里。
   - `governed`：这次改动触及数据迁移、跨仓库、发布等风险，改走正式流程（见第 3 节）。
   - `needs-info`：缺事实，让 Agent 先调查并补进任务单，再判定一次。
4. 完成后核对任务单里的实际测试结果和审查结论；没有执行的检查必须写明，不能算通过。

这一步只读，不会创建阶段文档、批准或提交。日常路径的细节见[日常交付与正式功能目标](cli/daily-and-targets.md)。

## 3. 什么时候改走正式流程

命中下列任一情况时，`route` 会返回 `governed`，按[用户手册](用户手册.md#先完成-spec再继续设计与交付)从最近可信阶段推进。完整清单以[请求分流合同](../process/orchestration/entry/request-triage.yaml)的 `excluded_impacts` 为准。

| 情况 | 举例 |
|---|---|
| 数据或平台变化 | 数据迁移、平台或架构转换 |
| 跨仓库或权限 | 一次改动涉及多个实现仓、权限变更 |
| 发布与外部审批 | 部署、发布、需要外部审批 |
| API 风险 | 不兼容的 API 变更，或 API 影响无法判断 |

已经处于正式流程的任务不会降级为日常路径；Design Profile 不提供日常路径。
