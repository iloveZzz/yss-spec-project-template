# 战术设计子项目用户手册

本入口保留给既有读者。“战术设计子项目”通过 `yss-technical-design` 统一承接技术设计，整体主控仍为 `yss-product-lifecycle`。先确认后端项目采用 `domain-driven` 或 `layered-mvc`，再分别调用 `yss-tactical-design` 或 `yss-mvc-design`；DDD 是选项，不是默认要求。技术设计不代替 API Freeze 或 Slice Contract 批准。

## 输入与开始

先核对本仓身份、profile、根 CONTEXT.md、适用的战略交接、需求及批准证据。已有战略包时，导入快照后完成目标词汇对账，再逐项登记源规则/关键场景的承接；缺失、冲突或过期先回交，不能猜测业务规则。

```text
请按本仓生命周期检查“设备领用”当前战略输入及目标词汇对账。
使用 yss-technical-design 核对已确认的项目架构并起草技术设计，
DDD 调用 yss-tactical-design，传统 MVC 调用 yss-mvc-design；
解释设备占用的竞争、状态转换和一致性边界，并映射公开测试 seam。
逐项列出已承接、冲突、延期及依赖切片，等待适用审查后再编译实现合同。
```

## 评审要回答的问题

| 设计问题 | 设备借用中的例子 |
|---|---|
| 谁保护不变量 | 哪个对象/边界保证设备不能同时被领用 |
| 状态是否合法 | 未批准申请是否允许领用；重复归还如何处理 |
| 一致性在哪里保证 | 申请与设备占用是否同事务；失败如何恢复 |
| 外部依赖如何隔离 | API/Repository/适配边界怎样映射而不篡改业务含义 |
| 如何证伪设计 | 并发领用、无权限、重复请求的公开 seam 与预期结果 |

案例只是提问方向，答案由项目实际业务与工程条件决定。MVC 不要求先完成战略 DDD，也不要求聚合、值对象或 DDD Gateway；用例、规则、事务、幂等、并发和测试承接仍须清晰。没有相关技术设计影响时记录带原因的 not-applicable。

## 从设计到实现

综合项目由本仓生命周期继续路由，通用研发/后端由 Harness 流程承接。前端专职只消费上游规则、冻结接口并准备前端工程设计，不在本仓派发后端战术实现。

技术设计经现有门禁批准后，编译器消费当前设计并起草实现合同，批准与可实现状态由本仓编排和门禁控制。实现前确认工程登记、冻结接口、测试 seam、允许路径与回滚点。战术评审通过不等于 ready-for-agent。

过程示例见 [设备借用贯穿案例](设备借用贯穿案例.md)；项目选型见 [用户手册](用户手册.md)。
