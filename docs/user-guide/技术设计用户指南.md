# 技术设计用户指南

本指南说明批准战略或 Spec 如何进入后端技术设计。统一入口是 `yss-technical-design`；工程采用 `domain-driven` 时调用 `yss-tactical-design`，采用 `layered-mvc` 时调用 `yss-mvc-design`。架构类型来自当前工程登记或经用户确认的脚手架决定，不能按目录或个人偏好猜测。

## 开始前检查

先核对仓库身份、根 `CONTEXT.md`、批准战略或 Spec、目标实现仓登记、工程基线和适用批准。既有 Java/Maven 工程还要提供当前的 repository registration、engineering baseline 与 observation manifest；三份原始证据、实际 Git/Maven 工程和摘要必须一致。

```text
请读取当前批准战略或 Spec、根 CONTEXT.md 和工程登记。
核对架构身份与既有工程证据，再用 yss-technical-design 起草当前技术设计。
domain-driven 使用 yss-tactical-design；layered-mvc 使用 yss-mvc-design。
说明状态、事务、并发、幂等、持久化和公开测试 seam，并逐项映射源规则与关键场景。
列出冲突、延期、依赖和需要的批准；不要提前实现代码。
```

缺失、冲突或过期输入应回交事实所有者。技术设计不得改变业务规则，也不能用“实现方便”覆盖已批准行为。

## 两类架构分别回答什么

| 设计问题 | `domain-driven` | `layered-mvc` |
|---|---|---|
| 业务不变量由谁保护 | 聚合、Entity、Value Object 或 Domain Service | 用例服务、事务边界和明确校验组件 |
| 状态如何变化 | 聚合行为和状态机 | Controller/Application/Service 调用下的状态规则 |
| 一致性如何保证 | 聚合边界、Repository、事件和补偿 | 事务服务、幂等、并发控制和持久化约束 |
| 外部依赖如何隔离 | Gateway/Repository/Adapter | Controller、Service、Mapper/Repository 和外部适配器 |
| 怎样证伪 | 领域公开 seam 的正常、拒绝和并发场景 | 用例/API seam 的正常、拒绝和恢复场景 |

MVC 不要求先构造聚合、值对象或 DDD Gateway；DDD 也不能把数据库表直接当作领域边界。两者都必须解释用例、规则、事务、并发、失败恢复和可执行验证。

## 从设计进入实现

API 有影响时先形成 OpenAPI 3.1 Draft，完成适用审查后 Freeze。随后把技术设计、冻结接口、工程登记、验证命令和回滚点编译进窄 Slice Contract。

`yss-implementation-contract-compiler` 只起草合同，不批准合同、不设置 `ready-for-agent`。实现前必须重新确认：

1. 技术设计和工程证据仍与当前源码一致。
2. Slice Contract 已由本仓适用门禁批准。
3. 允许写路径是批准范围与实现仓登记范围的交集。
4. 成功、拒绝、并发、幂等和恢复场景具有公开测试 seam。
5. 后端优先使用登记工程根 `./mvnw` 验证。

技术设计评审通过不等于实现、合并或发布就绪。过程示例见[设备借用贯穿案例](设备借用贯穿案例.md)，项目选型见[用户手册](用户手册.md)。
