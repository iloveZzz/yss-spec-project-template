# 分仓接入实践指南

本文面向产品实例操作者：如何把**研发管理仓库**（口语「研发仓」）、**前端实现仓库**、**后端实现仓库**分成三个独立 Git 来管理。术语以 `CONTEXT.md` 为准；决策见 [ADR-0008](../adr/0008-split-repo-and-monorepo-harness-topology.md)；登记字段见 [实现仓库接入](../process/implementation-repo-integration.md) §1.0。

口语「分层接入」按**分仓接入**理解，不是第四种拓扑，也不是把前后端嵌进研发管理仓库。

## 1. 三仓职责

| 仓库 | 放什么 | 不放什么 |
|---|---|---|
| 研发管理仓库（`project-instance`） | Spec、OpenAPI、Ticket、实现仓库登记、跨仓库切片、验证与发布记录 | 前端 / 后端运行时代码；不要把实现仓变成本仓的 git submodule |
| 前端实现仓库 | Vue / 微应用源码、该仓 CI、该仓 MR / PR | Harness 文档与 Ticket；不要对本仓单独 `attach` 冒充一体仓 |
| 后端实现仓库 | Java / DDD 源码、该仓 CI、该仓 MR / PR | 同上 |

绑定方式：在研发管理仓库做 `implementation-repo-onboarding`，登记各自的 `git_url` 和磁盘真实 `project_root`（`topology=分仓接入`，`layout_policy: external-repository-native`）。**不是** submodule、**不是** subtree、**不是** 把源码复制进 Harness。

三仓默认关系：

```text
研发管理仓库  --登记 git_url-->  前端实现仓库
研发管理仓库  --登记 git_url-->  后端实现仓库
```

主 Ticket tracker 仍是研发管理仓库里 `docs/agents/issue-tracker.md` 的配置，模板默认 `local-markdown`。Git remote（即使在 GitHub）不自动改 tracker。

分仓实例仓默认放在 GitHub。前端 / 后端实现仓沿用各自已有托管，不必迁到 GitHub 才允许登记。

## 2. 一次性搭台

适用于新产品、前后端已经（或即将）是独立 Git 仓库。

1. **空目录初始化研发管理仓库**（不要对 `template-source` 做 `attach`）：

```bash
npx create-yss-spec@latest \
  --project-name "项目名称" \
  --business-domain "业务领域" \
  --target-dir "./<product-harness>" \
  --git-init
```

命令细节见 [create-yss-spec 外部 CLI 实践指南](./外部命令行工具实践指南.md)。`init` 不创建前端 / 后端远程仓库。

2. **准备两个实现仓**：新建或指定已有前端仓、后端仓 URL。CLI 不会代你建仓。

3. **分别 onboarding**：在研发管理仓库工作树里调用 `implementation-repo-onboarding`，`repo_role` 分别为 `frontend` 与 `backend`。需要 clone 时只进**临时目录**，不要 clone 进 Harness 工作树。按 [实现仓库登记模板](../templates/implementation-repo-registry-template.md) 落盘，至少填写：

   - `topology` = `分仓接入`
   - 两个不同的 `git_url`
   - 各仓真实 `project_root`（不要填本仓的 `apps/` 占位路径）
   - CI、测试 / 构建命令（前端优先 `pnpm`，后端优先 `./mvnw`）

4. **阻断项**（命中即停）：

   - 对本 `template-source` 执行 `attach`
   - 把 Harness 资产 `attach` 进仅前端或仅后端仓
   - 用 `git submodule add` 把实现仓嵌进 Harness
   - 实现仓 URL 尚未提供就开始 Router 写业务代码

已有前后端**同仓**时不要走本节：对该仓根目录 `attach`，见 CLI 指南「接管已有项目」。

## 3. 工作区怎么摆

### 本地

三个并列 clone，目录名可自定，不要把前后端放进 Harness 子目录：

```text
~/work/<product>-harness/     # 研发管理仓库
~/work/<product>-frontend/    # 前端实现仓库
~/work/<product>-backend/     # 后端实现仓库
```

### Cursor Cloud

分仓使用**多仓环境**：创建环境时勾选上述三个 GitHub 仓库。Cursor 会把每个被选仓库 clone 到 Agent 机器（并列工作树），不是 nested gitlink。不要发明 `environment.json` 的 `repos` 字段来代替 dashboard 多选。一体仓才用单仓环境。

### CI

需要同时看到多仓时，对每个仓库做一次 checkout 到不同 `path`（GitHub Actions 的 side-by-side checkout）。不要把实现仓做成 Harness 的 submodule 再设 `submodules: true`。默认 checkout 不会自动拉子模块；本拓扑根本没有子模块。

## 4. 日常一个垂直切片

1. 需求、OpenAPI、Ticket 只写在研发管理仓库。
2. 实现前按 [跨仓库切片模板](../templates/cross-repo-slice-template.md) 绑定：`topology=分仓接入`；`backend_repo` 与 `frontend_repo` 为两个 `git_url`。
3. 建议交付顺序：Harness 冻结 OpenAPI → 后端 MR → 前端消费 Freeze → 两边 CI / 验证命令回写 Harness checkpoint。
4. 写路径用登记根。禁止用实例仓 `apps/` 冒充外部仓路径。
5. 任一实现仓未完成验证，不得声称该切片完成或可发布。

## 5. 不要走分仓的情形

- **已有一体仓**（前后端已在同一 Git）：仓根 `create-yss-spec attach`，按磁盘真实 `project_root` 登记，不迁到 `apps/`，也不拆 Git 历史来「符合分仓」。
- **用户明示新建一体仓**：运行时落在 `apps/backend/<project>/` 与 `apps/frontend/<project>/`。
- **想一次 clone 看到三份代码**：用 §3 的并列 clone / Cursor 多仓，不要改成 submodule。

Git submodule 能嵌出组合工作树，但钉的是子仓某个 commit，子仓前进后父仓还要再提交 gitlink。机制事实见 [submodule 研究笔记](../reviews/research-git-submodules-layered-access-2026-08-24.md)，不在本指南重写 Git 手册。

## 6. 常见失败

| 现象 | 处理 |
|---|---|
| 把实现仓 URL 填成模板源 | 停；模板源不是产品研发管理仓库 |
| 用 `attach` 代替 onboarding | `attach` 只用于已有一体仓；分仓用 `init` + 分别登记 |
| 把 GitHub remote 当成 Ticket 主 tracker | 只改 `docs/agents/issue-tracker.md` 才换 tracker |
| 前端仓尚未提供就开始实现 | 先 onboarding；缺 URL 视为阻断 |
| 在 Harness 里 `git submodule add` | 撤销；改回登记 + 独立 clone |
| 用 `apps/` 占位冒充外部 `project_root` | 改成该实现仓磁盘上的真实根 |
