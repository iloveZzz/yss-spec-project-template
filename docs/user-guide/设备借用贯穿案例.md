# 内部设备借用：贯穿四个现行家族的教学案例

本文是虚构教学说明，不是已批准 Spec、真实交付包或可直接执行的产品合同。示例路径、规则和标识由学习者在独立 `project-instance` 中确认后落盘；模板源不登记这些业务词汇。

## 业务故事与范围

员工申请借用设备，负责人审批，管理员记录领用和归还。第一轮仅支持一张申请借用一台设备；采购、计费和维修不在案例范围。统一管理方协调战略、后端和前端版本。

| 场景 | 正常结果 | 必须讨论的反例 |
|---|---|---|
| 提交申请 | 形成待审批申请 | 日期非法、设备不可借 |
| 审批 | 形成批准或驳回结果 | 无权限、重复审批 |
| 领用 | 记录领用并改变设备占用状态 | 未批准、设备被另一申请占用 |
| 归还 | 记录归还并释放设备 | 重复归还、设备损坏如何另行处置 |

“审批是否预占设备”“谁能代领”“超期如何处理”是待用户决定，不由 Agent 默认为业务规则。完整故事贯穿教学；每次实现仍只选一个窄业务切片，例如“已批准申请领用设备”。

## 1. 选择工作组织

综合模板可承载从澄清到业务验收的管理资产。战略模板只负责上游方案，后端和前端模板按交付协议接力；专职路线必须登记统一管理方及独立实现仓，不把源代码复制进模板。既有通用研发实例只按原固定版本维护，不作为本案例的新建路线。

## 2. 战略方形成可交接输入

```text
请按本仓战略流程澄清“内部设备借用”。
逐轮确认参与者、目标、范围、申请/审批/领用/归还规则及失败场景。
先提出会改变业务结果的问题，不替我决定审批是否占用库存。
确认后再起草 Spec、需要的页面流程、视觉基线和业务级 Ticket。
列出准备交接的规则、关键场景、版本、批准证据和研发待决事项。
```

用户逐项核对业务和页面。预期输出为本仓合同要求的已批准战略资产、根词汇、交接描述及证据闭包，不能只交聊天摘要。战略方不在此生成后端工程或冻结工程 API。UI 有变化时交付已批准原型；确认无 UI 变化的既有工程使用 `existing-ui-baseline`，不能用截图把既有界面伪装成原型。

由 Agent 给出实际交接描述路径后，在战略实例执行以下命令。尖括号必须替换为真实路径，输出目录须新建；`--handoff` 是相对源实例的文件路径。

```bash
node scripts/preflight-delivery --input <战略预检输入.json> --stage export --json
node scripts/strategic-handoff export --source-root . --handoff <交接描述相对路径> --output <新包目录> --zip
node scripts/strategic-handoff verify --bundle <包目录或ZIP>
```

预检输入使用 `delivery_kind: strategic-handoff`，绑定交接描述和当前 UI 基线。预期验包输出 `result: verified` 及包摘要；缺证据或被修改的包会失败。把完整目录/ZIP 交给下游，保留版本与摘要，不手改包内文件。

## 3. 后端接收

在接收实例运行：

```bash
node scripts/strategic-handoff verify --bundle <包目录或ZIP>
node scripts/strategic-handoff import --bundle <包目录或ZIP> --target-root .
```

```text
请读取导入收据和包内规则/场景，核对本仓根 CONTEXT.md 并形成正式对账。
为“已批准申请领用设备”逐项登记承接、冲突和依赖。
按当前流程核对既有工程身份，准备技术设计、API Draft/Freeze 和后端 Slice Contract，
登记真实实现仓、验证命令和回滚点。合同获准前只准备材料，不写代码。
```

预期保存导入收据、目标词汇对账、规则/场景承接与当前合同；导入成功不会自动批准这些资产。既有 Java/Maven 工程需要 repository registration、engineering baseline 和 observation manifest 三份当前原始证据。设备占用竞争应落实到设计与可执行测试，不能只在页面禁用按钮；API 变化回到冻结流程。

## 4. 后端交付当前切片

```text
请按已批准且当前的合同实现领用切片，使用登记实现仓根 ./mvnw 验证。
整理成功/失败契约测试、冻结接口、合同批准、构建产物、部署身份和测试数据证据。
按本仓 backend-delivery schema 起草交付描述，核对本次切片范围与战略摘要。
缺可达环境或版本证据就列为缺口，不写成已完成。
```

在后端实例执行（交付描述已由实际证据形成）：

```bash
node scripts/preflight-delivery --input <后端预检输入.json> --stage export --json
node scripts/backend-delivery export --source-root . --delivery <交付描述相对路径> --output <新交付包目录> --zip
node scripts/backend-delivery verify --bundle <交付包目录或ZIP>
```

后端预检输入使用 `delivery_kind: backend-delivery`，绑定工程身份、技术设计、冻结接口、批准合同、实际制品、部署证据和后端交付源记录。预期 `verified`，但离线验包不能证明环境当前可用。交付不包含账号密码；实际 API 和版本探测由已登记环境提供。

## 5. 前端联合接收与准备

在前端实例执行：

```bash
node scripts/backend-delivery import --bundle <交付包目录或ZIP> --target-root .
node scripts/preflight-delivery --input <前端接收预检输入.json> --stage accept --json
```

战略快照随交付链导入，后端包与战略包分别验证。导入产生接收草稿；核对目标词汇、规则/场景、接口和视觉用例后才能形成正式接收记录。

```text
请联合核对战略和后端交付，完成目标词汇对账与前端场景映射。
检查部署/源码/接口/构建/测试数据版本及真实服务。
通过后只准备前端工程设计、frontend_implementation_plan 和 Slice Contract，
列出待批准事项。输入不齐时只诊断并回交缺口，不写前端或后端代码。
```

由 Agent 返回当前接收记录相对路径和切片 ID 后执行：

```bash
node scripts/verify-frontend-delivery --root . --slice <切片ID> <接收记录相对路径>
```

成功是 `inputs-verified` 且 `ready_for_agent: false`。这允许准备前端工程设计、实现计划和合同，正式编码仍须批准且当前的 Slice Contract。Handoff v5 必须明确 `prototype`、`existing-ui-baseline` 或有原因的 `not-applicable`；发现业务、API 或 UI 基线缺口时回交维护方，不在前端仓悄悄重定义。

## 6. 实现、联调与业务验收

```text
请复验接收输入与合同仍然当前，再按批准写范围实现前端领用流程。
使用登记前端工程的 pnpm 命令，记录实际退出码、截图、状态交互、
console warning、失败恢复及真实后端联调结果；交独立 Reviewer 审查。
```

后端记录可交付、前端记录可验收，统一管理方汇总同一战略、API、部署、前端版本的业务证据。用户检查一次真实领用及“重复领用/无权限”等约定反例，再按角色政策完成验收和发布裁决。单端完成、离线验包或一张截图都不能替代整体业务验收。

## 7. 变更、失败与恢复

| 情况 | 应做的事 |
|---|---|
| 包摘要不一致/批准缺失 | 保留失败输出，要求源方重出完整包；不手改摘要 |
| 对账冲突/规则含糊 | 回交战略方决定，阻断依赖切片 |
| 服务不可达或版本不符 | 后端补环境/部署证据，前端重新接收 |
| 已导入更新的同身份后端包 | 旧接收记录失效，重新验证并编译依赖合同 |
| 战略或视觉基线变化 | 评估规则/场景/页面依赖，更新合同后恢复 |
| 模板同步失败 | 检查事务回滚结果和旧 metadata；从 Git 基线或备份恢复 |

重试使用真实当前输入，不能复用旧成功日志当本次放行。已成功导入的战略快照可在后端包导入失败后保留，修复后幂等重试。

权威接力语义见 [前后端交付与联合接收](../process/frontend-backend-delivery.md)，具体阶段/门禁见本仓 lifecycle-registry.yaml；案例不另定义状态、角色或批准政策。
