## 1. 目的与范围

让业务人员、产品设计者及消费 Spec 的研发人员，能从同一组材料确定业务信息、权限、完整任务流程、可复现验收与采用版本，减少依赖口头补充和自行推断。

本次覆盖用户选定的六项增强：

1. 业务对象、关系及字段规则。
2. 权限与数据范围。
3. 完整流程与原型覆盖范围。
4. 可复现的验收场景。
5. 版本与变更说明。
6. 一份绑定同一功能的完整教学示例。

完整 Spec 的内容分类仍为业务规格、高保真交互原型、交互说明，三类内容可以共用文件。业务票仅按明确拆票请求组织。本设计只维护模板、技能方法、教学资源和受影响分发引用。

设计阶段仅保存文档，不修改上述实现资源，不提交、推送、安装消费项目、发布公开技能或发行 CLI。

## 4. 内容适用与权威位置

### 4.1 内容覆盖与填写形式

完整产品 Spec 对适用业务内容负责，但不强制每项使用独立文件或表格：

- 单个对象、简单权限及直线流程可用明确短段落；多对象、多角色、条件组合或跨页流转时用对应表格。
- 已有权威材料能回答问题时，引用具体章节、规则或现有编号，并补充当前范围的差异；不重复维护。
- 不适用的维度简述原因。缺少事实或决定写未决项，不能用“不适用”代替未知。
- 普通查询不生成完整规格；局部改稿只检查受影响的字段、规则、页面、AC 和版本对应，不补齐整套空表。
- 完整交付先明确范围内的任务与界面，再按风险选择状态与验证深度。按风险裁剪不能省略有 UI 完整交付的高保真要求。

### 4.2 权威位置

| 内容 | 权威位置 | 其他材料如何使用 |
|---|---|---|
| 业务含义、归属、唯一性、权限、合法状态和可观察结果 | Spec 或其明确引用的既有业务材料 | 页面、交互说明及 AC 引用同一规则 |
| 页面入口、布局、控件反馈、返回与场景操作 | 交互说明及选定原型 | Spec 保留任务和验收引用，不复制组件细节 |
| 实际执行结果、条件和未验证项 | 当前交互说明或已有检查记录 | Spec 与交接只引用结果，不把预期写成实际 |
| 设计 Token、组件来源与运行方法 | 已有 DESIGN 和设计技能资源 | 示例复用，不另立主题或 vendor 源 |

已有 FR/AC/场景编号继续使用；没有编号时可用稳定章节锚点或已有业务名称，不要求批量补号。原型发现改变业务结果时，先回写同一规则和 AC。

## 5. 业务规格模板的增强

保持现有章节顺序和交付边界，在相关章节内增加以下内容。

### 5.1 采用版本与关键来源

在文首给出轻量说明，包含当前文档状态、采用来源、选定原型及交互说明位置、可获得的版本或读取时点。已提交材料使用实际提交或已有版本；工作树材料说明路径、相关未提交变化和读取时间；链接无版本时如实注明。

同一文件承载多类内容时只记录一次。没有 Git、版本号或审批流程不阻断起草，不新建版本系统，也不以 draft/已发布推导业务批准。

修订已有规格时，补一条有实质意义的变更记录：变更内容、影响的规则/AC/页面、采用的旧新材料。纯排版修订不要求完整变更清单；真实行为变化不能只写“优化体验”。

### 5.2 业务对象、关系与字段

在业务规则章节前后增加条件适用的“业务信息”结构。

| 对象 | 业务含义与归属 | 与其他对象的关系 | 生命周期/约束 | 来源 |
|---|---|---|---|---|
| 使用实际对象名称 | 谁负责、属于谁、由谁提供 | 一对一/一对多等业务关系及能否改变归属 | 当前范围适用规则 | 具体来源或待确认 |

| 对象/信息项 | 业务含义 | 输入、默认及有效值规则 | 可见/可修改条件 | 规则来源 |
|---|---|---|---|---|
| 使用业务名称 | 单位、含义、空值含义 | 必填、值域、默认、唯一性等适用条件 | 创建、保存后、不同状态或角色的差异 | 同一规则或来源 |

填写指导明确：唯一性需说明业务范围及编辑时是否排除自身；默认值需区分初始建议值与强制值；关系需说明归属能否调整；已知值和未知值分别表达。无关约束可以省略，不为填表编造长度、数量或时限。

这里只定义业务信息，不指定数据库类型、主外键、索引、DDL 或生产请求响应结构。

### 5.3 权限与数据范围

涉及角色、归属或数据可见范围差异时，增加下列结构；各角色行为完全一致时用一句话说明即可。

| 角色/身份前提 | 可见数据范围 | 操作与适用状态 | 允许结果 | 拒绝结果与界面呈现 | 规则来源 |
|---|---|---|---|---|---|
| 实际业务角色 | 自己/团队/明确归属范围等 | 查看、创建、编辑、提交等 | 可观察业务结果 | 数据不展示、只读、禁用或说明等实际规则 | 同一规则 |

区分“能看哪些数据”和“能做哪些操作”，说明范围外直达入口、只读字段及必要的权限变化场景。界面隐藏或禁用不能代替业务拒绝规则。未确认采用隐藏还是禁用时保留未决，不能由组件代码暗定。

权限执行机制、认证系统和生产安全实现留给研发；模拟角色切换不代表真实权限已验证。

### 5.4 用户任务与完整流程

在使用者与场景章节增加任务结构：角色、起点与前提、跨页面动作顺序、终点、失败/返回分支、规则/AC 引用。单页短任务可以用编号步骤，多角色或分支复杂时再附流程图。

流程应足以发现缺失入口和流程中断；只交孤立页面清单不能证明用户能完成任务。流程图引用相同规则，不产生第二套规则。

### 5.5 可复现验收

增强现有 AC 表，至少能定位：AC 或章节、关联规则、初始角色/状态/代表数据、操作顺序、可观察结果、边界及未决项。涉及数据变化时说明变更后状态和应保持不变的数据。

较长的初始数据和操作可放到交互说明的场景段落或已有教学 fixture，通过具体场景引用关联；不在 AC 表中重复大段数据。纯业务 AC 不要求依赖浏览器、hash 或某种测试框架。

## 6. 交互说明与原型覆盖

### 6.1 全范围可见

在现有页面/状态与验收表前补充任务到页面/区域的对应：页面或区域、入口/出口、承接任务、权限差异、关联规则/AC、原型位置和覆盖情况。无 UI 时改为输入、动作与状态范围。

覆盖情况区分“可操作、静态展示、仅说明、未覆盖”，另记“实际验证、未验证或失败”。不能把已制作写成已验证，也不能把静态画面写成动态行为通过。

完整交付需让范围内任务和相关界面均可追溯。允许按风险选择非关键状态的表达与验证深度，省略时写清影响及理由；关键路径、拒绝或恢复仍有缺口时如实报告未完整交付。

### 6.2 具体场景

在现有说明中使用以下字段描述需要复现的场景：

- 场景名称或现有标识、关联规则/AC。
- 初始角色、业务状态与实际代表输入；外置数据给出具体文件及记录位置。
- 可访问的原型入口及进入该状态的方法。
- 顺序动作、预期可见反馈、数据变化及不变项。
- 重置方式、重置后应恢复的状态与数据。
- 实际检查的条件、结果和未执行项，或对已有检查记录的定位。

现有场景运行器采用 `#scenario=<id>`，此类原型说明给出真实存在的链接；其他原型形式使用其实际可访问入口。模板不要求所有产品接入该运行器，不接受编造不可直达的链接。

“失败后重试成功”需说明失败前后保留了什么、再次执行哪些校验；重置需同时恢复输入、正式值、错误、选择及当前场景的模拟次数。迟到回调不能污染新场景。

### 6.3 避免重复材料

Spec 负责业务预期；交互说明负责如何在选定页面重现；实际检查负责观察。状态复杂时继续引用现有状态矩阵，不新增第二份状态机文件或统一测试报告。

对状态矩阵模板仅补充相关场景及入口的可定位引用；对原型复核模板仅补充当前材料版本、代表输入和覆盖差异的检查位置。

## 7. 贯通教学示例

### 7.1 选择与来源

采用“附件提交校验”作为一个教学功能，复用已有普通样例的缺附件拒绝、一次列全、保留输入、补齐重试及不验证附件真实性等规则。示例选择及以下新增业务细节是本设计的 Agent 提案，不冒充用户实际业务决定。

旧 `ordinary-source.md` 的附件清单读取失败行为仍未决定。新示例单独声明教学设定并给出来源表，不修改旧样例、不关闭旧 Q-001、不复用其编号表示新增规则已经被确认。

新示例的 `spec.md` 包含自足的教学输入/来源说明和稳定规则；`interaction.md`、场景数据和页面引用该规格，不依赖未默认分发的旧 fixture。

### 7.2 最小教学业务

| 项目 | 教学设定 |
|---|---|
| 业务对象 | 申请单属于一个团队和一个申请人；申请单具有一份所需附件清单，附件条目以名称标识 |
| 业务信息 | 编号由教学数据提供、在数据集中唯一且只读；团队和申请人只读；标题去首尾空白后必填；备注可选，默认空；附件只模拟齐备状态 |
| 状态 | 草稿、已提交；用户不能直接编辑状态 |
| 经办人 | 只查看自己所在团队且由自己发起的申请；可编辑、保存和提交自己的草稿；已提交申请只读 |
| 团队观察者 | 只查看本团队申请，详情只读，无保存/提交权限 |
| 范围外记录 | 列表过滤；尝试打开时显示无查看权限，不呈现详情字段，不改变原数据 |
| 保存 | 校验标题、操作权限和草稿状态；成功后更新当前内存中的正式值，返回列表可看到结果，不检查附件齐备 |
| 提交 | 校验权限、草稿状态、标题及必需附件；缺少时一次展示全部名称并保留编辑输入；齐备时更新正式值并进入已提交 |
| 清单读取失败 | 新增教学设定：保留输入、阻止提交、显示失败与重试入口；再次读取成功后重新校验，不能把失败解释为清单为空 |
| 模拟提交失败 | 新增教学设定：第一次有效提交失败，状态不变且输入保留；再次提交重新校验后成功；校验未通过不消耗模拟失败次数 |
| 离开与取消 | 有未保存变化时确认；留在当前页保留全部输入，放弃后返回列表且正式值不变；无变化直接返回 |
| 重复与持久化 | 已提交不能再次提交；保存、提交及角色均为内存模拟，刷新重新初始化，不承诺关闭/刷新恢复 |

附件条目使用 Checkbox 等已随附组件表示齐备状态，页面及说明明确没有真实上传、文件存储或内容校验。标题不新增无来源的生产长度约束；长文本仍应正常布局。

### 7.3 任务与代表场景

核心任务为：申请列表进入详情，编辑标题/备注及附件齐备状态，保存或提交，观察结果并返回列表。列表与详情消费同一份内存正式数据，详情编辑值单独保存；取消不能悄悄写回。

| 场景 | 初始条件与操作 | 预期结果 |
|---|---|---|
| primary | 经办人从列表打开自己的草稿，填写有效标题，补齐两项附件，保存后再提交并返回列表 | 保存后的数据可见；提交后状态变为已提交，详情只读，重复提交无效 |
| missing-attachments | 草稿初始缺少报价单、采购说明，带有已填标题和备注；直接提交，再逐项补齐并重试 | 一次列出两项缺失；补齐一项后只剩另一项；保留输入；全部齐备后成功 |
| readonly | 团队观察者进入本团队申请 | 数据可读；说明只读原因；不能修改或产生保存/提交结果 |
| out-of-scope | 当前身份尝试打开另一团队的记录 | 不显示详情数据，给出拒绝及返回路径，正式数据不变 |
| submit-failure | 有效草稿、附件齐全；第一次有效提交失败，再次提交 | 保留输入和草稿状态，重试重新校验后成功 |
| requirements-failure | 清单读取首次失败；用户重试读取，再执行提交 | 不将失败显示为空清单；输入保留；重试后执行实际附件校验 |
| dirty-leave | 修改草稿后返回，先选择留在当前页，再选择放弃离开 | 第一次完整保留输入；第二次恢复列表正式数据；成功保存后离开不再误报未保存 |

每个场景都能独立初始化和重置；primary 为默认入口。未知或重复场景参数沿用现有运行器的错误处理，不回退正常数据。覆盖记录还需说明标题空白的拒绝、只读状态及必要焦点行为对应哪个场景的哪一步。

### 7.4 资源组织与运行

新增源目录为 `.agents/skills/yss-design-system/assets/spec-delivery-example/`，集中维护本例的 README、完整 Spec、交互说明、Vue 业务页面、入口及场景 JSON。目录属于教学作者资源，不是一个真实产品项目。

示例复用现有 `assets/prototype/` 中的 package、锁、Vite 配置与许可，现有 shadcn 快照、全局 Token、场景运行器和必要的 mount/workspace 来源。只增加表达本功能所需的业务代码和数据，不复制维护第二套框架、vendor 或主题基线。
