# YSS 技能安装状态与 Help 推荐维护计划

默认 Spec 工程借用了前端应用技能的一份参考资料，CLI 却把整个技能报告为 `installed`。工作台用这个值显示「已安装」，而 Codex 在该工程中找不到技能入口。本次维护要让安装清单准确反映工程装了什么，并让 Help 给出用户在当前宿主可以直接使用的写法。

2026-11-21，用户确认了三项取舍。

1. 工程只有借用的参考文件时，CLI 返回 `not-installed`，工作台显示「未安装」。原技能继续使用这份文件。
2. 本版给 `yss-help` 补充纠偏示例，沿用现有自然语言触发范围。用户问“下一句该怎么说”时交付提示词，用户直接纠正任务时由当前任务处理。
3. 首轮在模板仓保存这份跨仓维护规格与执行计划。用户随后点名 `implement` 执行两仓修改，结果见[首轮实测](#2026-11-21-实施与实测)。后续关于实际接棒和页面纠偏的决定见[四项审查的补充执行计划](#四项审查的补充执行计划)。

## 安装状态怎样解释

针对当前 Profile 库中的名称，先区分**安装收据是否管理这个技能的入口**和**工程里实际有哪些文件**。`result.available` 说明当前库提供什么，`result.selected` 说明按当前 Bundle 选中了什么。已经接入的旧工程和项目自行维护的文件，要结合原收据和磁盘内容解释。

| 工程现场 | `result.installed` 中该名称的值 | 工作台显示 | 对用户的含义 |
| --- | --- | --- | --- |
| 收据未登记技能入口且工程没有可核实的普通入口文件，包括只有借用资料的情形 | `not-installed` | 未安装 | 原技能仍可读借用资料。宿主另行发现链接指向的技能时，按实际来源判断是否适合本次请求。 |
| 收据未登记入口，项目自行放置了普通文件 `SKILL.md`，即使目录里另有受管参考 | `unmanaged` | 工程自行维护 | 以目标宿主实际发现的入口和项目正文为准，保护自管文件。 |
| 收据登记的入口及其目录内受管文件齐全、匹配 | `installed` | 已安装 | 工程已安装。需要给出显式调用写法时，采用该宿主支持的入口。 |
| 收据登记的入口或相关受管文件缺失，或文件位置被目录、链接等占用 | `missing` | 文件缺失 | 缺入口时查宿主实际发现情况。仅缺参考时，指出哪些工作需要该参考。 |
| 受管入口存在，相关文件齐全且有本地修订 | `modified` | 本地定制 | 按本次问题读取有影响的正文或资料。仅改主题文件时，技能职责可继续按本地正文判断。 |

入口被宿主禁用、从其他工程读到同名技能、当前 CLI 库已省略旧名，都可能改变 Help 的答案。工程尚未接入 YSS 时，`skills list` 也可能返回 `NOT_READY`。遇到这些情况，就核对目标宿主、入口来源和本次必需的资料。能确认入口时给实际调用写法，仍无法确认时给可直接发送的普通提示词，简要点明缺哪项依据。安装或修复文件另按用户对该动作的要求处理。[Help 现有推荐规则](../../.agents/skills/yss-help/SKILL.md) · [宿主来源与发现依据](../../.agents/skills/setup-yss-harness/references/host-compatibility.md)

## Help 怎样写出有用的提示词

用户问用法时，默认给一个首选、一句理由和一段可直接发送的中文提示词。不同请求需要补充的信息如下。

- **用户问两个技能怎么选。** 给一个首选，并说出哪个条件会改变答案。例如同是退款失败恢复，检查原型是否符合规格选 `prototype-review`，审查指定 MR 是否引入回归选 `code-review`，要求按已确认原型修正正式页面的局部行为选 `yss-frontend-application`。推荐以目标工程实际可用为前提。
- **任务有可观察的结果。** 沿用已知规则，把接收者能判断的完成条件写入提示词。例如规格已经要求失败后保留输入，复核提示词就写“触发一次提交失败，记录哪些字段保留，再核对重试后的状态”。规格未定义的行为，分别报告实际表现和待定规则。探索任务可以用“指出依据和仍未知之处”收尾。
- **用户要把提示词交给另一个会话或工程。** 写明接收工程、所选材料的实际位置、已确认规则、本次产物和动作终点。同名 `to-tickets` 在共享版本可按请求组织业务票或工程票，Backend 版本面向后端实现切片。只要求后端在对话拆分时，把这个终点写进提示词。原会话继续任务时可直接沿用已有上下文。[共享拆票入口](../../.agents/skills/to-tickets/SKILL.md) · [Backend 拆票入口](../../profiles/backend/.agents/skills/to-tickets/SKILL.md) · [已有 Spec 交接方法](../../.agents/skills/yss-build-spec/references/spec-workflow.md#交接提示)
- **用户指出任务跑偏。** “我只让你审查这个 MR，先停下改动”由当前任务立即处理。“我该怎么说才能让它回到只读审查”由 Help 给一句可发送的话，例如“请保留工作树现场，只读审查这个 MR，在对话里列出有文件位置和依据的缺陷，并说明刚才已经改过什么。”点名某个技能作为调研对象时，仍按请求交付调研结论。

提示词写法吸收了 pstack 的完成条件和相邻入口辨析。执行方法由接收任务的专业技能负责，具体场景继续放在 YSS 现有技能地图。[pstack 提示词指南](https://github.com/cursor/plugins/blob/0b46ec399d55f2829e88822998f53b84944837d3/pstack/skills/poteto-help/references/prompting.md#L3-L17) · [pstack 相邻入口辨析](https://github.com/cursor/plugins/blob/0b46ec399d55f2829e88822998f53b84944837d3/pstack/skills/poteto-help/SKILL.md#L103-L111) · [YSS 场景地图](../../.template-spec/agents/profile-skills.md#用具体请求检查选择是否合理)

| 验收 | 实际观察 |
| --- | --- |
| AC-01 | 两种默认 Spec 安装中，旧 CLI 都报 `installed`，候选都报 `not-installed`。用浏览器打开工作台，工程检查与「查看技能」在这两个工程均显示「未安装」。`yss-design-ui` 正文指向的组件参考可以读取，内容摘要与完整 Frontend 工程相同。 |

### 第 3 项　跨工程交接

发送方先确认用户要哪种产物，再核对接收工程可调用的入口和可读取的材料。交给新会话的提示词要能单独读懂，带上目标工程、所选材料的位置与采用版本或读取时点、原验收、影响这次工作的待定规则、预期产物和本次动作终点。沿用原会话时，只补新信息即可。共享版按请求拆业务票或工程票，Backend 版细化后端实现项。本次选择 Spec 工程代表共享版，让两个接收方使用同一份规格，各自接到意图明确的任务。[共享拆票职责](../../.agents/skills/to-tickets/SKILL.md) · [Backend 拆票职责](../../profiles/backend/.agents/skills/to-tickets/SKILL.md)

**给两种接收方的示例。** 沿用首轮隔离样本的退款规格，已核实文件 SHA-256 的前 12 位为 `55d5d81fbd15`。下例假设验证时将这份原件放在 `refund-spec/docs/refunds.md`，相邻的 `refund-backend` 可以只读访问，两边的 Codex 都启用了各自的拆票入口。实际交接时采用目标工程能解析的路径和选定版本。

### 入口来源和退役查证

- 按**实际接收聊天**判断其已启用入口及显式调用方式，再区分宿主允许隐式选择与本次确实采用。Spec 和 Frontend 的共享 `to-tickets` 按其显式调用策略，Backend 按本项目的隐式策略和职责。宿主语法和权限以实际证据为准。

### 已有提示词改写、验收与续办

- 改写时保留用户本轮的目标和授权，补足与结果有关的一手线索、可观察结果及动作终点。原稿建议调长定时器、用户只要诊断时，保留重试卡住的症状，把定时器作为待查线索，要求有支持或排除原因的观察。用户只要可粘贴的文字时，直接交付该段文字。
- 按接收方实际可用的证据写验收。静态稿可核对可见状态，能打开的页面实际操作失败恢复，无法观察的一侧标明待验。模拟验证注明范围。可观察要求来自已经选定的规则，备注是否保留等未定事项继续待定。
- 新聊天接续未完成工作时，按已有记录带上目标工程、当前候选或工作树、旧证据对应的版本、正在运行的检查和结果未知的操作，并写到用户指定的终点。先回读未知写入结果，沿已有授权继续。地图区分一次状态查询、只读缺陷审查、跟到当前版本可合并、实际文件交付。真实合并由用户选定对应目标和授权。
