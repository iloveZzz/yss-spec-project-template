## 1. 目标与方案选择

沿用已确认目标：交代一次任务和完成条件后，Agent 能持续处理审查反馈、CI 失败和版本变化，直到达到指定结果。沿用方案 A：在当前会话中执行，中断后由后续会话依据已有记录和平台现状接续；宿主退出后持续运行和自动唤醒不在承诺内。[原设计与已确认决定](2026-11-16-pr-mr-followup-design.md)

本轮希望回答：在这项真实任务中，Agent 是否完成了约定工作，是否发生可避免的催办或误判，以及具体原因在哪一层。没有发现有证据的问题时，保留现有方法即可。发现问题也应继续完成授权内可推进的交付工作，不能以“找到接管点”代替任务完成。

| 方案 | 做法与取舍 | 本轮选择 |
| --- | --- | --- |
| 真实任务观察，按问题修订 | 使用现有入口承接一项真实交付，记录实际事件与结果；贴近使用，但未发生的情境无法验证，也不能由单例推导普遍收益 | 用户接受的调整方向；延续会话内方案 A |
| 继续扩展受控演练 | 可重复构造版本变化、失败与中断，适合复现具体问题；仍不能代替真实平台与工程采用证据 | 仅作为具体问题的补充诊断，不作为下一轮主线 |
| 新建通用 watcher 或后台执行服务 | 可研究宿主退出后的推进与恢复；引入持久状态、调度、并发及维护职责，改变已选范围 | 本轮不采用；有新需求和具体证据后另行讨论 |

本文只设计如何使用和改进已有能力，不新增技能命令、CLI 接口、数据库结构、统一状态文件、固定多代理流程或模板脚本与测试套件。PR 栈重排、跨平台全面认证、生产部署和普遍效率评估不属于本轮目标。

## 3. 任务输入与执行边界

观察单位是一项已有业务目的的真实研发交付任务。它可以对应一个 PR/MR，也可以天然对应多个仓库和 PR/MR。起点可以是已有请求，也可以是用户已要求实现并交付的工作；不创建无业务目的的变更，不为覆盖跨仓或失败情境扩大任务。

执行前从当前请求、任务链接、已选工作树及原有记录恢复以下信息，不要求用户重新填写：

- 业务目标、规格或问题依据，以及约定终态，例如指定检查通过、可交付或实际合并。
- 实际工程、平台实例、相关 PR/MR 或待创建对象，以及允许读写的范围。
- 有效的动作授权和已知外部依赖；提交、推送、评论、重试、合并和发布按实际请求分别判断。

工程路径、远端身份、工具版本、当前状态等事实由 Agent 查询。用户已明确对象时沿用；多个对象会改变任务范围且无法从上下文消歧时，只询问该选择。没有指定真实任务时，下一步保留为选择任务，不擅自把模板、CLI 或 SCRM 的其他工作当作试点。

本设计不绑定尚未选定的 PR/MR 编号、平台、业务验收或外部写入授权。它们是后续执行的实际输入，必须在相应动作前明确；不能将本文获批解释为任意项目的写入许可。可以先制定以这些输入为条件的计划，涉及真实对象的执行须使用当时有效输入。

## 4. 沿现有入口推进

1. **核实实际采用内容。** 按 [仓库定位与上下文方法](../../.agents/skills/implement/references/repository-scope.md) 确认工程、工作树、局部规则和当前方法来源。核对本任务必需的正文及资源，记录版本或相关差异，避免仅凭版本号判断。原始任务请求保持原意，不额外塞入指定技能路径以制造自然采用成功。可见读取依据用于事后解释；缺轨迹时来源采用情况保留未知。
2. **处理来源差异。** 工程仍使用旧方法或资源缺失时，保留现状与影响。升级只有在已有对应授权内沿实际安装同步方法处理，并保留前后来源；不能覆盖工程修改、切换 Profile 或手改收据。普通任务仍按可用方法完成允许部分。旧方法下的结果不归到本轮候选；明确指定来源后的结果单列，不替换原始自然请求观察。
3. **完成真实交付。** 由主 Agent 负责推进，沿 [PR/MR 持续跟进](../../.agents/skills/implement/references/pr-mr-followup.md) 处理反馈、CI、版本变化、等待及最终核实。验证复用工程现有入口、前端 [verification](../../.agents/skills/yss-frontend-application/references/verification.md) 或 Backend [test-execution](../../profiles/backend/.agents/skills/yss-backend-testing/references/test-execution.md)，只覆盖任务必要路径。不能为满足观察而强制读取无关 guide。
4. **记录实际事件。** 复用原聊天、任务说明或已有 Workbench 记录，保留发生的关键变化、Agent 动作、结果和剩余依赖。无变化时不写重复记录。新增反馈、CI 失败、源或目标版本变化、超时未决写入、入队和中断是否出现，分别按事实说明。
5. **按原因处理问题。** 使用下一节分类定位失效。授权覆盖的修复继续完成并重验；需新增业务决定或超出写入范围的事项只暂停对应动作，保留其余可推进工作。任务中修改了方法时，变更前后的执行分开记录。
6. **核实约定结果并交付。** 按实际完成条件读取当前平台及工程证据。发现外部阻塞时说明缺什么、等待谁、仍在运行的动作及续办入口；不能把受阻、观察结束或已入队报告成任务完成。达到目标后结束本次观察，不为凑样本继续运行。

会话等待、用户状态询问、暂停或撤销、合并版本条件及写入超时后的回查均沿现有跟进参考执行。真实中断发生时，后续会话先核对未决操作、工作树与平台现状；未发生中断的任务不能证明恢复能力。不会为观察而故意中断或破坏正在交付的真实任务。

## 5. 问题归因与最小修改位置

先保留现象，再调查机制。不能只凭失败次数、某文件未读取或失败位置不在 diff 中得出原因。

| 问题类型 | 判断依据 | 合适的处理位置 |
| --- | --- | --- |
| 工程说明漂移 | 文档的启动、操作或恢复路径与真实工程不符 | 在授权范围内修订原 README、项目技能或运行说明；实际执行受影响步骤 |
| Agent 漏跟进或误判 | 已有目标、授权和可用工具，仍漏处理、重复催办或错误宣布完成 | 先定位入口、上下文和方法执行环节；有因果依据后最小修订相关导航或参考 |
| 验证工具或环境限制 | 所需动作因工具能力、身份、沙箱、网络或服务条件失败 | 核实可用替代路径和恢复方式；超出当前范围的工具适配另列，不能以补写提示词宣称解决 |
| 产品行为回归 | 实际业务结果违背已确认规格或验收 | 按工程修复授权修改实现和受影响检查；保留原规格与失败证据 |
| 必要人工决定或外部依赖 | 新业务取舍、必要审批、缺失动作授权或他人工作阻塞 | 定点说明缺口，继续独立工作；不计为 Agent 漏跟进，不绕过权限 |
| 原因尚未明确 | 只有现象，存在多个合理解释 | 保留未知并做能够区分原因的必要调查；不提前建设通用机制 |

正确结果可以来自不同的合理执行路径。即使未读取某份新增文档，只要必要行为得到完成，也不构成该任务的行为缺陷；反之，读取过文档也不能抵消实际遗漏。

## 6. 观察结果与改进依据

交付结果与能力观察分别报告，使用已有任务记录即可。

| 判断对象 | 所需依据与可得结论 |
| --- | --- |
| 任务是否完成 | 原约定终态、当前对象和版本、必要检查及实际产物；目标为合并时核实最终合并结果 |
| 某事件是否处理正确 | 事件确实发生，能够关联 Agent 的动作、版本、运行和结果；未发生写“未观察”，不能写通过 |
| 是否需要人工接管 | 原始消息、介入时点和原因；区分可避免的重复提醒、必要业务决定及环境协助。缺少完整记录时数量未知 |
| 是否完成跨仓交付 | 仅在任务天然跨仓时，关联各仓实际输入、PR/MR、版本组合及必要联调结果；各仓分别通过不代替组合证据 |
| 是否独立续办 | 仅在真实发生中断并接续时，核对恢复输入、未决动作及后续执行；人工补充上下文或资源协助单列 |
| 某项修改是否有效 | 保留原始失败、修改内容及针对受影响行为的复验；同条件重现受限时降低归因强度，不假称因果已证实 |
| 是否节约成本 | 有原始数据时记录等待、执行、失败重试及人工介入；不由一次顺利任务推导整体效率，缺失指标不填零 |

没有新增反馈或 CI 失败的顺利任务，仍可能满足业务目标；它只留下实际发生路径的证据。无需为此重新制造失败、故意撤销权限或触发额外 CI。

如果确需修改技能触发或行为并比较效果，复用 [技能行为改版对照](../../.agents/skills/i-have-adhd/references/pr-and-retro.md) 保存原始来源与输入，在可隔离且已授权的载体中针对具体失效复验。代表请求、相邻非触发场景和必要授权边界按改动影响选择；不把成套评估变成每次交付的前置。

已经完成的真实合并、外部评论和生产数据操作不能为对照重复执行。无法等价重放的任务保留单次观察限制；可复现的问题可另用受控案例调查，但与真实平台结果分别标识。两侧都正确时记录未观察到增益，候选产生新误判或越界时修正或撤回对应增量。

## 8. 结束条件与交付内容

任务达到原约定终态，或确有外部阻塞、用户暂停和宿主限制时，按事实报告执行状态。阻塞与暂停保留未完成事项、远程运行中动作及接续信息，不能当成任务成功。用户只是询问进度时，回答后继续原目标。

最终说明至少能回答：哪项任务、实际采用什么方法和版本、约定结果是否达到、观察到哪些事件、哪些问题确实需要修正、采取了什么动作、哪些能力仍未观察。简单任务可以用一段及必要证据链接，不要求新建报告目录或统一数据模型。

观察后的维护结论允许三种结果：有证据且已授权的必要修正已经完成；没有发现需要修改的问题，保留现状；存在具体待决或受阻事项，说明责任和接续条件。它们不能覆盖或改写业务任务本身的完成状态。

本轮不设没有数据支持的成功率、提醒次数目标、持续运行时长或成本预算。若一次任务不足以判断某个已观察问题，下一次观察应说明要区分的假设与停止条件，不自动建立常驻监控或周期评估。
