# Spec 执行与验收结果增强

日期为 2026-11-28。本文是 YSS 模板维护规格草稿，供技能维护者实施和复核。对应模板基线 `v5.19.2`（`59dc25d3`）与本机实际核对的 CLI `3.19.0`（`72e9608`）。首轮验收后再根据试点决定是否扩大能力。

## 目标与范围

执行 Spec 的人交付结果后，接手人应能从原任务找到本轮采用的版本、实际覆盖的验收条件（AC）、可核对的证据及仍待处理的事项。小改动只需简短说明。执行完整 Spec 的约定范围、跨仓联调、指定环境验收、兼容迁移或明确交接需要一份可持久回读的汇总。

本文延续 11 月 25 日增强所用的原 FR/AC、材料采用版本和高风险反例，覆盖从执行验证到结果交付。适用于采用 Spec、工程票或已有验收的研发任务，以及具备相同交付职责的专项前端或后端路径。本轮交付是技能与文档约定，场景样例直接写在本文。 [11 月 25 日 Spec 流程增强](2026-11-25-pstack-spec-workflow-upgrade-plan.md)

## 首轮要求

### FR-01 · 按本轮终点选择交付形式

按下表从上到下选择交付形式。复杂度和交付终点以本轮实际受托的范围为准。例如，依据一份完整 Spec 只修一个局部 AC，且没有指定文件、联调、环境验收或持久交接要求时，使用短摘要。

| 任务条件 | 交付形式 |
| --- | --- |
| 用户明确指定报告文件 | 在获准位置交付该文件。已有摘要和原始证据作为来源复用，同时交付用户指定的产物。 |
| 审计、归档、跨权限交接确需独立材料 | 按项目现有约定及写入授权交付一份可独立阅读的报告，附可共享证据。已有可独立阅读的材料满足交付要求时直接引用。 |
| 本轮执行完整 Spec 的约定范围、跨仓联调、指定环境验收、兼容迁移或明确需要接手 | 在一个可回读的主记录中汇总本轮范围、实际终点及本轮适用验收的结果。优先沿用已有父任务、工作台或团队交付记录，其他入口引用主记录。 |
| 其余无需持久交接的任务，包括清晰的局部改动 | 在当前回复或原任务写实际改动、做过的检查及结果、影响判断的版本、环境或限制。说明深度与改动范围相称。需要辅助测试时沿用工程现有入口。 |

用户指定的本地实现、合并或环境验收仍决定执行终点。范围内检查完成、失败、跳过或受阻时，收尾均可据实交付结果。由后续业务方确认的事项写明当前状态和接收方，实际确认后补入同一记录。报告形式不改变测试范围、交付授权或已有终点条件。

### FR-02 · 让验收与实际证据逐条对应

完整汇总首部写本轮范围、实际采用的 Spec 和有影响的关联材料版本、各工程候选及环境。共用版本和环境可在报告头写一次，条目覆盖不同组合时单独标明。没有提交时引用可回读的工作树摘要或快照。只有读取时点可用时注明限制。

按本轮适用的原 AC 或原验收章节列结果。原任务没有编号或验收章节时，引用真实工单中的具体条款，或用户原话中可观察的目标与其可定位出处，沿用已有标识。预期结果确实缺失时，记录已经观察到的事实和无法判定的验收项。每条指出验证层级、观察结果和证据入口。需要复验或判定副作用时，补最小初始条件、真实入口与操作、预期及实际可观察结果。按需要用通过、失败、未执行、跳过、受阻或仅模拟说明状态及覆盖。部分通过时写清已覆盖和待补的行为。一个证据能支持多条验收时可共同引用，并指出其实际覆盖的断言。原规则、权限判断时点及失败后的数据不变项沿用原出处。

原型演练、模拟接口、单仓测试、跨仓真实联调和目标环境各自说明覆盖。全套测试或 CI 通过的结果应能定位到实际候选及检查项。涉及重试、权限或迁移时，选择能看见行为与副作用的既有入口，保留实际操作证据。高风险且难理解时可附一条可重放反例或一张局部图，按现有 [图解方法](../../.agents/skills/yss-write-docs/references/visual-explanation.md) 绑定对应 AC 和运行证据。

供他人接手时核实证据链接指向预期版本及接收人可读的材料。链接只有发送方可读、内容含敏感数据或留存尚未核实时，按授权用可共享的最小摘要或脱敏证据，并注明仍不可核实的部分。

### FR-03 · 沿现有工作台和业务确认方式交付

已登记且写入有依据时，沿用同一工作台数据目录、`specId`、`goalVersion`、`specDigest`、阶段和参与工程。每个阶段及参与方在其实际报告内保留当前证据，AC 明细使用报告摘要、证据标签或可读的主记录承载。按照现有阶段汇总语义提交报告，避免把每条 AC 拆成互相替换的阶段报告。相同输入重试沿用原报告 ID 和请求 ID。报告内容变化时按原目标提交新报告，使用新报告 ID 和请求 ID。 [工作台上报](../../.template-spec/agents/workbench-progress.md#上报阶段进展)

上报验证前按实际采用的 Spec 或原任务核对全部必验条件和所需验证层级，再与当前目标的 `acceptanceRefs` 对照。目标引用为空、遗漏验收或只指向包含多个条件的章节时，仍逐项核对实际必验范围。目标登记已获授权时，采用能精确对应现有验收的稳定引用。已有目标沿现有授权使用，其登记缺口在原任务明示。

每个参与方或整体阶段在自己负责的必验项全部满足后可报 `done`。存在必验项未执行、失败、证据不足或只完成较低层级验证时，按事实报 `doing` 或有实际阻塞时的 `blocked`，同时保留已核实部分的通过凭证和其余条目的观察。仅当该阶段确实适用跳过规则且没有待完成的必验项时使用 `skipped`。参与工程已达成本方验收时可以报告其实际完成，整体联调如有缺口仍按实际进度上报。

两仓分别完成但整体仍有缺口时，先保存并回读整体或集成验证的未完成报告，再登记可能触发整体验证完成的参与方结果。无法上报整体缺口时，在原任务保留实际分仓结果和待同步项。终端 `workbench request` 等直接进入上报指南的路径适用同一判断。 [工作台上报指南](../../.template-spec/agents/workbench-progress.md#上报验证结果)

上报已完成的验证时，`scopeRefs` 及标记通过的验收引用只覆盖达到要求层级且有对应凭证的范围。用于自动覆盖判定的 `scopeRefs` 或通过凭证的 `reference` 与目标中的引用逐字匹配。证据标签可明确条款与行为。若 `reference` 填的是验收引用，在摘要或其他证据中保留实际产物的可读入口。当前 CLI 会用报告级范围和通过凭证判定覆盖，含义不明的宽泛引用要按实际覆盖说明。写入后回读同一目标、阶段和确认来源，核对其与交付摘要相符。发现工作台仍显示与已核实事实不符的结果时，在原任务说明当前显示、证据缺口和可用的复核入口。 [CLI 3.19.0 覆盖判定](https://github.com/iloveZzz/yss-cli/blob/72e9608d0065bd37963c41de0ed44fd5b0515d13/src/workbench/progress.rs#L2501-L2536)

工作台已有自动核实时，在摘要保留其来源。用户或项目明确要求人工业务验收且尚未收到对应范围的人工决定时，原任务显示待业务签收，任务按实际签收条件收尾。收到真实确认或退回时，记录实际决定出处、范围、版本和证据。部分决定在原任务记录真实范围。只有实际收到覆盖完整当前目标的明确决定，且符合现有接口条件时，才保存整目标人工确认或退回。没有人工验收要求的任务沿用现有自动核实流程。

没有登记、所装 CLI 缺少相应接口、权限不足或回写失败时，在已有任务保存可复核结果，说明实际回写缺口及影响。已获授权且具备依据的验证和交付照常完成。首次写入任何外部记录继续遵照该操作的真实授权。新摘要可用于旧项目，历史报告保留原内容和确认，未记载的逐 AC 对应关系保持未知。

### FR-04 · 换版或续办时按影响复用

续办人从同一主记录核实 AC、采用的 Spec 与关联材料、实际工程或制品版本、环境和已做检查。候选或依赖变化时，指出受影响的 AC、已失效或待复核的证据、仍可采用的依据。可独立判断的本地验收项，在已能证明规则、相关输入和验证环境仍适用时，可以引用原证据并写明理由。对合并、指定环境及跨仓集成的工作台验证，沿用现有精确版本规则，按实际候选组合取得凭证。旧证据可说明原候选的情况，局部输入摘要相同仍须核验本轮所需的实际组合。原规则或原型语义有变时，沿原 Spec 处理。

目标版本和实际工程候选分别核对。旧报告及其确认保留原范围与版本。迟到结果在工作台可核实并接受时按原目标版本及实际测试的候选上报。因旧输入不可复核或版本冲突而被拒时，在原任务保留原目标、候选、原始证据和实际回写错误。后续按授权补报并复核，同步缺口仍在时由原记录支撑续办。

## 示例 · 同一报告里有多种结果

以下为模板方法演练。假设目标是前后端版本组合 B 在隔离测试环境完成回归，并提交业务确认。三条 AC 属于同一原 Spec，实际项目沿用自己的编号。

| 原验收 | 实际结果与证据 | 后续 |
| --- | --- | --- |
| AC-DEMO-01 · 响应丢失后重试保持唯一 | 组合 B 已在浏览器和实际测试服务验证。首次响应丢失后用同一请求标识查询并重放，返回原记录 ID，数据库仍一条。引用对应用例与数据库回读日志。 | 本轮技术验证通过，业务确认待记录。 |
| AC-DEMO-02 · 失去权限后撤回失败 | 仅在模拟前端看到操作禁用。目标服务的拒绝及原数据是否保留还未执行。引用模拟记录。 | 保留模拟观察，补实际 API 和状态回读。 |
| AC-DEMO-03 · 迁移后的旧数据仍可读 | 隔离环境缺少适用的旧数据快照，本轮受阻。注明实际缺少的输入。 | 由具备权限的工程负责人补齐测试快照后复验。 |

演练中，整体验证因缺少旧数据快照而受阻。上报保留 AC-DEMO-01 的实际通过凭证、AC-DEMO-02 的模拟观察和 AC-DEMO-03 的阻塞依据。集成人交付各证据指针、实际版本组合及可继续处理的事项。

下列场景定义实施验收。实际执行范围和结果见 [实施结果](#实施结果)。

| 编号 | 给定与操作 | 可观察的预期结果 |
| --- | --- | --- |
| AC-01 · FR-01 | 在未登记工作台、无 tracker 的旧工程，仅修复一份完整 Spec 中的一条局部 AC。用户只要求本地实现和受影响路径检查。 | 原任务留下短摘要，能读到实际变更、检查结果及限制。未因引用完整 Spec 增加报告文件、工单或确认步骤。 |
| AC-02 · FR-01、FR-02 | 同一 Spec 跨两仓，以指定环境验收为终点，提供组合实测通过、仅 mock 和受阻三条证据，以及一条泛化 CI 成功。另以无编号、无验收章节的现有工单验证同层级行为，其中一项只给出操作、缺少预期。 | 接手人只用一个可回读的摘要及其链接，即可定位版本组合、逐项结果、证据和缺口。泛化 CI 成功不改变其他条目的结果。无编号时用原工单条款或原请求定位，缺预期的条目只记实际观察及无法判定的原因。 |
| AC-03 · FR-02、FR-03 | 对隔离工作台按下表回放部分通过、真实全部通过和实际阻塞。回读同一目标、验证阶段及新增确认记录，并比较原请求重试和证据更新后的新上报。 | 目标和相关证据可回查。状态和自动确认符合各对照预期。相同请求重试不新增记录，补证用新报告 ID 和请求 ID，原报告保留。 |
| AC-04 · FR-03 | 在 CLI 已记录 `origin=automatic` 后，对明确要求人工签收的任务分别提供无答复、部分确认、符合接口条件的完整确认及完整退回。另回放证据齐备且无人工验收要求的任务。 | 原任务保留自动核实来源。无答复或仅部分确认时，仍列相关待签收范围，未提交整目标人工确认，也未以此结束必须签收的任务。完整决定回读为人工来源，并匹配实际范围、版本和证据。无人工验收要求的对照按现有规则完成。 |
| AC-05 · FR-03、FR-04 | 按下表分别回放工作台不可写、局部证据可复用、精确候选换版和旧报告迟到的情形。 | 实际交付及回写结果均可定位，当前范围只采用仍适用的证据，旧候选结果保留原归属。 |
| AC-06 · FR-01、FR-02、FR-03 | 只授权本地实现和验证，提供远程 Issue、PR 链接和私有测试日志。另使用一份已有足够主记录的任务，用户明确指定获准位置的独立报告文件。 | 本地任务返回可核对结果，远程记录和证据权限按原授权维持。指定文件按要求交付并复用已有材料，证据受限时说明限制及获准附上的最小证据。 |
| AC-07 · FR-01、FR-02、FR-03 | 核对受影响的 Spec、Backend 和 Frontend 安装。分别从共享及 Backend 的 `implement`、直接调用 `yss-frontend-application` 和直接调用 `yss-backend-testing` 完成代表任务。后端专项包含指定环境验收与普通单测两个对照。 | 受影响的 project 和 skills 安装内容能取得所需共用说明，来源及分发副本一致。独立入口能按原 AC 汇总环境验收，普通单测仍使用短摘要。验证入口和宿主实际运行范围据实记录。 |

### AC-03 · 工作台验证状态对照

除表中变化外，使用同一原验收定义、已登记的必要参与工程及可核实的候选版本。检查写入前后当前目标版本的验证阶段与其新增确认记录。其他阶段的决定及原历史保留。

| 输入 | 预期 |
| --- | --- |
| AC-DEMO-01 实测通过，AC-DEMO-02 仅模拟且本轮要求真实联调。分别用逐条明确、空和仅引用宽泛章节的 `acceptanceRefs` 回放。 | 整体验证为 `doing`，有实际阻塞时为 `blocked`。实际通过凭证及模拟观察均可回读。工作台未为该目标的验证阶段新增自动确认。已有目标保留实际登记内容。 |
| 在部分通过基础上加入缺少测试快照的必验项。已完成独立范围的参与工程提交本方结果。 | 缺项所在报告为 `blocked` 并写出具体原因。其他参与方仍可如实报告本方完成，整体未报完成或跳过。 |
| 从终端续办直达指南。两仓分项均完成，整体联调未做，且目标引用为空或仅为宽泛章节。按指南先报整体缺口，再登记两仓完成，最后才补实际组合凭证。 | 第二个分仓报告写入后的整体仍为进行中或阻塞，历史中没有提前产生的验证自动确认。补齐组合凭证后沿现有规则核实。 |
| 本轮目标含两条逐字可匹配的验收引用。一条实际证据明确覆盖两条断言，必要角色、目标组合及其他自动确认条件齐备。 | 同一证据可用于两条验收。阶段为 `done`，回读能看到验证阶段的自动确认及来源。 |

### AC-05 · 续办与版本对照

| 输入 | 预期 |
| --- | --- |
| 缺上报命令的旧 CLI，或当前项目无工作台写权限。本次验证本身已有授权。 | 各自从原任务读到实际结果及对应回写缺口。 |
| 本地两条独立验收均有证据。新候选只改变其中一条所依赖的输入，另一条有可核对的等同性依据。 | 只把受影响的验收列为待复核，另一个保留原证据、原版本和采用理由。 |
| 当前 CLI 下更换合并、环境或集成验证所需的工程候选。局部输入摘要相同，尚无新候选的精确组合凭证。 | 回读仍能见到旧候选的报告。当前候选等待实际组合凭证，取得后才报告对应验证完成。若只是工程版本变化，按原目标核实实际候选。 |
| 当前已有另一轮目标。旧作业带原目标、原工程版本和输入摘要迟到上报。分别回放旧候选仍可复核，以及换版后 CLI 拒绝旧版本输入的情况。 | 成功上报仍绑定原目标和候选。被拒时在原任务留原证据和真实错误。当前轮次的验证状态只反映本轮适用的凭证。 |

## 后续增强条件与成本

首轮落在现有共享 `implement` 的收尾方法、Backend 同名覆盖，以及 `yss-frontend-application` 和 `yss-backend-testing` 的直接交付路径。共用说明供各入口直接读取。Spec 交接沿既有方法提供原 AC、已知验证及模拟边界，研发结果沿原来源回流。工作台写入和 PR/MR 表达沿现有入口。实施时核对实际受影响 Profile 的 project 与 skills 装配，确保直接调用专项入口时可以读取需要的共用说明和适用的 Profile 覆盖，沿仓库分发规则同步受影响副本。

| 顺序 | 何时值得推进 | 成本与兼容边界 |
| --- | --- | --- |
| 首轮 · 结果摘要与验收对应 | 本文 FR 和 AC。 | 增量主要是写作、复核和分发。既有技能名、Spec 标识、模板默认范围、工作台接口与历史记录直接沿用。 |
| 后续 · 把重复验证做成可重放入口 | 多次接手仍要重建同一测试数据、启动或操作步骤。优先补项目既有 README 或测试入口，覆盖真实操作、结果回读、证据留存及清理。 | 需要环境、样本数据和工具维护。现有验证足够的路径继续复用。模型验证或独立复核由实际风险与收益决定。 |
| 后续 · 工作台展示或结构化关联 | 多个真实交付反复人工拼接相同摘要，或有明确的逐 AC 查询与自动判定需求。先评估只读汇总。 | 结构化关联另作设计，验证旧 CLI、旧报告及消费者兼容。旧报告缺少对应依据时显示未知。自动确认语义、持久化字段及 UI 不属于首轮实施范围。 |

实现后选择一次小改、一次跨仓联调和一次候选换版，用相同任务输入与环境对照旧方法和候选。观察接手人定位原 AC、证据和版本的步骤，补问次数、重复验证、任务耗时及可取得的模型用量。不能取得的数据保留未知。依据实际观察决定后续范围。 [既有技能对照方法](../../.agents/skills/yss-write-docs/references/pr-and-retro.md#技能行为改版的对照)

### 审查修复与回归

- 工作台 CLI 回放复现了两个参与方先报完成时的提前汇总。空验收引用可直接触发自动确认，宽泛章节被误报为已覆盖时也会触发。补写整体未完成只撤掉当前确认，原历史仍保留。修订后先报告整体进行中或阻塞，再报告两个参与方完成，回读未出现验证自动确认。实际组合 HTTP 和 SQLite 断言通过后，提交新的整体完成报告才出现自动确认。 [上报验证结果](../../.template-spec/agents/workbench-progress.md#上报验证结果)
- 终端续办的 Codex 对照只装工作台指南，其实际轨迹先保存并回读整体阻塞，随后上报前端本方结果。两仓均显示分项完成，前端证据仍为待核实，整体阻塞且没有验证自动确认。指南同时以实际测试版本填报，迟到结果按原目标和报告 ID 回读。
- 部分签收对照使用已有有效自动核实的同一目标。Codex 将 AC-01 的人工决定和 AC-02 的待签收分别写入原任务。回读目标版本及自动决定没有变化，轨迹没有调用整目标确认或重新登记。
- 编号 AC-02 补做了独立样本。外层进程执行真实回环 HTTP 和 SQLite 探针，Codex 隔离会话读取回执并只读查询数据库，再把编号 AC、真实通过、仅模拟、缺快照及泛化 CI 范围写回既有交接。探针回执自身未内嵌两个 Git 提交，记录按实际读到的候选注明这一限制。
- 旧目标工程缺少共用参考时，Codex 会话从已明确采用的新版 Home 读取后端测试说明和同源参考，实际运行单测，并仅在目标工程按既有约定保存审计归档。
- 修复候选继续用 CLI `3.19.0`（`72e9608`）隔离构建，内嵌 Bundle SHA-256 为 `ed5a20f43d9e95aa0a95ef03b5b5a1d8f52c42fec2b0b51e6799ea578967cce3`。六种默认实际安装、十二种单技能选择和十二种无 `implement` 的工作台直达装配通过。三个 Profile 的旧版 skills 同步通过 `doctor`，重复同步无变化。
