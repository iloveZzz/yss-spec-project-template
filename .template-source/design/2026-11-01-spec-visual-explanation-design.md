## 1. 决定与依据

用户要求从 Why、What、How 分析 ShowMe 如何引入 Spec，并明确关注“详细的规格 spec 设计文档、业务状态流、交互说明等”，允许补充相关内容。比较方案后，用户选择方案 A：将图解方法融入现有技能，不新增独立 ShowMe 技能入口。

本设计补充 [Spec 技能整合与完整预装设计](2026-11-01-spec-skills-integration-design.md)，沿用其已确认的能力归属、16 个默认入口、全新安装范围和交付边界。该整合方案尚未实施；当前 `bundle-profile.json` 中 `project` 与 `skills` 仍分别配置 7、10 个入口。本设计不把目标集合当作当前已安装状态，不重新执行旧实例迁移。

用户先确定关注范围和方案 A，随后批准本文。具体文件拆分、触发条件、图形选择、预览方式和验证样例由本设计提出，随本次批准成为实施依据。规则决策、权限和需求变更说明是对用户所列内容的补充，不代表所有任务都要生成六类图表。

## 2. Why：为什么引入

详细规格需要同时说明角色、条件、规则、状态、交互和验收。只靠顺序文字，读者可能需要跨章节重建这些关系；只有页面截图，又难以说明规则和异常。本设计用适合问题的图表承接这些关系，帮助业务方核对、帮助研发理解，并暴露尚未确定的部分。

当前仓库已经有三项基础：`i-have-adhd` 维护中文文档表达，业务分析负责规则与边界，产品设计和逻辑原型负责行为呈现与验证。本次补强的是这些内容如何被读懂，不建立第二套需求来源或设计流程。

预期结果：

1. 读者可以追踪一个主要任务从入口到完成、拒绝或恢复的路径，并定位相关规则。
2. 状态改变能够解释“谁在什么条件下做什么、系统得到什么结果”，不只展示状态名称。
3. 交互说明能够解释操作、反馈、权限与失败处理，研发无需凭页面外观猜行为。
4. 需求变更能够指出改变的行为及受影响的规则、状态、页面和验收。
5. 图文之间有可核对的对应，未决业务问题保持可见。

这些是目标和观察标准，不是已证实的收益。不以图表数量、视觉复杂程度或文档长度评价效果。

### 非目标与失败结果

不新增独立 `show-me`、别名、全局模式、插件依赖、渲染服务或自动化引擎。不把上游调用树、组件树和代码结构作为 Spec 的默认要求，不提前引入数据库、API 或技术分层。

不要求每份规格拥有全部图表，不为短问题生成 HTML，不为了“图文齐全”重复维护相同规则。不用漂亮的图掩盖缺失的业务决定，不把静态说明当作交互验证，不新增批准包、固定证据格式、维护脚本或测试套件。

## 3. What：具体提供哪些能力

| 内容 | 优先表达 | 需要读者看清的事情 |
|---|---|---|
| 规格总览与业务边界 | 简短总览；必要时角色关系或范围图 | 目标、涉及角色、主要任务、责任边界、非目标及规格入口 |
| 业务状态流 | 状态图；条件复杂时配合转换表 | 源状态、动作、执行角色、前提、目标状态、可观察结果和禁止操作 |
| 交互说明 | 页面/任务流程、局部标注、动作与反馈表 | 入口、输入、操作、校验、反馈、导航、退出和恢复 |
| 复杂规则 | 决策表、分支图或代表性案例 | 条件组合、优先级、量词、边界和例外 |
| 权限与可见性 | 角色权限表；多方交接时补协作图 | 对象和数据范围、操作权限、状态约束、无权限时的表现 |
| 需求变更 | 前后对照或局部差异图 | 变化前后行为、影响范围、仍保留的规则和对应验收 |

图表与完整文字规格相互补充。简短规则可以直接写在转换表或交互表中，不需要再复制成另一段正文；较长规则保持一个权威定义，图中使用可定位引用。规格章节、已有规则编号或可点击锚点均可，不强制补建编号体系。

### 3.1 详细 Spec 的阅读结构

继续使用现有规格结构，按需要在相应章节内加入表达，不另建一份“图解版 Spec”。详细资料可以提供简短总览和锚点导航，但总览不能成为另一套规则。

- 问题、目标、范围和场景解释业务意图，复杂责任关系可补图。
- 规则章节保留条件、权限、例外、量词和来源，复杂组合用决策表。
- 状态与恢复章节解释业务状态和适用转换，失败、取消、重试、冲突按风险覆盖。
- 原型及交互说明引用实际页面/原型，明确动作、结果、模拟范围和实际检查。
- 验收与未决项继续存在，图解不替代可观察结果。

完整产品 Spec 交付研发仍遵循既有整合设计中的“规格、原型、说明”三类内容。图表不形成第四类必需交付物。普通事实查询、局部修订和模板维护依当前任务完成。

### 3.2 状态表达

区分业务状态与界面显示状态。例如，业务处理中的对象不应因为界面加载失败而自动被画成业务失败；加载、空数据、禁用等显示条件由交互说明解释。

每个受本次说明影响的业务转换应能找到适用的角色、触发、条件、结果和规则来源。无权限或条件不满足时，说明是否保持原状态及用户得到的反馈。终态、回退、撤回、重试与并发冲突仅在业务适用时表达；来源未决定的转换不得补造。

大流程按读者任务或业务责任拆为局部视图，明确局部范围及跨图入口。不能通过省略关键转换制造“只有一条成功路径”的错觉。

### 3.3 交互说明

围绕用户任务组织：从哪里进入、看到什么、允许做什么、输入如何校验、成功或失败后怎样继续、如何取消或离开。字段含义、权限、保存语义、草稿保留或恢复方式有来源才写确定行为。

已有原型或页面可以通过标注解释，但原型中的模拟与未实现行为必须可见。普通说明不更改生产界面；只有用户任务包含原型制作或修改时，才由设计负责人开展相应工作。

### 3.4 规则、权限与变更

决策表保留重要条件和优先级；未列组合不得暗示“全部允许”或“全部拒绝”。权限表区分看见对象、读取字段和执行动作，不能把页面按钮隐藏当作业务权限已经实现。

变更说明以真实的前后材料为依据。没有可访问的旧版本时，说明当前提案和无法核验的历史，不虚构 Before。图表包含的规则更新时，同批检查相关图示、交互说明和验收；无关文件不顺手改写。

## 4. 方案比较与选择

| 方案 | 做法 | 收益与代价 | 决定 |
|---|---|---|---|
| A：融入现有能力 | 共享图解参考归 `i-have-adhd`，内容负责人按需使用 | 复用现有文档配套能力，保持 16 个入口；须补齐跨技能引用和独立包资源 | 用户已选择 |
| B：新增独立 ShowMe 技能 | 新增适配入口并纳入 Spec 预装 | 可单独调用；默认集合变为 17 个，须新增调用策略并处理与设计、表达能力的重叠 | 不采用 |

A 仍允许用户自然地要求“解释这份状态流”或“把交互说明讲清楚”，由当前任务选择现有能力；不需要用新技能名才能获得图解。

## 5. How：职责、触发与执行方式

### 5.1 单一方法来源与业务所有者

新增共享参考 `.agents/skills/i-have-adhd/references/visual-explanation.md`。它只持有表达选择、图文对应、阅读方式和少量教学样例，不持有产品规则，也不复述完整业务分析或原型制作流程。

| 现有能力 | 对本次引入承担的职责 |
|---|---|
| `i-have-adhd` | 选择表达形式，维护图文一致性原则，保留事实、限制和未决项 |
| `yss-stage-decision` | 确定和解释业务边界、状态、规则、权限与影响；无法决定的事项交回澄清 |
| `yss-product-lifecycle` / `to-spec` | 按原调用政策组织规格和已有决定；引用共享方法，不复制第二份正文 |
| `yss-design-system` | 页面流程、原型及交互说明的制作和相称检查 |
| `prototype` | 确有需要时验证业务逻辑与状态问题，不由画图要求自动启动 |
| `prototype-review` | 检查实际规格与设计的行为一致性；声明真实验证范围 |
| `yss-research` / `domain-modeling` | 分别提供事实依据、稳定术语和概念关系；不因表达调整重新启动全量调查 |

`i-have-adhd` 当前允许隐式调用且限定于当前文档工作，继续保留此政策。不复制上游 ShowMe 的禁止隐式调用配置。`to-spec` 等既有显式入口的调用权限保持不变：图解参考的读取不授权执行另一技能的完整工作流或对外发布。

### 5.2 何时加载图解方法

文档配套入口与共用写作规范加入简短指针。用户要求图解、流程、状态说明，或当前资料包含需要关联阅读的多角色交接、状态变化、复杂条件、交互路径或前后差异时，读取图解参考并判断是否需要图表。属于这些主题不意味着必须生成图。

简单事实、单条规则、局部措辞修改、纯命令或代码执行不触发额外图解工作。已有表格或图足够时复用，用户明确要求纯文字时遵从。临时解释只在当前对话交付；没有保存请求或已有文档修改范围时，不因使用此方法自动创建文件。

技能内部只新增一个条件参考，不新增运行时条件框架、Schema 或任务状态。

### 5.3 表达选择与交付

1. 读取当前授权范围内的规格、已有决定、实际原型和稳定术语，明确本次要解释的关系与读者需要判断的问题。
2. 保留未决项，选能说明问题的最小形式：文字、表格、Mermaid、现有图稿或必要时的单页 HTML。沿用项目既有图稿格式，不强制格式迁移。
3. 将图表放在支持的短说明附近，注明局部范围，引用相关规则和验收。关键限制不能藏在远处或仅通过颜色表达。
4. 对照来源核对角色、条件、顺序、状态和例外；发现业务冲突交回内容负责人，不以润色名义选择业务方案。
5. 使用实际可用的显示方式检查并交付，报告已核对的内容、未观察的呈现及未验证的交互。

Markdown 内的表格和 Mermaid 是可用时的轻量选择；不能假定所有 tracker 或宿主都支持 Mermaid。目标不支持时，以同一来源提供可读的表格或文字，必要时附可访问的图稿。无法实际检查目标渲染时说明限制，不称“显示已验证”。

HTML 只用于难以由现有文档形式表达的局部比较或说明，不替代正式产品原型。默认采用可离线查看的自包含文件，不主动引入 CDN、在线图表服务或上传业务资料；已有经授权的项目环境可以复用。避免覆盖同名成果，路径遵循目标项目约定。浏览器或宿主预览工具按实际能力选择，不硬编码 `open`、浏览器名称或私有绝对路径，也不自动安装工具。

HTML 和图稿保留可读标签、合理窄屏布局和适用的键盘访问；颜色不能成为唯一语义。未实际打开时，提供文件引用并说明未预览，不能声称用户已看到。交互是否通过仍由真实操作决定。

### 5.4 图文更新规则

正文、转换表或现有规则表可作为当前规则的权威位置，由当前文档结构决定；不引入自动生成图表的要求，也不建立第二份机器规则模型。

每个重要图示节点和转换能回到已有章节、编号或锚点。修订规则时检查本次影响的图示与说明；修订图示时反查是否改变业务语义。授权范围以外的关联材料只报告具体差异和影响，不擅自修改。

总览可省略低层细节，但必须给出详细规则入口；未知、提案、已确认规则和模拟行为在文字中可区分。标注简短不等于省略重要的权限、例外或恢复条件。

### 6.1 安装与独立公开分发

项目安装以 `.agents/skills` 为来源，`.claude` 是链接，`.workbuddy` 是副本。图解参考和许可放在技能包内，确保 `project` 与 `skills` 两种范围都能读取；不能依赖仅维护仓存在的 `.template-source`。使用当前支持的规范技能路径和 `skillReferences` 表达依赖，并在实际产物中核对，不假定自然语言提及技能名就会安装资源。

当前公开清单未选择 `i-have-adhd`，而已选择 `yss-product-lifecycle`、`yss-design-system`。本设计不因此新增一个公开入口。独立导出某个消费者且不能保证安装了 `i-have-adhd` 时，按既有直接导出方法，把它实际需要的图解参考及许可从唯一来源复制到该包的 `references/shared/`，将引用改为包内路径，并在包内保留来源说明。该副本是分发产物，不能反向作为第二份编辑源。

常规项目分发继续引用共享技能正文，不为所有技能都复制参考；只有独立包确需自包含时才形成投影。导出说明记录来源到投影的对应，后续修改同批核对受影响投影。不增加导出脚本、运行时依赖解析器或新的打包格式。

本次不改 `i-have-adhd` 的原始主来源标识和上游哈希为 HumanLayer；补充来源记录在适配说明内，现有锁文件支持的有效内容哈希按实际结果更新。不得把本地适配日期冒充上游版本。

新内容要成为 CLI 新安装的一部分，仍需按既有整合计划在授权的 CLI 仓库生成内嵌 Bundle 并构建。源文件准备、构建、正式发行、安装和宿主发现分别报告。当前会话的设计授权不等于公开发布、提交、推送或替换用户工具的授权。

## 7. 如何判断引入完成

沿用直接内容核对、现有工具和少量代表性任务，不新增测试套件、固定验证报告或发布门禁。以下结果服务于本次改动，不要求每份业务 Spec 逐项生成材料。

| 场景 | 应观察的结果 |
|---|---|
| 给定一份详细需求，要求整理 Spec | 在复杂关系处选择必要图表；保留详细规则、原型说明与验收，不默认六类全出 |
| 要求说明业务状态流 | 角色、触发、条件、目标状态和拒绝结果可定位；业务状态与界面显示状态分开 |
| 要求交互说明 | 入口、动作、反馈和适用恢复有依据；未运行原型不称交互通过 |
| 某条状态转换或权限尚未决定 | 保留待定项和影响，不根据示例或视觉完整性猜默认规则 |
| 已有状态图与规则冲突 | 指出具体冲突并按授权修正；业务决定未明时不静默选一方 |
| 修改规则或权限 | 本次影响的图表、交互说明和验收得到同步或明确报告；图中仍可追踪依据 |
| 单条规则解释、纯文字要求、局部改字 | 不产生无必要图稿、HTML、完整原型或新文件 |
| 宿主不支持 Mermaid，或没有浏览器 | 仍有可读说明，准确报告未验证呈现；不自动安装或上传资料 |
| 两种 Spec 安装范围与独立公开包 | 新参考、来源及许可可达；独立包不留下必需的跨包死链接；入口数量不因 ShowMe 增加 |
| 宿主副本和 Backend 消费 | 实际受影响内容一致，专有覆盖和默认集合保留；结构检查与实际宿主行为分开报告 |

内容自检可复用少量明确标注的教学例子，覆盖状态、交互和变更，并包含一个“输入缺失，不能补造”的反例。样例是方法说明，不维护为脚本或测试套件。

实际运行代表性 Agent 请求时记录观察和限制；未运行只报告文本与资源核对。没有真实读者反馈时，不宣称理解速度提高、歧义减少或返工率下降。实施完成后的真实 Spec 可作为后续效果观察，不成为本次新增的研究流程。

## 8. 风险与实施者可决定事项

- **图文漂移**：沿用一个规则来源，图表使用可定位引用，变更时检查实际关联材料。人工对应仍可能遗漏，不能承诺自动一致。
- **过度图解**：入口明确简单任务不触发，方法要求先判断读者问题，不把详细规格理解为无限增加图表。
- **职责扩大**：表达能力发现冲突后回到业务所有者，不重做访谈、业务分析或产品设计。
- **分发缺口**：项目共享引用与独立公开包分别处理。本文已选定独立包投影方式，不把补装依赖转交给普通读者。
- **新旧材料交叉**：以已确认整合设计及当前真实文件为依据，历史记录保留原意，旧流程不因被引用重新生效。
- **工具可用性**：可读的文字和表格保持可用；预览、渲染和交互声明只到实际观察范围。

实施者可决定参考内的小节顺序、教学样例用词、图形布局、局部引用落点及临时核对命令。不能自行改变方案 A、来源唯一性、显式调用政策、16 个目标入口、规格/原型/说明的交付边界或外部操作授权。
