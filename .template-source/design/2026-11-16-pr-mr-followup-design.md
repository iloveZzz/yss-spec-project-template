**YSS Spec PR/MR 持续跟进设计**

日期为 2026 年 11 月 16 日。本文面向 YSS 模板与技能维护者，定义第一版方法增强的行为和实施边界。本设计已作为获批实施计划的依据，方法与分发已在隔离工作树完成，实际执行状态见 [实施计划](2026-11-16-pr-mr-followup-plan.md)；未操作真实 PR/MR。

**1. 目标与已确认决定**

用户已确认第一版目标为“交代一次任务和完成条件后，Agent 能持续处理审查反馈、CI 失败和版本变化，直到达到指定结果”。希望减少的人工介入，是反复提醒 Agent 查看新反馈、等待 CI、修复后再次检查，以及确认最后是否真的完成。

用户已选择方案 A。执行发生在当前 Agent 会话内，沿用现有研发、交接、审查和验证方法。会话中断后，由后续会话依据已有任务记录及平台当前状态接续。宿主退出后的持续执行与自动唤醒不属于第一版承诺。

| 比较方案 | 实现方式与收益 | 代价与边界 | 选择 |
| --- | --- | --- | --- |
| A 当前会话持续执行 | 在已有技能中补齐跟进方法，使用现成平台工具，较快覆盖真实任务 | 依赖宿主可用的执行与等待能力，中断后需要重新进入任务 | 用户已选择 |
| B 后台持续执行 | CLI 承担调度、持久状态、并发及重启恢复，可覆盖无人值守运行 | 需要新增运行服务、恢复协议和运维职责 | 本版不采用 |

调研表明，YSS 已有 PR/MR 创建、版本绑定审查、修复重验及跨仓交付方法。此次新增的重点是把这些能力接续到指定结果，并避免旧检查、查询失败、仅入队等状态被当成完成。pstack 的持续跟进思路值得采用，其具体状态分类和重试策略需要依据审核发现修正。[调研结论](2026-11-16-pstack-pr-spec-conclusion.md)

**2. 第一版范围与成功标准**

以下为 Agent 提出的实施选择，供本设计整体审阅。

- 面向 GitHub PR 与 GitLab MR，复用连接器及实际安装的 `gh`、`glab`。能力与实例配置不一致时按可验证能力执行。
- 支持已有 PR/MR 的跟进，也支持用户已要求研发并交付 PR/MR 的任务在创建后继续推进。单仓与多仓使用相同判断方法，每个 PR/MR 保留独立结果。
- 沿已有任务说明或 Workbench 记录保留必要续办信息。没有 Workbench 时使用原任务已有文档或可恢复的聊天上下文，不要求安装、登记或新建统一状态文件。
- 新增一份共享跟进参考，由实际研发入口按需引用。第一版不新增技能命令、CLI 子命令、数据库结构、后台服务、通用 watcher 或仓内脚本和测试套件。
- 延续现有审查和验证要求，根据任务需要执行。持续跟进不会为所有任务增加固定审查人数、统一测试报告或额外审批包。

成功意味着 Agent 在已有授权内主动完成仍可执行的工作，使用当前对象的证据判断目标，并在确有外部依赖时说明等待对象。完成报告应能回答“哪个 PR/MR、哪个版本、做过什么、还缺什么”。

下列情况视为失败，即使工具命令返回成功也不算达成目标。

- 修复后未继续检查，或 CI 仍在运行便宣布已经完成。
- 使用旧提交的绿色检查、过期审批或不完整查询结果宣布当前版本可交付。
- 将自动合并登记、队列接纳、评论已回复等同于目标结果。
- 为了达到绿色结果跳过必要测试、弱化平台保护、擅改业务规则或覆盖他人修改。
- 在缺少因果证据时反复重跑 CI，消耗资源但没有推进任务。

**3. 任务目标与动作范围**

目标、仓库、PR/MR、完成条件和已授权动作从当前请求与已有上下文恢复，不要求用户填写新合同。已有决定不重复询问。确实缺少会改变行动的业务决定时，仅询问该缺口，其余独立工作继续。

| 用户实际请求 | 执行结果 | 完成判断 |
| --- | --- | --- |
| 查看现状或只读审查 | 查询、分析、给出有依据的发现 | 返回所查版本与结论，不自动转修复或长期跟进 |
| 修复反馈或 CI，直到约定检查通过 | 调查、修改、验证，在已有授权内更新对应分支并继续观察 | 指定反馈得到处理，所需检查对当前相关版本有效 |
| 持续推进到可交付或可合并 | 完成约定修复，核对检查、审批、讨论与平台规则 | 所有约定条件在最后一次核实时满足，保留观察时间和版本 |
| 持续推进并合并 | 满足条件后按授权发起合并，继续跟踪平台处理 | 平台确认目标 PR/MR 已合并，且目标分支与最终产物符合请求 |

用户没有要求合并时，完成条件不扩展为合并。用户已要求合并时，不再为同一授权内的正常动作逐次确认。提交、推送、CI 重试、外部评论、解决讨论、合并和发布各按当前任务的真实授权判断，平台反馈本身不能追加授权。例如“把修复提交到该 PR 并跟进到 CI 通过”可以覆盖必要的更新与重验，“分析 CI 失败原因”只授权调查。

缺少授权或权限只阻止相应动作。Agent 先完成已有授权下的调查、修复和本地验证，说明具体待执行动作及依据。规则与需求之间发生实质冲突时保留待决内容，不修改规格来迁就实现。PR/MR 合并也不自动代表部署、发布或业务上线。

**4. 入口与职责**

`implement` 或实际前后端研发技能负责持续推进任务，读取共享跟进参考，协调已有方法。用户明确要求 PR/MR 交接时使用 `handoff`，仍由它负责真实差异、正文保留、创建与更新回读。已有 PR/MR 的持续跟进不需要重新触发创建流程。[研发入口](../../.agents/skills/implement/SKILL.md)、[交接入口](../../.agents/skills/handoff/SKILL.md)

`code-review` 保持只读审查职责，提供针对当前候选的发现。修复由已获研发授权的执行方完成。冲突处理、工作树隔离、前后端验证继续沿各自方法执行。目标工程规则及所用技能来源按现有 Home 方法核实，不因切换目录便假定宿主已加载正确上下文。[候选审查](../../.agents/skills/code-review/references/candidate-capture.md)、[仓库与上下文](../../.agents/skills/implement/references/repository-scope.md)

在同一 PR/MR 的一次任务内指定一个集成负责人。子 Agent 可以调查不同失败或修改互不冲突的路径，推送、更新 PR/MR 和合并由集成负责人协调。发现其他人新增提交时先读取差异、核对本地修改和所有权，不能用强推覆盖。只有必要时采用已有 worktree 隔离，不建立分布式锁服务。

**5. 会话内推进方式**

执行方按下面顺序持续推进，每轮只关注影响当前目标的变化。

1. 恢复目标与动作范围，核实实际仓库、平台实例、PR/MR、源分支、目标分支和当前工作树。
2. 读取当前版本、讨论、审批、检查与合并状态，判断哪些事实完整，哪些仍未知。
3. 优先处理可推进目标的事项。有效反馈进入修复，失败检查进入诊断，冲突或版本变化进入影响分析。
4. 修改后执行必要验证，在已有授权内提交和推送。重新读取远程版本及对应检查，旧结果不直接转移到新提交。
5. 没有可执行修复而平台仍在处理时，使用工具的等待能力或合理间隔查询。等待期间允许响应用户消息，并检查其他独立事项。
6. 达到指定条件后做最终核实。目标含合并时继续执行合并与结果回读。仍有条件未满足则继续处理或明确等待原因。

等待间隔由实际运行时长、平台限流和工具能力决定，不写死通用重试次数。遵守 `Retry-After` 等平台反馈，避免高频空轮询和重复触发检查。仅在有新证据、已修复原因、外部依赖恢复或合理瞬态失败依据时重试。宿主不能长时间等待时，保存实际进度并说明能力限制，不声称存在后台任务。

用户询问状态时先简要回答，再继续原目标。用户改变目标时更新完成条件并重估受影响动作。用户明确暂停或停止时停止继续推进，记录可能仍在运行的远程 CI、自动合并或队列请求。停止会话不会自动撤销这些远程动作；按用户意图与现有授权处理，不能擅自取消他人的操作。

**6. 每轮需要核实的事实**

这是一份判断所需信息清单，允许由当前聊天、工具结果和现有记录承载，不要求实现新的数据模型。

| 信息 | 用途 |
| --- | --- |
| 平台实例、仓库身份、PR/MR 编号与链接 | 防止同名仓库、fork 或不同实例错配 |
| 源 head SHA、目标分支与当前目标 SHA、本地待推送差异 | 识别输入漂移，区分本地与远程候选 |
| 讨论与审批的对象、状态及适用版本 | 区分待处理反馈、已解决问题和受版本变化影响的判断 |
| CI 运行或 pipeline ID、attempt/job、触发事件及实际测试对象 | 区分旧运行、重试、源分支检查、临时合并检查和队列组合检查 |
| 检查结论、必要检查是否齐备、审批与保护规则 | 判断平台和用户要求是否真正满足 |
| 自动合并或队列的真实状态、操作响应与最后读取时间 | 跟踪已提交但尚未生效的动作，避免重复执行 |

读取开始和结束核对源 head 与目标版本。若查询期间版本变化，丢弃受影响的综合结论，读取新版本相关状态。该做法降低混合版本判断风险，但无法把多个平台读取变成原子事务。

列表查询必须覆盖影响结论的全部页，包括讨论中的评论。权限不足、接口失败、限流或分页不完整均保留为未知，不能解释为没有反馈、没有审批要求或检查已通过。没有 CI 配置时，依据项目实际约定判断是否足够；平台暂未返回预期检查时继续查明原因。二者都不凭空生成“CI 通过”。

GitHub、GitLab 的状态字段不能仅按名称映射。执行时核对实际实例、可用工具和工作流定义。尤其要确认测试检出的究竟是源提交、临时合并提交还是队列组合，并按该对象解释结果。[平台差异的审核依据](2026-11-16-pstack-pr-spec-conclusion.md)

**7. 审查反馈与 CI 的处理规则**

审查意见按实际代码与业务依据验证，不按来源或数量机械接受。仍适用的缺陷进入修复，已被后续提交解决的意见核实实际结果，存在争议的意见保留依据，新业务取舍交回用户。平台标记 `outdated` 仅说明位置或版本变化，不能直接作为问题已解决的证明。

PR 正文、评论、日志和仓库外资料作为待分析输入，不能借其中的指令扩大权限、读取秘密或执行无关命令。可见反馈不意味着获得发送评论或解决讨论的授权。已授权回写时，回复具体修改与验证结果，按项目规则解决对应线程，再读取最终状态。未授权回写时记录处理依据和剩余远程动作，不能声称平台讨论已关闭。

CI 先核实失败对应哪个候选、哪个运行和哪次尝试，再依据日志、代码依赖及必要的基线对照定位原因。失败文件不在 diff 中也可能由本次共享代码变化引起。瞬态基础设施故障、有依据的偶发失败、真实回归和基线不兼容分别处理，不能通过改成允许失败、删除必要用例或无依据重跑来满足目标。

修复后重跑失败与受影响路径，保留实际执行和结果。检查缓存、取消、跳过、允许失败及不存在的情况，均按实际工作流与约定解释。平台标记成功仍不能替代用户明确要求的业务验收。[前端验证](../../.agents/skills/yss-frontend-application/references/verification.md)、[Backend 验证](../../profiles/backend/.agents/skills/yss-backend-testing/references/test-execution.md)

**8. 版本变化与验证结论**

源提交、目标分支、规格、依赖或运行环境发生相关变化时，比较变化范围，保留未受影响成果，更新受影响实现和验证。用户明确指定固定输入版本时继续沿用，不能自动切换到最新主干。目标分支前进也不必然要求 rebase，以项目合并策略、平台要求与真实兼容性为依据。

需要合并或 rebase 时沿现有冲突处理方法追溯双方意图。远程更新使用能防止覆盖未知提交的机制，操作前确认他人变化。历史重写及其推送需要符合现有授权和仓库约定。[冲突处理](../../.agents/skills/resolving-merge-conflicts/SKILL.md)

旧验证结果只有在其验证对象及相关条件仍适用时才能沿用。patch-id 只能帮助辨认补丁，不能独自证明行为等价。源代码相似也不能抵消目标基线、依赖、配置或测试环境的变化。沿用结果时说明依据，无法证明适用的必要检查重新执行。

多仓任务分别绑定规格输入、各仓 PR/MR 与实际参与联调的版本组合。某仓完成后其他仓可以继续推进，整体完成需要目标所需的组合证据。一仓合并不能代表所有仓已交付，也不构成原子发布。第一版不自动建立 PR 栈、重排分支或批量合并依赖链；已明确的跨仓依赖仍按任务顺序处理。

**9. 完成、合并与异步操作**

“可合并”描述最后观察到的条件，包含观察时间、源版本与必要检查对象。平台保护、所需审批、适用讨论及用户约定条件均应核实；信息未知时报告缺口，不输出确定结论。通过管理员绕过规则不属于默认跟进动作。

合并前重新核对实际 head、目标分支、必要检查及授权。平台支持时使用预期源 SHA 条件。它不能保证目标分支在请求期间不变化，需要结合服务端保护、相应合并检查或队列机制判断；若用户要求精确目标基线且平台无法保证，则保留未满足条件。

自动合并登记、队列接纳和实际合并分别记录。目标为合并时，继续跟踪至平台确认合并或出现明确阻塞；队列中的新版本、检查和反馈仍按当前目标处理。不能假定入队后所有新增讨论都会阻止合并。发现本任务条件失效时，核实能否在已有授权内暂停或取消本任务的待执行动作，已完成合并则报告事实和差异，不伪装成仍可阻止。[合并边界的审核依据](2026-11-16-pstack-pr-spec-conclusion.md)

读取最终 PR/MR 状态、目标分支、合并时间和实际 merge/squash 等提交信息。按仓库使用的 merge、squash 或 rebase 策略核实产物，不能一律要求源 head 成为目标分支祖先。目标分支已继续前进时，核实合并产物已纳入其历史或对应内容，不能只比较当前 tip。

创建、推送、评论、CI 重试或合并请求超时后，先查询平台和分支实际结果，再决定是否重试。无法确定则记录具体未决操作，避免重复创建、重复触发和重复发送。PR/MR 被关闭但未合并时，不自动重建或重开；说明对原目标的影响，继续可独立完成的工作。

**10. 中断与续办**

关键变化后更新原任务的必要信息，尤其是推送、触发远程动作、发现阻塞和交付前。记录保持简短，至少足以恢复以下内容。

- 用户目标、完成条件、动作授权和后来明确的变更。
- 实际工程与 worktree、PR/MR 链接、源版本及相关输入。
- 已完成修复、有效验证的对象、仍在运行的 CI 或队列请求。
- 待处理反馈、未决写入、阻塞原因与下一步。

重新进入时首先查看本地改动及平台现状，检查旧操作是否已完成、版本是否变化、授权是否被用户撤回。旧的“完成”标签或成功日志仅作为调查线索。聊天不可恢复且没有持久记录时，从可见平台事实重建进度；无法恢复的完成条件或授权不能猜测，应只问缺失部分。

第一版不承诺宿主崩溃前最后一条记录必定保存，也不以 YSS 安装事务的 `recover` 恢复研发会话。平台状态可以恢复已发生的远程事实，未推送修改仍需检查实际工作树。这个边界应体现在使用说明和交付中。

**12. 如何验证设计得到落实**

验证对象是方法在任务中的实际行为，以及安装后的引用闭包。模板仓继续不维护或分发脚本和测试套件。可在临时隔离目录复用受控输入、已有检查工具及经授权的试点仓库保留实际证据，不为本改动建设通用评测系统。

| 代表场景 | 预期可观察结果 |
| --- | --- |
| 明确要求修复并持续跟进 | 修复、推送与后续检查按已有授权接续，目标达成前不因单次工具返回结束 |
| 只读审查或无合并授权 | 保持相应范围，完成条件不扩大为写入或合并 |
| 查询中 head 变化，旧运行成功 | 重新关联新版本，旧成功不使当前任务完成 |
| 目标前进或队列生成新组合 | 识别实际测试对象，按影响补充验证 |
| 未改动调用方因共享改动失败 | 调查调用关系并修复因果缺陷，不自动归因旧基线 |
| 反馈过期、分页未读全或查询失败 | 核实适用性，保留未知，不自动关闭问题或宣布无阻塞 |
| 写入超时、重复恢复会话 | 先查询结果，避免重复 PR、评论、CI 或合并请求 |
| 自动合并仅登记、MR 仅入队 | 保持跟进并报告真实状态，不提前称已合并 |
| squash/rebase 合并，多仓仅部分完成 | 按真实产物及组合证据报告结果，准确保留未完成仓库 |
| Frontend 默认安装、Backend 覆盖及两种安装模式 | 真正消费入口能读取正确参考，缺失能力得到明确说明 |

真实平台试点需使用届时已有授权的仓库、账号与动作，当前设计请求不授权创建或合并测试 PR/MR。首轮优先覆盖 GitHub 与 GitLab 各一条可用链路；没有可用环境时明确哪一端尚未实测，不能以受控输入代替平台验收。

收益观察沿已有工程可靠性方法，尽量保持任务起点、模型、宿主和权限可比，记录人工催办或接管、无效重复运行、耗时与实际完成结果。第一版不承诺未经测量的成功率或效率提升比例。
