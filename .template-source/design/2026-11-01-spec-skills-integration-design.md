# Spec 技能整合与完整预装设计

日期：2026-11-01
状态：用户已于 2026-11-01 确认，并明确取消旧版兼容和迁移；尚未修改技能、安装清单或 CLI
适用范围：YSS `spec` profile 的全新安装，以及共享技能受到影响的分发副本

## 1. 要解决的问题与已确认方向

Spec 安装完成后，应能直接完成需求研究、业务分析、澄清、规格设计、原型设计、说明和交付，不需要在正常分析过程中反复补装技能。

用户已确认按能力归并重复职责，并一次预装完整的 Spec 能力；随后明确**不考虑旧版兼容和迁移**。本设计以全新安装为目标，直接移除被合并的入口，不保留别名、转向入口或旧项目升级方案。用户进一步明确：**Spec 阶段完成 Spec 设计、原型设计及说明，才交给研发；研发阶段专注技术设计与实现。**

本设计将“安装齐备”“按问题选用”和“产物完成”分开处理：所有 Spec 能力可以预装，但不要求每项任务执行所有技能；产品需求交付研发时，规格、原型及说明必须齐备。普通事实查询、局部修订和模板维护仍按用户当前范围完成，不因为安装了 Spec 技能就自动生成整套产品产物。

### 目标

- 同一个问题有清楚的能力负责人，避免研究、设计、原型与复核重复接管。
- 研究从简单资料汇总扩展到足以支持需求决定的事实调查；业务分析有独立职责，不能由竞品对照代替。
- Spec 的 `project` 与 `skills` 使用相同的默认技能集合，安装范围只影响项目文档与入口资源。
- 普通产品需求无需先取得实现仓库、技术架构、OpenAPI 或实现切片，便可完成 Spec 和原型。
- 下游能够依据已完成的业务决定、验收与原型开展技术设计，不必重新猜测产品行为。
- 新集合只提供实际能力入口；现有用户文件、Backend 专有能力和外部操作授权受到保护。

### 非目标与不接受的结果

不把全部 62 个技能设为 Spec 默认，不把 Java、数据库、API 设计或生产实现放回 Spec 阶段。不引入新的生命周期引擎、强制审批、批准包、检查脚本或测试套件。不提供旧入口兼容、旧安装升级、用户原型迁移或相关验证。不考虑兼容不等于可以覆盖或删除用户既有项目；本次不操作这些实例。不能只增加安装数量而保留重复正文，也不能只缩短技能入口而继续分发冲突的旧参考。

预装不包含第三方插件、工具账号或模型服务授权；不自动安装 Node、浏览器或前端依赖。技能可发现不等于工具可用，工具不可用时不能宣称原型已验证。

## 3. 方案比较与选择

| 方案 | 做法 | 取舍 |
|---|---|---|
| A：保留全部入口并明确分工 | 不合并技能，修正文案并扩大预装 | 修改少，但相邻入口仍多，重复方法容易再次出现 |
| **B：按能力归并，移除重复入口** | 统一研究和产品设计负责人；逻辑原型、复核、业务分析保持独立；直接删除被合并入口 | 内容与引用需统一，但入口清楚，不承担旧版兼容和迁移；**按用户最新决定执行** |
| C：单个大型 Spec 技能 | 将研究、分析、设计和评审合成一份入口正文 | 入口少，但条件方法容易混杂，独立调用与维护困难 |

以下职责与内容归并方式延续已确认设计；默认数量按用户取消兼容的决定由 18 调整为 16，不将设计者的措辞写成用户原话。

## 4. 能力归属与调用边界

保留有独立职责的现有 ID，不新增一个大型技能。默认集合含 **16 个功能入口**；`competitive-intelligence` 与 `yss-prototype-stage` 的能力归并后，删除其目录、运行时入口和清单条目。

| 技能 | 整合后的唯一主要职责 | 不承担的职责 |
|---|---|---|
| `yss-product-lifecycle` | 从当前目标选择能力、复用已有决定、组织三类交付物及授权内的发布 | 不重复研究、设计或复核方法，不授予实施资格 |
| `yss-research` | 对需要证据的事实进行调查，包括竞品、现状、规则来源、用户资料和既有系统约束 | 不替用户决定目标和取舍，不把资料比较当完整需求分析 |
| `yss-stage-decision` | 业务分析、范围和方案比较；解释场景、责任、规则、状态、权限、影响和验收缺口 | 不选择技术架构、数据库、接口或实现分层 |
| `grilling` | 收敛只有用户或业务方才能决定的问题，检验假设和方案取舍 | 不将可调查事实转成访谈问题，不重复已有确认 |
| `domain-modeling` | 业务词汇、概念关系和责任边界的一致性；按授权维护稳定词汇与决定 | 不重新组织完整访谈，不按数据库表生成领域模型 |
| `wayfinder` | 在显式要求下管理跨会话的复杂决定及其依赖 | 不成为每项需求的必经流程，不自动创建远程地图 |
| `to-spec` | 在显式要求下，将既有分析、决定和设计综合为可验收的非技术规格 | 不重复访谈，不产生技术设计或实现资格 |
| `yss-design-system` | 产品流程、信息结构、视觉、UI 原型和原型说明；选择合适表达深度 | 不独占业务规则，不再与原型阶段技能双重编排 |
| `prototype` | 可操作的业务逻辑和状态原型，验证有边界的问题及异常组合 | 不探索视觉方向，不把试验代码自动作为生产实现 |
| `prototype-review` | 复核规格与实际设计/原型的一致性、可观察行为、适用视觉与可访问性 | 不重新设计产品，不凭静态图证明交互，不替用户批准 |
| `to-tickets` | 在显式要求下，按业务结果拆分可验收的业务 Ticket | Spec 模式不拆 Controller/Service 等技术任务，不要求实现仓 |
| `triage` | 在显式要求下，整理已有需求、反馈和 Issue，形成有依据的处理建议 | 不代替普通需求路由，不因读取请求自动评论、改标签或关闭条目 |
| `llm-wiki` | 在显式要求下沉淀和查询可追溯的知识 | 不取代当前规格及真实来源，不为普通分析自动创建知识库 |
| `i-have-adhd` | 当前文档的中文表达、准确性与可读性 | 不改变业务决定，不附加旧阶段合同 |
| `handoff` | 用户明确要求时，通过真实 PR/MR 文件差异交接选定材料 | 不代替普通 Spec 交付，不将 PR/MR 设置为交付研发的必需载体 |
| `setup-yss-harness` | CLI 和技能安装、同步与故障说明 | 不因调用技能而自动升级、初始化或改全局配置 |

### 4.1 发现、阅读和执行

预装不改变外部动作权限。保留 `to-spec`、`to-tickets`、`wayfinder`、`triage`、`llm-wiki`、`handoff` 的显式调用政策；路由技能可以使用已授权的共享方法，不能把“已安装”当成隐式执行这些入口的许可。

Spec 侧 `yss-stage-decision` 改为可以根据业务分析任务自动选择，描述明确其非技术职责；这是拟议行为变化，需要同步其 frontmatter、Codex 元数据和注册表。Backend 专有版本不因此改变调用政策。

两个被合并入口不再可发现或调用，不保留别名、转向文档或隐式 fallback。保留入口的 Claude `disable-model-invocation` 与 Codex `policy.allow_implicit_invocation` 分别按实际政策设置；其他宿主只报告已观察到的行为，不假定相同字段都有效。

### 4.2 同时遇到多类问题

事实不明由研究取得证据；业务选择未定由澄清取得决定；术语含混由业务词汇能力处理；业务关系和影响由业务分析整理。已有输入足够的部分继续完成，只有依赖未决决定的部分等待。研究不能代答业务选择，设计不能用视觉结果替代缺失规则。

制作方负责修正其产物，复核方负责指出有依据的缺陷；需要补充业务决定时交回澄清。普通自检不宣称独立评审，也不强制为每项任务创建第二个代理。

## 5. 研究与业务分析如何补强

### 5.1 统一研究方法

`yss-research` 根据要支持的决定选择调查方式，而不是默认输出一份竞品矩阵。其条件方法至少覆盖：

- **现状和业务事实**：现有文档、实际流程、代码中的可观察行为、用户提供的工单与历史记录；明确现状和期望的差异。
- **竞品与替代方案**：比较同一用户任务的流程、能力边界、限制和适用条件，不止比较功能名称。
- **规则和外部约束**：追溯标准、合同、法规或第三方行为的一手来源，注明日期、版本及适用范围；没有来源时保留未知。
- **用户与使用场景**：分析可访问的访谈、反馈、使用记录；确需外部访谈时准备具体问题与观察任务，不代造参与者和回答，不自动联系他人。
- **产品行为验证资料**：分析实际原型操作或可用性观察，区分真实用户结果、Agent 自检与教学模拟。

每次研究明确问题、已有证据、来源适用范围、相反证据、结论和剩余不确定性。区分事实、推断、建议和用户决定；没有价格、性能、样本或使用数据时不制造排名、收益或精确数字。无法访问来源不等同于功能不存在。

竞品方法只保存在研究技能内一个权威参考，所有当前调用方直接引用该方法。用户研究中有关来源、样本、观察与解释的方法归研究；关于在页面中模拟状态和执行动作的制作方法归设计或逻辑原型。

默认在当前对话或既有 Spec 中提供足够结论；用户要求独立报告才单独保存。保存位置复用现有约定，不建立强制研究包、搜索日志或额外证据协议。

### 5.2 业务分析的明确产出

`yss-stage-decision` 保留 ID，入口标题改为“业务分析与方案判断”。它消费研究和已有需求，按当前影响回答以下问题：

1. 谁在什么场景遇到什么问题，期望获得什么结果，已有流程哪里不足。
2. 目标、范围、非目标、优先级及相互冲突的要求是什么。
3. 角色、业务对象、信息来源、责任边界与协作关系是什么。
4. 触发条件、业务规则、权限和数据可见范围是什么，状态如何变化。
5. 成功、拒绝、取消、失败、重试、并发冲突或恢复应产生什么可观察结果。
6. 哪些方案有真实取舍，选择依据、代价及重新考虑条件是什么。
7. 哪些质量要求已有业务依据，如何观察是否满足，哪些数值仍未确定。
8. 哪些验收仍无法写清，需要调查、澄清或原型验证。

这些是按适用范围工作的分析维度，不是必须逐项生成文件的模板。分析结果回到一份当前规格或其引用材料，不再保存一份容易漂移的第二规格。已有事实、决定及稳定编号继续复用。

## 6. 产品设计、逻辑原型和复核的整合

### 6.1 产品设计归 `yss-design-system`

把 `yss-prototype-stage` 中有效的表达选择、流程和状态设计、场景组织、原型制作与说明归入 `yss-design-system`，随后删除 `yss-prototype-stage`。设计技能描述明确其负责产品设计和原型，而不只是颜色和 Token。

在同一能力内按问题选择文字说明、流程/状态图、线框、静态视觉或可操作 UI，不再为选择深度单独调用一个阶段技能。完整产品 Spec 仍须交付原型；按风险选择的是原型形式、覆盖范围和精度，不是是否完成原型。

已有产品延续真实设计基线；新 UI 项目可继续使用现有 Vue + shadcn-vue 默认，允许用户指定其他形式。原型库、设计工具和运行方式是制作手段，不构成生产技术选型。不得把缺失的插件或旧脚本当作普遍前置。

### 6.2 `prototype` 保留独立价值

逻辑原型适合审批状态、规则组合、金额分配、权限动作、撤销重试等难以仅靠静态描述确定的问题。表达业务输入、动作、当前状态和结果，提供代表场景和重置方式，界面只服务于理解逻辑。

有 UI 的完整需求以产品 UI 原型为交付主体；逻辑原型按需要辅助，不能用规则按钮台代替用户需要的产品页面。没有 UI 的需求以业务逻辑或状态原型承接原型交付，说明行为与异常，不虚构页面。

修正 `LOGIC.md` 中“模块可直接迁入正式代码”等表述：实验观察可以支持业务结论；实验代码只是候选参考，生产使用需研发重新设计和验证。删除没有真实调用方的旧捕获、分支或封存步骤，不新增技术实现流程。

### 6.3 `prototype-review` 统一复核方法

该技能持有产品设计与逻辑原型的共同复核方法：规则与验收一致性、主路径、状态与异常恢复、信息与动作可理解性，以及当前产物适用的视觉与可访问性要求。设计技能保留执行检查的责任，在需要的方法处引用这里，避免复制另一份清单。

检查的深度与产物承诺相称。静态图只能证明展示内容；有交互承诺必须实际操作；可运行代码不证明用户研究结果；模拟服务不证明真实接口。发现以产物位置、规则或验收依据、影响和未验证范围表达，偏好和未来改进单列。

不要求每项设计经过独立评审、固定六轴报告或全浏览器矩阵。关键行为错误和交付所必需的验证缺失必须如实报告，不能以“工具运行成功”宣布原型完成。

### 6.4 参考文件和资产归并

逐项保留有效的组件用法、复杂表单、查询、日期、多页工作区、键盘焦点、状态模拟和恢复经验，归入相应能力的条件参考。重组内容时保持许可证、固定来源和实际使用边界；这是新集合的内容整理，不是用户旧项目迁移。

`yss-prototype-stage` 当前含大量组件及 Vue 示例资产。归并后产品设计资产由 `yss-design-system` 持有，更新所有当前源码引用、模板渲染路径和打包资源，然后删除旧目录，不保留资源转向路径或第二套资产副本。用户已生成的原型目录不在本次范围。

清理 `prototype-profile-routing.md`、`product-design-adapter.md`、`prototype-verification.md`、`component-qa.md` 及其他命中引用中的固定 H1/H2 升级、先验审批、固定证据 Schema、`seal-project` 等失效要求。历史合同或用户实际已有的交付约定不能被覆盖为新事实，按其适用范围继续读取。

## 7. Spec 交给研发时必须具备的内容

这是用户要求的产品交付完整性，不引入自动门禁、批准系统或“实施资格”。材料不足时可以继续保存草稿和完成独立工作，但不能报告“Spec 已完成，可以交给研发”。

| 必需内容 | 必须让研发看清的事情 | 不足以替代的材料 |
|---|---|---|
| **完整 Spec** | 问题、目标、角色场景、范围、规则、权限、状态异常、非目标、业务质量约束、可观察验收、重要来源与已确认决定 | 竞品矩阵、想法列表、仅有页面标题 |
| **原型设计** | 用户如何完成任务，关键信息和动作在哪里，规则和状态如何表现；无 UI 时通过逻辑/状态原型表现行为 | 仅靠研发推断的文字、无代表内容的空骨架、与真实任务无关的组件展示 |
| **原型及交互说明** | 页面/状态与 Spec 的对应、入口和退出、动作结果、校验与权限、失败和恢复、模拟范围、查看/运行方法、实际检查与未覆盖项 | 截图本身、启动命令本身、没有业务含义的技术 README |

以上是三类内容，不要求三个固定文件。说明可与 Spec 合并，原型独立保存并提供可读引用；同一规则只有一个权威定义，原型使用它的引用或明确对应关系。

### 7.1 原型完成标准

- 涉及操作或状态变化的核心用户场景应可操作；纯展示页面可以使用可审阅的静态设计。复杂或危险行为不能只靠静态图声称已验证。
- 原型覆盖当前承诺的主要任务及风险相关的拒绝、权限、校验、失败、取消和恢复；不机械要求每页拥有所有状态。
- 使用真实或有代表性的内容，标明模拟数据和未实现动作；不得用可点击外观暗示不存在的行为。
- 说明中能找到对应规则和验收，并记录实际检查。依赖真实服务、组件或技术条件的假设交给研发验证，不把它们冒充产品实证。
- 用户给定的行为冲突、关键权限和恢复规则尚未决定，或必要原型行为无法验证时，交付状态仍为草稿并列明影响。

“核心场景可操作、非 UI 使用逻辑/状态原型”是本设计为落实用户边界提出的默认值，不等于用户要求所有页面高保真，也不要求先产出低保真再逐级升级。

### 7.2 交接与研发边界

交付提供一个明确的规格入口，能读到原型、说明、真实决定和剩余限制。已配置 tracker 沿用它；本地文件、Issue 或用户明确要求的 PR/MR 均可作为载体，不强制创建交接包。无法确认研发可访问时如实说明，不把文件存在当作接收成功。

`to-tickets` 可按用户要求进一步拆出业务 Ticket，保留原始规则与验收引用，依赖表达业务前后关系；它不是每次交付的必要步骤。不得在 Spec 内细化数据库迁移、接口端点或技术层任务。研发侧再选择架构、接口、存储、组件实现、技术验证和实现切片。

Spec 可以记录已知的系统事实和已确认外部约束，也可以研究技术可行性事实；这不授权 Spec 替研发完成技术方案。研发发现业务冲突或新约束时，提出具体影响并回流受影响的规则，不能静默改写产品决定。

## 8. 默认预装与实际安装行为

### 8.1 两种安装范围统一为 16 个

`installations.project.skills` 与 `installations.skills.skills` 使用以下相同集合：

```text
setup-yss-harness
yss-product-lifecycle
yss-research
yss-stage-decision
grilling
domain-modeling
wayfinder
to-spec
yss-design-system
prototype
prototype-review
to-tickets
triage
llm-wiki
i-have-adhd
handoff
```

两份数组保持显式配置，不为共享 16 个名称新增配置层或生成脚本。注册表与使用说明同步同一集合，并说明分发配置是默认安装的权威。

新 Spec 安装不再默认选择 `implement` 和 `code-review`；它们继续保留在可用技能库供有需要时补装。已有受管项目的升级和技能保留策略不在本次设计范围。本设计不修改 Backend 默认的 4 个技能，也不把全部 Spec 集合安装到 Backend。

`project` 保留其必要项目文档；`skills` 只带技能、宿主入口及必要引用，不强制创建 Context、设计基线、业务 Spec、wiki 或 tracker 配置。缺项目文档时仍可按用户指定路径形成草稿及原型，不能伪造已有治理身份。

### 8.2 安装闭包

必须核对每个入口及条件参考实际使用的文件。当前 CLI 依赖收集不能理解所有自然语言提及和相对链接，不能假定修改一句“调用某技能”就完成分发。

优先用现有 `skillReferences`、技能包内文件和 CLI 已识别的规范技能路径表达必要依赖，不新增运行时依赖引擎。当前调用方直接引用研究或设计负责人；产品设计引用的复核方法及所有必要资源必须实际进入分发集合。

从技能正文、条件参考和资产实际消费者出发检查闭包，不能只验证 16 个 `SKILL.md` 存在。尤其检查 `to-tickets` 目前提及但分发清单未列入的集合模板：本设计取消固定集合文件的要求；若仍有适用消费者，则保留并列入必要引用，不能留下不可达路径。

项目技能库和公开独立技能包分别检查。公开清单移除被合并入口，研究、设计及其他保留的公开技能连同必要内容与参考进入可用导出范围。更新公开清单与分组只表示源配置准备完成，不表示已发布公开仓库。

### 8.3 CLI 交付与全新安装

目标行为保持现有命令语义：

```text
yss init --root <新目录> --profile spec --installation skills
yss attach --root <已有普通工程> --profile spec --installation skills
yss skills list --root <受管工程>
```

省略安装范围的新安装仍遵循实际 CLI 的 `project` 默认；两种范围都应获得上述 16 个入口。`attach` 仅验证首次接入普通目录，不承担旧 YSS 实例转换。`--dry-run` 只预览，不生成目录或保存计划；`skills list` 仍要求受管安装根，不新增全局目录查询语义。

CLI 使用内嵌 Bundle。模板源合并后，必须在 `yss-cli` 仓库按其现行构建约定生成 Bundle 并构建新程序，才能让新安装携带本设计；不会从模板 main 自动获取。仅编辑模板清单不能宣布 CLI 安装已生效，也不能把开发构建标成正式版本。

本次不制定或验证旧项目 `sync`、旧二进制升级或既有原型转换，也不提供兼容保证；不因此删除 CLI 现有通用同步能力。正式发行、工具替换、提交推送及公开发布仍按对应授权执行，用户既有项目不自动改动。

## 11. 风险与实施边界

- **只合并入口而遗漏深层参考。** 从实际引用和资产消费者追踪归并，条件参考和旧工具要求同批处理；不为省事保留互相冲突的两份规范。
- **把完整预装变成每次全量工作。** 路由始终依当前任务；只有完整产品 Spec 的研发交付承诺需要三类内容齐备。
- **删除入口后残留调用或清单。** 同批更新全部现役消费者、宿主副本和可用库；不以默认不安装代替真正移除。
- **Backend 或独立技能受到共享改动影响。** 先保留覆盖层，再检查共享依赖；不顺手扩充 Backend 默认或重写工程能力。
- **版本滞后。** 源清单、打包内容、本机程序、正式发行和用户实例分别说明，不把任何一项等同于全部已更新。

留给实施者的判断包括参考文件的具体拆分、条件方法的文字组织、临时验证命令和同批整理顺序。改变 16 个默认入口、研发边界、必需交付物、直接删除策略或用户文件处理方式时，应说明对本设计的实质变化。

本设计文件位于模板源已有的 `.template-source/design`，不创建产品项目资产，不修改被忽略的 `docs/superpowers` 路径规则，也不自动提交。设计确认后再形成实施计划；本文件不是技能、CLI 或安装已完成的证明。
