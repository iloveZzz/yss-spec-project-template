# PR/MR 真实任务验证与按需改进 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在一项真实交付任务中，沿现有方法持续推进到约定结果，并只修正实际观察到、有依据且已获对应授权的问题。

**Architecture:** 复用已有研发入口、PR/MR 跟进参考、工程验证入口与任务记录。以实际任务及其 PR/MR 集合作为观察单位，执行过程中按具体失效进入最小修正，再返回交付循环；没有问题时不产生方法改动。交付状态、实际发生事件的处理结果与未观察范围分别报告。

**Tech Stack:** 当前宿主 Agent、已有平台连接器或实际配置的 gh/glab、Git、目标工程已有构建与验证工具、Markdown；仅在模板方法确需改动时涉及既有 JSON 清单、有效树摘要及 Bundle 工具。不新增依赖、后台服务或统一状态 schema。

**Spec:** [获批设计](2026-11-17-pr-mr-real-task-validation-design.md)。用户于 2026 年 11 月 17 日批准设计、实施计划及执行，随后指定 `/Users/zhudaoming/Projects/SCRM/scrm-backend`，要求自主实施 PR/MR 验证。实际选定任务为修复 MySQL 验证入口的环境隔离缺陷，终点为可审阅的真实 MR；提交、推送和 MR 创建属于该请求，合并、部署、Runner 配置和工程技能升级不在本次范围。

## Global Constraints

以下约束沿用获批设计，所有任务均适用。

- 在当前会话中执行，中断后由后续会话依据已有记录和平台现状接续；宿主退出后持续运行和自动唤醒不在承诺内。
- 项目验证、PR/MR 持续跟进和跨仓组合是观察维度，是否涉及由真实任务决定，不预设三项都需要建设。
- 没有发现有证据的问题时，保留现有方法即可。
- 发现问题也应继续完成授权内可推进的交付工作，不能以“找到接管点”代替任务完成。
- 不创建无业务目的的变更，不为覆盖跨仓或失败情境扩大任务。
- 不能将本文获批解释为任意项目的写入许可。
- 没有新增反馈或 CI 失败的顺利任务，仍可能满足业务目标；它只留下实际发生路径的证据。
- 已经完成的真实合并、外部评论和生产数据操作不能为对照重复执行。
- 不新增技能命令、CLI 接口、数据库结构、统一状态文件、固定多代理流程或模板脚本与测试套件。
- 提交、推送、发行、项目升级分别按实际授权执行；修复已提交也不能代替消费者已采用的证据。

本计划安排实际执行与针对性核验，不要求制造失败或为了满足计划新增代码、测试框架、报告目录。保留失败证据、修正后重验；不涉及行为的文字修改只做相称核对。
