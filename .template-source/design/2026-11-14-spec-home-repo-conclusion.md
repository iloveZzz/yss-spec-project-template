# Spec 作为 Home Repo 的定位与价值结论报告

日期为 2026 年 11 月 14 日。用户已确认本报告所述定位，本文作为后续规划、方案设计和实施计划的输入。具体机制、迁移范围和交付安排由后续设计确定。

## 已确认的定位

**Spec 仓是产品定义、业务规格和原型的上游，同时是该产品研发任务的默认统一会话入口。Agent 从这里理解目标、查找依据和协调工作，在相应工程仓完成技术设计、实现与验证，并将影响产品定义的反馈更新到上游。**

该定位同时支持方法论、研究、产品设计、规格修订、单端研发和跨端研发。前端、后端、移动端及其他落地端可以分别位于独立仓库。一份规格可以涉及多个落地仓，一个落地仓也可以承接多份规格。

用户已接受这一方向。后续规划应围绕如何可靠实现统一入口展开。默认入口提供共同的工作起点，执行过程可以使用多个会话、子 Agent 和工程工作树，具体组织方式按任务选择。

本报告按一个产品或业务系统及其关联工程分析。跨多个无关产品的组织级 Home 如何设置，可在实际出现该需求时另行设计。

## 价值判断

**建议将 Spec 兼任 Home Repo 作为后续演进的主要方向。** 对当前同时维护规格、原型及多个实现仓的工作方式，最主要的新增价值是连续推进产品目标，并把仓库选择、资料定位、跨端影响分析和结果整合交给 Agent。

| 价值 | 发生作用的场景 | 可观察结果 | 证据状态 |
|---|---|---|---|
| 减少重复说明和环境切换 | 用户连续处理同一产品的分析、设计和实现 | 更少重复提供仓库位置、背景和原型入口 | 用户已表达使用偏好，改善幅度待实际观察 |
| 提前识别跨端影响 | 一项规则同时影响前端、后端或其他端 | 实施前找到受影响工程、共享规则和调用方 | 多仓结构支持该需求，覆盖效果待验证 |
| 保持产品决定与执行输入关联 | 需求从讨论进入原型，再进入研发 | 各执行任务能引用准确的规则、材料和版本 | 已有规格与交接机制可复用 |
| 统一呈现交付结果 | 同一任务在多个工程中推进 | 能核对每仓实际变更、验证、未完成项及整体影响 | 需要各仓真实记录，入口本身不能证明完成 |
| 复用工作方法 | 多种任务使用共享技能与工程方法 | 根据任务选择适用方法，降低反复配置的负担 | 统一技能源和 Profile 分发已存在，属于现有基础 |

跨端需求、产品规则调整、原型与实现对齐，最有条件获得上述收益。明确到单仓文件的小修复、依赖升级和内部重构，应从统一入口直接进入相关工程上下文，使简单任务保持简短路径。

价值成立的条件是，入口减少的重复解释和协调工作，大于新增的上下文读取、路径维护和结果整合工作。目前可以判断定位适配，尚无实测数据支持工时、Token 或正确率的提升幅度。

## 职责与资料归属

会话入口、工作任务和成果保存位置分别处理。统一入口可以承接明确的研发请求，各类成果按其责任保存。

| 位置或角色 | 负责内容 | 主要关联 |
|---|---|---|
| YSS 模板与共享技能源 | 通用方法、模板、技能维护及按职责分发 | 为产品 Spec 和各工程提供可安装的方法 |
| 产品 Spec / Home 仓 | 产品目标、业务词汇、规则、规格、原型、交互说明及共享导航 | 引用相关工程和交接结果，承载产品层面的修订 |
| 从 Home 发起的 Agent 会话 | 理解请求、识别范围、选择资料与技能、协调执行、汇总结果 | 按任务进入实际工程与适用上下文 |
| 各落地仓 | 技术方案、代码、构建、工程测试、部署及实际实施记录 | 引用采用的上游资料，反馈问题和实现约束 |
| 个人 Workbench | 个人任务、答复、确认记录及续办信息 | 索引真实规格与资源，辅助个人继续工作 |

在模板维护层面，当前 `yss-spec-project-template` 提供可复用的入口与方法。具体产品的 Spec 仓承载真实业务和工程关系。SCRM 的 `pd-spec` 可以作为这种定位的候选实践实例。

完整产品 Spec 继续以业务规格、高保真交互原型及交互说明表达产品要求。用户明确提出技术设计或开发时，同一入口按研发任务承接，技术成果进入相关工程。现有 Spec 入口已经允许这种工作方式。[Spec 入口约定](../distribution/entries/spec-project-AGENTS.md)

## 后续方案应实现的行为

以下是规划所需的能力目标，具体实现由方案设计确定。

1. **从目标识别任务范围。** 用户在 Home 提出研究、规格、单端或跨端请求后，Agent 识别本次需要的工作和成果位置，复用已有决定，事实缺口自行调查。
2. **找到实际工程与资料。** 根据产品关系定位相关仓库，再核实本次工作树、分支、资料版本和读取范围。团队成员目录不同、仓库缺失或存在多个工作树时，仍能解释当前选择及缺口。
3. **选择适用规则与技能。** Home 提供共同上下文，目标仓提供具体工程约定。按任务读取所需技能及其资源，处理同名技能和 Profile 差异，简单任务能够直接进入相关工程。
4. **协调跨仓执行。** 对相关仓明确工作范围、依赖及执行责任。并行任务使用适当隔离，保留用户已有修改，避免多个执行者覆盖同一内容。
5. **持续核对上游变化。** 能区分固定提交、当前工作树和历史材料。执行中遇到产品规则变化时，识别受影响范围并更新对应任务输入。
6. **按真实结果交付。** 从统一入口汇总各仓实际变更、验证与剩余事项，引用对应记录。影响业务规则、权限或交互的研发发现，沿原规格或验收依据反馈上游。

这些行为建立在已有授权和文件保护规则上。拆票按用户明确要求开展，检查按任务实际需要选择，提交、推送、发布和对外发送使用对应动作授权。当前仓库约定继续作为后续设计输入。[仓库工作约定](../../AGENTS.md)

## 验证建议与风险判断

后续验证应同时观察执行正确性和实际使用负担。建议利用真实任务及其已有记录比较以下表现，具体范围与验收方式由实施计划确定。

| 代表场景 | 重点观察 | 成功信号 | 反向信号 |
|---|---|---|---|
| 明确的单仓小修改 | 从统一入口进入工程的成本 | 直接找到目标与适用规则，完成本次工作 | 读取大量无关规格，反复要求解释背景 |
| 一项跨端需求 | 影响范围、分工和依赖 | 找全相关实现与调用方，各仓结果可核对 | 用户事后补充遗漏端，局部完成被当作整体完成 |
| 执行中规格修订 | 采用版本与变更传播 | 识别受影响规则和执行输入，保留其他有效工作 | 继续使用旧依据，或无依据地要求所有端同步 |
| 多工作树或并行任务 | 目标选择、隔离和文件保护 | 正确定位本次工作位置，职责和结果清楚 | 改错工作树、覆盖已有修改、结果混入其他任务 |
| 另一位成员或新会话接手 | 入口可复用性 | 能从共享资料恢复所需上下文 | 依赖创建者的个人记忆、固定绝对路径或隐含技能 |

扩大采用的依据应是，跨仓任务减少重复说明和遗漏，单仓任务保持直接路径，导航与资料维护能够随正常工作完成。若路径、版本和技能选择需要频繁人工纠正，应先修正对应机制，再评价统一入口带来的净收益。

主要风险是目标仓或工作树误选、资料版本漂移、工程规则遗漏、并行写入冲突，以及整体完成判断缺少工程证据。上述风险是方案设计和试用需要覆盖的可能失败方式，本次没有证明它们已经在统一 Home 方案中发生。

## 规划承接与证据限制

建议后续先形成一份方案设计，明确入口职责、任务场景、资料与工程关系、规则和技能选择、执行组织及迁移影响，再根据选定机制编制实施计划。复用本报告的定位和价值目标，将具体设计选择与新增证据写入后续方案。

规划产物应能回答三个问题。用户从统一入口可以完成哪些任务，Agent 如何找到并使用正确的工程上下文，以及用什么真实结果证明跨仓工作完成。实现范围和阶段安排由这些答案推导。

本次研究核对了文章、公开技能与工具源码、本地模板和相关交接记录，并检查了已安装 CLI 的版本、命令帮助及技能可用列表。未安装运行 Matt skills、OpenSpec 或 Spec Kit，未开展 Home 入口到多仓实施的完整试用，未重新验证 SCRM 产品行为，也未测量效率收益。

外部固定提交可用于复核当时的公开实现，在线文档后续可能变化。本地资料链接对应已核实的工作区；隔离工作树中的跨仓链接指向原工程，跨环境使用时按仓库身份重新定位。后续涉及安装、宿主加载或数据结构的设计，应核对当时实际版本和当前源码。

本报告确认的是定位与规划依据。工程规则加载、多仓执行可靠性、团队可复用性及效率改善，仍由后续方案验证和真实使用结果建立证据。
