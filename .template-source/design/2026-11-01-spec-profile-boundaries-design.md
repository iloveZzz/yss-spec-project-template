# Spec 与 Backend 的职责及分发边界

日期：2026-11-01

状态：用户已批准设计与执行；技能和分发调整已实施，四种本地安装核对通过，独立审阅未发现阻碍交付的问题。真实宿主自动发现/调用和已有实例升级未验证。

## 1. 目标与已确认决定

修复 Spec 工作中的过度交付：用户要求确认规格、拆 tickets 或准备交给研发时，Agent 不应据此生成物理数据库设计、生产 API 契约或技术实现切片。

用户已明确：

- 完整 Spec 的交付内容只有业务规格、高保真交互原型及交互说明；三类内容不要求拆成三个文件。
- 业务票仅在明确要求拆票时输出，是业务规格的组织形式，不是第四类必交付物。
- 采用现有 profile 分工：Spec 的 `to-tickets` 负责业务票，Backend 的同名覆盖负责研发实现切片。
- 保留现有免阶段审批的原则；免审批不扩大任务范围，也不取消产品与研发的职责区别。

以下具体文件安排和例外处理是本设计的实施建议，不记作用户已经单独确认的决定。

## 2. 现状与方案取舍（Approaches）

当前 [.agents/skills/to-tickets/SKILL.md](../../.agents/skills/to-tickets/SKILL.md) 同时描述业务票与实现 Slice；[Spec 分发配置](../distribution/bundle-profile.json) 的两种安装模式也同时为该技能分发两类模板。“不要求 API 冻结”取消的是起草前置条件，没有排除生成生产契约。

[lifecycle](../../.agents/skills/yss-product-lifecycle/SKILL.md) 已说明研发承担技术设计，但未把普通 Spec 请求与明确研发请求的区别传递到拆票入口。现有材料说明容易发生越界的路径；没有那次实际执行记录，不能把推测写成已复现的事故根因。

另外两处现役入口必须一起处理：

- Spec 与 Backend 的 `project` 安装共用 `project-AGENTS.md`；直接把它改成 Spec 专用会限制 Backend。
- Spec 的 `project` 安装还分发 `local-parent-ticket-template.md`，其中列出 API、Architecture、Vertical slices 及旧门禁资料。目前查到的现役引用仅为该分发项。

| 方案 | 取舍 | 结论 |
|---|---|---|
| 保留双职责，增加条件与禁止项 | 修改较少，但 Agent 仍同时拿到两种输出路径与模板 | 未选 |
| 按现有 profile 拆开职责与模板分发 | 需要同步入口、覆盖层和分发配置；职责与实际提供的材料一致 | 用户已选 |

保留技能 ID，不增加模式参数、新技能、生命周期路由器或执行门禁。Spec 默认的 16 个技能入口保持不变。

## 3. Spec 的输出边界

### 完整交付与局部工作

完整有 UI 的 Spec 交付包括业务规格、高保真产品原型及交互说明。核心操作和状态变化必须能在模拟环境中操作；纯展示场景可以使用高保真静态稿。低保真草稿可支持探索，但不能单独被称为完整交付。

无 UI 的需求沿用业务逻辑或状态原型，不虚构页面。普通查询、局部修订和模板维护只完成当前范围，不自动补齐整套产品成果。研究资料、来源、未决项和必要概念说明可以支持规格，不因此成为额外的必交付包。

交互说明承接规则与 AC，说明入口、动作、结果、权限与校验、失败与恢复、模拟范围、查看方式和实际未验证项。原型代码、演示用数据和浏览器内模拟行为属于原型材料，不承诺可直接用于生产。

### 业务内容与技术决策

| Spec 可以表达 | 不能由 Spec 请求推导出的技术设计 |
|---|---|
| 业务对象、概念关系、信息含义、必填与唯一性规则、业务量值范围 | 物理表、字段存储类型、主外键、索引、DDL、迁移方案 |
| 用户动作、系统业务结果、权限、状态、异常、恢复与可观察验收 | 新生产 API 路径、HTTP 方法、请求响应 schema、DTO、技术错误码或 OpenAPI 契约 |
| 有来源的业务质量要求、既有系统或第三方的真实限制 | 无依据的生产技术栈、组件选型、模块分层、部署方案与实现切片 |
| 为交互演示服务的模拟数据和局部逻辑 | 将原型数据结构、请求模拟或框架选择提升为生产承诺 |

已有技术事实可以读取和引用，注明来源及其对业务的影响；不得借引用扩写新的技术决策。约束应按内容与用途判断，不能把 SQL、API 等词作为简单的禁止词列表。例如业务上的“编号唯一”应保留，不能因为可能需要数据库约束就删掉。

### 业务票

Spec 的 `to-tickets` 只在用户明确要求业务拆分或显式调用时使用，保持现有显式调用策略。票据沿用原 Spec、FR、AC、稳定 ID 和已确认决定，按完整可观察业务行为组织，写业务价值、范围、规则、验收、业务依赖和未决项。

“确认 Spec”“继续完善规格”“准备交给研发”不触发拆票；“拆 tickets”在 Spec 任务中只产生业务票，不触发技术设计。保存和发布继续使用对应授权，普通分析不自动写 tracker。不要求每个 Spec 先有业务票才能交给研发。

## 4. 研发承接与用户授权

Backend 的 `to-tickets` 只负责把已有 Spec、业务票或明确需求细化为窄垂直实现切片，不再提供产品业务票输出分支。直接消费既有输入，不要求补建业务票或集合文件。

需要技术决策时，先读取真实工程、已确认技术栈和适用设计；缺少必要方案时由 Backend 的 `yss-technical-design` 等研发技能在本次授权范围内处理。切片引用真实技术依据与验收，不凭模板补造 DDL、接口或已经确认的选型。暂时缺失的事实写为未决项及影响，可以继续整理已有依据的行为范围；不恢复统一冻结、合同或阶段准入条件。

一票贯穿当前行为实际命中的技术层，不按 Controller、Service、Repository 横向拆票。保留原有仓库与路径范围、子模块保护、真实 tracker 关系、分页、授权和保存结果约束。

用户在 Spec 工作区明确要求技术设计或开发时，任务范围可以扩大：识别为研发任务，按可用研发能力承接，并把研发成果与 Spec 成果分开说明。不能因为 profile 标签拒绝用户已授权的任务，也不能静默把 Spec 的 `to-tickets` 改回双职责。不强制换仓、安装 profile 或新增审批；确实缺能力或工程事实时说明具体缺口。

## 5. 入口、模板与分发安排

| 位置 | 设计中的调整 |
|---|---|
| 根及 Backend 源工作区 `AGENTS.md` | 明确免流程审批不扩大任务范围；按当前任务和 profile 区分产品、研发及模板维护，不能把源码维护限制成产品 Spec 工作 |
| 新增 `.template-source/distribution/entries/spec-project-AGENTS.md` | 供 Spec 的 `project` 安装使用，明确三类交付物、可选业务票与研发边界；保留现有命令、文件保护和动作授权要求 |
| 现有 `project-AGENTS.md` | 保持为 Backend 的项目入口；补充研发承接职责，不能写成 Spec 专用限制 |
| `spec-skills-AGENTS.md`、`spec-project-README.md` | 与 Spec 项目入口使用一致的边界和完整交付表述 |
| 根 `to-tickets` 及其发现描述 | 仅业务票，移除研发切片路径和实现方法；保留显式调用、来源与 tracker 保护 |
| Backend `to-tickets` 及其发现描述 | 仅研发切片，消费原业务输入；保留 Backend 现有按需自动选择政策 |
| `yss-product-lifecycle`、`to-spec` 及共享规格方法 | 明确 Spec 完成范围、普通请求的含义、可选业务票和研发承接规则；不自动调用显式技能 |
| `yss-design-system` 与相关原型说明、复核方法 | 对齐完整有 UI 交付的高保真要求、模拟边界和真实检查声明，保留探索草稿、纯展示和无 UI 的适用形式 |
| `business-ticket-template.md`、`spec-template.md` | 给出允许内容和技术设计边界，保留原规则与验收引用；不增加生产设计字段 |
| `vertical-slice-ticket-template.md` | 研发模板的现役来源只保留在 Backend 覆盖层；移除根共享副本及 Spec 分发引用 |
| `local-parent-ticket-template.md` | 移除 Spec 默认分发及无其他现役消费者的旧模板，避免技术资产与门禁目录被当作待填必需项；不另建替代父票模板 |
| 两侧 `bundle-profile.json` | Spec 两种安装仅为 `to-tickets` 配业务票模板；Backend 两种安装仅配实现切片模板，读取既有业务票不依赖业务票模板 |
| 当前用户指南、tracker 说明、入口政策与技能适配说明 | 修正直接涉及本次分工的现役表述，分清两侧票据职责；历史设计记录保留原文，不扩展成全仓文档重写 |

Spec 的 `project` 安装将 `AGENTS.md` 映射到新增 Spec 专用入口；Backend 继续映射现有入口。使用已存在的 entries 映射机制，不改 CLI schema 或程序。

是否实际分发某文件，以两种安装模式的 files、skillReferences、有效覆盖层和生成结果共同核对；只改技能正文不算完成分发调整。Spec 仍可按真实用户请求补装研发能力，本次不清空可用技能库或改变可选安装策略。

## 6. 同步与兼容边界

共享技能以 `.agents/skills` 为源；Backend 专有技能以 `profiles/backend/.agents/skills` 为源。更新实际受影响的 `.workbuddy` 普通副本、`.claude` 链接及发现元数据，Backend 按共享树加覆盖层形成有效内容，不能用共享 Spec 正文覆盖 Backend 专用版本。

更新适用分发引用和技能来源说明；按照现有维护规则更新受影响的 Backend `effectiveHash`，保留上游版本与 `upstreamHash`。不新增锁 schema，不因为正文调整改变默认技能集合或创建新技能 ID。

只修改模板源及其受管副本，不批量改写用户项目、已发布 Issue、既有票据 ID、原型或历史批准记录。不自动清理用户已有技术文档，也不声明已安装实例会随源码更新。需要迁移已有实例时，另按用户目标与所装 CLI 的真实能力处理。

本次不修改 `yss-cli` 源码，不新增脚本或测试套件，不提交、推送、发行、部署或向外部发送内容。模板源改动、实际打包、实例安装和宿主行为分别报告。

## 7. 判断调整是否有效

| 代表请求或输入 | 期望行为 |
|---|---|
| Spec：完成某功能规格并准备交研发 | 交付规格、高保真交互原型及说明；不自动拆票或生成生产技术设计 |
| Spec：根据已确认规格拆 tickets | 只形成业务票，保留 FR/AC 与业务依赖；不新增 DDL、索引、生产契约或实现切片 |
| Spec：只修正一条业务规则 | 更新本次受影响内容，不补建完整产品成果或票集 |
| 原型需要编号、金额、错误反馈或模拟请求 | 可以实现业务演示；说明模拟范围，不输出数据库类型或生产接口承诺 |
| Spec 材料附已有第三方 API 或数据库限制 | 引用来源及业务影响，不把引用改写成新生产设计 |
| Spec 工作区：用户明确要求设计生产 API | 识别为授权研发任务，使用适用研发能力；不把它算进 Spec 标准交付或调用业务拆票替代技术设计 |
| Backend：依据 Spec 拆实现任务 | 消费原输入和真实工程/设计，生成实现 Slice；不要求先补业务票，不猜未确认技术方案 |
| 完整需求无 UI，或全部为静态展示 | 分别使用业务逻辑/状态原型，或高保真静态稿，不虚构交互页面 |
| 两侧各自执行 project / skills 安装 | Spec 获得正确入口及业务票模板；Backend 获得研发入口及切片模板；引用闭合、宿主政策与副本一致 |

结构检查应覆盖 JSON/YAML 可解析、引用目标、两种安装资源选择、有效覆盖树和内容副本。行为核对应使用以上代表请求及相邻反例，区分文本核对、实际 Agent 演练和安装运行；不能用禁用词扫描或命令退出 0 证明模型不会越界。

只有实际执行的检查才写结果。若未打包、安装或演练，应明确对应能力未验证，不新增长期自动门禁。
