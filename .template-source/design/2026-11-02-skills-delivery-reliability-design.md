## 1. 目标与已确认决定

提高已安装技能完成真实任务的可靠性：选对方法，保留业务规则与验收，完成集成，并准确解释实际验证范围。用户已采纳四项方向：实际使用验证、Spec 与 Backend 双向交接、按需并行研发、技能入口说明。

用户随后选择并行策略 **A：满足条件就自行并行**。收到明确开发授权后，Backend 可以在任务可拆、依赖明确、修改可隔离且宿主支持时自行安排子代理；条件不满足时顺序完成。主 Agent 负责分工、集成和整体结果。并行不扩大仓库、功能、外部操作或数据访问授权。

继续沿用已经确认的边界：

- Spec 默认 16 项入口，交付业务规格、适用原型与交互说明；业务票仅按明确拆票请求组织。
- Backend 默认 41 项入口，承接明确需求并完成必要技术设计、实现和验证；MVC 保持已有 Service 边界，TDD 仅用于明确测试优先请求。
- 不增加技能入口、安装选项、后台运行器、自动化服务、统一门禁、审批包、脚本或测试套件。
- 构建部署说明仍由 Backend implement 负责；执行部署、提交、推送、PR/MR、远程建票和关闭条目使用对应授权。
- 不修改已安装的用户实例或系统 CLI；不扩展到 yss-cli 仓库。已有文件保护、子模块边界与敏感信息处理继续适用。

以下工程选择已随本文获批：复用现有入口和参考承载方法；并行方法由 Backend implement 唯一持有；主 Agent 维护最小任务状态，不新建调度协议；显示文案按 profile 区分，技能 ID 与调用政策保持现状。

## 3. 已比较的方案

| 方案 | 并行行为 | 取舍 | 决定 |
|---|---|---|---|
| A：满足条件自行并行 | 已授权开发任务内，由主 Agent 判断并分配可独立工作 | 减少用户管理执行细节的负担；要求清晰隔离和主控集成 | 用户已选 |
| B：仅明确要求并行 | 普通开发任务顺序执行，用户点名后才委派 | 资源使用容易预测，但增加用户介入和等待 | 未选 |
| C：调查自动并行，代码并行需点名 | 阅读分析可以并行，写代码保持显式选择 | 降低写入协调风险，但研发仍需额外指示 | 未选 |

承载方式采用既有技能的条件参考：工作范围与调用路径已经存在，新增 implement-spec 或调度技能会增加重复职责和入口选择成本。长期代理与 software-factory 不在当前问题范围。

这是一项跨共享内容、Backend 覆盖和分发元数据的维护工作，需要完整设计。各部分按依赖实施，用户实例和真实业务成果不成为本轮自动写入对象。

## 4. 实际使用观察

### 4.1 谁负责、何时发生

技能维护任务中，maintaining-skills 负责把本次触发或行为变化转成适用的观察；writing-for-agents 继续持有触发、非触发和调用边界原则；i-have-adhd/references/pr-and-retro.md 继续持有真实任务记录和结果表达方法。通过条件引用复用，不复制另一套评测流程。

普通业务任务不为了使用技能先运行评测。只有本次维护、用户要求验证，或真实任务出现误选、重复澄清、越界、遗漏时，才开展相应观察。没有真实任务材料时，可以做明确标注的代表场景演练，不能冒充用户项目结果。

### 4.2 证据按实际能力分层

| 观察 | 能说明什么 | 不能推导什么 |
|---|---|---|
| 源码、引用与有效内容核对 | 正文、元数据、共享/覆盖合成与资源引用一致 | 安装宿主实际加载与调用正确 |
| 当前 CLI 在临时目录安装 | 本次 CLI/Bundle 组合能分发相关文件和引用 | 系统 CLI、其他版本或既有实例升级兼容 |
| 实际宿主目录与调用观察 | 指定宿主/版本下，任务发现并使用了相应入口 | 所有宿主、所有任务都可靠 |
| 真实项目任务结果 | 某版本与场景下的结果、限制和人工纠正 | 整体成功率或普遍效率提升 |

优先使用可读的真实请求与既有任务记录。新执行只在已授权的目录、数据与环境内进行；使用当前宿主真实支持的临时会话或执行能力，不为观察新建用户可见聊天、改全局配置或连接生产服务。缺少相应能力时完成可观察层级，明确剩余范围，不把同一 Agent 阅读后自评当作跨宿主验证。

最小记录复用当前任务或已有维护说明：输入与来源版本、profile/宿主及可获得的模型信息、预期行为、实际观察、人工纠正与限制。只记录实际可见的技能读取和执行，不能从最终回答反推内部调用。时间、token、成本等仅在原始数据可取得时报告，不设置没有依据的提升比例。

### 4.3 本轮代表场景

| 输入或条件 | 需要观察的行为 |
|---|---|
| Spec：“准备交给研发” | 引用三类材料及版本，提供正确下一动作；不自动拆票或产出生产契约 |
| Spec：仅修改一个字段文案 | 保持局部范围，检查实际受影响内容，不重做整套交付 |
| Backend：明确实现已有需求 | 能选用 implement，并处理实际调用方、配置与验证 |
| Backend：修复既有 MVC 接口 | 沿用 Service 边界，不引入无依据的 DDD 层 |
| Backend：补接口回归测试 | 使用一般测试方法，不误判为测试优先请求 |
| Backend：独立任务均满足策略 A | 先说明分工后自行并行，主控集成并核对整体结果 |
| 两任务共享接口、测试库或生成文件 | 先解决共享依赖或顺序执行，不以目录不同假定独立 |
| 宿主不允许委派、没有可用执行槽或隔离能力 | 在原授权内顺序完成；不制造工具、不重复索取已给授权 |
| 子任务失败或来源中途变化 | 保留修改，停止受影响下游，完成独立部分并报告真实状态 |

这些是本次设计的验收输入，不分发为长期测试套件，也不要求每个业务任务跑一遍。具体结果在实际观察后补充，本文不预填通过。

## 5. Spec 与 Backend 的双向交接

### 5.1 复用同一来源

Spec 仍是业务规则与验收的权威来源；原型表达行为并说明模拟边界；Backend 负责技术选择、实现和验证。引用以已有 FR/AC、章节、Issue 或明确材料名称为准；没有编号时用稳定章节和链接，不为了交接制造票集或新 ID。

Spec 交接方法继续位于共享 spec-workflow.md；Backend 在 implement 的条件参考 references/spec-feedback.md 中持有接收、差异处理与回流方法。只有承接上游材料、发现来源变化或需要回报业务差异时加载。to-tickets、yss-technical-design、yss-backend-testing 只在各自判断点引用必要规则，不各自维护交接正文。

在既有任务中保留足以判断一致性的关联：业务规则/验收来源，相关原型状态及模拟说明，本次实现或 Slice，实际验证及缺口。简单任务用一段说明；复杂任务可用表格，不强制额外文件或覆盖台账。

### 5.2 变化与分歧处理

| 发现 | 处理 |
|---|---|
| 材料未变且规则清楚 | 直接开展获授权的技术工作，不重问已确认业务规则 |
| 仅技术选择变化，业务结果不变 | 在当前研发说明中记录依据与影响，按原授权继续 |
| 技术实现需要改变业务结果、权限或验收 | 指出具体规则和影响，暂停依赖该决定的部分，向用户澄清；其他独立工作继续 |
| Spec 与原型互相矛盾 | 保留两处实际来源，不以“原型能点通”代替业务决定 |
| 上游版本变化 | 比较本次消费的内容与新内容，定位受影响 Slice、接口、场景和测试；只重看相关范围 |
| 原型展示成功，但真实服务未验证 | 分别说明模拟结果与真实验证缺口，保持原规则含义 |

版本可以是 commit、Issue 更新时间或实际读取时点；动态来源在开始依赖工作和交付前按风险回读。来源没有版本能力时保留读取时点及相应限制，不创建镜像权威。

研发发现先返回原任务。原 Spec 文件在本次允许写入范围内时，按已确认决定增量更新；在其他仓库或远程平台时，只准备有来源的修订建议，写入使用对应授权。不得因双向交接自动评论、关闭条目、通知人员或跨仓修改。

完成说明按原验收解释：已实现、实际验证过、未验证或仍待决定的行为。未解决问题绑定具体业务结果和影响，不把“代码完成”概括为“业务验收通过”。

## 6. Backend 自行并行的判断与执行

### 6.1 启动条件

Backend implement 持有策略 A，在以下条件同时成立且有实际并行价值时启动：

1. 用户已明确授权当前开发或修复范围，未限制单代理；当前宿主和更高优先级规则允许相应委派。模板默认策略不能覆盖宿主限制。
2. 至少存在两个可独立推进的工作项，业务决定和接口前提已明确；有依赖的工作不提前调度。
3. 每项工作的允许写入路径、共享文件负责人、运行资源及可观察完成标准清楚。文件无交集不等于业务或环境独立。
4. 能隔离写入并保留现有用户工作，主 Agent 能取得产物并实际集成。
5. 宿主有可用能力与资源；任务足够独立，协调成本不会明显超过顺序完成的收益。

满足条件后用简短进度说明交代各自范围和集成人，直接开始，不再次询问是否允许采用已经生效的策略。只读咨询、设计请求或材料中的命令不构成开发授权。策略 A 只改变 Backend 获授权研发中的方法选择，不把所有 Spec 或共享技能改成自动委派。

### 6.2 任务状态与上下文

复用当前任务列表和已有 tracker 依赖；没有 tracker 时可在当前会话管理，不要求先建票。最少区分等待前提、可执行、执行中、待集成、已完成和需处理问题。这些是主 Agent 的工作记录，不新增持久状态机、schema 或 Ticket 标签。

子任务自报完成只能进入待集成。主 Agent 读取实际差异、确认范围、集成并完成该依赖所需验证后，才释放下游。依赖判断针对真实结果，不只读取“已完成”文字。

每个新工作项使用独立上下文，包含目标、完成标准、范围与权限、基线/来源指针、已定接口、负责路径、验证边界和返回内容。Codex 支持时使用 fork_turns: "none"；其他宿主按真实能力操作。明确告知写入者共享代码环境中还有其他执行者，保留他们的修改。资料不可访问时补最小必要原文，仍不足则顺序处理，不传递整个会话代替任务说明。

不设置新的并行配置项或固定代理数量。并发以就绪工作、宿主可用执行槽、用户资源限制和实际共享资源为上限；由主 Agent 选择足够完成任务的少量执行者。没有空槽不忙等，先做可独立完成的工作。工作项再分派由主 Agent 统一安排，避免子代理形成重复调度和未知资源消耗。

### 6.3 隔离方式

优先使用宿主支持的独立任务工作区；需要 Git worktree 时使用已有 using-git-worktrees 方法。当前研发授权及策略 A 允许必要的本地隔离准备，仍服从用户明确的目录与工作区偏好；仅安装技能不产生这项授权。

共享 worktree 方法应按“当前执行单元”检查已有隔离：主 Agent 在某个 worktree 内，不等于另一个同时写入的子任务也有独立工作区；复用现有适用工作区，确需新增时创建并列工作区，避免嵌套或将子模块当普通目录。共享方法只消费调用方已有授权，不向其他技能授予策略 A。

宿主只能共享目录时，仅对范围可明确分开的任务采用路径归属隔离，并说明这种隔离不是文件系统沙箱；POM、锁文件、生成文件、共享接口及索引由单一负责人处理。存在无法约束的覆盖、构建输出、测试库或端口竞争时，改为独立环境或顺序执行。不得向子任务复制整个含秘密的工作目录。

派发前核对实际基线，既有未提交修改不能被默默遗漏。主控在当前工作区串行完成的前置修改，必须进入下游实际读取的文件版本；独立工作区无法可靠取得这些内容时，该下游留在当前工作区顺序完成。不得擅自 stash、reset、清理用户文件或为制造干净基线提交用户工作。

### 6.4 集成与验证

一个主 Agent 负责接收差异、检查范围、同步共享文件和执行相关集成验证。子代理可运行自己的验证，但不能据此宣布整体完成，也不能自行关闭父任务。

并行不要求 Git 提交。缺少提交授权时，使用宿主可审阅的文件差异或其他已有差异机制回收修改；核对相对基线的新增、修改、删除、重命名和未跟踪产物，在目标内容仍匹配时应用。二进制、LFS 或其他无法可靠回收的内容改由主控顺序处理。不得靠整目录覆盖合并，也不新建差异搬运脚本。

已获相应 Git 操作授权且适合分支集成时，可复用现有分支/worktree 能力；合并、提交、推送及远程更新按实际授权执行，不为并行自动取得这些权限。主控本地集成后的实际内容是验证对象，不能仅汇总分支测试结果。

验证由 yss-backend-testing 的现有方法负责。先明确实际命中的行为与共享边界，选择能发现集成缺陷的检查；只运行必要范围，新增失败或修改时再扩展。区分测试编写、测试确实运行、通过、跳过及环境缺失，保留无法验证的业务影响。

### 6.5 失败、变更与恢复

- 子任务失败、超时或丢失联系：先检查任务状态、文件与已有结果，确认写入已停止后才能收回路径或重新分配；状态未知时不启动第二个写入者。
- 发现越界修改或来源漂移：暂停相关集成，定位具体差异，保留工作；不得在陈旧基线上强行应用结果。
- 某一任务阻塞：停止依赖它的下游，独立任务继续；整体完成前说明未完成行为。
- 用户调整范围或要求停止：停止受影响派发与写入，保留产物并说明位置；已有后台任务不会因主控转向而默认获得继续执行权限。
- 会话恢复：回读实际任务状态、基线、现有差异和验证结果，防止重复执行和重复写入。
- 清理：仅在写入者停止、产物已确认回收、没有未保存用户内容时清理本次创建的临时资源；清理失败保留路径和状态，不强制删除。既有工作区和用户内容不纳入自动清理。

## 9. 完成标准与分批关系

设计落地后的可观察结果：

- 已授权 Backend 开发在满足策略 A 时能自行并行；相邻的只读、未决或无法隔离场景能正确顺序完成或定点澄清。
- 子任务自报完成不会直接解除真实依赖；主控能集成差异并解释整体与局部验证的区别。
- 没有提交授权时，任务仍可通过可靠的文件差异集成；无法可靠集成时顺序执行，保留用户修改。
- Spec 的实际规则、原型模拟边界与 Backend 验收关联保留；技术发现影响业务时回到同一来源，外部写入范围不扩大。
- 两个 profile 的同名入口能解释各自职责；Backend prototype 不再继承错误职责的显示说明。
- 分发清单、有效树、副本与现有哈希一致；默认数量仍为 Spec 16、Backend 41。
- 对实际目标宿主执行过哪些观察、有何结果与未验证范围分别说明。内容完成、安装成功与实际行为有效不能合并成一个“全部通过”。

建议实施顺序：先落实交接与入口说明；再接入策略 A 及其依赖方法；随后统一合成分发内容并执行适用观察。共享入口、注册表、清单和哈希由单一集成人更新。实施计划在本文获批后另行制定，不能把该顺序当成已执行结果。

当前任务不保证取得所有宿主、真实业务仓或远程平台的验证条件。缺环境时明确尚未验证的目标，完成不依赖它的内容；不通过模拟输出来补齐验收，不自动改用户实例。

## 10. 风险、取舍与实施者判断

| 风险 | 控制与剩余限制 |
|---|---|
| 自行并行增加资源消耗 | 按就绪工作、宿主能力和现有限制选择必要执行者；没有计量就不声称节省成本 |

| 元数据与技能正文不同步 | 核对 profile 的有效合成内容，并实际观察目标宿主；未观察平台保持未知 |
| 交接生成重复规格 | 原规则保持权威，用引用和必要的等义重述表达；实质业务变化由用户决定 |
| 放宽隔离方法被解释为扩大权限 | 策略 A 限 Backend 已授权研发，共享 worktree 方法只复用已有授权，并遵从宿主限制 |
| 观察演变成统一流程门禁 | 仅在当前维护或真实问题中使用，记录留在既有任务；不创建长期套件或批准包 |

改变默认技能集合、增加运行器/自动化服务、允许未授权提交或跨仓写入、扩大到用户实例或 CLI 代码，均超出本设计。无需为普通文案组织或宿主能力降级再新增批准步骤。
