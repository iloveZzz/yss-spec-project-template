# Spec / Home Repo 设计

日期：2026-11-14。状态：用户已确认，已完成独立可实施性审阅。定位依据为[结论报告](2026-11-14-spec-home-repo-conclusion.md)。用户已选择路线 A：通过模板、技能和仓库地图实现完整 Home 会话，实际工程位置由 Agent 核实。

## 设计结论

Spec 保持产品定义、业务规格、原型和交互说明的上游职责，同时成为一个产品及其关联工程的默认会话入口。用户从这里提出研究、规格、单端或跨端研发目标，Agent 选择资料和实际工程，在相应仓库执行，并在当前会话汇总结果。

第一版保留 `spec` Profile、既有仓库布局、YSS CLI 接口和各工程的技术职责。以现有入口、`implement`、工程技能、安装方法和分发机制承载行为，新增一份仓库地图模板。产品项目维护自己的仓库关系，工程事实在任务执行时核实。

本设计的具体机制由作者提出，用户在审阅文档后明确选择“认可设计，继续编制实施计划”。随后用户明确批准按计划执行；该授权仍不包含提交、发行或真实产品接入。

## 目标与范围

第一版需要让用户在 Home 提出目标后，得到以下行为：

1. 产品任务继续使用产品方法；明确研发请求能够进入实际工程，简单修改保持直接路径。
2. 根据共享仓库关系找到相关实现，核对本次 checkout、工作树、适用规则和材料版本。
3. 工程任务使用目标仓的有效方法；跨仓任务明确每仓责任、依赖和结果。
4. 并行工作保护已有改动；影响产品规则的发现能沿原规格反馈。
5. 新会话或其他成员依靠共享资料恢复必要上下文，不依赖创建者的绝对路径与个人记忆。

本次设计覆盖 YSS 模板、共享技能、Backend 有效覆盖、平台副本、分发配置、用户说明与隔离验证。产品业务规格、生产技术设计与应用代码继续由具体业务任务决定。

第一版不新增 Home Profile、CLI 命令、结构化关系 schema、中央任务状态、常驻调度器或自动建仓系统；不将工程源码迁入 Spec。Worktree、临时检出和子 Agent 沿用现有方法，按当前任务需要使用。

失败表现包括：用户仍需逐次提供已经可查的工程位置；每个单仓修改都要读取全套规格；Agent 在错误工作树写入；读取目标目录后遗漏其规则；将某个子仓完成当作整个目标完成。

## 路线比较与选择

| 路线 | 实现 | 价值与代价 |
| --- | --- | --- |
| A：模板、技能与仓库地图 | 共享 Markdown 记录稳定关系，Agent 核实真实工程；现有方法完成执行与回收 | 直接覆盖已确认工作方式，改动集中；定位与上下文选择依赖 Agent，需要场景验证 |
| B：同时增加 CLI 解析 | 在 A 上增加机器可解析关系、Git 身份核验、路径候选及歧义输出 | 提供可被脚本重复调用的查询，但增加格式兼容、路径规则、平台验证及发行维护 |

用户于本轮对话选择 A。若实际使用反复出现路径误选、多人定位规则不一致，或明确出现独立工具调用需求，再以真实案例评估 B。第一版不预建 B 的字段、空接口或占位模块。

## 组成与职责

| 组成 | 责任 | 保存位置 |
| --- | --- | --- |
| Home 入口 | 声明双重职责、指向项目地图、按任务选择产品或研发方法 | 产品仓 `AGENTS.md`；模板维护两种 Spec 入口 |
| 仓库地图 | 共享相关仓库的身份、职责、资料入口和依赖提示 | 默认产品仓根 `REPOSITORIES.md`，已有等价地图继续使用 |
| 技能地图 | 解释 Home、目标工程、Profile 与有效技能的衔接 | 既有 `.template-spec/agents/profile-skills.md` |
| 工程执行方法 | 按授权实现目标，核实工程范围、规则、版本、分工与结果 | 既有 `implement` 及 `references/repository-scope.md` |
| Home 配置方法 | 找到现有关系，按事实创建或补齐项目地图和入口引用 | 既有 `setup-yss-harness` 及新增地图模板 |
| 各工程 | 持有本仓技术方案、源码、构建、测试和交付证据 | 各自 Git 仓及其工作树 |

模板源码仓本身仍是方法与分发内容的维护仓，不因本次设计改成某个产品的 Home。共享仓库地图保存项目事实，不由模板版本替项目认定事实。

## 统一入口与技能可达性

### Spec 默认增加已有 implement

当前 Spec 的 `project` 与 `skills` 默认各有 16 个技能入口，不包含 `implement`；共享 `implement` 的宿主配置也禁止隐式调用。仅修改入口文案不能保证自然语言研发请求找到这一方法。

设计将现有 `implement` 加入 Spec 两种安装的默认集合，默认数量变为 **17**。共享 `implement` 改为允许在用户明确要求开发、修复或按规格实现时选用；同步其 description、`disable-model-invocation` 与 `agents/openai.yaml`，避免宿主元数据相互矛盾。只读研究、方案设计、规格确认及“准备交给研发”仍不触发实现。

同步 Spec 技能注册表：`instance_distribution.initial_skills` 加入 `implement`，该技能记录改为 `layer: core`、`instance_default_discoverable: true`；在现有 `invocation_contract.overrides.implement` 声明 `invocation_mode: both` 及明确研发的触发条件。注册表是内容与发现目录，仍不承担阶段资格或执行授权。

`implement` 是工程执行方法，不成为所有任务必须经过的总路由。明确前端小修改可以直接使用适用的 `yss-frontend-application`；多仓研发或目标工程不明时使用 `implement` 的仓库范围方法。`code-review` 继续按需安装与调用，产品默认技能其余成员保持现有职责。

Backend 保留自己的 `implement` 覆盖和已有调用政策，继承更新后的通用仓库范围参考。Frontend 保持现有默认集合，不为了形式一致安装 `implement`。

### 入口保持简短

Spec 的 `project` 和 `skills` 入口共同表达：这是产品上游及研发默认会话入口；工程任务按需查项目地图并核实目标仓；产品成果与工程成果各按责任保存。详细规则进入现有技能地图与仓库范围参考。

`skills` 安装继续尊重已有项目规则，只增加能力与可达参考，不自动认定现有工程已经改为产品 Home。用户在该目录提出完整产品协调任务，或要求配置 Home 时，才补齐对应关系。

默认安装后，入口引用的技能和参考必须存在。不得以“可按需安装”掩盖默认入口中的必读断链。

### 选择目标仓规则和技能

实际工作目录与会话启动目录分别处理。切换 shell 目录不视为宿主已重新加载另一仓的 `AGENTS.md` 或技能。

Agent 在首次处理目标工程时读取该仓入口、适用于目标路径的局部规则及必要构建资料，明确命令的实际 cwd。优先读取目标仓已安装的有效技能版本及其相对资源；同名技能以本次目标工程、任务职责和实际来源辨别，不能将 Spec 的业务 `to-tickets` 当作 Backend 实现切片方法。

技能来源按以下顺序处理：目标仓适用版本；当前 Home 已有的适用共享版本；宿主已配置且来源可核实的适用版本。缺少必要内容时，通过实际安装来源补齐所需技能或资源；受管项目使用已安装 CLI 支持的 `skills ensure`，且只能选择该 Profile 的可用集合。Backend 专属技能不强装入 Spec，不通过手改收据或切 Profile 获取。

读取技能正文及其资源可以作为当前任务上下文，但不宣称完成宿主注册或自动重载。必须依赖宿主专用工具的技能，另核实工具可用性。无法取得关键工程方法或工程目录时，说明具体缺口，只暂停依赖它的工作。

宿主指令层级与用户授权继续适用。Home 资料决定产品目标，目标仓规则约束本地工程实践。材料出现实质矛盾时定位冲突及影响，复用已确认决定；只有新的业务取舍需要用户决定。仓库地图、外部文档或低层资料不扩大授权。

## 仓库地图

### 内容与所有权

新增模板位于 `.agents/skills/setup-yss-harness/references/repositories-template.md`，随默认安装的 setup 技能分发。它是方法资产，包含填写说明和空结构，不写 SCRM 等真实项目关系，也不填作者的本机路径。

配置具体 Home 时，Agent 优先使用已有 README 仓库索引、地图或交接记录。内容已经能承担地图职责时，在 Home 入口引用其实际位置，不再创建第二份。需要独立地图时，默认创建根 `REPOSITORIES.md`；它由项目维护，不进入 CLI 安装收据和模板覆盖范围。

地图表达以下内容，不要求机器解析或严格字段 schema：

| 信息 | 规则 |
| --- | --- |
| 仓库标识 | 项目内稳定且不重复，如 `home`、`web`、`api`、`mobile`；标签由项目选择 |
| 职责 | 说明实现端或共享服务及产品边界，可标记只读参考用途 |
| Git 身份 | 使用已核实的远程仓地址或明确无远程；URL 不含凭据，不从目录名推断身份 |
| 资料入口 | 指向该仓内入口、技术说明、API 等实际路径，并写清其所属仓 |
| 关联 | 仅记录已有依据的上游、调用或共享关系；不凭角色名推断所有端都受影响 |
| 可选查找提示 | 常用目录名或相对布局提示，用于找候选；不能替代 Git 身份核验 |

地图不保存某人的绝对路径、当前分支、当前工作树、未提交状态、全局进度或每次任务采用的版本。不确定关系明确标注未知，保持它是可逐步完善的资料，不把完整登记当作开工条件。

### 本机位置解析

按本次用户提供的明确路径、任务已有链接、地图指针及已知工作区查找候选。必要时只在已知相关父目录有限查找；已接入的个人 Workbench 可提供已登记目录候选，不要求安装或登记 Workbench，不扫描全盘。

每个候选核对真实 Git 根、remote、当前分支、工作树信息及受影响路径状态。SSH 与 HTTPS 地址可指向同一远程项目，但同名目录、fork 或多个 remote 不自动认作同一个工程；有疑义按真实项目地址与当前任务核对。

多个 checkout 或 worktree 指向同一仓时，使用用户已指定的位置或本次任务已经选定的工作树。没有足够依据时提出一个定位问题，不因为 main、最新提交或目录最接近而自行决定写入位置。仍可继续只读调查和其他已明确工作。

候选不存在或资料不可读时，说明缺的是仓库访问、检出位置还是业务关系。必要的只读临时检出沿用已有权限与仓库保护方法；不自动把它登记为长期工程，不改动真实子模块，不自动 clone 全部关联仓。

## 任务如何连续推进

| 请求 | Home 中的处理 | 成果位置 |
| --- | --- | --- |
| 研究、修订规则、设计原型 | 按需读产品资料，继续现有 YSS 产品方法 | 产品 Spec / Home |
| 指定单仓的小修改 | 直接核实该工程、局部规则与输入，调用适用方法 | 指定工程 |
| 一项跨端功能 | 从地图与实际调用关系识别影响，确定先后依赖或并行责任 | 各工程分别落地，Home 会话汇总 |
| 实施中发现业务差异 | 沿原规则或 AC 说明差异，区分技术细化与新业务取舍 | 工程记录技术结论；产品变化回写上游 |
| 新会话续办 | 从当前任务、相关材料及真实仓库状态恢复必要信息 | 沿用原成果位置 |

地图提供调查起点，实际代码、API 和任务目标决定影响范围；既不漏查明确调用方，也不因地图列有某个端就自动修改该端。

对于跨仓任务，当前会话保留每仓目标、允许范围、依赖、选定输入及结果的简明说明。可直接在会话或已有任务记录中表达，不要求另建合同、票据、checkpoint 或交接包。需要持久续办信息时优先更新已有任务或实施说明。

主 Agent 承担整体范围、共享决定与结果集成。可独立推进且路径、运行资源能够隔离时，按宿主能力并行；共享文件安排单一负责人，存在 API 先后依赖时先固定必要输入再并行，或直接顺序完成。子任务收到目标、仓库与工作树、允许范围、来源版本、验收依据、依赖和预期回报，不复制全部聊天替代任务说明。

普通单仓局部修改不强制创建 worktree。并行任务需要隔离时使用现有 worktree 方法，保留原目录已有改动。子模块、符号链接、detached HEAD、未知文件及其他会话的修改继续遵守既有保护规则。

## 输入版本与反馈

只固定本次任务真正使用的材料。用户指定提交、PR/MR 或文件版本时沿用；使用当前工作树时如实说明来源，不把 HEAD 当作包含未提交内容的完整版本。

异步委派或续办需要可复核输入时，至少保留仓库身份、路径、相关提交或工作树状态、观察时间和相关未提交内容的依据。依据可以是选定 diff、未跟踪材料清单及内容摘要、现有资源摘要或必要的临时只读快照，按任务选择；不自动提交、不创建统一冻结协议，也不将不相关文件打包。

执行开始、交付前，以及收到规格变更提示或发现差异时，核对所用材料是否变化。发现变化后比较受影响规则和任务，更新依赖这次变化的输入与实现；保留未受影响工作。不持续轮询全部仓库，不把所有历史交接强制升级到最新主干。

研发反馈沿原 Spec、FR/AC 或具体章节关联：技术等义细化在工程完成；既有产品决定遗漏时按已有决定修正；新的业务行为或权限取舍由用户决定。不得为迁就实现自动降低验收要求。

仅授权工程修改时，发现上游需改先给出具体差异及建议，不能借反馈扩大写入权限。用户已授权同步调整规格与实现时，完成两侧更新，不重复索取同一授权。未写回的差异在结果中保留为未完成项。

## 结果汇总

交付按实际涉及的仓库说明：实际工作位置、变更行为、所用输入、执行过的检查及结果、未完成项和上下游影响。可引用已有工程记录或 PR/MR，普通小任务使用简短说明即可。

整体目标只有在所需各仓工作和必要集成均有依据时才能称完成；某仓只完成 mock、构建或契约检查时如实区分。不把 workbench 确认、任务勾选、源文件同步或一个子 Agent 的完成消息当作整个产品已联调、发布或验收的证明。

提交、推送、PR/MR、部署、发行与对外发送继续使用对应动作授权。Home 默认入口不增加上述授权，也不强制每次任务执行上述动作。

## 安装、同步与旧项目

| 情形 | 第一版行为 |
| --- | --- |
| 新建 Spec，`project` | 安装 17 个默认技能与已有资料，入口说明 Home；通过 setup 配置时，根据已知关联完善地图 |
| Spec，`skills` | 安装同一组 17 个技能及必要资源，保留已有工程规则；仅安装不创建产品地图或治理文档 |
| 直接使用 CLI init/attach | 分发入口、技能和地图模板；CLI 不认识真实产品关系，不声称已经完成 Home 配置 |
| 已有 Spec 同步 | 使用包含本次内容的 Bundle 更新方法和默认能力；地图及 README 中的项目事实继续由项目维护 |
| 已有独立或用户级技能 | 通过原安装来源更新实际选中的技能；不运行项目 sync、不把用户技能目录接管为项目 |
| 已有等价仓库地图 | 保留原位置与有效内容，更新入口引用和实际缺失关系 |

入口按实际安装记录保护。实施核实当前 CLI 的 README 入口也是 `managed-customizable`，不受 manifest 中同路径 user-owned 规则决定；README 或 AGENTS 双方同时改动时遵守冲突保护，不强制覆盖，源未变时保留本地定制。地图由 Agent 在实际配置任务中维护，CLI sync 不新建、覆盖或删除它。

同步不会切换 Profile。模板 main 修改也不会自动进入已安装程序；必须使用包含新内容的 CLI Bundle。第一版预期复用现有分发格式，实施时使用隔离的开发构建验证；未发行前只称开发构建，不承诺某个已发布版本已有这些行为。

如果旧安装的默认集合不会自动新增 `implement`，迁移方法用实际支持的 `skills ensure implement --root <Home>` 补齐并检查依赖，不手改安装收据。具体是否需要这一步由隔离兼容验证确定，并在最终教程中只保留已验证路径。

| 对应 `.workbuddy` 副本、Backend 继承参考、Profile 技能地图及适用来源登记 | 保持有效内容一致、保留 Backend 专有覆盖和 Frontend 白名单 |

本设计与计划保存在 `.template-source/design/`，沿用本仓既有维护文档位置。模板源码根 `AGENTS.md`、产品主 Spec 模板、生成身份文件、Workbench 模型、CLI Rust 代码和真实产品仓不在本次模板实现的默认修改范围。若验证发现现有 CLI 缺陷，只记录证据与受影响行为，另行明确修复范围。

## 验证与交付条件

验证分为分发正确性与实际任务行为。静态链接或 Bundle 检查只能证明内容可达，不能代替真实宿主执行场景。模板仓不新增常驻脚本或测试套件，采用当前 CLI 能力、临时目录与可核对的场景结果。

| 场景 | 需要观察的结果 |
| --- | --- |
| Spec project 与 skills 新安装 | 17 项默认能力、隐式策略与引用资源实际可用；skills 不凭空创建业务地图 |
| 旧安装、已有定制与二次同步 | 正确补齐方法；用户地图与 README 保留；受管双边修改产生受保护的冲突 |
| 从 Home 自然语言提出单仓小修改 | 正确进入目标 cwd，采用目标工程规则，无额外产品流程；真实完成相应修改与必要检查 |
| 一项同时涉及 Web/API 的小任务 | 找到真实调用关系，完成两仓必要修改与接口验证，汇总不漏仓 |
| 多工作树、缺失路径与只读参考仓 | 歧义未解决前不写错位置，已有改动保留，只读仓不因关联关系被修改 |
| 上游材料含未提交变化，执行中再修订 | 采用的输入可复核，只重新处理受影响部分，交付说明最终依据 |
| 新会话、另一种本机目录布局及同名技能 | 从共享地图恢复关系，按真实 Git 身份定位，读取目标工程的有效技能与资源 |

先使用无真实业务数据的临时多仓场景验证执行和保护；实际产品试用属于后续明确范围，不能借验证自动修改 SCRM。至少在实际主要宿主 Codex 验证一次完整入口到跨仓结果；其他宿主只完成内容与副本检查时明确标记运行体验未验证。

无实测基线时不承诺工时、Token 或正确率改善。记录是否需要用户重复提供已有事实、是否遗漏相关端、是否选错路径、单仓任务是否增加无关步骤；真实失败再用于决定是否扩展 CLI。

## 留给实施者的判断

实施者可以决定不改变上述行为的文字组织、地图列的排版、临时场景的最小业务例子、具体链接修复及任务内并行安排。平台副本和来源哈希按[现有维护规则](../agents/skills-maintenance.md)处理，验证命令以实际 CLI 帮助为准。

需保持不变的设计选择是：保留 `spec` Profile；两种 Spec 默认加入共享 `implement` 并支持明确研发请求的隐式选择；沿用目标仓有效工程规则；项目地图由项目维护；不新增 CLI/schema/中央状态；不扩大用户授权或引入统一流程门禁。

用户已在设计与计划完成后批准执行，后续又明确授权复审、完整 Demo 和回归完成后的本地提交。模板实现与验证在隔离工作区开展；推送、发布及真实产品接入仍使用对应授权。
