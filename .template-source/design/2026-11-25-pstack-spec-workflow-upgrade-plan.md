# YSS Spec 流程与技能升级计划

2026-11-25。用户已同意升级方向，本计划供 YSS 模板与工作台维护者实施。首轮解决两类问题：需求表述含糊时容易把假设写成规则，新会话续办时容易把主 Spec 版本当成全部材料的版本。其后补充进度答复和高风险反例记录。

## 工作项与顺序

| 顺序 | 何时触发 | 改动位置与行为 | 完成标准 |
| --- | --- | --- | --- |
| 1. 澄清前拆分歧义 | 同一句需求有多种解释，且会改变权限、状态、结果或验收 | `yss-research` 给出两三种合理解释，各列一条能区分它们的可观察证据。`yss-analyze-business` 先核对原需求、有效决定和可读事实，再把真正需要业务选择的部分交给已有 `grilling` 入口。证据明确时，用已确认口径继续。 [事实调研](../../.agents/skills/yss-research/references/fact-finding.md#现状与差距) · [业务分析方法](../../.agents/skills/yss-analyze-business/references/business-analysis.md) · [pstack reframe](https://github.com/cursor/plugins/blob/41e400932eca14f289e7db717a70455256b6d388/pstack/skills/reframe/SKILL.md#L7-L16) | 能用证据消掉的解释自行排除。仍有业务取舍时，提出本轮最关键的一个问题，写清选项会怎样改变验收。沿用已确认决定，仅暂缓依赖未决回答的部分。 |

## 工作台的改动条件

已有案例表明，只修改关联资料时，主文件的来源摘要可以保持相同，而整体产物摘要发生变化。终端 `workbench request` 与工作台复制续办文本已有 `specDigest`、`observedArtifactDigest`、`materialReviewDigest` 和 `materialChanges`。Pi 从映射后的隔离工程组织续办文本，另附主文件和目标信息。用实际回放判断 Pi 能看到哪些材料。 [历史实测](2026-11-21-decision-review-handoff-spec.md#提交前审查与回归) · [工作台续办指引](../../.template-spec/agents/workbench-progress.md#交接与-agent-续办请求)

- 若回放证实 Pi 缺少可获取的版本差异，工程改动限于该入口，复用现有材料评估与字段。核对 `yss-cli/src/workbench/agent.rs` 的续办提示和 `service.rs` 的共用上下文；分别标明原工程、已接收成果和隔离稿的来源。原工程可观察到的版本只有带入隔离稿并可读后，才可写成实际已读版本。
- 若 Pi 能正确判断材料变化，实施范围落在模板与技能。若材料本身未带入或无法访问，记录读取缺口。若工作台沿用已确认的共享材料，以可观察摘要和变更记录判断新版，以现有确认依据判断采用版。

## 用同一个案例验收

在临时 Spec 工程和隔离工作台数据中准备一个重试案例。v1 的主 Spec 已确认同一请求最多产生一条业务记录，并有一条独立的权限验收。确认范围包含该 Spec 自有原型。模拟用户发来“失败后可以重试”。v2 只把原型中的“结果未知时直接再次提交”改成“先查原请求结果”，主 Spec 字节、其他输入及 v1 确认证据按原值保留。这两种行为是试点输入，最终产品规则仍沿有效业务决定确认。

1. **回放现状，再回放候选。** 用基线及候选 Bundle 分别安装临时 Spec 项目，记录模板、CLI、宿主与材料版本。终端和工作台分别生成续办输入，检查实际附带的证据。在同等输入下，以相同的自然请求分别通过新会话和 Pi 实际隔离续办入口接手，检查技能是否被采用。Pi 场景同时确认隔离稿实际带入 v2 时能判断变化，隔离稿仍是 v1 时能交代读取边界。
2. **核对歧义和变更范围。** Agent 能区分请求未发出、已受理但结果未知、已确认失败。它能指出 v1 与 v2 的具体差异并定位受影响的验收，保留无关验收及仍有效的旧决定。遇到原决定和新版有冲突时，只提出还需业务方裁决的一项。材料变更按现有规则保留其确认和采用依据。
3. **核对同一案例的回复与审查记录。** 用“现在需要我定什么”检查待决事项及选项影响。用该恢复路径检查反例能否由另一个会话重放。按实际操作核对是否出现第二次提交或重复记录，并注明原型模拟范围。

交付时记录候选来源、实际输入、观察结果和未覆盖的入口。分发一致性、实际读入材料和会话行为各用对应证据说明。

## 实施审查与修复

- 基线终端和工作台复制都能看到原型 v1 到 v2 的材料差异，Pi 的实际启动和恢复提示缺少这组证据。隔离稿只带入 v1 时，Pi 无法知道原工程已经有 v2。修复复用 `content::inspect_record`，为 Pi 分别提供原工程与隔离稿的版本摘要和变更。材料采用沿原有确认，已接收范围沿实际接收记录。
- Rust 增量审查发现，直接序列化材料变更会把核实备注和外部链接带入提示。最终摘要只含版本摘要、变更类别、有效的本地相对路径及可读性标志。无确认基线时，即使变更列表为空也要看可观察摘要和实际文件。
- 首轮无登记的 Codex 回放曾尝试按答复 ID 从其他临时工作台定位记录。业务分析、Spec 续办和工作台指引已补充目录、工程根及主文件的核对约束。没有匹配记录且缺少其他目录依据时，沿当前材料继续并报告缺口。纯进度询问直接在会话答复。
- 一次 Pi 真实模型回放读取了 Spec 入口和编制方法，却未读取业务分析方法，随后依据“失败后可以重试”改写了独立的权限验收。Spec 入口现直接指向歧义核对方法，要求先查用户这句答复实际覆盖的条件，余下取舍先澄清，独立确认的条款和验收直接引用。
