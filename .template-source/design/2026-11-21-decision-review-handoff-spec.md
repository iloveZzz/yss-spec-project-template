# 工作台答复复查与领域规则交接

2026-11-21 · YSS CLI 工作台与 YSS 模板技能的增量规格。首轮已在本地实施答复复查、已有决定查证、原 Spec 反例和研发接手。本次补充三项维护：业务前提改变后怎样复查原问题，跨责任区怎样传递和使用业务信息，以及工程改动怎样保留仍有效的原验收。见[第 8.3 节](#83-业务前提与旧验收的维护)和[第 9 节](#9-验证与交接)。

工作台要让用户看清「我上次怎么答」和「我现在采纳哪一条」。研发接手同一份规格时，要能从原条款判断谁有权操作、按哪个时点判断，以及拒绝后保留什么。工作台据此筛选可回写的答复，技能交接时引用足以判定行为的原条款。

本篇是既有工作台与 Spec 交接方法的增量规格。工作台既有约定明确了个人记录和来源文件的归属。全流程规格 FR-03 要求接手方能够定位并读取原规格。本篇在原主规格上补充复查行为与验收。[工作台原有约定](https://github.com/iloveZzz/yss-cli/blob/74f3f5c5c8f67bc1526ae5e0de64e2d2346ee2b9/docs/workbench.md#主-spec-与内容确认) · [全流程规格 FR-03](2026-11-17-full-lifecycle-spec.md#fr-03-业务来源保持一致交接可实际读取) · [打开离线交互原型](2026-11-21-decision-review-handoff/preview.html)

## 1. 澄清结论

| 决定 | 用户选定的处理 | 对最终行为的影响 |
| --- | --- | --- |
| D1 · 沿用旧答复 | 先填入编辑区，点击「保存答复」后生效 | 打开问题或点击沿用均不产生新版答复。用户可以照录、修改或放弃。保存成功后才得到关联当前问题的新答复 ID，进入待回写。 |
| D2 · Agent 接续原 Spec | 单列历史原文并写明待复查原因，只有当前有效答复可用于回写 | 旧答复和到期延期可供人和 Agent 追溯。当前无有效决定时保留待复查问题，其他已有依据的条款可以继续。 |
| D3 · 研发交接深度 | 原规格有完整反例就引用具体条款，缺失或接手方无法读取时再补最短反例 | 接收人能直接找到裁决依据。摘述只使用已确认事实，来源缺少的优先级或失败结果继续列为未知。 |
| D4 · 建模时主动回查已有工单 | 按需查项目已配置、可读取的工单，包括已关闭项。找到仍适用的明确决定就注明出处并复用。 | 即使无人提供票号，只要词义分歧会改变业务行为，且根词汇表、原 Spec 与当前有效答复仍不足以裁决，就在该项目定向查找。可用证据仍留有实质取舍时，再请业务方决定。 |

D1–D3 来自首轮澄清。D4 来自本次会话中用户对 Q1「领域建模要主动查到哪里」的答复。D1–D4 是本文引用决定的编号。工作台的个人答复 ID 以实际保存返回值为准。文中 `OQ-01`、`D-01` 等仅用于演示。

## 3. 领域概念与责任

| 概念 | 谁维护、如何关联 | 约束 |
| --- | --- | --- |
| 问题及其当前含义 | 主 Spec 定义问题、影响范围和建议。稳定的问题 ID 标识同一问题，摘要标识此次提问的内容。 | 同一 ID 下改了问题含义，旧答复需要复查。建议只代表提议。 |
| 个人答复与延期安排 | 用户针对一个问题版本保存答复。一个问题可有多次个人记录，延期带原因、影响、排除范围、复查日期或条件。 | 旧记录保留原文与原 ID。即使新旧文字相同，也凭本次真实保存记录区分。 |
| 采纳与回写 | Agent 将当前决定落实到原 Spec 的业务条款、验收和受影响的原型或交互说明。原问题引用实际采用的 `appliedDecisionId`。 | 已解决须能在产物中看到结果。有效延期只决定暂缓的范围。整份内容的个人确认沿用独立操作。 |
| 领域词义、规则与工程模型 | 已确认且可复用的词义归项目根 `CONTEXT.md`。业务规则、反例及决定归原 Spec。研发结合实际架构承接。 | 遇到同词异义时注明使用场景、谁负责裁决、谁消费结果。DDD 工程需要划聚合时，再核对一致性和事务事实。MVC 工程沿原有分层。 |

例如，事项转交生效后，系统按当前负责人身份判断撤回权限。规格作者写明这一判断及其结果，工作台记录用户对规则的答复。聚合边界、数据库锁和并发胜负仍需要各自的事实。词汇归档沿用现有写入权限和 `ContextId`。只有难以逆转、缺上下文难理解且确有方案取舍的决定才考虑 ADR。[领域建模](../../.agents/skills/domain-modeling/SKILL.md) · [DDD 战术设计](../../profiles/backend/.agents/skills/yss-tactical-design/SKILL.md) · [工程技术设计](../../profiles/backend/.agents/skills/yss-technical-design/SKILL.md)

## 4. 工作台行为

**FR-01　复查时打开一份属于当前问题的编辑区。** 问题变更后，先显示当前问题及范围。历史区展示旧答复原文、答复 ID 和失效原因，本次答复起始为空。用户可直接填写，也可点「沿用原答复」把原文带入编辑区，再决定是否修改、保存。取消、关闭、切换到其他问题或恢复旧版本个人草稿都不能把草稿升级为有效答复。同版本且仍有效的已保存内容仍可继续编辑。

**FR-02　只在保存成功时形成新版答复。** 保存前复核当前问题。空答复、必填延期内容缺失、关键问题排除范围不完整或复查日期已到时给出具体原因。期间来源发生变化时保留本次输入，让用户看到新问题再决定是否保存。保存成功后使用新答复 ID，旧记录可追溯，页面显示待回写。同一次写入失败后恢复编辑时，以真实保存结果判断是否已生成答复。

**FR-03　完整续办文本按用途提供资料。** 用户从工作台、终端或工作台内 Agent 继续处理原 Spec 时，应能找到当前问题 ID、当前摘要、适用范围及真实答复 ID。具体用途见下表。

| 读取时的事实 | 给接手方的内容 | 可采取的动作 |
| --- | --- | --- |
| 当前摘要匹配、有效业务答复待回写 | 当前答复原文与真实 ID | 落实相关正文与 AC，核对受影响产物，再按实际结果记录采纳。 |
| 当前摘要匹配、有效延期待回写 | 当前延期的原因、影响、排除范围、复查日期及时区或条件 | 只回写延期安排并保留范围。条件型延期显示原条件。已核实条件触发时转入复查，缺少事实时提示接手方核对。 |
| 已回写且仍有效 | 已采用答复或有效延期及对应条款，标明已回写 | 引用现有结果。重复续办时跳过已完成的回写。 |
| 问题变更、有效范围不符、答复已被替换，或延期已到复查日期 | 单列相关历史，给出原文、原答复 ID、能取得的原问题摘要和具体复查原因。延期保留四项原始信息及已存的时区 | 当前没有其他有效答复时，保留问题待复查。日期按该安排保存的时区判断，到期当天即须复查，包括尚未回写的延期。 |
| 没有个人答复，或旧记录无法证明针对当前问题 | 当前未决或已有研究结论及来源。历史中无法核实的字段明确标为未知 | 对可查事实自行查证。仍缺业务裁决时才提问。 |

列表摘要要标明旧答复仅供复查。页面的「复制有效答复」可继续只复制有效项。完整续办文本保留相关历史原文。两种入口对同一条记录的用途应一致。现有问题视图只取最近一次答复，历史应从同一主 Spec、同一问题的个人原始记录取得。只有旧摘要可查时展示摘要，不补写旧问题标题。权限、来源路径、项目范围及现行 `dataDir` 继续沿用实际工作台上下文。[问题记录结构](https://github.com/iloveZzz/yss-cli/blob/74f3f5c5c8f67bc1526ae5e0de64e2d2346ee2b9/src/workbench/model.rs#L651) · [Pi 的问题复用](https://github.com/iloveZzz/yss-cli/blob/74f3f5c5c8f67bc1526ae5e0de64e2d2346ee2b9/src/workbench/agent.rs#L905)

## 5. 规则如何交给研发

**FR-04　引用足以裁决行为的证据。** 交接涉及权限变化、判定时点或失败后数据保留时，先找原 Spec 的具体条款或 AC，标出材料位置及版本或读取时点。交给接收人的内容取决于条款完整性及其访问情况。

| 接手时的情况 | 交接动作 |
| --- | --- |
| 原文含完整反例，接手方能够读取 | 指到具体 FR、AC 或稳定小节，点明它裁决哪个场景。接收方能直接据此判断时到此为止。 |
| 原文未写成反例，但已确认条款足以推导结果 | 引用依据，再补一句「谁在什么条件下做什么，结果怎样，哪些数据保留」，标明哪些结果由已确认条款推导。 |
| 发送方读过材料，接手方无权或无法读取 | 注明哪项来源不可达、采用版本和影响，在允许共享的范围摘述最短反例。接手方可读性尚未核实时注明未知。 |
| 两端都缺事实，或条款冲突 | 点出缺失的时点、结果或优先关系及受影响条款。可查事实由 Agent 查证，真正影响行为的取舍回到原问题。其余有依据的部分继续。 |

**教学示例。** 已知「仅当前负责人能撤回待处理事项」和「转交只改变负责人」，可在交接提示中写「甲打开待处理事项后，转交乙已生效，甲在旧页面撤回，系统拒绝，事项仍为待处理，负责人仍是乙」。这句话覆盖发起人、时点、拒绝结果和保留数据。若输入只有「支持转交、撤回，操作按负责人权限控制」，应指出按哪个时点判断、拒绝后状态如何仍缺依据。「转交和撤回同时发生谁优先」在两组材料中都没有答案。

事实调查交给 `yss-research`，用户取舍由 `grilling` 澄清，词义与归属由 `domain-modeling` 核对。行为组合由 `yss-analyze-business` 分析并在原 Spec 留下 FR/AC。一次简单文案修改可直接完成。Frontend 可从可见行为、可用操作和错误反馈接手。Backend 只有在目标工程采用 DDD 且任务涉及建模时，才进一步设计聚合、不变量或领域行为。[确认与提问方法](../../.agents/skills/grilling/SKILL.md) · [业务分析方法](../../.agents/skills/yss-analyze-business/references/business-analysis.md) · [Frontend 技能分发范围](../../profiles/frontend/.template-spec/agents/yss-skill-registry.yaml)

### 从一个词义分歧走到可验收的行为

**FR-05　提问前找出同一业务范围内已有的决定。** 以「当前负责人」为例，先查根词汇表、原 Spec 的相关 FR/AC 和针对当前问题仍有效的答复。如果「打开页面时」和「处理撤回时」会产生不同结果，且这些材料无法裁决，沿已有工单链接查证。即使无人提供票号，也按 D4 用相关术语或业务动作在本项目已配置、可读取的工单中查找，包括已关闭项。

找到决定时，指到具体正文或评论，核实决定人的权限、适用对象与版本，以及是否已有后续决定取代它。工单的关闭状态只能帮助定位。核对代码后，若确认的规则清楚而实现有偏差，记录受影响的行为。若项目缺少配置且没有明确来源，或相关来源不可读，说明实际缺口，继续有依据的部分。确有两种业务解释待选时，才用能区分结果的场景提问，例如「转交已生效，甲从旧页面撤回，应接受还是拒绝？」[工单读取约定](../../.template-spec/agents/issue-tracker-operations.md#定位与读取)

**FR-06　让原 Spec 单独承载可判定的反例。** 从讨论写回原 FR 时保留「当前」「待处理」「只改变负责人」三个限制。用原 AC 记录动作前的角色与状态、转交已生效、处理撤回时甲已无权、拒绝后事项仍待处理且负责人仍为乙。若原 FR/AC 已完整，直接复用其编号。交接文本按 FR-04/D3 引用或摘述。只有「按负责人权限控制」这一句时，原 Spec 应指出判定时点及失败结果缺少依据，并标明受影响的验收。确认有稳定词义且任务允许归档时，词义归项目根 `CONTEXT.md`。本例的具体行为和例外归原 Spec。

**FR-07　研发分别说明已知的先后顺序和尚缺的并发规则。** 接手人先从原 FR/AC 和工程事实核对三个问题。谁对负责人及转交生效负责？哪次动作必须依据生效后的负责人？若转交和撤回重叠，哪些用户可见结果被允许？本例能裁决转交已生效后甲的撤回。负责人由哪个业务对象权威维护、两次操作真正重叠时谁能成功，还需分别查证。只有选择会改变可见结果且来源无法裁决时，才把具体分歧交还业务方。研发结合这些事实说明一致性边界。DDD 工程有据时选择聚合及跨聚合协作，MVC 沿实际 Service 边界，纯前端文案沿既有交互处理。[后端技术设计方法](../../profiles/backend/.agents/skills/yss-technical-design/references/design-method.md) · [DDD 战术设计](../../profiles/backend/.agents/skills/yss-tactical-design/SKILL.md)

### 业务前提改变后的交接

**FR-08　沿原问题定点复查失效前提。** 关键问题的题意或影响注明所依赖的原 FR、AC 或前置 OQ，以及哪项业务条件会改变答案。修改规则、采纳替换决定或回写前，对照其实际适用范围，找到依赖该前提的原问题。改变了权限、时点、结果或适用范围时，保留问题 ID，更新题意或影响里实际变化的前提。旧答复留在历史，只复查受影响的问题及验收。已有明确裁决时引用其来源，仍缺业务决定才提问。原分支已不适用时在原 Spec 说明依据和影响，该题无当前有效答复时继续待复查。仅需核对的独立问题保留原状态、答复和条款，另有实际授权时再采纳。

用现有问题字段承载业务前提，由工作台原有的问题摘要识别变化。前置决定从允许沿用改为立即失效时，「允许时保留多久」的旧答复只供复查。排版变化、技术等义调整和无关答复沿用原问题及有效结论。整份 Spec 的版本确认沿原确认约定处理。[规格回写方法](../../.agents/skills/yss-build-spec/references/spec-workflow.md#主-spec澄清与确认) · [澄清入口](../../.agents/skills/grilling/SKILL.md)

**FR-09　跨责任区交接要能找到权威事实及消费方式。** 同一词在不同责任区含义不同，或已确认规则要跨边界生效时，沿已有 `ContextId` 区分两端的业务概念。原 Spec 或现有设计写清事实由谁维护、哪个动作消费、什么时点采用，以及过期或不可用时允许看到的结果。已知与未知分别注明出处。稳定词义归根 `CONTEXT.md`，具体业务行为归原 FR/AC，接口、事件和读取策略归工程设计。跨区事实影响后端一致性时，DDD 沿实际权威边界判断聚合与应用协作，MVC 沿既有 Service，Frontend 采用真实契约的交互与显示约定。

既有联系人试点提供一个可验证的场景。姓名由当前字段配置和权限决定，详情消费派生的只读展示值，动态表单沿已确认的字段键处理。研发接手前可从资料定位各项职责。缺失无权或无值时的输出规则，则标明影响并继续有依据的路径。[联系人试点](2026-11-17-full-lifecycle-spec.md#实际反馈与修复) · [词汇身份](../../.agents/skills/domain-modeling/CONTEXT-FORMAT.md#术语身份)

**FR-10　共用规则的改动同时承接仍适用的原验收。** 工程工作项引用本次行为与仍受影响的旧 FR/AC，指出实际消费者、采用版本、共享前提和可观察结果。若多项工作共同满足一项验收，注明真实依赖和可验证的解除条件。实施或续办时从实际用例入口核对受影响场景，保留拒绝后的业务不变项，并区分构建、模拟与实际结果。审查本次涉及的权限、状态或跨责任区映射时，按需读取相关词汇和 ADR，核对原验收是否仍能满足。已获批准的新规则明确替换旧验收时记录依据及适用范围。
