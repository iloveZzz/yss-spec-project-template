# Matt 技能适配完整收敛设计

日期：2026-10-31。状态：用户已批准本设计，进入实施计划编写。

本设计面向 YSS template 维护者，解决技能入口、参考资料、调用方式与分发记录不一致的问题，并选择性吸收 Matt 上游的工程方法。用户已选择“完整收敛，分批实施”，并在审阅本文后回复“批准 进入设计”；按此前约定进入实施计划。批准设计不等于已执行实现、提交或发布。

设计遵循当前 [AGENTS.md](../../AGENTS.md)：按任务直接工作，保留输入校验、错误处理、权限和文件保护，不恢复统一阶段门禁、批准包、脚本或测试套件。本文的批次与验收仅服务本次维护，不成为日常任务的新流程。

## 1. 要达到的结果

同一任务无论从技能入口、条件参考或 Backend 覆盖层进入，得到的职责、必要输入和完成依据都一致。技能能解释需要执行的方法，也能区分当前任务确实缺少的业务决定与可以自行查明的事实。

| 场景 | 改进后的可观察结果 |
|---|---|
| 调查明确缺陷或复杂故障 | 按问题选择复现、阅读、测量和探针；参考文件不会额外强制固定阶段或阻止有依据的分析 |
| 审查分支、PR 或工作树 | 确定实际范围，覆盖规范和已有验收，报告有证据的问题；不会要求先补 Spec、测试报告或候选 manifest |
| 依据 Ticket 开始工作 | 读取真实条目及相关补充，识别标题与范围；引用歧义时只澄清该歧义 |
| 配置或使用 tracker | 使用已明确的平台、仓库和实例；命令符合实际安装版本，结果未知时先查询，不盲目重试写入 |
| 查找技能来源 | 能读到原始来源、比较版本、采用内容及保留差异；不会把选择性借鉴称作整体升级 |
| 运行相关技能的不同平台副本 | 共享内容一致，Backend 的确有必要差异保留，必要参考实际随安装内容可达 |
| 使用已有 wiki | 复用原位置与文章；代码结论注明来源时点，查询不改文件，不再指向已删除的脚本和事务系统 |

收益目标是减少错误命令、相互矛盾的指令、重复确认和过期知识误用。本次没有可信的两侧行为数据，不承诺 Token、耗时或返工率改善比例。

## 5. 执行方法的收敛

### 5.1 入口、参考与历史规则

每个当前入口保留任务触发、必要输入、关键选择、完成依据，以及真实权限或业务决定缺失时的处理。仅用于特定分支的细节，在分支出现处给出包含读取条件的引用；不把“先读全部参考”作为默认步骤。

同一规则只由一个当前文件持有，调用方引用它。本文所说的“完成依据”是具体任务的结果，不是新增状态机或资格校验。

当前技能参考中的旧流程按以下方式处理：

- 有效工程方法改写为当前任务可直接使用的参考。
- 只有旧脚本、批准包或已退役执行器才能运行的步骤，从当前执行路径移除。
- 必须保留的历史兼容说明明确写为只读解释，不尝试重建旧执行器；当前入口与发现依赖不再把它当操作前置。
- 没有现行消费者、只有重复历史规则的技能内参考，可在确认所有引用后删除。删除仅限本轮受管范围，不能自动清理用户实例中的文件。
- `.template-source/contracts` 的历史记录原文不改，不用新设计替换过去的决定；当前可读的业务约束不因流程退役而失效。

### 5.2 诊断与测试优先开发

`diagnosing-bugs` 允许直接修复已有充分依据的明确缺陷；不确定时选择能区分假设的反馈。复现、最小化、比较版本、测量和探针是可组合方法，不要求固定数量的假设、每一步询问或完整阶段链。

没有可运行环境时，仍可读代码并提出有依据的分析，但必须区分推断和观察；不能宣称修复已经验证。涉及生产探针或额外访问权限时，仅暂停依赖该权限的操作。保留敏感信息脱敏、探针清理和原始症状回查。

人为修改代码或 fixture 制造失败时，保留现有要求：确认字节确实变化，并证明失败对应目标症状；已有失败不必另造变异。不得在用户工作树中 reset 或覆盖修改以构造反例。

`tdd` 继续仅在用户要求测试优先方法时启用。保留公共接口、独立预期值、一次一条行为反馈和外部边界 mock。对有选择意义的关键测试边界，增加一句覆盖与遗漏说明；已有验收和接口足够时不重复要求用户确认 seam，不给每个断言增加表格。

### 5.3 审查范围与检查来源

`code-review` 继续只读，除非用户同时要求修复。分支/PR 审查读取指定基线和实际 head；工作树审查覆盖目标范围内已暂存、未暂存及相关未跟踪文件，不能静默退化成只看 `HEAD`。不要求落盘候选 manifest；在当前报告中说明实际范围即可。基线可从明确上下文确定时直接采用，存在实质歧义再询问；空差异报告无可审内容，不宣称代码质量通过。

规范检查读取存在的 `CODING_STANDARDS.md`、`CONTRIBUTING.md`、适用 YSS 技能和当前工程约定。需求检查使用当前请求、Ticket、Spec 或已有验收；缺少独立 Spec 文件不阻断已有依据的检查。完全没有需求依据时说明不能评价该维度。

保留规范与需求两类问题的区分，以及 UI 还原仅在存在相关设计输入和变更时适用。代码坏味道是需要证据的判断，不是自动违规；工具未运行本身也不是代码缺陷。测试或构建按任务需要运行，报告实际结果与环境失败的区别，不强制安排两个子代理。

先清理 `candidate-capture.md`、`yss-review-standards.md`、`review-axis-checklists.md` 和适用历史参考，再从主入口接入必要条件指针。避免重新链接旧规则后把已取消的门禁带回。

### 5.4 需求、拆票与决策地图

`yss-product-lifecycle` 组织现有需求、研究、业务决定及必要设计；当解释某技能的前提、例外或决定跳过某步骤时，读取实际技能入口。仅列出可选技能时不加载全部正文。宿主有技能工具就使用实际工具，没有时按可用路径读取，不虚构工具调用。

`to-spec` 综合已有讨论，`to-tickets` 拆出可验收结果；两者不重复访谈，也不要求先取得工程身份或形式化任务集合才能起草。保留业务票与研发细化的差异：产品侧描述行为和验收，研发侧在适用时细化到实现 Slice。已有集合、模板与 ID 继续复用；普通拆分可使用现有 tracker 或授权文档，不强制额外创建 YAML 集合。

远程票在平台支持且操作已获授权时使用真实父子与阻塞关系；平台不支持时使用明确文本引用。依赖以已取得的真实 ID 建立，原生关系存在时不再维护相互独立的阻塞清单。保留宽范围重构的 expand → migrate → contract 方法及共享集成验证边界。

`triage` 与 `wayfinder` 在当前授权范围整理事实、建议及可执行结果，不要求交回已退役主控取得资格。缺 tracker 时，可读分析和当前对话中的地图继续；已授权保存且没有目标偏好时使用已约定的本地位置并说明选择，只有远程动作或真实位置歧义才需要补信息。不得同时要求 setup 又静默切换 tracker。

`grilling` 增加“肯定回答接受推荐项”的表述约束，保持只问当前有依据的问题、事实自行调查和有效确认复用。涉及第三方独有知识时，可生成授权范围内的简短问题清单，明确回答者及需要解决的决定；本轮不新增问卷技能、默认文件或对外发送动作。

`domain-modeling` 保留词汇身份和写入准确性要求，删除对已退役流程身份或无工具上下文的验证参数依赖。只读讨论可以继续；实际词汇写入缺少必要业务依据时保留候选，不猜 `ContextId`，不自动建 `CONTEXT.md`。

### 5.5 真实 Ticket 与已有子代理

`implement` 收到编号或 URL 后，先在明确目标中解析条目，读取正文及与任务相关的评论，并以标题说明承接范围。可访问性失败不等同于条目不存在；不使用标题猜测另一条记录代替。已有用户输入足够的独立部分继续，无法获知的验收保持缺口。

子代理约束只在任务已授权并且所选方法确实需要派发时生效。研究、审查、设计不因本设计而普遍强制使用子代理。

派发时使用宿主支持的独立上下文机制；Codex 当前工具可使用 `fork_turns: none`。任务说明包含目标、只读或写入权限、明确负责路径、必要事实指针及版本、完成结果和待报告限制。写入者须知道还有其他执行者，不覆盖他人修改；共享索引由一个指定执行者维护。

不自动复制整段会话，也不只发送缺少范围和约束的裸路径。子代理无法访问必要来源时，由主执行者提供最小必要内容或调整执行方式，不据无上下文结果判断完成。宿主不支持独立子代理时顺序完成，不为此停工。

本轮将这些规则放在实际已有派发分支，例如 `codebase-design/DESIGN-IT-TWICE.md`；不创建新的整规格并行执行流程。设计备选数量以真实取舍和可用资源决定，不要求固定 3 个以上子代理。

## 6. Tracker 操作适配

现有 `.template-spec/agents/issue-tracker.md` 是明确配置存在时的权威。用户明确指定的新目标可在本次授权中使用，并明确与已存配置的差异；不因 Git remote 存在而静默改写配置。多个仓库或实例不可无歧义确定时才询问。

远程工具优先使用已连接且能力足够的连接器；CLI 后备先读实际版本与对应子命令帮助。示例优先长参数：GitLab 列表用实际支持的 `--output json`；GitHub JSON 字段按命令支持范围选择。普通 CLI 操作显式绑定仓库，API 调用显式包含已解析的 owner/repo 或项目路径，GitLab 保留已明确实例。

| 操作 | 设计要求 |
|---|---|
| GitHub 外部 PR 列表 | 使用连接器返回的作者关联字段，或分页 REST 列表的 `author_association`；明确排除仓库成员类作者 |
| Issue/PR/MR 读取 | 取得实际正文及相关评论、标签；不假定 `--comments` 同时返回正文 |
| GitLab Issue/MR 列表 | 分别核对各子命令帮助，不跨子命令推断短参数含义 |
| 子票、依赖和前沿 | 使用平台支持的关系与真实标识；完整读取相关分页，前沿依据未完成的实际阻塞项 |
| 标签、关闭、评论 | 只在对应操作已授权时执行；不能把显示建议当作修改授权 |
| 失败与恢复 | 创建超时先查询目标和可用稳定标识；无法判定保留未知，更新前检查并发修改，完成后回读实际结果 |

修订同时到达技能种子模板、写入说明和本仓实际含有相同命令的当前配置。保留现有账号、仓库、实例、标签和用户自定义内容；不以更新示例为由重跑 setup 或重建整个配置。已安装用户项目不在本次范围。

## 7. 写作与知识记录

### 7.1 PR 描述和轻量复盘

复用 `i-have-adhd` 持有的中文写作方法。建议新增技能内参考 `references/pr-and-retro.md`，将当前有效的 PR/复盘方法从 `.template-spec/process/document-writing.md` 转移到该参考；旧位置保留导航，避免同时维护两份正文。普通 PR 写作、复盘入口明确按任务读取，不再要求先涉及治理或批准。

PR 描述围绕问题、可观察变化、实际验证、影响和回滚限制；图示只有有助于理解时使用。复盘从本次真实失败、返工、导航或工具阻碍出发，提出有依据的最小改进，不把没有 CI、没有预提交 hook 本身判为本仓缺陷，不自动增加脚本或检查套件。

现有公共表达、历史材料和业务批准事实不在迁移时改写。根据实际引用更新 `i-have-adhd` 的分发依赖，不因新参考在技能内就删除其他仍有消费者的外部资源。

### 7.2 Wiki 时效与旧参考清理

`llm-wiki` 先找用户已指定或任务内已有的 wiki，沿用目录和页面约定；没有且任务确实要求新建时使用入口约定的位置并说明。不全盘搜索用户文件系统，也不把查询请求变成初始化。

页面记录来源和有效时点。代码行为结论引用仓库与 commit；未提交内容使用读取时点、工作树状态和文件位置说明，不能冒充已有提交。决策和偏好记录确认日期与可读来源。只对易变结论要求时效，不机械给每句常识添加日期。

新事实改变旧结论时，清楚标记旧结论已被替代并保留来源；当前答案依靠本次读到的权威资料，不把旧 wiki 当实时事实。查询保持只读，来源无法访问时说明可信范围。

同步重写 `discover.md`、`ingest.md`、`query.md`、`writing.md` 中仍有价值的方法，移除已删除的脚本、schema、manifest、事务和固定数量门槛要求。按用户实际范围直接维护 Markdown；保留人工所有内容保护、来源脱敏、事实冲突处理和引用追溯。已有用户 manifest 或历史记录不自动删除或迁移。

## 8. 来源说明与分发

建议将适配说明放在 `.template-spec/agents/matt-skills-adaptation.md`，以 root 版本为内容源，Backend 同路径为受管副本。选择这个位置，是因为 `.template-source` 被现有分发清单排除，不能再让实例内的来源锁指向不分发文件。

这份说明只记录来源，不承载日常操作前置。内容包括原始引入提交、本次比较提交、逐技能采用状态、本地差异与理由、未采用或待观察内容以及核验日期。原始 `sourceRevision` 与 `upstreamHash` 保持原义；只有重新引入真实来源字节时才按现有定义更新，不能用本次调研日期重写来源。

本轮更新根锁的 17 个及 Backend 锁现有 16 个 Matt 来源条目的 `adaptationRef`。Backend 继承共享技能时应继承其来源信息；对当前标为本地来源的 `yss-research`，先确认有效内容确实来自共享源、没有专有覆盖，再沿用根条目的原始来源字段，保留其实际 targets 和内容哈希。不能按目录数量强行补齐，也不能把 Backend 专有改写的有效内容哈希替换为根哈希。

复用现有 `installations.project.skillReferences` 和 `installations.skills.skillReferences`，将共同说明加入最终确认属于 Matt 来源的已分发技能的必要资源，并去重分发；不新增锁字段、schema 版本、下载器或运行时依赖引擎。不要求每次执行技能都读取适配说明。

其他同步范围：

| 内容 | 处理 |
|---|---|
| 共享技能 | 仅编辑 `.agents/skills` 源内容，更新根 WorkBuddy 普通文件副本，检查 Claude 链接目标 |
| Backend | 按当前 profile 清单与有效入口引用组合共享内容和覆盖层；特别核对 `prototype`、`to-spec`、`triage`，不把根版本直接覆盖专有内容，也不因根目录有某个文件就补入 Backend 不使用的资源 |
| 运行时元数据 | 保留名称、描述用途及显式调用策略；只有触发说明实际变化时同步对应元数据 |
| 注册表、锁与资源清单 | 只更新受影响路径、内容记录和依赖；入口数量及默认安装技能不变 |
| 公开技能清单 | 不新增公开技能；本次改变的引用若影响既有导出，按现有包内引用规则处理，不声称已发布 |

安装文件存在、来源可追溯、宿主实际发现和模型正确执行分别说明。实际 CLI 不支持某操作时使用获授权的直接文件操作维护本仓；不恢复已删除脚本，不修改用户安装实例，不把旧二进制描述为已携带新内容。

## 9. 分批实施与本次验证

以下是设计层面的交付顺序，具体任务拆分留给设计通过后的实施计划。每一批都同步它影响的副本和清单，不把已知不一致留到最后。

| 批次 | 交付内容 | 依赖与结果 |
|---|---|---|
| 第一批：命令与来源 | tracker 示例、明确目标选择、适配说明和锁引用 | 可独立开始；消除已知错误命令与来源断链，不进行远程写入 |
| 第二批：执行路径 | 诊断、审查、规格、拆票、triage、wayfinder、词汇与相邻参考的语义收敛 | 基于已选职责逐项处理；旧文件处理与当前调用方在同批闭合 |
| 第三批：方法补强 | 提问表达、测试边界说明、Ticket 解析、已有子代理分支、PR/复盘、wiki 时效及参考清理 | 可独立的正文准备可并行；最终整合依赖第二批的职责边界 |
| 第四批：整体核对 | 21 个技能范围内的引用、元数据、Spec/Backend 组合和代表性任务观察 | 不再新增功能；报告已确认结果与未验证兼容范围 |

本次适配采用临时只读检查与人工/Agent 场景观察，不向仓库新增脚本、测试套件、CI、检查计划或证据包。已有仓库测试工具并非必须运行，只有本次实际改动需要时才使用。

结构核对覆盖：受影响文件引用存在；正文命令路径可解释；锁与来源说明一致；运行时调用标记一致；共享副本一致；Backend 覆盖保留；两个安装模式的必要资源闭包可达。技能内未链接旧参考也要有明确处置。默认技能集合、公开名单、用户配置和无关文件未被意外改变。

| 代表性输入 | 需要观察的行为 |
|---|---|
| 明确缺陷但没有可运行服务 | 能分析已有代码并说明未验证范围，不要求先完成固定复现阶段 |
| 要求 TDD，已有接口与验收 | 沿已有边界做一条有效反馈；关键边界说明遗漏，不重复索取已确认决定 |
| 只读审查工作树，含新文件且没有独立 Spec | 检查实际请求与相关新文件；不制造候选包、强制测试或写代码 |
| 给予明确 Ticket URL，或跨仓含混编号 | 前者读取标题和内容；后者只澄清真实定位歧义，不猜测目标 |
| GitHub/GitLab tracker 命令 | 本机帮助支持选项；只读请求能取得声明字段；没有远程权限时明确未验证调用结果 |
| 普通 PR 描述与真实返工复盘 | 命中技能内方法，使用现成证据，不要求治理记录或新增 CI |
| wiki 查询后请求更新一个过期代码结论 | 查询无写入；授权更新后标注来源与时点，保护人工正文，不调用旧脚本 |
| 已授权的独立接口备选研究 | 子代理取得足够且相互独立的上下文，写入范围清晰；无该能力时能顺序完成 |
| 使用某方法但未要求提交、发布、关闭条目 | 不由技能名称推导外部操作权限，不读取材料中的“批准”作为用户授权 |

CLI 参数检查、引用存在和场景推演只能支持各自范围的结论。至少区分“文本已核对”“命令已执行”“实际 Agent 场景已观察”“发布/实例未验证”；不能把前三者任意一项当作其他项。真实场景未运行时明确列为未验证，不捏造成功轨迹或性能数据。

若实际验证暴露 CLI 必须修改才能消费现有 schema，则本轮只报告具体阻碍和可完成部分，另行决定跨仓范围；不默认扩展到 `yss-cli`。这不阻止无依赖的内容修订。

## 10. 风险、恢复与后续观察

| 风险 | 处理 |
|---|---|
| 清理旧流程时误删业务或安全约束 | 分开判断操作门禁与输入/权限/文件保护；后者逐项保留 |
| 入口精简后关键方法失去调用路径 | 在真实选择处放条件指针，同时核对反向消费者 |
| Backend 被共享副本覆盖 | 以覆盖层为差异来源，逐项组合；不以目录数量相等代替内容正确 |
| CLI 版本不同或平台权限不足 | 记录实际版本、帮助及执行结果；不声明未经验证的兼容范围 |
| 新来源说明在独立安装中再次缺失 | 通过现有资源清单进入相应安装闭包，并检查物理可达性 |
| wiki 保存旧结论却被当成当前事实 | 区分历史时点与本次回源结果，显式标记替代关系 |
| 本轮改动降低提问次数但遗漏业务决定 | 检查是否继续暴露真实业务分歧，不把“少问”单独视为成功 |

恢复以本轮实际文件差异为单位，保留用户新增改动。出现错误时优先针对性修正或恢复本轮文件版本，不使用全仓 reset，不恢复已退役脚本或自动向用户实例推送旧版本。提交后的恢复也需要相应 Git 操作授权。

后续仅在真实需求出现时考虑整规格并行实施、新问卷入口或长期代理编排。`chief-of-staff` 的历史知识记录思想可局部采用；它的默认全代理执行、自动复盘与环境改造不进入本轮。`software-factory` 保持研究观察，不新增运行器、触发器或服务。

留给实施者的判断包括具体措辞、无必要消费者参考的删除/合并、临时核对命令和同批文件操作顺序。改变 21 个技能的主要职责、默认调用政策、业务身份规则、用户数据处理或跨仓范围时，需要回到当前设计说明实质变化。
