# DDD / MVC 多版本平台加固记录

本轮按用户“OK 按照你的建议优先级处理”继续实施 P1 → P2 六项优化；仓库为 template-source，维护强度为 L3。保留已有未提交修改，未提交、推送或发布。本记录只覆盖平台加固，不把整个脏工作区计为本轮实现。

## 已实现

1. **证据绑定配方与源码**：新增 `backend-platform-provenance.mjs`；兼容证据绑定完整配方、生成器与验证器源码、生成文件及执行位摘要。源码、模板或 Wrapper 改变后须重新验证，历史证据不能继续开放新生成。普通 Skill 说明文字不进入执行源码摘要。
2. **运行时依赖核验**：只从启动模块的 compile/runtime 树判断必需能力；独立解析所选 Boot 精确版本 BOM，比较实际版本和明确的第三方组件配方。检查可执行 Jar 的 BOOT-INF/lib，拒绝缺库、额外错误版本与命名空间污染。打包例外仅允许对应 Boot 的 jarmode 工具和配方指定的 provided Lombok，不能补足运行时能力。修正了模块依赖树重复收集，并在实际 package 后收集依赖证据。
3. **实际 HTTP 测试模板**：DDD 和 MVC 的测试 Controller 使用随机端口，验证 JSON POST 往返与非法参数返回 400；保留 Validator、JSON、MyBatis 查询映射与可选 Feign Decoder 测试。Controller 只在测试源码中；Surefire 必须有本次执行的新报告，旧结果与跳过测试不能补证据。
4. **精确补丁并存**：清单按平台 ID、Boot 精确补丁、Java 唯一；新增补丁追加行，所有决定/合同/查询/矩阵都以精确补丁解析。出现多个补丁时仅提供平台 ID 会被拒绝。共享 MVC 的数据分析调用方继续显式绑定原 2.7.18 范围。
5. **维护候选安全重试**：矩阵命令提供 `--resume`，重新检查原批准合同、架构与工程前提、Manifest、源码摘要及生成文件清单；不重新生成，不覆盖用户修改。每次写独立证据目录；合同、生成文件、额外源码或工具源码漂移均拒绝恢复。
6. **分离用户决定和证据刷新**：平台配置升级至 v2，Project Scaffold Contract 保持 v4。`compatibility_digest` 表达配方语义，追加或刷新同配方证据不修改用户选择摘要；配方改变仍须重新确认。证据自身仍绑定字节摘要并强校验。历史 v1 只读审计，不自动迁移原批准。

另补充首切片衔接：空脚手架验证与首切片报告区分 verification_scope。首切片在既有批准门禁通过后允许业务代码变化，不能用首切片报告认证平台支持；候选不能进入首切片。空脚手架证据目录放在生成工程外部，避免误报新增源码。
