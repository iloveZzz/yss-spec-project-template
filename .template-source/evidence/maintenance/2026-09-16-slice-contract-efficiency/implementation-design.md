# Slice Implementation Contract 成本优化实施设计

本轮交付实施设计，未实施编译器改造。用户已确认目标、范围、验收思路和关键取舍，并在本轮明确选择“本轮只完成实施设计”。后续按本文分批实施时沿用已确认设计，不重复询问相同取舍；代码实施、提交、推送和发布权限分别按实际授权判断。

方案先减少重复取数、整理和填写，再减少重复阅读。保留 YAML 为唯一权威合同，保持现有 schema，不批量删字段、不拆分权威合同，不建设管理页面。用户决定交付目标、范围、验收和关键取舍；Agent 整理草案；独立专业审查核验适用工程约束，生命周期沿用当前批准协议。

## 2. 端到端处理过程

1. 从当前 Ticket / 生命周期已有引用确定切片、Spec、仓库、基线和契约；不递归扫描目录猜“最新”资产。
2. 原字节读取一次，建立本次调用的来源快照，核验身份、版本、摘要、批准与适用范围。输出前重验读过的来源，防止生成期间被替换。
3. 提取已确认事实，按既有映射推导 Skill 和约束，保留来源定位。只让 Agent 补本切片新增细化、例外与未决缺口。
4. 组装完整 schema v2 YAML 草案；缺口进入现有 `readiness.blockers` / `stale_inputs`，未命中项进入带原因的 `not_applicable`。不填空字符串或空数组伪造就绪。
5. 对草案运行适用校验；从同一份持久化 YAML 及绑定上游生成审阅视图、工作单元视图和差异报告。
6. 独立专业审查、用户决定及生命周期批准仍按当前协议办理。派生输出不提供批准入口，不设置 `ready-for-agent`。

生成报告中的来源索引、差异和计量属于派生证据，可以随已有命令输出或聊天展示；不作为另一份必须人工维护的输入合同。

## 3. 输入自动填充

### 3.1 输入与输出接口

保留 `compileImplementationContract` 的现有签名和返回行为。建议在同一模块导出外层 `prepareSliceImplementationContract`，内部复用原编译函数；名称为拟新增接口，本轮未实现。

入口接收治理根、切片标识、已有 Ticket / checkpoint 引用、必要的上游来源选择，以及仅本切片新增的细化。已有草稿只作为本次细化载体；已批准合同仅作为只读基线。不要要求用户先重新填写完整 `compiler_input_required` 对象。

返回两部分：现有 schema 的 `slice_contract` 草案，以及自动生成的 `report`。report 记录字段来源、缺口、冲突、验收覆盖、检查结果和计量；不得被执行器当作合同。Agent 可通过现有 Node 模块调用和聊天输出使用这些结果，第一批不新增独立管理入口。完整合同仍保存到现有切片目录。

草案生成只允许写新输出路径；输出已存在、指向源合同或别名 / 符号链接指向源文件时拒绝覆盖。旧草案若需更新，先生成新文件供比较。已批准合同不改状态、不重新排版、不补默认值。合同 ID、版本沿用既有版本策略；需要新版本却无法确定时记录缺口，不能猜版本。

### 3.2 字段映射与职责

| 目标字段 / 内容 | 来源与自动处理 | 需要 Agent 或专业审查补充的部分 |
|---|---|---|
| `contract_id`、`contract_version`、`slice_id` | 已有 Ticket / 草案身份；首次身份按既有命名规则生成 | 同名冲突、版本历史不明确时阻断 |
| `lifecycle_refs.*` | checkpoint / Ticket 的已登记引用，按 `lifecycle_ref_by_readiness` 映射 | 缺少适用资产，指出具体类型、引用与补齐责任 |
| `resolution.architecture_identity` / `architecture_evidence` | 已登记工程基线、仓库登记和 Manifest；复用架构一致性校验 | 架构冲突不能择一覆盖，不重新推荐既有工程架构 |
| `resolution.technical_design`、前端 delivery 绑定 | 读取已批准的设计和联合接收引用，保留 ref / version / 原字节 digest | 上游未批准、已过期或不覆盖本切片时阻断 |
| impact、Recipe、capability、conditions | 采用已有明确影响结论，依据 `impact_to_capabilities`、架构 Profile 和 Registry 推导 | 不从文件扩展名、目录或 Skill 名猜业务影响；模糊处待确认 |
| `resolution.*` 的 Skill 及原因链 | 原编译器一次计算；重复引用从此结果复制，保留所有原因 | 工作单元主 Skill 依据任务行为选择，不能把闭包第一项当主 Skill |
| `common.project_roots` / 路径策略 | 仓库登记的真实项目根和 scope | 未登记的路径不能由本地目录存在推定获准 |
| `common.allowed_write_paths` | 取明确的切片实施授权范围并验证受登记边界约束 | 仓库登记上限不自动成为整份切片授权；范围扩大回到既有决定流程 |
| frontend / backend 及工作单元路径 | 从已确认的任务映射提取，分别核验满足整体、子合同和任务限制 | 保留各层字段；不取并集扩大权限，不按字符串前缀误判子目录 |
| `quality_baseline_ref`、验证命令、禁用模式、回退触发器 | 引用当前基线；合并适用工程和编译器要求，保留命令的工作目录 / 仓库上下文 | 已有字段无法无歧义表达执行位置时阻断，不能静默在错误仓库执行 |
| `contract.*`、`cross_repo.*` | 冻结 API / 无影响记录、仓库登记与已确认交付、回滚顺序 | 缺 API 测试或跨仓回滚依据时补原资产，不生成默认空项 |
| 验收、测试 seam、工作单元行为与证据 | 从 Ticket 的验收标准和 Spec 规则定位到现有 `work_units`、测试 seam、预期证据及契约测试字段 | 验收到任务 / 测试 / 证据的覆盖由 Agent 整理、专业审查核验；未知不判已覆盖 |
| 风险、例外、不适用 | 沿用上游明确结论并检查适用性 | 只补本切片新增项，未决项不得自动写为 not-applicable |

完整交付与非目标、验收正文仍在已确认 Spec / Ticket 中。schema 没有对应直接字段时，不新增平行正文；用已有 `lifecycle_refs` 定位，视图读取原文并绑定该文件摘要，自动报告记录所选规则和覆盖关系。

### 3.3 来源、冲突与缺口

结构化来源使用精确属性定位；Markdown 使用标题、稳定规则 ID / 验收 ID及对应原文范围。源文件没有稳定 ID 时，使用文件原字节摘要加标题 / 行区间定位，不在本任务自动改写上游。标题重复、引用不唯一、同一验收无法区分时输出歧义，Agent 依据原文补充选择。

Agent 整理的业务语义只作为草案，不把文本抽取成功当作批准。每个自动填充字段可追溯到 `target_path → source_ref + raw_digest + locator + rule`。report 由程序生成，用户无需维护该映射表。

同义事实多源值不一致时输出 `conflict`，列出双方值与来源；不采用“最后一个覆盖”。整体允许路径与工作单元允许路径属于不同语义，核验包含关系，不机械去重。仅集合语义已由原规则定义的 Skill 等字段可以去重；保留数组顺序、重复验收项与顺序敏感的交付 / 回滚内容。

缺口至少给出目标字段、所需来源、当前引用、原因、受影响工作单元和恢复动作。影响不能确定时扩大阻断至整份草案。未登记责任人显示“未登记”，不虚构人员。

## 4. 两种只读视图

建议在 `scripts/lib/slice-contract-views.mjs` 实现投影与差异函数，消费完整合同和本次验证过的来源快照。该路径为实施建议，尚未创建。Markdown 用于聊天 / 人工阅读，结构化结果用于 Agent；它们是同一次投影的两种序列化，不分别维护内容。

视图头统一显示：权威合同 ref、ID、版本、**原字节摘要**、生成时间、当前状态、检查范围与结果。由上游补充的内容额外绑定每个来源的版本（有则保留）及原字节摘要。将 `view_kind`、生成器版本和 `read_only: true` 放在输出包，不加到权威合同 schema。

| 视图 | 默认展示 | 必须可展开的内容 |
|---|---|---|
| 人工审阅 | 本切片交付、非目标、逐项验收、重要约束与风险、本次实质变化、所有待决定和阻断事项 | 对应原文、适用完整子合同、每项差异依据、全部来源和校验结果 |
| 工作单元 | 当前行为、仓库 / cwd、整体与任务写边界、适用全局约束、主辅 Skill、所需上游引用、验证命令、完成证据、停止条件 | 完整 common、适用子合同、原始 work unit、跨仓依赖及回滚要求、所有未能分类约束 |

工作单元视图按任务 ID 选择，不默认挑第一项。同名、找不到、版本不匹配均报错。停止条件从原规则生成，至少覆盖越界、缺证据、未执行验证、上游变更、drift / violation / new_impacts 和任务状态不可执行。

所有适用全局约束对执行 Agent 可见。分组折叠可以减少阅读，但不能只给摘要后要求 Agent 凭记忆执行。未知字段放入“其他完整约束”，不能静默丢弃；如无法判定其执行影响，该视图保持仅供查看，不输出执行就绪结论。

旧合同允许生成只读视图，缺字段如实显示“源合同未提供”。不先迁移或补字段才允许查看。未做批准校验的查看标为“批准有效性未核验”，草案视图标为“草案，不授予执行权限”。执行入口仍读取权威 YAML，并通过当前 `createApprovedExecutionContext` 核验；不可反向导入视图来执行或批准。

## 5. 差异展示与批准绑定

差异报告绑定旧 / 新合同 ID、版本、ref、原字节摘要，以及双方上游来源快照。不能只比较 YAML 文件：同一引用路径下的验收、基线或批准证据变化也必须报告。缺少旧来源快照时明确标为“上游差异无法证明”，按未知影响处理。

| 分类 | 判定方法 | 展示及后续检查 |
|---|---|---|
| 格式变化 | 严格 YAML 解析成功、类型及数值含义一致，仅注释 / 空白 / 已明确无序的映射顺序变化 | 展示字节已变和语义未变的比较依据；原批准仍按原字节校验，不能沿用旧 digest |
| 实现细化 | 仅处于已登记的细化范围，且专业审查能证明不改变目标、授权、验收、契约、质量、风险和外部承诺 | 展示前后值、受影响任务和需补验证；程序只给分类候选，不自动认定批准可延续 |
| 影响决定的变化 | 路径 / 仓库、API、数据或状态行为、验收、质量、风险、回滚、验证命令、Skill / seam、审批条件等变化，或影响不明 | 列出受影响批准、工作单元与原规则中的回退方向；按现有用户决定协议处理 |

先比较原字节，再做严格结构比较，再关联依赖影响。重复 YAML key、不可支持的 tag / alias、数值解析可能丢精度等情况，不允许宣称格式等价。数组顺序默认有意义；不使用全量排序消除交付顺序等差异。新字段或无法分类的删除默认属于影响未知，不被显示过滤器隐藏。

报告保留每项 `path / before / after / category / affected_scope / required_checks / decision_impact / evidence`，并聚合全部阻断与待决定事项。文本自然语言是否等价由独立专业审查裁决，不能用摘要相似度自动批准。即使仅 `compiled_at` 变化，仍展示原字节变化对批准绑定的影响。

本方案不修改 `verifySliceContractApproval` 的摘要算法，不把 `digestDocument` 的规范化摘要替代批准用原字节摘要。已有授权延续流程可以消费报告，但其检查不能被差异分类或缓存绕过。

## 6. 检查复用后置，首批只复用可证明的纯计算

A、B 两批不依赖检查缓存，分别交付收益。C 批先覆盖同一进程中重复请求的 Skill 依赖闭包与静态规则计算；只有从现有函数中明确分离出无文件副作用、无批准判断的纯函数后才启用。当前 `compileImplementationContract` 包含工程、设计和前端输入校验，不能整体 memoize。

首版不建立跨进程磁盘缓存，不复用测试执行、构建、Git 工作区检查、外部服务检查、专业审查或用户批准；它们继续按现有验证要求执行。这样减少能够明确归因的重复计算，并避免把暂时无法穷举的环境依赖纳入缓存。

复用必须同时满足：

- 当前合同原字节、所有已声明输入原字节和身份 / 版本未变；依赖集合也未变，缺失来源不能视为相同。
- Registry、编译规则、被调用纯函数及其传递依赖代码 / vendored parser 摘要未变；不能仅以 package version 或 HEAD 代表工具版本。
- 当前进程的 Node 版本、执行平台、运行选项、适用配置与显式环境依赖相同；依赖未声明或无法取指纹时不复用。
- 结果由当前进程实际计算并保存，未失败、未被取消或撤销，绑定摘要一致；不接受调用者传入“之前通过”的 JSON。
- 输出前重新核对来源，读取期间变化则放弃复用；结果注明 `computed` / `reused` 及原计算依据和时间，不伪造新的执行时间。

进程结束即失效。环境、工具、校验器变化或影响未知时执行完整适用检查；已证明的输入变化按依赖图重算受影响纯计算，但受影响验证依旧需要执行。合同字节有变化时，前一合同的复用结果不能为新合同放行。

交付、合并和发布边界始终禁用本复用路径并保留 Fresh Verification。首版收益不足时先据实记录，不扩展缓存来追求预设提速比例。

## 7. 分批实施及改动清单

| 批次 | 可独立交付的结果 | 主要改动位置 | 退出条件 |
|---|---|---|---|
| A：输入填充 | 从同一典型切片上游生成完整草稿和具体缺口报告 | `scripts/lib/implementation-contract-compiler.mjs`；必要的内部取数 helper；compiler Skill 正文 / references；编译器 tests | 映射、冲突、缺失、禁止覆盖通过；原函数兼容；人工只补新增细化 / 例外 |

| C：限定复用 | 同一依赖快照下减少重复纯计算，变化即重新计算 | 编译器内部纯函数分离与调用期 memo；tests | 依赖失效反例通过；批准、交付预检与 Fresh Verification 全部保留 |

不改 Slice schema，不改技术设计、脚手架、审批和交付合同结构；不在本试点顺手整理现有模板中的其他字段差异。`approved-execution-context.mjs`、`delivery-preflight.mjs` 作为兼容回归边界，原则上不改授权语义；若实施证明需要改动，先重新评估影响。

## 8. 典型切片与验收基线

机制验证选一个已有工程 `layered-mvc` 后端窄切片，覆盖冻结 API、既有技术设计、仓库登记、工程基线、一个实现任务和独立验证任务。所有输入、验收和人工补充固定后，分别运行优化前和优化后流程。现有 `approvedFixture` 仅是合成机制测试，合同字段不完整且没有真实业务批准，不得直接拿它证明真实效率收益；需补足完整 fixture 后用于自动化反例。

真实试点的项目、Ticket 与批准合同尚未指定，留待实施时从已授权项目选取。此缺口不阻断工具设计和合成测试，但阻止宣称实际准备耗时已改善。没有真实切片时明确报告“机制验证完成，真实效率数据待采集”。

| 指标 | 计量口径 |
|---|---|
| 人工补充项 | 区分真实业务决定、切片新增细化、重复抄录；按唯一字段 / 决定项计数，不把机器默认值当作节省 |
| Agent 重复读取 | 分别记录相同文件摘要的物理读取次数、重复进入 Agent 上下文的字节数、必需新鲜性核验读取；缓存读取与阅读成本分开 |
| Agent 重复填写 | 相同来源事实向多个合同位置手工整理的次数；机器派生复制单独统计 |
| 准备耗时 | 从固定输入具备可读条件开始，到完整草稿具备交审条件、再到实际获准执行分别计时；用户等待和执行计算时间分列 |
| 完整性 | 每条验收对应行为 / 测试 / 证据，所有适用路径、API、回滚和停止条件均可定位 |

同一原始输入、工具版本和测量环境比较；计时顺序与是否使用热缓存要记录，避免把熟悉材料或人工等待差异当作优化收益。不预设提速百分比。A / B 可以在 C 未实施时验收，不能为了缓存拖延前两批交付。

### 必测反例与预期

| 场景 | 预期结果 |
|---|---|
| 工作单元新增未授权写路径；`src/a` 与 `src/ab` 混淆；路径穿越 / symlink 越界 | 阻断，不能通过合并路径数组扩大写权限 |
| 漏掉一个 Ticket 验收、失败场景或 API 契约测试 | 覆盖报告指出具体缺口，不标为就绪 |
| Spec、Ticket、登记 / Manifest 存在同义冲突 | 列出双方定位，阻断相关任务；不按优先级覆盖 |
| 仅 YAML 注释或空白变化 | 可以标格式变化，原批准摘要校验仍拒绝旧绑定 |
| 数组顺序、数值类型、大整数、未知字段变化 | 不得误判为格式等价；未知影响进入扩大检查 |
| 合同字节未变，上游文件内容或批准证据变化 | 视图标过期，差异报告体现依据变化，执行重新校验 |
| 生成 / 查看期间输入被替换 | 输出前检测，丢弃当前结果并重试或报阻断 |
| 只提供 approved 状态、伪造 view / cache / context | 不能获得执行上下文，原批准入口继续拒绝 |
| 新旧视图混用或选择另一任务 ID | 拒绝，重新从对应权威合同投影 |
| 旧合同缺新增规则所需信息 | 可以只读展示缺口；不能自动迁移、补批准或执行 |
| 工具 / parser / 环境改变，证据过期，依赖新增或未知 | 不复用；按影响扩大验证，必要时完整适用检查 |
| 缓存损坏、失败结果、外部导入“已通过”结果 | 拒绝复用并重新计算；不得转成通过 |
| 交付 / 合并 / 发布边界遇到缓存命中 | 仍执行 Fresh Verification，不以命中省略 |

## 9. 验证、审查和回滚

后续实施时在现有 compiler tests 和 `scripts/fixtures/delivery-preflight/approved-execution.test.mjs` 扩展上述关键反例；保留 DDD / MVC、前端、已有工程和跨仓消费的兼容检查。新模块不能只在编译器六个基础测试通过后就宣布执行约束完整。
