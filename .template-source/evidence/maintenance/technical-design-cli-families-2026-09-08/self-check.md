# 四家族技术设计升级维护者自检

本轮按用户已确认的影响面升级研发、后端、前端及战略设计 CLI，并提交/推送 GitHub；不发布 npm。维护强度 L3，采用 maintaining-skills 的维护者自检与本轮 Fresh Verification。各源模板身份均为 template-source；产品 Spec、原型、OpenAPI、业务实现与 context_reconciliation 为 not-applicable：本轮只维护模板治理和 CLI 分发，不推进具体产品阶段。

研发与后端同步 yss-technical-design / yss-mvc-design，保留 DDD 专家和旧 v1 合同的显式只读兼容。设计前绑定用户确认的架构；已有工程沿用登记。新流程采用 technical-design 稳定 ID，旧 DDD 工作单元/阶段/门禁 ID 明确退役、不复用，历史资产不自动迁移批准。旧 DDD 产物与评审证据 ID 仍保留原义。

战略设计只更新下游交接入口与协议，前端只接收交接、持有前端工程设计。共享同步脚本保留专职模板自己的执行范围校验，后端继续使用 wire 校验器，不恢复被排除的原型技能。

战略 CLI 原先没有已有项目同步入口；为满足已确认的原地更新范围，新增默认只预览的 sync 与显式 --apply。仅更新未被修改的治理文件；冲突整次拒绝，业务/词汇/批准资产保留，写入失败回滚。已初始化实例的 templateName 必须按实际模板身份核验。附加测试覆盖异族、路径穿越、符号链接、局部失败回滚和幂等。

实际旧实例测试发现前后端公共核心在模板与用户同时修改 CONTEXT.md 时产生冲突。核心 0.1.1 将已有词汇表作为保留项，缺失才初始化，--force 也不能覆盖；业务语义变更继续由项目自己的对账负责。其他治理文件继续三方冲突与事务规则。

源模板先通过各自完整 scripts/verify-template，再提交并推送。CLI 固定对应模板 commit；前后端固定公共核心来源 commit。检查实际 tgz 与本轮源码一致，使用旧版实际包创建实例，再用新版包验证预览零写入、升级、业务文件/词汇表/架构登记/批准记录保留；另验证新实例和新旧战略交接包便携导入及幂等。

研发 CLI 初始未提交改动仅为 template.snapshot.json 的 working-tree 标记和生成时间，原字节保留于 /tmp/yss-dev-snapshot-before-technical-design.json。没有丢弃模板能力差异；新快照绑定已发布的固定源提交。

回滚顺序：必要时先回退 CLI 到交付记录中的 before 提交，再回退主模板 gitlinks 与锁；历史实例不自动降级，使用同步备份或项目 Git 恢复受管资产。源模板旧 commit 保留。GitHub 推送只更新本轮授权仓库的 main，未强推、未创建 npm 发布或部署。

可执行证据及实际提交见同目录 github-delivery.json、checkpoint.yaml 和验证日志。模板 Profile 的既有 draft 状态与产品批准门禁保持原样；模板分发验证不宣称真实业务切片已投产。

复盘：共享脚本同步不能抹掉专职执行限制和 wire 适配；跨仓源提交更新时必须同步上游来源锁。主模板已补齐这两处规则及核心回归门禁。前端旧包初始化首次因 240 秒测试时限中止，仅清理临时测试目录后以 600 秒时限重跑；最终完整初始化、升级与文件保留验证通过。研发包最后一次重打包仅更新 README 版本/固定提交说明，代码、模板与已测包一致，并重新执行包内源码逐字节核对。
