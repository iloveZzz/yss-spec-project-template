## Executive Read

**需要增强，优先增强 Spec 的可验证性和 Plan → Spec 的事实连接；保留已有阶段、聚合批准、摘要绑定与按影响面裁剪。** 当前机制的强项是防止无状态流转、过期引用、未决阻塞和未确认规则进入下游。增强点集中在模板如何引导作者把需求、验收、指标和来源写得可检查，而不是继续增加文档或审批。

最优先的三个改动是：① Spec 中需求来源和验收引用显式化；② 把 NFR 正文要求落实为可填写的字段；③ 在现有审查内加入内容完整性检查，机器检查确定性缺陷，独立审查判断业务语义。成功标准、异常场景和差异传播作为第二批。以下均是候选建议，尚无实际团队效果测量。

## Findings

### 1. Plan 的控制骨架应保留；正文质量检查需要补强（claim-001）

观察：注册表要求 goals、scope_and_priority、boundaries_and_rules、open_questions、handoff、context_reconciliation、grill_exit 七项检查。入口实现核验检查状态、依据摘要、影响判断、未决项、Context 和用户决定。Plan 模板仅 62 行、2405 字节，已把领域与阶段决策作为引用，不复制正文。没有证据支持“Plan 本身过长”或“门禁应该拆掉”。

本轮运行：`node scripts/verify-plan-spec-entry-scenarios` 退出 0，2118 ms；`node scripts/verify-plan-requirements-context-scenarios` 退出 0，1220 ms。详见 checks.json。合成边界实验用仓库现有 fixture：正文只有“测试规划：小范围修订，不改变业务边界或关键规则。”，七项检查声明都引用该正文，结构校验返回 allowed（quality-probe.json）。这是工具职责边界，不是业务事实已正确，也不是批准漏洞的实证；合成批准绝不可用于真实项目。

建议：复用现有 Plan 审阅包，在 goals / scope / grill_exit 的 evidence_refs 中增加可定位到正文条目或原始事实的定位信息。先做诊断输出，后由维护者决定哪些确定性缺陷进入阻断。独立审查仍判断问题是否真实、取舍是否合理，不能让 LLM 自评分承担批准。

### 2. Plan 成功标准应从“信号”细化为可核验的测量定义（claim-002）

观察：Plan 已要求成功标准、验证方式、事实证据和成功信号；阶段决策 v3 已要求带稳定 ID、来源 ID 和证据的成功标准。因此建议不是新增另一份成功指标合同。默认 Plan 没有显式展示基线、统计口径、观测窗口或数据可得性。

建议：在已拥有成功标准的权威资产内按需补“指标定义/口径、当前基线或未知及补齐动作、候选目标或已确认目标、观测窗口、数据来源、确认状态”。Plan 仅引用并展示当前决定需要的摘要。优先用用户任务完成和结果指标，技术性能在 Spec NFR 细化。GOV.UK 强调从项目开始规划测量；借鉴测量方法，不照搬公共服务 KPI 或对外公布义务。[GOV.UK 测量指导](https://www.gov.uk/service-manual/measuring-success/using-data-to-improve-your-service-an-introduction)

假设：该增强可能减少“已交付功能但无法判断有没有解决问题”的返工；尚未测量。未知目标保持待确认，不能由 Agent 编造阈值。

### 3. Spec 应显式连接上游来源、需求和验收（claim-003）

观察：Spec FR 表只有 ID、需求、优先级、备注；正文要求关联验收，但没有默认 AC ID 或 source_refs 列。战略交接已强制 rule.* / scenario.*，并检查悬空引用与未覆盖规则；Slice 已检查验收→验证→工作单元覆盖。因此不能将现状描述成“没有可追溯体系”。

建议：FR 保留现有 ID，补上游引用（Plan 已确认条目、rule.* / scenario.* 或其他合法证据来源）与 AC 引用；AC 采用稳定标识，绑定 FR/NFR、前置条件、触发、可观察结果与适用分类。只建连接，不复制上游规则正文或另造完整需求管理系统。已有来源体系未覆盖的需求应能说明合法来源，不强制所有 NFR 都伪装成领域规则。

候选链：`当前批准来源 → FR/NFR → AC → 已有 Slice acceptance → verification/evidence`。先检查重复 ID、悬空引用、无验收需求和无来源验收；业务必要性仍由人审。NASA 与 SEBoK 支持需求理由、基线与双向追溯，但没有要求 YSS 使用某种新文件格式。[NASA 需求定义](https://www.nasa.gov/reference/4-2-technical-requirements-definition/)、[SEBoK 需求管理](https://sebokwiki.org/wiki/Requirements_Management)

### 4. NFR 模板字段应与现有正文要求一致（claim-004）

观察：Spec 已要求工作负载/适用条件、目标值及单位、验证方式与依据，但表格只有类别、需求、目标。作者容易将其写成“高性能、稳定可靠”，或把验证细节挤进备注。

建议：按命中项记录 `NFR ID、适用条件/工作负载、测量指标与单位、目标及确认态、验证方法、依据引用`。延迟只有在适用时选择分位数、统计窗口和负载；恢复指标只有可靠性影响命中时登记。采样环境、观测工具与实际命令在后续工程验证中确定，不在 Plan 提前固定技术实现。不可测的必要约束可用检查、分析或演示验证，不把所有 NFR 硬改成数值。

验收：已确认 NFR 应有合法验证方法；单位与指标缺失返回明确诊断；未知目标连到有负责人与时点的未决项。NASA 的清晰、单义、必要性、可验证性检查可作为审查依据。[NASA 需求检查表](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)

### 5. 场景增强应沿规则组织，按影响面覆盖失败和恢复（claim-005）

观察：Spec 已要求成功、拒绝、边界和恢复；默认只给一个 Given/When/Then 文本片段。战略场景已有成功/失败路径，不应重复建立全局状态矩阵。

建议：用一个规则关联若干有区分能力的例子，明确哪类适用、哪类不适用及原因。状态变化时补起止状态、重复操作和恢复；异步影响时补超时、失败后的可见结果；多方协作时补竞争或重复请求，但均不得无条件成为所有功能必填。规则说明一般成立条件，例子验证具体情况，例子数量不是完整性证明。

Cucumber 的 Rule / Scenario 与 Example Mapping 分离规则、例子和问题，适合当前 Spec 审查；可直接用中文场景表，不强制安装 Cucumber。当前 Markdown 中 Gherkin 片段本身不等于可执行测试，自动化还需语言设置、Feature/Scenario 结构及 step definitions。[Gherkin](https://cucumber.io/docs/gherkin/reference/)、[Example Mapping](https://cucumber.io/docs/bdd/example-mapping/)

### 6. 审查模板的技术示例应防止被误读为全局门禁（claim-006）

观察：Spec 默认列支付逻辑、原生 SQL、公共基础库 API，均填“需要人工审查：是”。裁剪规范明确 SQL 等技术载体不自动升级为安全专项，人工暂停由决定变化触发。二者并不必然冲突，但孤立复制表格可能扩大适用范围。

建议：把默认行标为示例，实际行记录“受影响规则/资产、触发依据、独立专业检查、是否命中真实用户决定及引用”。审查和用户决定分开表达，仍消费现有 gate_policy。禁止以此变更豁免项目外部制度、重要风险或适用强制门禁。需用“普通查询、授权变化、支付风险、外部强制审批”四类 fixture 验证路由一致性。

### 7. 变更传播应连接需求条目，并复用现有失效机制（claim-007）

观察：Spec Delta 已有 ADDED/MODIFIED/REMOVED 与验收验证映射；战略消费校验已根据 source_id、digest 和依赖阻断下游，Spec 整体摘要变化目前也可导致整体 stale。没有证据支持重新造一套变更状态机。

建议：Delta 引用当前冻结基线与稳定 FR/NFR/AC ID，展示改变、保留、删除及受影响消费者，生成覆盖差异作为诊断。只有依赖图能证明局部完整时考虑细化失效范围；未知影响继续保守阻断，不能仅凭行级 diff 或模型等价判断复用批准。高风险 Delta 保持现有适用范围，不要求所有小改动都生成它。

### 8. 采用前应做语义质量与成本的配对验证（claim-008）

观察：本轮证据证明结构与场景检查的行为，不证明实际需求遗漏率、人工耗时或模型成本收益。模板体积小，不能把增加字段天然称为提效。历史效率研究仅用于检索线索，未引用旧数字作为本轮效果。

建议：先在仓库外合成 fixture 验证，再在另获授权的真实任务上对比。至少覆盖新功能、中等变更、无 API、状态变化、已有冻结基线、仅非关键延期等类型。相同输入、模型、预算和批准边界，记录必须保留规则的遗漏数、未知内容被补造次数、悬空链接、返工次数、用户确认轮数、阅读字节/token、实际耗时。禁止预先承诺“提效30%”。结构 lint 通过与语义审查通过分别报告。

## Counter-Signals

1. 现有阶段决策、战略交接和 Slice 已有稳定 ID 与覆盖检查，抵消“从零新增追溯系统”的建议。
2. Plan 模板 62 行，Spec 模板 115 行；文件长度不支持“模板正文太长是首要瓶颈”。审批材料、跨资产成本尚未测量。
3. 入口文档已明确结构校验不证明业务事实；短正文实验复现的是已声明边界，不能直接报告成缺陷逃逸。
4. 不同影响面可记录有原因的 N/A；全量字段与场景强制填写会违反裁剪原则并增负担。
5. NASA 系统工程方法、政府公共服务指标与 YSS 场景不同；只采纳需求质量和测量思路，不迁入组织制度。
6. 已有摘要失效机制偏保守可以保护批准有效性。条目级优化需证明依赖完整，局部放行不是本轮结论。
