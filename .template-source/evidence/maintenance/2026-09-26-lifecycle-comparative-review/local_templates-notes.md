## 发现与建议

### LT-01：阶段分工和按影响裁剪应保留（合理部分）

**事实。** Plan 模板要求战略事实只引用，不复制第二套正文（`plan-template.md:23-36`）；Spec 按影响覆盖行为和测试（`spec-template.md:28-99`）；Technical Design 明确 MVC 不要求战略 DDD、聚合或 Gateway，并支持不触及业务模型的显式 `engineering-only`（`yss-technical-design/SKILL.md:20-39`）；原型 Skill 区分产品设计影响和孤立视觉修复，H1/H2 采用当前决策需要的最低档位（`yss-prototype-stage/SKILL.md:20-25`）。

**判断。** 未发现必须整体推翻阶段顺序、另加快速状态机或强制 DDD 的依据。优化重点应是让这些条件更容易执行。

**反证/边界。** 这证明合同具备裁剪路径，不证明 Agent 在真实项目中每次都正确裁剪。应以代表性实例测量误路由和不必要追问，不能仅看技能文字。

### LT-02：09-25 的具体缺陷已在当前工作树修复（合理部分）

**事实。** 原型路由已使用 `work-unit.prototype-design-v2` 和 Evidence v4（编排合同 358-375）；原型评审/确认产物的 trigger 已使用当前检查/门禁（注册表 268-275）；L3 已改成维护者自检和 Fresh Verification（注册表 372-383）；Ticket 后端规则已按 DDD/MVC 区分（Ticket 73-77）；阶段决策用户决定路径已有效（`yss-stage-decision/SKILL.md:39`）。Plan 入口已提供只输出候选的 `prepare/diff`（`entry-review.md:5`）。

**判断。** 不能再次提出“补 prepare/diff”“修 DDD 强加”“原型仍用 v3”作为当前未解决缺陷。

**反证/边界。** 当前代码/文档存在这些修复，不等于正式版本已分发，更不证明所有外部 CLI 消费者已发布验证。

### LT-03：两处说明仍无条件要求“两个 Reviewer”（明确文档缺陷，建议优先处理）

**事实。** `references/state-model.md:74` 与 `references/orchestration.md:81` 均写两个 Reviewer 消费同一快照；权威编排合同 1219-1221 则规定默认一个推进负责人、一个独立 Reviewer，仅专业能力缺口、冲突或外部制度才增员；`orchestration.md:82-83` 同时允许普通变更由同一独立执行者完成审查与验证。

**影响推断。** 主控按需读取这两段时可能误派第二个 Reviewer，造成额外会签；当前没有实际误派轨迹，不能宣称已发生。

**建议。** 说明改成“所有参与审查的执行者消费同一候选”，人数和分离条件只引用权威策略；增加策略与说明一致性的定向检查。

### LT-04：根入口和配套 Skill 存在两层版本合同漂移（明确文档缺陷，建议优先处理）

**事实。** 根 `AGENTS.md:63` 要求脚手架 schema v3 已批准才能运行，但编译器 Skill 52 行、新 MVC Skill 14/72 行、新 DDD Skill 77 行都要求新生成使用统一 Project Scaffold Contract schema v4；MVC 72 行明确历史 v2/v3 不用于新生成。这是顶层硬门禁和执行入口的直接版本冲突，应先于一般说明润色处理。

此外，`orchestration.md:46,48`、编译器 Skill 52 行、MVC Skill 14 行、DDD Skill 77 行均写新脚手架必须绑定 API Contract Decision v1；`contract-reading.md:29-38` 明确 API 决定新结构使用 v2、保留 v1 兼容。当前 API 校验器按 `schema_version===2` 选择 v2 schema（`scripts/lib/api-contract-decision.mjs:28-35`），准备器生成 v2 草案（63-77）。Project Scaffold schema v4 与 API Decision schema v2 是两个独立版本，不应混写成一次升级。

**判断。** 这些是当前阅读与派发合同未同步；不等于“API v1 已不支持”，也没有证据证明当前生成器拒绝 API v2。本次没有进行新生成尝试，不宣称已发生实际失败。

**建议。** 首先对齐根入口的脚手架版本，再修正配套 Skill 和流程说明中的无条件 API v1 约束；当前新建格式与历史兼容从同一权威来源引用，并加入入口/派发说明/准备器/消费者的一致性检查。

### LT-05：Plan→Spec 的 continuation 机制比阅读说明完整（说明缺口/操作风险）

**事实。** `entry-review.md:11` 只列 `plan_user_decision_ref`，23-25 行将摘要变化表述为重新展示并取得当前确认；实际 `scripts/lib/plan-spec-entry.mjs:75` 也向用户决定校验器传递 `plan_continuation_ref`。编排合同 1207、1218、1224 允许通过独立等价证据复验已有范围授权，并只使受影响依赖/授权变化失效。

**影响推断。** 阅读入口可能让执行者漏用已有授权延续而重复提问。不能把所有摘要变化视为语义等价，也不能自动复用旧批准。

**建议。** 在入口说明补充二选一的用户决定/延续字段和一个“机械变化可验证延续、实质变化须新决定”的对照案例，继续由现有校验器裁决。

### LT-06：产品总体设计仍有重复填写的诱因（优化假设）

**事实。** Plan 已写用户、MVP、非目标、成功标准（Plan 14-21、38-41）；产品总体设计又给出同组空白字段（`product-overview-design-template.md:23-29`）。总体设计的页面地图（75-79）与交互说明的页面地图（19-23）列内容近似。共同写作规范已要求引用上游、仅写本阶段新增细化（`document-writing.md:41-45`）。

**判断。** 重复栏目存在，但不能由此推断实际反复手填或变慢：总体设计和交互阶段的粒度可以不同，共用规范也允许引用。

**建议。** 为这些栏目增加“上游引用/沿用内容/本阶段新增或变化”提示或派生视图；先试一个案例，测量重复输入、漂移修复和读者理解，再决定是否合并栏目。不得简单删除必要行为细化。

### LT-07：Fresh Verification 模板对可复验证据的提示偏弱（风险/模板优化）

**事实。** `verification-record-template.md:24-28` 的命令表只给时间、命令、pass/fail/skipped、备注；49-53 行直接给 Approved/Blocked 和可合并/可发布字段。候选身份、执行 cwd、退出码和机器日志没有专门位置。审查输入合同仍明确绑定候选摘要和合同（编排合同 700-718），发布要求独立审查、全部适用门禁及回滚证据（997-1006）；交付验收也明确不授予合并或发布权限（注册表 210-218）。

**判断。** 模板本身不是漏洞，但只按此模板填写的人容易只记一个 pass，后续再补证。现有门禁可能阻断不足记录，本次未测试绕过，不能报告为已证实的放行漏洞。

**建议。** 将候选/合同/实际运行日志作为引用，机器采集 command/cwd/exit_code/time；将“证据支持的就绪结论”与“外部动作授权”分开提示，继续复用现有批准和结果记录。

### LT-08：发布和复盘模板尚不足以引导治理闭环（优化空间）

**事实。** 发布说明目前仅变更、迁移、验证三个标题（`release-note-template.md:8-14`）；复盘仅做得好、改进、动作、沉淀去向（`retro-report-template.md:8-16`）。权威工作单元要求发布窗口/回滚点输入、发布或回滚证据、人工裁决和治理回流（注册表 480-485）；编排合同要求 `governance_reflow_decision`（997-1000）。

**建议。** 发布模板加入既有候选/版本、授权记录、观察信号与回滚引用；复盘补“事件/失效机制 → 改进行动 → owner/验收/期限 → SSOT 修订引用”。这些属于引导字段，不新增门禁和状态文件。

**反证/边界。** 简模板允许按上下文自由填写，合同仍强制要求相应证据；不能仅因为标题少就断言实际项目没有回滚或复盘。

### LT-09：恢复和机器字段生成已形成可用路径（合理部分）

**事实。** stage-tracking 将 checkpoint 作为唯一机器状态源，摘要变化只让受影响项回到待核查，无依赖工作可继续（`stage-tracking.md:11-28`）；check/plan 只读，apply 复验、备份、处理并发冲突并支持幂等（30-43）。合同视图区分 review/task/full，已有 Slice 与 API 准备器自动生成机器摘要，视图不授予批准（`contract-reading.md:3-10,25-38`）。设计模板也已提供场景例子，并把状态矩阵作为唯一轻量状态机（`state-matrix-template.md:3-5`）。

**建议。** 沿现有命令增加跨阶段操作示例和帮助入口，不应再建一套状态或要求人工抄写摘要。工具存在与用户实际找到它是两件事，后者需观察真实使用。

### LT-10：当前试点证明机制样本，尚不能证明真实项目吞吐改善（已知证据边界）

**事实。** 分诊报告明确 14 个合成场景、零工具调用、脱敏真实案例 0，模式错误从 2/14 到 0/14（`triage-replay-report.md:5-8,31-38`）；跨仓试点使用 test-data-only 批准，简化 Java/Vue 样板，未证明真实 Spring 平台/部署/浏览器视觉/正式 Slice 批准；还保留前端 Harness 通用测试缺夹具的分发待办（`cross-repo-pilot-report.md:5,16,29`）。

**建议。** 下一轮选真实已有项目的窄切片，观察从目标澄清到交付的人工干预次数、错误拒收/漏拒收、恢复动作、回填次数及实际时间。先记录基线再比较，不把此次合成改善外推成百分比效率收益。分发待办另按当前实际消费者复核。
