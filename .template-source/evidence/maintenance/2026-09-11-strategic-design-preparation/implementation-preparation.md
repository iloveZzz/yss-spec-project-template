## 工作包 A：状态与编排一致性（问题 1）

主要范围：战略模板 AGENTS.md、docs/agents/issue-tracker.md、docs/process/harness-process-tailoring.md、checkpoint 示例、yss-strategic-design 的状态/执行引用，以及 yss-stage-decision 的主控绑定。

执行顺序：列出主控和 tracker 消费点 → 使用现有 ticket_sync.status/refs 整理新记录 → 明确历史 parent_ticket 解析边界 → 补 profile 语义核验 → 同步共享 Skill 的本体薄适配。

验收：新建、恢复、显式 to-tickets 和交接均不生成禁止的父 Ticket/垂直切片；业务 Ticket 不进入 ready-for-agent；错误 profile 主控绑定被发现；本体原有父 Ticket 路径不回退。map.md 与 checkpoint 不一致时以 checkpoint 为权威重新生成导航；源引用本身冲突时阻断。

## 工作包 B：用户决定校验（问题 2）

主要范围：战略角色表、会签/工作单元/恢复校验、Plan 与原型调用点、交接验证；复用本体用户决定协议，不复制本体工程门禁 ID。

保留已存在的 Plan → Spec 审阅确认。Spec、产品设计及最终交接分别核验决定适用范围；通过确定性引用证明复用关系，不以文字相似推断授权。新增绑定应避免会签记录和用户请求相互包含摘要造成循环；用户决定绑定所展示的业务资产及依据，会签记录引用该决定。

验收：无回复、数字人代答、错误负责人/范围、摘要漂移和撤销均不能作为当前批准；当前有效回复可复用；无关资产变化不扩大失效；历史批准不会自动变成符合新策略的批准。测试既覆盖单函数，也覆盖恢复和交接的真实入口。

## 工作包 C：决策证据与规则身份（问题 3、4）

主要范围：战略 yss-stage-decision 的两个 schema、合同、模板、校验器、迁移入口；本体集成清单及薄适配；共享交接工具和离线 schema 副本；实际命中的研发、后端、前端读取器。

v3 最小语义：关键决定有稳定身份、结论、负责人和依据；关键假设有验证方式、时点和影响对象；成功标准有可观察的判定方式，量化时才要求相应统计口径；重要约束注明来源与范围。证据关联研究包、包摘要和 claim 身份，负责人作出的取舍须作为决定来源表达，不伪装成研究事实。未知信息留在待确认项，按关键性决定阻断。

规则 ID 在确认时建立，场景显式关联规则、关键性及成功/失败结果；规则文字变更保留身份并更新业务版本/摘要，拆分、合并、退役不复用旧身份表达新含义。迁移不得依据序号或文本 hash 静默创造稳定业务身份。

实施顺序：整理 v2/v3 fixture 与消费者矩阵 → 增加明确版本分派和只读兼容 → 编写显式迁移草案能力 → 更新校验器 → 最后启用新资产默认生成。不得先生成 v3 再补消费者。

验收：缺失/重复 ID、悬空或不支持结论的证据、未审计关键 claim、错误责任区、遗漏关键失败场景、新旧 schema 混用均可发现；已批准旧包原范围消费保持原有严格度；新合同离线验包通过；旧工具对新合同拒绝；迁移不会伪造批准或覆盖源文件。

## 工作包 D：反馈案例（问题 5）

先用受控合成案例验证，不冒充真实用户项目：v1 战略包交给后端与前端 → 后端提出异常规则矛盾 → 战略方受理并裁决 → 修订或维持原决定 → 两个接收方分别承接。

逐项记录现有 Ticket、checkpoint、回执及影响报告能否表达来源包/规则、提出方、证据、战略责任人、处理结论、受影响资产和接收方状态。覆盖重复反馈、旧版反馈、拒绝修订、多个接收方进度不同及未裁决阻断。

结果分支：已有结构能闭环时只补引用、路由和案例；确定存在必要字段或路由缺口时提出最小差异。需要改变已确认权限、生命周期边界或新增不可兼容协议时回到澄清，不以本工作包为扩大授权依据。不得写回修改不可变旧包。

## 工作包 E：文档与分发（问题 6）

修正已确认的 CLI 版本/SHA/sync 说明漂移。战略维护强度文档与本体政策差异须先查明是否登记为有意适配；未解释的规则冲突不可当作普通文案自动覆盖。
