## Executive Read

**建议重构，并删除没有新增检查目标、有效证据或真实授权作用的会签步骤。保留能阻断过期输入、越权实施、缺证据和实际验证失败的控制。**

当前设计已经减负：默认一名推进负责人和一名独立审查者，候选职称不是全员签字名单，相邻检查可合并，模板日常维护不强制独立审查。继续机械地减少角色名称或把所有 `gate/check` 删除，收益依据不足，也会损失已有约束。（claim-001、claim-002）

更具体的问题有四处：固定职称限制阻碍合法合并审查；暂停说明可能把专业等待误变成人类询问；单条会签验证与完整生命周期验证的保障不一致；普通局部修复的复审口径不一致。本轮已复现第一项和第三项，另外两项是当前源码与文本事实，其实际频率和耗时尚未测量。（claim-003、claim-004、claim-005、claim-012）

现有项目数据不能证明多角色会签的整体收益或损耗。历史对照没有证明提效；外部研究说明多 Agent 的收益取决于任务可分性与预算。推荐逐项重构后，用同输入对照决定哪些审查点值得继续保留。（claim-007、claim-008、claim-009、claim-010、claim-011）

## Findings

### 1. 先分清登记对象、审查动作与真实停顿

当前根注册表的静态统计如下，实测来源为 [policy/stdout.log](intake/policy/stdout.log)。（claim-001）

| 对象 | 当前登记数量 | 不能据此推断什么 |
|---|---:|---|
| 阶段 | 8 | 每个任务都走完整八阶段 |
| 聚合门禁 | 7 | 每次需要七次人类回复 |
| 内部检查 | 14 | 每项都需要新 Agent 或审批 |
| 业务角色 | 6，主控另列 | 必须启动七个运行时实例 |
| 其他对象 | 30 产物、25 工作单元、23 证据类型 | 每个任务都生成全部文档 |

7 个聚合门禁中，3 个归 `dual_digital_human`、2 个归 `biological_human`、1 个由主控关闭、1 个是数字人交付验收。14 个检查中有 6 个自动检查、8 个专业审查。根表当前分类完整，没有未分类或重复对象。

**会签主体与用户决定是两个维度。** 用户决定政策横切覆盖 Plan、Spec、产品设计、架构平台、工程契约五个门禁，并覆盖实施范围和脚手架选择的工作单元消费点。数字人专业会签不能代替这些适用的原始回复或有效授权延续。多个工作单元消费同一决定也不能重复累加为多次人类停顿。

| 当前场景 | 已有政策允许的减负 | 应保留的边界 |
|---|---|---|
| 已授权模板日常维护 | L1/L2/L3 最低独立审查次数为 0；按需独立审查 | 分级实际验证、适用反例、发布前完整验证 |
| 既有工程 | 核验并复用登记架构和平台，不重复问 DDD/MVC、Boot | 真实工程基线与升级/迁移影响 |
| 已批准范围内细化 | 有效原回复或延续通过后，新增用户回复可为 0 | 当前资产审查、范围及摘要绑定 |
| 普通产品实现 | 默认一个独立审查者；小/中变更可同时执行审查和验证 | 审查者独立于实现者、实际验证结果 |
| 新模块、高风险、职责冲突 | 额外分工按触发条件决定 | Reviewer 与 Verifier 分离及专项闭包 |
| 新体验、新范围、新承诺 | 可把已经可审阅的独立事项集中展示 | 真实用户决定；不能预先批准未知资产 |
| 合并、推送、发布 | 复用已有明确动作授权 | 交付验收不隐含外部动作授权 |

这些都是政策能力，不是本轮测得的生产停顿次数。（claim-002）

### 2. 固定职称约束与合并审查目标存在可复现错配

角色表声明默认一个独立审查者、相邻检查一次审查逐项结论。但 `check.openapi-draft-reviewed` 仅接受前端工程师，`check.engineering-baseline-accepted` 仅接受测试工程师。两候选集合没有交集；`reviewBundleRows` 又要求所有行使用同一 `role_id/runtime_id/principal_ref`。（claim-003）

[补充探针日志](intake/assurance-bundle/stdout.log) 的五个用例分别证明：两条记录各自合法；同一 principal 在一个包里使用 FE/QA 两角色被拒；全部改为 QA 会被 API 角色限制拒；全部改为 FE 会被工程基线限制拒。

这证明**一个合法组合审查包无法覆盖这两项**。它没有证明必须启动两个不同 Agent：同一运行时可以写多条记录或多个包并切换职称。但这种替代增加记录摩擦，角色标签变化本身也没有证明新增专业能力。

建议以审查能力和覆盖目标选人：审查者需要哪些 API、客户端适配、测试、数据或架构能力；一个独立实例覆盖得了就一次审查，覆盖不了才增加专家。保留逐项结论和当前候选绑定，角色名称继续用于阅读、历史兼容和技能导航。不能只放宽 `role_id`，却丢掉能力约束与实现/审查分离。

### 3. 暂停说明存在误读风险，实际频率尚未测量

当前 `orchestration.md:109-117` 将数字人/生物人会签等待与“即将作出可合并、可发布或完成结论”都列为必须暂停，并固定要求“推荐答案、一个问题”。同文件 `:150-156` 又规定内部检查与正式门禁不同、交付验收可以由测试角色完成，阶段完成不请求发布权限。（claim-004）

推断：Agent 可能在可自行派发专业审查或已能执行 Fresh Verification 时，也向用户发起不必要的“是否继续”。本轮没有读取足够真实用户任务轨迹来估计该误读的发生率，不能直接说当前每次完成都会多问一次。

建议让暂停输出由阻塞原因决定：

- 等待专业结果：派发或等待已授权审查，主控继续无依赖工作。
- 等待真实用户决定：展示已完成材料和实质选项，仅询问缺少的决定。
- 自动验证失败：修复或回到影响分析，提供实际失败信息。
- 外部输入或动作授权不足：说明缺少的输入及适用范围。
- 即将给出完成结论：执行 Fresh Verification 并核对授权；仅在实际缺口存在时暂停。

这些输出应消费现有 checkpoint 和权威规则，避免新增状态系统或新审批层。

### 4. 单条会签与完整门禁的保障不一致，需要统一

本轮实测并重新阅读了相关源代码。（claim-005、claim-006）

| 路径 | 本轮实际观察 | 结论边界 |
|---|---|---|
| 单条 `validateApprovalRecordFile(..., requireApproved)` | 非用户决定的 `check.design-reviewed` 可接受无 subject/evidence、任意非空 principal；单条也可接受自签和错误摘要 | 校验通过未必证明当前独立审查成立 |
| `review-bundle` 的严格文件校验 | 相同自签、过期摘要均拒绝 | 比单条路径有更强独立身份/当前主体检查 |
| 直接调用 `assertApprovedGateHasValidApproval` | 最小 synthetic delivery 记录的自签和过期摘要可被接受 | helper 单独调用的保障不足 |
| 完整 `assertCheckpointApprovals` | 同 synthetic 自签 gate 被拒；依赖 `assertGateChecks` 校验当前摘要、依据和独立身份 | **本轮没有证明正常完整 checkpoint 可绕过** |
| 真实用户决定核验 | 合法 synthetic capture 通过；数字人冒充生物人、主体漂移被拒 | 证明捕获与绑定自洽，未证明外部消息作者认证 |

优先统一当前批准验证，让单条、组合包和直接 helper 使用同一套主体、范围、摘要、独立身份及适用用户决定检查；历史结构阅读保留明确的只读入口。避免使用一个笼统的“校验通过”表达不同强度的保障。

完整根门禁已经重新读取证据摘要，覆盖检查依赖、适用性、证据分类、范围和审阅包。后端审查还绑定当前合同、Git 候选、实例分离、双轴审查和实际命令记录；这些不是空签字字段。**应保留这些控制，减少人来搬运它们的工作。**

不同 principal 字符串、Schema 或文件 hash 也不等于可信身份认证。根用户决定协议明确承认本地捕获的这一限制；同模型、同事实来源的多个角色也可能产生相关错误。加强审查应要求直接查看原始需求、源码和运行结果，输出可定位、可复现的发现。（claim-006、claim-011）

### 5. 本地历史评测没有证明整体提效

[2026-09-26 Agent 对照报告](../2026-09-26-lifecycle-improvement-implementation/agent-comparison-report.md) 与其 `evaluation-summary.json` 保存了 48 次主运行；本轮重新读取并核算摘要。（claim-007）

| 指标 | 基线 | 候选 |
|---|---:|---:|
| 通过 | 22/24 | 22/24 |
| 场景耗时合计 | 3851.89 s | 3996.67 s |
| 工具调用 | 397 | 396 |
| 人工等待 | fixture 没有实时回复 | fixture 没有实时回复 |

总耗时变化为 +3.76%，原报告四舍五入为 +3.8%；这不能解释为稳定因果效应。两次重复、固定顺序、共享主机、UI 超时和任务提示引导都限制外推。原报告明确不支持“整体效率已提升”，也没有测得真实人工会签等待。

这批实验比较的是当时生命周期改进基线/候选，**没有单独控制本轮当前角色数量或门禁组合**。它既不证明所有门禁有效，也不证明删掉会签能提效。保留失败与限制，不能用较快场景或后补测替换原分母。

### 7. 局部修复的复审口径不一致，应先统一

canonical `code-review/SKILL.md:55,61` 规定普通修复只复验受影响结论及其依赖，未受影响项有依据地复用，并重绑当前候选；`:59` 仅明确历史候选合同采用两轮协议。生命周期 `orchestration.md:95` 却要求产品切片违规修复后全轴复审，`:97` 对任何UI修复要求重新跑Standards、Spec、UI fidelity及验证。（claim-012）

两种说法在普通YSS候选修复场景有重叠，主控与Reviewer可能选择不同复审范围。静态不一致已经确认；本轮没有运行真实修复循环来量化重复成本。推荐由事实源统一“修复差异→受影响结论与依赖→定向复审→当前候选重绑定”。首轮审查完成全部适用检查；复审仅复查受影响结论、相关行为及依赖。范围、合同或风险变化时，先分析变化，再明确列出受影响检查和验证要求；影响未知先补调查，不能直接升级成整包全轴重跑。摘要变化、UI修复和新影响也不应成为笼统全轴复审理由。本报告不建议全轴复审作为默认或兜底。不能把定向复审理解为沿用过期证据或省掉完成前Fresh Verification。

独立核查的 [Matt 上游固定源码](https://raw.githubusercontent.com/mattpocock/skills/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/code-review/SKILL.md) 仍采用双轴并行subagent，区分硬规则与heuristic建议，并跳过工具已覆盖判断；它没有本仓的角色门禁协议。当前YSS锁定revision为`0ab1b63a410a03d3627979a109c8695de27af954`，上述上游源码来自另一固定revision，不能当作YSS已采用版本。可借鉴其检查组合与可执行反馈，也不能直接覆盖本仓授权和合同。（evidence-023）

## Counter-Signals

反对“整体剔除”的证据明确存在：完整 checkpoint 能拒绝自签或过期依据；用户决定能拒绝数字人冒充与资产漂移；真实代码审查还检查 Git 候选与规范覆盖。删除这些控制会移除已经可执行的约束。（claim-005、claim-006）

反对“多角色当然值得”的证据也存在：合法审查包的角色集合错配已复现，历史评测未证明提效，外部原始研究包含协作退化与验证失败。不同角色共识不是测试通过，也不能替代真实用户决定。（claim-003、claim-007、claim-010、claim-011）

正向边界：宽范围资料研究、跨仓独立实现面、确有专业缺口的高风险审查可以受益于多 Agent。每个额外实例应有清晰目标、原始输入和不重叠写范围。固定职称不应被直接当成启动人数。首轮适用审查覆盖与修复后的定向复审分别定义；定向复审依然要求当前候选和证据绑定。历史合同保留原字节，兼容处理由后续 owning work unit 明确。（claim-012）

## Decision Handoff

推荐分三步推进；这是研究建议，不是已批准维护任务。

| 顺序 | 具体修改建议 | 完成后应观察什么 |
|---|---|---|
| P0 | 统一单条/bundle/helper/checkpoint 的当前批准校验；统一定向复审及暂停与 Fresh Verification 的关系 | 相同非法记录各入口一致拒绝；复审只覆盖明确受影响结论和依赖；正常交付完成不凭“即将结论”新增询问 |
| P1 | 以检查能力覆盖选择独立审查者；角色保留为导航/兼容；自动生成 subject、basis、摘要、差异和覆盖表 | 一名有能力的独立审查者合法覆盖适用整包；能力缺口明确增加专家；专业判断仍逐项保存 |
| P2 | 进行配对试点，按具体门禁新增价值决定保留/合并/删除 | 减少等待、重复读写与误拒，同时保持缺陷识别、越权拒绝和验证完整性 |

建议保留的最小控制骨架：一个推进负责人；按候选和风险触发的独立审查；自动合同/测试/摘要验证；已经可审阅范围的真实用户决定及其合法复用；实施写范围与外部副作用授权；交付/合并/发布时的 Fresh Verification。这里“一名审查者”指适用审查包的默认，并非全生命周期永远只能一名专家。

建议压缩：没有独立检查目标的职称切换、按候选名单集齐签字、机械校验的人类审批、相同依据的重复确认、手写重复的摘要/路径/报告。前两项应先核查实际执行，当前权威 policy 已经禁止全员签字，不应以不存在的全员要求作为重构收益。

判断某项会签是否删除时，要求它说明：所防错误、适用风险、能否机器判定、是否发现其他步骤遗漏的有效缺陷、增加的时间/token/误阻断、缺席后的可观察影响。仅新增“approved”记录且没有独特控制作用的步骤优先进入合并或删除候选。未分类新 gate 建议作为配置错误阻断并修复路由，避免默认为一轮真人审批；当前根表没有这一实际漏项。

试点至少覆盖模板小改、既有后端普通行为、API/UI变化、数据迁移或跨仓高风险。冻结同一输入、模型/预算/工具条件，比较当前流程与能力覆盖/合并审查方案；任务配对并调整执行顺序，保留失败和未报告用量。记录有效缺陷、漏检、误拒、返工、端到端时间、专业等待、真实人类回复次数/等待、Agent数、工具和token。用实际验收/故障注入及独立判读评估输出，不能只统计文档、签字或测试总数。不声称小样本有统计显著性。

若用户采纳，资产所有者为 `yss-product-lifecycle` 与模板维护者；行为、许可或门禁语义变化按实际触发重新判为相应维护强度，修改角色表、注册表或消费者的单一事实来源。涉及 canonical Skill 时使用 `maintaining-skills`，再生成投影、锁与专职 profile/CLI快照，保留历史批准原字节、当前重新核验及实例按需迁移。无需新建一套生命周期或第二个批准系统。

## Evidence Limitations

1. 没有当前真实项目逐门禁收益、审查召回/误报、用户等待的可归因数据；无法量化“鸡肋程度”或承诺提效百分比。
2. 当前数据是根模板工作树和指定输入快照；没有完成全部子仓、生成器版本、实例迁移或发布验证。
3. 18个 synthetic探针与28个确定性测试仅覆盖声明场景，不证明真实 Agent 能力、生产安全或流程效率。
4. 当前暂停段的实际误询问频率仍 `needs-deeper-research`；本报告只把其视为文本风险，未作为已发生事件发布。
5. 标准和原始研究的对象不同；DORA为组织关联研究，供应商案例和多 Agent benchmark 不能直接转成 YSS 维护收益。
6. 原始用户回复/运行时身份的真实性由可信来源建立；本地hash与Schema核验自洽，不等于身份签名。
7. 研究包结构校验与本轮材料审计是两个层面；通过结构校验不批准建议、不授予重构，也不等于整套模板可合并或可发布。
