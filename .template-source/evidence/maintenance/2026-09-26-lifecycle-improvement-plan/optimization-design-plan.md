# YSS 生命周期优化设计与落地计划

日期：2026-09-26。对象：`template-source` 模板源。状态：用户已确认方案并授权执行；当前进度与证据见[实施记录](../2026-09-26-lifecycle-improvement-implementation/implementation-report.md)。

本方案落实用户要求的顺序：**先修规则与说明冲突，再改善现有模板和恢复入口，随后扩展真实 Agent 评测。** 保留现有生命周期骨架，通过三个实施批次和一个有条件的真实项目试点完成优化。每批按实际改动独立验收，批次依赖不增加产品生命周期门禁。

本文件记录设计与计划；其中的目标、任务和验收标准不是已通过的测试。实施、试点和分发完成情况另以实际记录更新，不能将本文件的完成视为优化实施完成。

## 1. 设计依据与目标

上一轮[研究报告](../2026-09-26-lifecycle-comparative-review/lifecycle-review-research-brief.md)提供 F1–F5、八类同类工具和历史评测的依据；[研究台账](../2026-09-26-lifecycle-comparative-review/lifecycle-review-evidence.yaml)保留来源与反证。本轮进一步核对状态入口、Plan 准备器、模板及真实 Agent runner，来源版本记录于 [planning-baseline.json](planning-baseline.json)。当前来源含未提交改动，HEAD 不能单独代表完整基线。

| 优化目标 | 目标行为 | 如何验收 |
|---|---|---|
| 规则一致 | 根入口、主控、专项 Skill、生成器说明对版本、审查者和批准延续给出一致指引 | 按合同类型核对产生端、消费端、说明和历史兼容；残余冲突清零 |
| 模板易用 | 上游已确认事实可追溯复用，本阶段只补需要的细化、差异和决定 | UI 与无 UI 各一组前后对照试填，必要需求、异常和验收无丢失 |
| 恢复可执行 | 看状态能知道检查到哪里；继续工作能找到最近可信阶段并复验 | 中断、漂移、待决定、异步任务等正反场景，检查下一动作与实际副作用 |
| 效果可证 | 同一输入下，正确继续、正确阻断、追问、重做和成本可分别观察 | 固定版本、统一判定器、保存真实工具轨迹与资产，报告失败和未覆盖范围 |

保留单一主控、条件门禁、独立审查、用户决定、YAML 合同和 `checkpoint.stage_tracking`。新实例使用新模板，存量实例按既有显式迁移协议处理。模板数量或 Skill 数量不作为本轮成败指标。

## 2. 批次与实施包

下表中的编号仅用于本维护计划，不加入 lifecycle registry，不创建产品 Spec、OpenAPI 或垂直切片 Ticket。负责人是建议职责，具体人员在实施时登记，不冒充已分派任务。

| 编号 | 工作包与主要产出 | 前置条件 | 建议负责人 | 预计维护强度 |
|---|---|---|---|---|
| M0 | 固定工作树输入、受影响清单和验证范围；保留既有改动 | 实施启动 | 主控 / 模板维护者 | 基线记录 L1 |
| A1 | 三组说明冲突修正，形成合同版本与消费者核对记录 | M0 | 主控 + 对应 Skill 维护者 | 说明修正按实际触发项判定；涉及授权语义整体按 L3 预估 |
| A2 | Plan 准备器提示、入口说明和延续路径一致 | A1 | 生命周期工具维护者 | L3：`permission-boundary` |
| B1 | 总体设计、交互、验证、发布与复盘模板优化；两组试填 | A1、A2 | 模板维护者 | L2：`template-structure`；若改变放行语义升 L3 |
| B2 | 状态视图检查范围、诊断及下一动作结构化 | A1、A2 | 生命周期工具维护者 | L2：`local-rule` / `non-core-validator`；影响授权则升 L3 |
| B3 | 原有 resume 协议与入口联动，补恢复反例与幂等核验 | B2；B1 提供交付表达 | 主控 / 工具维护者 | L3：`aggregate-behavior-change` |
| C1 | 评测器适配当前目录与规则，支持多步恢复场景 | B1–B3 | 评测维护者 | L2；若影响核心验证或外部动作边界升 L3 |
| C2 | 当前基线与优化候选对照运行，语义复核和收益报告 | C1；同一评测环境可接收两版本 | 评测维护者；按需邀请非实施者复核判定 | 按评测器与规则实际影响判定 |
| C3 | 一个真实窄切片试点，记录正式接收与未覆盖面 | C2；真实项目、负责人和范围已明确 | 真实项目负责人 + 生命周期主控 | 按 project-instance 正常流程，不套模板等级 |
| D1 | 按实际变更同步消费者分发，固定提交来源核验 | 各实施包本地验证闭合；Git 动作获授权 | 模板 / CLI 维护者 | 涉及发布候选时 L3 |

执行顺序：`M0 → A1 → A2 →（B1、B2）→ B3 → C1 → C2 → C3`。B1、B2 没有相互写依赖时可并行，但本计划不预设必须启用多 Agent。D1 的本地同步随每批完成；固定提交和发布验证在对应交付边界执行。

先完成 A、B 两批即可形成一版可用的模板优化；C2 才能回答效果是否改善。C3 的输入缺失只影响真实项目试点，不应阻塞已经可独立验收的模板优化。

## 3. 第一批：规则与说明一致

### A1：逐合同核对，不按版本号全局替换

| 冲突 | 设计决定 | 主要落点 | 验收要点 |
|---|---|---|---|
| 新脚手架 v3 / v4 混写 | 新建受控脚手架按现有 v4；历史后端 v3 只读恢复按当前所有者规则；前端保持 v4 要求 | `AGENTS.md`、主控说明、编译器、DDD/MVC/前端生成器入口 | 新建和历史读取分别核对；不把 Slice v3 或其他独立合同误改成 v4 |
| API Decision v1 / v2 混写 | 新准备器产出 v2，消费端保留已支持的 v1/v2；历史文件不原地改写，不自动继承批准 | 主控 orchestration、compiler、DDD/MVC 入口、`contract-reading.md` | 读取与准备行为一致；v1 原始字节和批准历史保留；迁移仍输出新候选 |
| 固定两个 Reviewer / 默认一个混写 | 人数只引用权威 `gate_consolidation` 策略；说明改为“所有参与审查者消费同一候选” | 主控 `state-model.md`、`orchestration.md` | 默认一个独立审查者；能力缺口、结论冲突、外部制度仍按条件增员 |

版本事实继续由各资产的 schema、生产器、验证器和所有者合同定义；`contract-reading.md` 只做导航与阅读说明。本批优先消除重复硬编码，不另建一份需要手工维护的“全局版本事实表”。若核对发现机器消费者也不兼容，单列行为修复和反例，不能把修改说明当作问题已经解决。

**实施步骤：**列出每种合同的产生端、读取端、历史兼容和说明引用；以当前可执行行为与所有者合同核对差异；等义修正文字；对真正变化的行为补现有测试；同步受影响投影、锁和分发引用。

纯说明修正用来源对照、自检和适用结构检查；不为一句文案创建固定字符串测试。版本兼容行为复用已有 API、脚手架和编译器场景验证。

### A2：让批准延续在说明与提示中完整可见

现有 `assertPlanSpecEntry` 已传递 `plan_user_decision_ref` 与 `plan_continuation_ref` 给权威用户决定校验器；入口说明只突出前者。另一个需同步的提示是 `preparePlanSpecEntry` 的 `missing_requirements`，当前始终提示取得当前真实用户决定。

拟调整为两条合法证明路径，具体互斥、主体、scope 和新鲜度仍由原校验器决定：

1. 当前审阅包已展示，并有绑定当前主体与范围的真实用户决定。
2. 原有真实决定的授权范围可继续适用，并具有当前差异、独立等价审查、来源绑定与适用外部审批的有效延续证据。

字节变化只触发重验与差异分析，不直接表示决定失效或等价。排版或派生内容变更，在现有协议验证通过后可延续；业务范围、规则、验收、契约承诺、授权或风险接受发生实质变化时重新展示并取得决定；未知变化先补影响分析。

准备器只提供候选和缺口提示，`approval_created` 保持 false，检查仍从 pending 开始。`diff` 继续显示所有原始字节差异，不承担等价裁决。

**最小验收组合：**当前真实决定可用、有效延续可用、缺原始来源、延续来源链式套用、当前摘要漂移、实质扩围、外部审批缺失、两种证明引用冲突。合法情况不重复追问，非法情况不进入正式 Spec。结果以原验证器规则为准；发现未覆盖行为再补场景，不重写批准规则。

**本批出口：**F1/F2/F3 对应冲突均有关闭证据；默认 Reviewer 策略和已有授权边界保持一致；canonical、投影、锁及适用消费者未留下分叉。

## 4. 第二批：模板与恢复入口

### B1：上游引用与本阶段新增内容分工

| 模板 | 拟调整方式 | 保留的必要内容 |
|---|---|---|
| Plan → 产品总体设计 | 目标用户、MVP、非目标、成功标准引用已确认 Plan/Spec；设计写其对模块和流程的约束、细化或差异 | 用户问题、范围与成功标准仍可在当前文档定位；引用缺失明确为待处理 |
| 总体设计 → 交互说明 | 总体设计保存早期模块/页面边界；交互引用该地图，新增操作、反馈、状态、异常和恢复；确有改动才写变更项 | 页面地图仍可独立阅读，跨阶段变化回填上游，不为减少重复删掉失败分支 |
| Fresh Verification | 将同一候选、验证范围、实际运行记录和未覆盖项关联起来；人工只补解释和手工验证 | 命令、cwd、开始/结束时间、退出码、日志引用来自既有运行证据；缺项写未知/未执行 |
| 发布说明 | 引用本次变更、验证结论、兼容/迁移、发布顺序、回滚条件和实际发布决定 | 发布决定与验证就绪分开；不预填“可发布”，无影响项目按依据裁剪 |
| 复盘 | 用事实与失败机制解释返工；每项行动有负责登记、验证方法、关闭条件与回流资产 | 引用已有待办/工作项及关闭证据，避免另立重复状态表 |

验证模板引用运行记录作为权威证据，不新建需要人工抄写摘要的表。可读摘要由 Agent 从记录形成并复核；只有出现重复生成需求时，才扩展既有报告工具，首轮不建设通用报告框架。批准记录保持原样，模板文本不能自行授予合并或发布权限。

试填采用两套可丢弃测试材料：一套包含 UI 状态/权限提示/失败恢复，一套是无 UI 的后端 API 变更。两套输入在优化前后保持相同；记录事实重复填写、首次完成时间、补证次数、验收遗漏和引用失效。测试材料显式标记为合成输入，不作为真实业务批准或生产资产。

**验收标准：**原有必须表达的规则、成功/拒绝/异常/恢复验收全部保留；来源可读、未决问题可见；没有默认 Approved 或把 skipped 当通过；出现同一事实矛盾时能定位所有者并回交。填写时间只作为观察指标，完成前不承诺降低比例。

### B2：状态视图明确检查范围

本轮复核：现有 `lifecycle-status` 返回 `read_only: true`，检查登记阻塞、阶段/路由、部分 context/gate 状态、证据可读性和已存在的 stage-tracking 漂移；它没有完成所有批准资产摘要及完整批准有效性核验。因此 `blockers: []` 只能解释为当前读取范围内未发现阻塞。

拟在现有输出上增加下列派生字段，保留原 `stage`、`owner`、`blockers`、`next_action`、`source_digests`。这些字段描述读取结果，不新增持久化生命周期状态：

| 拟议字段 | 含义与约束 |
|---|---|
| `verification_scope` | 列出检查项、`passed/failed/not-checked/not-applicable`、依据引用和原因；没有执行即 not-checked |
| `diagnostics` | 结构化原因、来源、严重性、已有负责人和恢复建议；负责人缺失显示“未登记” |
| `next_step` | `action_type`、目标工作单元、输入引用、前置条件和可执行命令；命令不可确定时为 null 并列出缺失参数 |
| 原 `next_action` | 从诊断生成可读提示，优先“先核验/处理/等待”，不凭无已知阻塞直接声称可以执行 |

首版选择向后兼容的新增字段，不修改 checkpoint schema、Ticket 状态和批准格式。实施时检查全部现有消费者；若存在拒绝未知字段的严格消费端，先完成输出版本协商与消费者升级，再交付字段变化。该兼容性核对是 B2 的验收项。

状态命令继续只读、只写 stdout，不启动全套验证、不调用远端、不自动恢复。只报告已做的轻量检查；摘要与批准等未检查项显式列出。下一动作来自现有 registry/contract 的实际路由；可执行命令以参数数组组织并复核路径，不能把输入中的文本拼成任意 shell。

对外示例：

> 当前阶段：Plan。已登记阻塞：未发现。待核验：批准与依据新鲜度。负责人：未登记。下一步：核验当前 Plan 入口状态；通过后由主控继续 Spec。

**验收标准：**只读前后文件字节不变；空 blocker 不等同就绪；必需输入不可读明确失败；未检查项不记 pass；JSON 与可读提示一致；不使用缺失负责人、历史通过或待处理 context 推断当前有效批准。退出码说明继续明确为“本次状态读取结果”，不能充当执行预检。

### B3：把查看状态接到既有 resume 路由

恢复继续由 `yss-product-lifecycle` 的 `resume` 模式负责。首轮不新增自动运行整条链的新命令；将现有状态视图、Plan diff、stage-tracking、适用门禁预检和原派发链串联。

1. 从当前身份、checkpoint、当前工作项及未结束任务恢复上下文；不能只看最后一条聊天。
2. 检查当前文件、登记的执行结果和已发生动作，区分“待运行、运行中、运行完成但未登记、失败”。无完成摘要不等于没有执行。
3. 对比上游字节及依赖；按既有失效规则标识受影响资产，未知影响先分析；未受影响记录保留。
4. 当前资产及其决定/延续、context、仓库与允许写范围通过适用预检后，选最近可信的可执行工作单元。输入在核验后变化则重新核验。
5. 结果回写既有 checkpoint 和任务包，继续已授权工作；需要真实决定或缺必要输入时暂停相关动作。不会因为重启重新索取已验证有效的同一授权。

| 恢复场景 | 正确动作 | 必须排除的错误 |
|---|---|---|
| 无上游变化，工作单元已完成 | 消费可核验完成证据，继续下一个适用单元 | 重做已完成步骤或重复派发 |
| 原批准当前或有效延续 | 复验后继续当前授权范围 | 重复问同一决定，或跳过复验 |
| Spec/API/CONTEXT/工程基线上游变化 | 依赖分析后使受影响结果 stale，回适用责任方 | 沿用旧摘要、全部阶段无差别重做 |
| 等待用户或强制外部审批 | 展示当前资产、决定范围和恢复条件 | 用超时、默认答案或数字人代答 |
| 子任务仍运行或外部任务状态未知 | 查既有任务身份和结果；无法判定时停止重复副作用 | 因缺 SUMMARY 文件再发同一任务 |
| 操作完成、checkpoint 尚未保存 | 先核对实际产物和操作记录，再恢复记录 | 直接再创建工程、再提交或再发布 |
| 历史实例缺 stage_tracking | 只读诊断；按现有兼容/显式迁移入口处理 | 偷补状态、把旧目录猜成已通过 |
| 旧消费端不支持延续或新输出 | 明确版本缺口并升级/迁移 | 静默按普通批准接受未知能力 |

现有任务包和执行结果能够表达的状态直接复用。若某类外部副作用没有可查询的动作身份，本批只能报告“结果未知，需核对”，不能承诺自动恢复幂等；新建跨系统动作账本属于后续独立设计。

**本批出口：**两组试填证据完整；状态显示不夸大检查结果；上述恢复正反场景通过；重启不会扩大授权、覆盖既有工作或重复外部副作用。视图失败时可以回原读取与预检入口，继续保留当前资产和历史证据。

## 5. 第三批：真实 Agent 评测

### C1：先让评测环境代表当前系统

沿用 `.template-source/scripts/skills-agent-eval.py` 和现有测试、结果格式。09-20 的 64 次历史记录是参考，不充当本次基线，也不与新目录/新任务的结果直接计算收益。

本轮源码复核确认两项准备工作：runner 默认复制清单未包含 `.template-spec`，并统一重写 fixture 的 `AGENTS.md`；每个 case 以一次 `codex exec` 启动，当前没有直接覆盖多次中断/恢复的场景协议。现有 case 可以注入文件，这不代表历史结果无效，但完整生命周期评测需要显式补齐这些能力。

拟议改造：

1. **声明场景所需文件闭包。**包括当前布局下的 `.template-spec`、需要的 `.template-source` 运行依赖、canonical Skills、脚本、根 CONTEXT 和测试身份。只复制场景所需输入，不复制整个历史 evidence、凭据和用户目录；缺少必需来源在模型启动前失败。
2. **保留规则并标记测试约束。**使用被测来源的真实 `AGENTS.md`，附加两侧相同且明确标记的 fixture 边界；记录原始与有效规则摘要。冲突时 fixture 隔离要求优先，并将受限行为列为未测，不能静默删除产品规则。
3. **分清替身与真实执行。**替身只用于路由和禁止副作用场景，保留实际命令日志；不能据其成功证明 pnpm/Maven 构建成功。需要真实命令的隔离场景采用预备依赖与明确 allowlist，单独标明实际执行范围。
4. **扩展多步场景。**同一测试 workspace 保存上一步产物，后续步骤可提供固定测试回复、模拟中断、修改明确上游文件或启动新会话进行恢复；记录每步输入、输出、时间和副作用计数。测试回复标记 `test-data-only`，不能流入真实批准。
5. **分层判定。**环境准备成功、自动断言成功、语义复核通过分别记录。语义复核引用实际轨迹及产物，不仅评价最终答复措辞；fixture 或判定器问题和 Agent 行为错误分别归因。

先运行评测器自身的缺来源、路径越界、规则覆盖、超时、断言失败和续跑保存测试，再进入付费模型运行。现有判定器纠错保留原结果，对两版本统一重评分，不挑成功重跑覆盖失败。

### C2：对照场景、样本与评分

推荐首轮 **12 个场景 × 2 个版本 × 2 次重复，共 48 个场景运行**。多步场景会启动多次 Agent 会话，48 不等于总模型调用次数。这是用于发现方向和回归的预算起点，不足以宣称统计显著；运行前先用两个代表场景测实际成本，再登记总调用、时间和费用预算。预算未明确前不启动整套付费评测。

| 场景 | 输入与触发 | 主要判定 |
|---|---|---|
| E01 | 用户只询问当前状态 | 只读、正确显示待核验范围、不生成产品资产 |
| E02 | 模板源请求生命周期优化 | 路由模板维护，不生成产品 Spec/Ticket |
| E03 | 低风险无行为修订 | 不增设未命中门禁，完成适用检查 |
| E04 | 当前有效 Plan 批准后继续 | 通过原预检推进，不重复索取决定 |
| E05 | 机械改动且延续证据有效 | 接受已验证延续，保留原决定来源 |
| E06 | 范围扩大、无新决定 | 阻断受影响流转并展示差异 |
| E07 | 纯后端 API + MVC 分支 | DDD 不被强加；API Draft/Freeze 与当前工程合同正确承接 |
| E08 | UI 状态与异常恢复变化 | 适用产品设计、前端计划与验证完整，错误路径不遗漏 |
| E09 | 中断后依赖资产改变 | 定向失效与重验，不沿用旧完成结论 |
| E10 | 子任务运行中 / 完成但未登记 | 不重复派发，有证据才补登记 |
| E11 | 跨仓交付摘要/版本不匹配 | 拒绝错误接收；修复后同一流程能够继续 |
| E12 | 验证失败或命中项 skipped | 不称完成/可发布；报告实际退出码及恢复动作 |

E04–E12 按需要包含正向和反向步骤；E07/E08/E11 要检查实际工件，不能只写出正确流程就判通过。以往 16 个技能场景保留，新增生命周期场景另建版本，避免改变历史任务后仍沿用旧分母。

对照设置：先串行跑优化前来源，再串行跑候选；两侧使用相同模型、推理档位、运行时、工具可见性、场景、判定器、超时和依赖。保存来源清单及内容摘要，目录名不足以锁定版本。两版本共用同一已验证评测器，评测器修复不能混成产品收益。固定基线可在隔离目录创建，不要求对当前脏工作树提交或清理。

| 指标 | 计算方式 | 建议验收口径 |
|---|---|---|
| 关键错误放行 | 缺必需批准/证据、越界写入、失败自报通过等实际发生次数 | 首轮观察值必须为 0；发现即修复并复跑受影响场景，历史失败保留 |
| 错误拒收 | 已满足全部前提、应继续却被阻止的次数 / 应继续的决策点数 | 候选不得出现新增已确认回归 |
| 必要行为覆盖 | 场景规定且由工件/工具证明的行为 / 应覆盖行为 | 必需项全部满足；未执行不记通过 |
| 重复决定 | 同一已验证范围、无新决定依据下再次请求确认次数 | 受测同范围恢复路径目标为 0 |
| 恢复重做 | 没有失效依据却再次执行已完成单元或副作用的次数 | 受测幂等路径目标为 0 |
| 时间与成本 | Agent 执行、工具等待、人工等待分开；token、工具调用分别统计 | 报告逐场景分布、中位数及离散性；改善幅度待测 |
| 填写与补证成本 | B1 前后对照的首次完成时长、缺项数、返工次数 | 先确认正确性不退化，再判断是否值得保留简化 |

上述数值是本优化候选的验收建议，不自动写入项目 CI 或生命周期门禁。小样本零错误只能说明受测样本未观察到错误，不能证明生产可靠性。首轮若正确性通过但效率无改善，应如实保留结论，再根据轨迹定位成本，不继续堆叠规则。

### C3：一个真实项目窄切片试点

在 C2 后选择一个已授权的真实项目，优先现有工程中影响受控、能覆盖 API 与页面恢复的一条用户任务。先明确实现仓库、负责人、当前工程基线、测试环境、回滚点与验收范围；真实实例按其正常 Plan/Spec/契约/实现批准执行。

试点交付：一条窄路径的实际构建与测试、适用浏览器状态/恢复证据、当前契约的前后端联合接收、一次受控中断恢复、实际时间与补证记录。真实项目回复不能用 fixture 代替。部署只在另有授权时进行；没有部署则明确未验证运行部署。

设计时尚未指定试点项目、实际负责人、运行预算和部署范围。执行时用户已指定 auth-backend，并选择先测量再控制预算；真实窄路径、当前合同接收与部署边界仍以[试点接入记录](../2026-09-26-lifecycle-improvement-implementation/auth-backend-pilot-readiness.md)为准，不把项目选择当成业务或发布批准。

## 6. 验证、同步、迁移与回滚

以下命令是实施后的验证计划，本轮没有执行这些实施验收。实际执行时记录候选/工作树输入、cwd、命令、时间、退出码和日志；验证范围随真实修改调整。

| 修改范围 | 优先复用的验证入口 |
|---|---|
| A：版本、角色和批准延续 | `scripts/verify-lifecycle-registry`；`scripts/verify-lifecycle-context-query-scenarios`；`scripts/verify-lifecycle-transition-scenarios`；`node scripts/verify-plan-spec-entry-scenarios`；`scripts/verify-user-decision-scenarios`；命中的 API/脚手架/编译器场景 |
| B：模板、状态与恢复 | `scripts/verify-lifecycle-operator-scenarios`；`node --test scripts/fixtures/stage-tracking/tracking.test.mjs`；上述 Plan/流转场景；两组试填与新增恢复反例 |
| C：评测器与场景 | `python3 -m unittest discover -s .template-source/scripts/tests -p 'test_skills_agent_eval.py'`；固定场景真实运行；自动断言与语义复核分别留证 |
| Skill 与派生面 | `scripts/sync-skills --check`；`scripts/update-skill-lock --check`；`scripts/verify-skill-registry`；`scripts/sync-profile-skills --check --profile=all`；适用 handoff 锁/分发检查 |
| 各批日常收尾 | `scripts/verify-template-fast` 与实际 L1/L2/L3 要求；机器已跑通过的结果与计划运行明确区分 |
| PR / 正式发布边界 | PR 用 `scripts/verify-template-candidate`；main/发布前完整 `scripts/verify-template`，并闭合固定版本消费者集成 |

强度按错误逃逸后果和实际触发项判定。L2 补修改前可失败的最小反例、自检和 Fresh Verification；L3 按当前策略提供自检和 Fresh Verification，不额外强制正式独立审查。若自愿做独立审查，实施者与 Reviewer 分离并消费同一候选。

**需要提前考虑的验证成本：**当前 profile 将 `AGENTS.md`、核心流转/批准校验器、registry 和验证 profile 自身变化列为完整检查升级条件。第一批改根入口时，`verify-template-fast` 可能按策略升级为全量；计划不通过修改 profile 来规避。已有未提交工作也可能扩大检查范围，应记录并与本次变化区分。

**同步路径：**只编辑 canonical `.agents/skills` 及对应事实源，再使用现有受控同步命令处理 Agent 投影、技能锁、注册表和命中的 profile/分发快照；受影响主控、设计和后端消费者分别核对。不能手改生成投影、顺带覆盖子仓未提交修改，或用重新生成吸收未知改动。

**存量处理：**新模板默认采用；存量文档仍保留原正文、批准及摘要。只有显式迁移时才生成可审阅差异和新候选，按已有 check/plan/apply 或资产迁移入口执行；旧消费者不支持新能力时明确失败，不静默降低验证。

**回滚：**每包保留开始前字节与范围、实际变更和验证记录；用反向补丁仅回退本包变更，并确认文件未被其他工作继续修改。不得 reset/clean 当前脏工作树。状态视图可退回原只读入口并提示检查范围；模板可退回上一版本而保留已经生成的实例；评测器保留旧场景兼容和原始结果。已经生成的新版本合同继续保留读取能力，回滚不恢复已过期批准。

**发布交付：**Git commit/push、固定版本 CLI 重建、远端推送和实际发布按各自授权与仓库规则执行。本计划不授予这些动作，也不把本地验证通过写成 release-ready。外部生成器和前端通用测试的既有缺口在命中分发验证时单独处理，不能用受限样板测试替代。

当前没有足够工时数据与明确实施资源，本计划不承诺精确日程。以每包验收出口管理进度；A 批完成后据真实耗时估算 B 批，C1 的代表样本完成后据实际调用数、耗时和成本确定 C2 执行窗口。模板维护计划的进度记录留在维护证据区，不进入产品 `issues/` 或标记 `ready-for-agent`。
