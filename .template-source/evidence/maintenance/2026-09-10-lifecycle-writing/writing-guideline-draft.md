# 研发文档中文写作规范草案

版本：v0.1；日期：2026-09-10；状态：待审阅，未接入默认技能或模板。

本草案用于改善研发文档的具体程度、阅读顺序和交接质量。试读时先看[三组改写对照](rewrite-comparisons.md)，再判断这些写法是否适合进入正式模板。研究依据和适用限制见[研究简报](lifecycle-writing-research-brief.md)。

## 1. 适用范围与保留项

适用于研究结论、Plan、Spec、产品设计说明、工程契约的解释正文、Ticket、审查、发布和复盘。聊天中的进度通知按第 4 节处理。

本文件是模板维护提案，不是已生效的流程规范。生命周期身份、门禁、资产所有权、批准和状态继续由根 `AGENTS.md` 指定的权威资产决定；标准术语消费根 `CONTEXT.md`。本轮只新增维护草案，不生成产品资产。

写作调整应保留这些内容的原意：主体、触发条件、规则、例外、量词、范围、非目标、数值及单位、证据引用、未决项、责任人、时点和依赖。稳定 ID、API 标识、schema、metadata、版本及批准记录按原合同保存。已经冻结的内容若需要改变行为，应回交资产所有者处理，不作为润色顺手修改。

## 2. 共用写法

### 先回答读者当前需要判断的问题

开头说明业务问题、本次结论或交付行为。必要背景紧接其后，让读者知道结论为什么成立。正式模板要求的 metadata 和身份信息仍保留；表达顺序的建议不能自行覆盖校验器要求的结构。

只在内容较长或需要导航时添加摘要。摘要引用正文，不另写一套范围和状态；维护时检查二者一致。

### 用主体、条件和结果表达需求

把“提升效率”“完善体验”等目标落实到具体场景：谁在什么情况下做什么，系统产生什么可观察结果。保留支持判断的业务动机，不把所有文字都拆成短句或编号。

输入没有规则时，记录待确认问题；不要为了让句子具体而补出时限、阈值、错误码或默认行为。重要缺口交回拥有该决定的工作单元。非阻断细节按既有流程记录责任人、解决时点和接收方。

### 让确定程度与证据一致

事实给出处；推断说明依据；方案使用建议语气；假设写明如何验证。章节开头已明确整段是假设或建议时，无须每句重复标签。

保留表达真实不确定性的“尚未确认”“可能”“取决于”。只有测试失败现象时，报告现象和下一项诊断，不编造原因；只有期望收益时，写目标和验证方法，不写成已实现收益。估算需有执行者、依据、范围和条件；无依据时不填精确工期。

### 让每段承担一项用途

一段解释一个问题、一项规则或一个取舍。顺序动作使用编号；同类规则、状态或选项比较使用表格；因果和取舍使用连贯段落。列表长度、段落数量和总字数按内容决定。

删除只有态度、没有事实或决定的修饰句。技术术语、业务术语和必要限定词保持准确，不使用同义词轮换制造变化。评价文档看它是否明确、可信和可执行，不追求模拟人的口头习惯或降低 AI 检测分数。

### 复用上游事实，交代本阶段新增内容

引用上游规则的可定位位置和必要版本，本阶段写新增细化、适用范围和交接。直接决定本地验收的条件可以在场景中重述，并绑定同一规则 ID；以一致性核验控制漂移。

不要用“详见相关文档”代替必要信息。引用不可读或版本不明时按现有合同处理。条件项只在流程允许时记录带原因的 `not-applicable`；命中的要求和必要异常场景应完整展示。

## 3. 各阶段怎么写

| 阶段 | 正文优先回答 | 本阶段需要写具体的内容 |
|---|---|---|
| 研究 | 已知什么，证据支持到哪里？ | 结论与来源、反证、限制分开；建议与事实区分 |
| Plan | 谁遇到什么问题，本期为什么这样取舍？ | 业务故事、MVP / 非目标、优先级依据、成功标准的确认情况、关键未决项 |
| Spec | 什么条件下，系统必须怎样表现？ | 规则与验收对应；按影响面覆盖成功、拒绝、边界、状态变化和恢复 |
| 产品设计 | 用户如何完成任务，失败后如何继续？ | 入口、操作、反馈、状态和恢复路径；引用 Spec，保留设计待确认项 |
| 工程契约 | 实现必须遵守什么，哪些地方有取舍？ | 精确协议与解释正文配合；标识、版本、范围及约束保持可核验 |
| Ticket | 本切片交付什么，如何证明完成？ | 窄而完整的行为、依赖、验收、公共测试 seam、当前合同及验证证据 |
| 审查 | 哪个具体条件下存在什么问题？ | 定位、触发条件、影响、依据与修复建议；推测和已复现问题分开 |
| 发布 / 复盘 | 验证了什么，还剩什么风险或决定？ | 实际验证范围、未覆盖部分、发布决定或失误机制与改进行动 |

这些指引帮助填写既有模板，不新增必填字段、阶段或门禁。Plan 不提前承诺详细 API 和工程实现；Spec 的例子不代替完整规则；Ticket 不重新设计已冻结行为。

## 4. 进度与会签提示

进度更新说明本轮有意义的变化、当前阻塞和接下来由谁处理。状态没有变化时，无须重述全部计划。已授权且 Agent 可以完成的动作继续执行，避免把操作转交用户。

请求决定时展示当前版本、推荐方案及理由、实质选项和取舍、风险、批准范围与后续动作，遵守既有用户决定协议。可以突出当前最重要的问题，但所有影响决定的阻塞和选项都应可见。一次回复需要多个相互独立的决定时，分别说明各自影响。

示例：“规则说明已补齐。成功标准仍缺统计口径，负责人需在 Plan 进入 Spec 前确认；当前材料尚不能支持流转。”这类表述需要实际资产支持，不能成为固定的完成话术。

## 5. 起草与修订时的检查

1. 确认文档读者、当前阶段、权威输入和允许改动的范围；区分从事实起草与对既有正文作等义改写。
2. 起草时按本阶段的问题组织内容；修订时先列出必须保留的规则和约束，再调整文字。
3. 对照输入检查有无新增承诺、规则丢失、范围扩大、责任转移或不确定性被抹去。发现源资产冲突时记录并回交，不自行选一个版本。
4. 检查正文、摘要、表格和状态是否一致；验证适用的引用、结构和合同。自检结论不代替独立审查或批准。

规则、例外、证据或状态变化属于实质差异，不能被“字数减少”抵消。不要只用禁用词扫描或模型给自己的分数判断效果。

## 6. 建议接入位置

推荐把共用写法收敛为一份实例可分发的文档引用；生命周期起草 / 修订工作单元和专项资产所有者按需加载，各阶段模板只保留短指引和相关例子。首轮不新增独立写作技能、独立审批或全局常驻模式。

| 现有资产 | 后续建议 | 本轮边界 |
|---|---|---|
| `docs/plan/templates/plan-template.md` | 在允许的结构内前置问题和本期取舍，保留复用依据 | 只演示写法 |
| `docs/templates/spec-template.md` | 给规则、非功能目标和验收增加具体填写示例，明确非目标唯一维护位置 | 只演示写法 |
| `docs/templates/vertical-slice-ticket-template.md` | 从核验结果填写状态和阻塞，减少通用约束重复正文 | 状态语义调整需另按实际影响分级 |
| `.agents/skills/yss-product-lifecycle/references/orchestration-contract.yaml` | 在相关文档工作单元明确按需加载入口 | 未修改路由 |
| `.agents/skills/writing-for-agents/SKILL.md` | 复用其层级和引用原则；维持 maintainer-only 身份 | 未改变技能发现面 |

正式接入应先核对事实源、模板校验和实例分发，再按 `maintaining-skills` 同步 canonical、投影及 lock。当前草案位于维护证据目录，不应被产品实例作为默认规则引用。

## 7. 如何判断值得接入

本轮对照是作者编写的说明性样例，只能展示目标写法和核对语义，不能证明模型稳定执行。

后续用同一事实输入、同一阶段模板和模型配置比较：现有规则、现有规则加上游原版、现有规则加本草案。每种条件至少重复三次；盲化顺序，由未起草样例的人评价。记录完整 prompt、模型版本、输出和具体差异，不预填结果。

先检查规则、限定条件、引用、状态和未决项是否完整且无凭空新增；再看读者能否定位问题、范围和待决定事项，以及验收能否直接执行。字数、套话和重复量只作辅助信息。增加超过五项规则、未知原因、冲突来源和冻结资产等反例，防止以压缩换取错误。

是否正式接入的下一项决定：在这三组对照上确认目标写法是否合适，再实施小范围模板与加载入口调整，并补充实际生成评估。
