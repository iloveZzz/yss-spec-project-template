版本：v0.1；性质：虚构的维护示例，非产品资产，未创建 Ticket、业务术语或批准记录。

本文件配合[中文写作规范草案](writing-guideline-draft.md)。每组先给固定输入，再给两种表达，最后逐项核对。三组独立提供事实，不表示真实项目已经从 Plan 进入 Spec 或取得任何批准。“原写法”由作者构造，不是对模型运行结果或真实文档的抽样。

## 1. Plan：让业务问题和取舍可见

### 固定输入

| 示例编号 | 已提供信息 |
|---|---|
| P1 | 示例访谈中，一名采购申请人说申请曾因缺少材料被退回；未提供访谈记录或样本统计 |
| P2 | 本期候选范围是在提交前检查必填附件，并指出缺少的材料；业务价值尚待验证 |
| P3 | 材料真实性识别、审批路线调整不在本期范围 |
| P4 | 建议用缺材料退回比例观察效果；基线、统计口径和目标值尚未确认 |
| P5 | 必填材料清单尚未确认，影响关键业务规则；需求经理需在进入 Spec 前取得业务负责人确认，并交接给 Spec 起草者 |
| P6 | 当前范围及成功标准仍待用户确认，本组示例不能支持 Plan 流转 |

### 原写法：事实齐全，但结论被修饰语遮住

为全面提升采购协作体验，本阶段拟通过前置校验能力构建高效闭环，实现申请质量的持续优化。一名申请人在示例访谈中提到材料缺失导致退回，但尚无访谈原始记录及统计数据。规划提交前检查必填附件并提示缺少材料，业务价值待验证；材料真实性识别和审批路线调整不纳入本期。建议围绕缺材料退回比例建立成效评估体系，相关基线、统计口径和目标值有待明确。必填清单影响关键业务规则，由需求经理在进入 Spec 前取得业务负责人确认并交给 Spec 起草者；范围和成功标准也待用户确认，当前不能流转。

### 改写：按问题、范围和未决决定组织

本期建议在采购申请提交前检查必填附件，直接告诉申请人缺少哪些材料。

问题线索来自一名申请人对材料缺失退回的描述；目前没有原始访谈记录和统计数据，尚不能判断问题发生频率或预期收益。

本期不做材料真实性识别，也不调整审批路线。建议观察缺材料退回比例是否下降；统计口径、基线和目标值仍待确认。

进入 Spec 前，需求经理需要取得业务负责人对必填材料清单的确认，并交给 Spec 起草者。清单影响关键业务规则；当前范围和成功标准也未取得用户确认，因此本组规划尚不能流转。

## 2. Spec：让规则可以转成验收

### 固定输入

以下是假设已由业务提供的七条规则，用于独立演示；它们不是从上一组待确认的 Plan 自动推导的决定。

| 示例编号 | 已提供信息 |
|---|---|
| S1 | 校验发生在申请人点击提交时 |
| S2 | 缺少任一必填附件时，拒绝提交，申请保持草稿 |
| S3 | 逐一列出所有缺少附件的名称，不只显示第一项 |
| S4 | 校验拒绝后，保留本次页面已填写内容；未承诺关闭或刷新页面后仍保留 |
| S5 | 补齐附件后，再次提交时重新校验 |
| S6 | 附件齐全且其他既有提交条件通过时，沿用既有提交流程；附件齐全本身不保证提交成功 |
| S7 | 不检查材料真实性；必填清单读取失败时如何处理尚未确认，交业务负责人在 Spec 冻结前确认 |

### 原写法：规则挤在一段中

系统应提供完善的附件校验能力和友好的异常反馈。在申请人点击提交时进行检查，缺少任一必填附件即拒绝并保持草稿，完整列出所有缺少附件名称，且保留本次页面输入，但不保证刷新或关闭页面后保留。补齐后再次提交需重新校验，只有附件齐全且其他既有条件也通过才能沿用既有流程，附件齐全不能单独保证成功。不校验材料真实性；清单读取失败行为尚未明确，需业务负责人在 Spec 冻结前确认，以保障整体体验。

### 改写：规则和例子对应

申请人点击提交时，系统检查必填附件。缺少任一附件即拒绝提交，申请保持草稿，并逐一列出所有缺少附件的名称。

| 条件 / 操作 | 可观察结果 | 对应输入 |
|---|---|---|
| 缺少任一必填附件，点击提交 | 拒绝提交；申请仍为草稿；列出全部缺失名称 | S1、S2、S3 |
| 因附件缺失被拒绝 | 本次页面已填写内容仍在；不承诺刷新或关闭后的保存 | S4 |
| 补齐附件后再次点击提交 | 重新执行附件校验 | S5 |
| 附件齐全且其他既有条件通过 | 进入既有提交流程 | S6 |

附件齐全不代表其他提交条件已经通过。本功能不检查材料真实性。

验收例子：在示例清单中，“报价单”和“采购说明”均为必填，申请人两项都未提供。点击提交后，应看到两个缺失名称，申请仍为草稿，当前页面已填写内容保留。这里的附件名称是测试数据，不扩展实际必填清单。

待确认：必填清单读取失败时的行为，由业务负责人在 Spec 冻结前确认。当前不能将失败默认解释为放行或拒绝。

### 保真核对

| 输入 | 改写落点 | 作者自检 |
|---|---|---|
| S1、S2 | 首段、首行条件 | 触发点和状态保持不变 |
| S3 | 首段、首行结果、验收例子 | “所有”未缩为一项，没有五项展示上限 |
| S4 | 第二行结果 | 页面内保留未扩展成持久保存 |
| S5 | 第三行 | 保留再次校验 |
| S6 | 第四行及后续限定句 | 保留与其他条件的合取关系 |
| S7 | 非目标与待确认段 | 未新增真实性检查，也未决定故障降级行为 |

本例比原文更长，增加的是规则之间的边界和定位信息；这不构成效果退步。

### 原写法：重点埋在实现名词之后

本任务将全面完善前后端附件校验链路，覆盖提交接口、页面交互及相关测试，遵循示例 Spec v2 / R1 和冻结 OpenAPI v3，以端到端切片交付提交申请时的必填附件校验及拒绝反馈，不按技术层横拆。需验证缺失拒绝且不提交、完整提示缺失名称、保留页面输入和补齐后重新校验；公共 seam 为提交接口与申请表单，命令需读取工程和合同。实现合同 v1 为草案且批准 pending，必填材料配置依赖尚未完成。状态 ready-for-human，尚无实现或测试通过证据，真实性识别不在范围。

### 改写：先说交付，再列验收和阻塞

本切片交付：申请人提交申请时，系统校验必填附件，并在拒绝提交后展示缺失材料。交付覆盖所需前后端行为。

范围依据：示例 Spec v2 / R1、冻结 OpenAPI v3；材料真实性识别不在本切片范围。

验收项均待验证：

- [ ] 缺少必填附件时拒绝提交，申请未提交。
- [ ] 页面列出全部缺失附件名称。
- [ ] 拒绝后保留本次页面已填写内容。
- [ ] 补齐后再次提交，重新执行附件校验。

通过提交接口和申请表单交互验证以上行为。具体命令待从真实工程与实现合同读取，当前没有实现或测试通过证据。

当前状态：`ready-for-human`。实现合同 v1 为草案，生命周期批准为 `pending`；必填材料配置切片也未完成。两项阻塞均需闭合，并由生命周期完成全部适用就绪核验后，才可决定是否进入实现。
