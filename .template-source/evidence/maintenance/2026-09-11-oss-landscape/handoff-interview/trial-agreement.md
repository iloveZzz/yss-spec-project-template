## 要回答的问题

现有跨仓交付机制能否让正确交付被接收，准确拒绝三类错误，并在修正输入后通过正常入口恢复？首轮回答可靠性问题，不证明团队效率、商业价值或对抗恶意伪造的能力。

## 候选与基线前提

候选接口为 `GET /file-sync/tasks/{taskCode}/target-data-preview`，真实 Java Controller 和 Vue 预览弹窗均存在。当前前后端测试包含 `scope`，历史契约审查仍描述仅 `taskCode`，尚不能直接认定历史批准覆盖当前实现。历史模块测试数量也不能替代此切片前后端同版本验收。

在执行前必须能够记录并核验：前后端各自固定提交与使用的源码状态、接口契约、有效批准及其内容绑定、部署与测试数据身份、同基线的真实验证结果。现在尚未形成这些完整证据；不把查证到的 HEAD 自动选为批准基线，也不混入未提交修改。

候选根缺少 `yss-project.yaml` 是已记录的接入前提缺口。只读候选查证不推定模式、不执行迁移；不能在本次访谈中补写身份来绕过接入流程。

最后一轮库存还发现：前后端工作区均有未提交修改；Java 源码检索未发现五项部署身份探针，但仓外平台是否提供尚未核实；starter 依赖私有组件、数据库、Redis、Nacos/本地档位及文件管理等，目前没有已验证的最小装配。已确认首轮仅采用 PostgreSQL，不覆盖 MySQL/Oracle；现有 JDBC mock 测试不是实库通过证据。这些均是准备前提，不是已经证实的接收机制失败。

## 场景矩阵

以下是访谈决定的操作化草案，具体文件、基线版本与预期错误标识在执行前固定。每个故障从已通过的正例独立派生，避免多个错误相互遮蔽。

| ID | 场景 | 预期与证据 |
|---|---|---|
| S0 | 正确包首次接收 | 正常接收检查通过；记录当前文件、收据、输入与部署身份。`inputs-verified` 不等于业务切片完成或实现已获批准 |
| S1 | 同一正确包重复接收 | 保持幂等，没有重复有效交付和错误状态推进 |
| S2 | 接收方已知新接口/交付基线，收到旧包 | 因版本或绑定过期被拒绝；不能因服务未启动等无关故障判通过 |
| S3a | 收到另一仓库交付范围的自洽包 | 因目标/归属不匹配被拒绝；具体归属判据须预先明确。若当前合同无法表达该归属，记录机制缺口，不用其他摘要错误替代 |
| S3b | 收到另一切片的自洽包 | 因切片不匹配被拒绝 |
| S4 | 当前交付内容携带只批准旧内容的记录 | 因批准与当前资产绑定不一致被拒绝；不测试恶意重签整包 |
| S5 | 各拒收场景后修正输入并正常重试 | 按既有正常流程恢复，无手工改摘要、删批准或跳过校验；允许复用已核验的不可变战略快照 |
| S6 | 从干净隔离环境再执行 S0–S5 | 结果一致；不依赖前次缓存、隐藏手工操作或共享源码 |
| O1 | 上游已变化但尚未同步，旧包内部仍自洽 | 观察实际表现并注明接收方知识边界；不以此声称已确认全局最新，不把本轮未建设的在线检测当成必过要求 |

每次拒收检查已有文件、批准和接收状态的前后差异；成功、拒收、修正、恢复分别保留日志。新增战略快照必须满足 Q7 的保留条件，不能把任意残留文件都归入此例外。

## 通过、完成与停止

- 只有全部必验场景符合预期，才判定本轮范围内机制通过；任一错误放行、误拒收、错误状态推进或恢复失败，都使对应项不通过。
- 可执行场景完成且所有失败/阻塞有证据，试验可以结束并给出“未通过”或“基线未就绪”，不能将这些结果写成机制通过。
- 基线前提缺失时停在前提核查，后续场景标记未执行；不得让基线配置错误充当故障注入的成功证据。
- 如需改变业务功能才能建立基线，按 Q8 暂停并重新选样；其余超出 Q12 的准备工作先单列范围，不自动开展。
- 本轮不对耗时、人工分钟或费用设置效果门槛；如实记录，作为后续研究输入。

## 交付物与后续边界

预期交付为基线清单、场景结果表、两侧日志与状态差异、恢复记录、已知限制，以及需要另行处理的前置缺口/修复建议。保留原始失败，不通过修复后覆盖证据来宣称首次通过。

本轮讨论没有授权修改原业务工作区、提交/推送、发布或使用真实业务数据。整体验收约定已确认；执行仍需满足接入/批准前提，不能沿用本轮只读查证作为运行验证证据。后续处理见[前置缺口方案](prerequisite-plan.md)，其中新增处理建议不自动继承为实施批准。
