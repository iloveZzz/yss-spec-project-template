# 真实样本后的机会收敛

本轮发现最急需补齐的是**已有项目进入跨仓交付闭环的能力**。真实 Java 与 Vue 的预览行为已经运行，当前 API 已冻结；但正式实现合同无法据实表达这个未由模板生成的既有工程。接收器尚未运行，不能据此前置失败判断旧接口、错包或旧批准是否会被误收。

这份建议只属于模板维护机会研究，没有修改运行机制，也没有授权新修复。优先级是基于本次实际阻塞的工程判断，不是市场份额或商业需求证明。

| 优先级 | 机会 | 本轮依据 | 最小后续验收 |
|---|---|---|---|
| P0 | 支持既有工程的真实架构身份 | 两类后端 recipe 都要求架构身份；目前身份被绑定到生成器、固定模块闭包、H2/not-bound。样本没有这些原始来源，不能伪填 | 以相同固定 Java 工程和 PostgreSQL 基线，从登记正常编译、审查并批准探针合同；无需生成脚手架或改业务架构 |
| P0 | 在初始化和构建之前检查完整交付前提 | 已有工程可以登记、真实服务可以运行，但实现编译边界仍阻断 | 同样输入可在只读预检中一次说明缺哪些原始资产、哪些可承接、哪些必须补证；错误包含责任来源与正常恢复路线 |
| P1 | 既有 UI 证据的受控交接方式 | 战略交接 schema 与 exporter 强制原型、视觉包和离线浏览凭据；本次现有 Vue 行为无改动，真实截图不能自行变成已批准原型包 | 明确既有 UI 基线类型、精确源码/动作/截图绑定和必要确认，提供可验证承接路径，保留真正新设计的现有要求 |
| 待验证 | 自洽包的目标仓归属判据 | 当前后端交付 schema 的 scope 只有 slice/source/operation IDs，未见显式目标仓身份；这是结构观察 | S0 建立后执行 S3a。用自洽的另一仓包检查真实目标授权绑定，不能用坏摘要制造“拒收成功” |

## P0 的建议变更边界

建议将“现有工程事实”与“脚手架生成事实”分开表达。现有工程以登记对象、固定源码、实际构建单元、边界审查和可执行验证为依据；生成工程继续保留生成器、受支持 profile 和原有模块闭包。不能仅取消校验或把 PostgreSQL 字符串替换进固定 H2 字段。

后续方案需明确架构身份的来源类型、支持范围、缺失/不一致的错误、变更失效规则、三个来源如何相互核对、数据库声明与真实验证的区别。兼容现有脚手架合同；是否需要新版本，应按实际 schema 兼容性设计后审阅，不能在本次试验暗改。

事实源范围为 backend-architecture、身份 schema、技能注册表/编译器、工程接入与技术设计绑定；同步范围包含后端/前端接收模板及各固定 CLI 快照。当前三份关键实现文件与主模板字节一致，见 [源码对比](compiler-source-comparison.json)，因此不能只建议升级到当前模板就假定解决。

建议采用可执行验收：既有样本正例、缺原始证据拒绝、架构/构建单元冲突拒绝、源码改变使批准失效、修正后正常重编译、已有生成式工程回归。修复后再回到同一试验的 S0–S6 与 O1，保留本轮首次阻塞证据。

## 试验边界

原约定 Q10 是“先完成可执行的原样验证，保留失败与复现证据，提交建议；不直接修复机制”。本轮依此保留原机制。未建立正例之前，不生成自签批准、假部署探针、错误包或伪造接收状态来凑场景覆盖。
