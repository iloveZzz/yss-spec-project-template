# 目标表预览试验前置缺口处理方案

日期：2026-09-11。当前结论：试验约定已确认，准备前提尚未齐备。先解决版本基线、治理接入、有效批准、部署身份和最小运行环境的证据缺口，再进入正确交付对照与故障重放。

本文是已完成访谈后的维护建议，不是产品 Plan 或实施批准。范围消费[已确认试验约定](trial-agreement.md)；只读事实来源、具体代码和文档位置集中在[查证记录](discovery.md)。以下处理顺序、责任分工与交付物为建议，未执行接入、代码修改、构建或试验。

## 当前缺口与建议处理

| 编号 | 已知事实及不确定性 | 建议处理 | 满足前提的证据 | 责任与越界条件 |
|---|---|---|---|---|
| P1 版本基线 | 后端与独立前端均有未提交改动；当前所见功能不能自动等同两个 HEAD | 先定位包含所选预览功能的各自固定提交，比较该范围的未提交差异。优先使用可复现提交；若必要功能仅在未提交内容中，形成逐文件快照候选及差异，由代码所有者确定是否纳入 | 两仓独立完整 SHA、必要文件摘要、范围清单、隔离来源；构建所用字节与该清单一致 | 主控整理、代码所有者裁决；不 stash、reset、清理或提交原工作区，不默认打包全部脏文件 |
| P2 治理接入 | 候选业务仓根缺身份文件；当前模板源不能承载产品生命周期 | 根据既有接入协议提出隔离治理/实现目录方案，登记前后端独立仓库及只读源、允许写路径、验证命令、回滚点。是否需要新的 project-instance 管理根由接入检查决定 | 可读、合法的身份与接入记录；真实目录及 Git 身份一致；相关合同可被正常校验 | 生命周期主控与仓库维护者；实际初始化、attach 或迁移需单列范围。不得仅补一行身份字段绕过接入，也不重选既有业务架构 |
| P3 契约及批准 | 当前实现/测试有 scope；历史审查描述仅 taskCode。没有足够证据证明当前基线的完整批准 | 对齐 P1 选定实现与现有 OpenAPI、场景及批准字节。查找可复用的真实批准；不匹配则起草准确差异，按对应项目现行流程重新审阅 | 当前 API、切片及场景身份一致，批准绑定当前内容；原始批准来源可追溯 | API/资产维护者和相应批准人；访谈确认不能代替 API Freeze 或 Slice 批准。需要变更业务功能则按 Q8 停下重新选样 |
| P4 部署身份 | 所查 Java 源码未发现五项探针，仓外平台是否提供未知 | 先核查可用的部署产物/平台是否已有同源、只读、可绑定真实部署的入口；有则整理来源和字段映射；没有则单列最小探针方案，不在本轮直接实现 | 实际部署能返回与交付一致的 deployment_id、source_commit、openapi_digest、artifact_digest、test_data_digest；记录生成和绑定路径 | 部署维护者；不能手工写五个正确常量或用合成 Node 服务替代真实部署身份。新增探针或外置适配超出 Q12 |
| P5 最小装配 | 文档支持 PostgreSQL 和 Vue standalone；Java starter 仍有私有组件、Redis、注册/配置与文件管理等依赖，尚无最小装配通过证据 | 列明所选预览实际必需依赖，优先复用项目已有本地档位；拟定隔离控制库/目标表、合成任务及 READY 目标元数据、前端代理配置。不以 mock 业务 API 规避真实服务依赖 | 实际 Java 构建和启动日志、前端实际 pnpm 结果、数据库初始化/数据版本记录、真实页面请求；不包含凭据和业务数据 | 环境执行者；若需修改业务代码或新建平台能力才能运行，列缺口停下，不扩张成环境改造项目 |
| P6 正例与故障基线 | 存在合成维护用例，但没有本候选同基线真实 Java＋Vue 接收结果 | P1–P5 满足后，先建立 S0/S1 正例。将既有正常/空表行为作为候选基线核查，必要范围以当前批准契约为准；固定三类故障的变更点及对应拒收原因 | 同一基线的契约/部署与前端证据、有效交付包、正例通过、幂等结果、状态前后摘要；各故障只改变目标变量 | 交付方、接收方分别执行，主控判定；正例不通则故障场景不执行，不把连接失败冒充拒收成功 |

上述责任是拟分工，不表示已指定某位负责人或取得其批准。所有缺口状态目前为待落实/待核验；没有用历史模块测试或本轮文档检查将其标记为通过。

## 推进顺序与最小产物

1. **先形成 P1 的基线候选。** 固定两仓范围，明确已有提交与必要未提交内容的关系。与之并行只读核查 P2 的接入布局、P4 的现有探针来源、P5 的依赖清单。
2. **围绕同一基线收敛 P2–P5。** 新增接入/探针或批准需求各自形成可审阅方案。P3 必须以已选字节为依据，不能先批准一个模糊版本再补源码。
3. **准备工作完成后建立 P6。** 首先证明一个正确交付可通过正常入口，真实 Java 与 Vue 使用同一契约/部署。只完成验包不称业务已验收。
4. **再执行已确认矩阵。** 独立派生旧接口、错归属、旧批准故障；检查保留规则、修正重试和干净环境重复。上游未同步变化作为 O1 观察项保留能力边界。

建议最小准备包包含：两仓来源及基线清单、范围差异、接入布局草案、契约/批准映射、部署身份来源说明、环境依赖清单和实际验证入口。此阶段不创建占位 approved 资产、不填未运行的成功日志。

## 验证入口及证据边界

后端采用根 `./mvnw`，前端采用 `pnpm`；具体模块/测试命令待 P1 基线和 P5 装配确定后登记，不能把 README 示例当作本轮已经执行的命令。

交付工具现有入口为 `scripts/backend-delivery export|verify|import` 和 `scripts/verify-frontend-delivery`，参数引用本仓 [交付说明](../../../../../docs/process/frontend-backend-delivery.md)。它们须在正确登记的环境运行；模板维护脚本中的 Synthetic Supplier 测试只提供机制线索，不替代产品验证。

最终证据应能串联：源码字节 → 构建产物 → API/批准 → 测试数据 → 实际部署 → 交付包 → 接收结果。任一关系只能靠人为声明、缺少可核验来源时，保留为未闭合项。首轮不承诺独立防伪、全局最新性或生产安全结论。

## 停止、恢复与清理

前置缺口未满足时，报告具体缺项和依赖，不启动 S0 或把后续场景记为失败。对能够独立完成的只读证据整理可继续；缺口需要超出 Q12 的改造时，提出范围、验证和回滚方案后单独决定。

正式试验的恢复按 Q5/Q7：修正输入，复用合格的不可变战略快照，从正常入口重试。准备环境清理仅针对执行时登记的隔离目录、服务和数据，保留结果日志；原业务工作区和共享环境不作为回滚对象。没有预授权删除未知路径或停止共享服务。
