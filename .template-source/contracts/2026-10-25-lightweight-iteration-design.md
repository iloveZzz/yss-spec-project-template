# 轻量 SDD、任务实施与末端质检设计

本方案让已有项目从需求快速进入可执行任务，由 Agent 连续实施、质检和修复。首轮优化入口一致性、需求到任务的衔接，以及真实执行结果到完成校验的衔接；不重建流程引擎。

用户已在本聊天明确回复“批准这个设计稿，构建执行计划”，本设计进入执行计划编写。下表九项取舍已分三轮确认；设计获批不代表现行政策已改变、功能已实现、实施计划已获批准或发布已获授权。本轮维护设计和计划及其文档检查登记，不生成产品 Spec、Ticket、checkpoint 或批准记录。

## 1. 已确认的取舍

| 决定 | 本轮采用的行为 |
|---|---|
| Q1：优先场景 | 已有项目中的修复、行为调整和小功能迭代；新项目不作为首轮效果验证对象。 |
| Q2：主要入口 | 用户自然语言驱动 Agent；Agent 使用现有 CLI 和工程工具，用户不必逐步操作命令。 |
| Q3：风险边界 | 普通任务采用轻量主链；已识别高风险及已有正式绑定继续适用原正式路径。 |
| Q4：需求缺口 | Agent 先调查代码和材料、补出建议；关键业务、验收和范围取舍集中询问，局部技术细节自主处理。 |
| Q5：任务细化 | 总清单覆盖全部已确认验收，详细展开当前实施任务；后续任务结合实际代码渐进细化。 |
| Q6：质检修复 | 当前范围内的问题自动修复，重验受影响内容；需要新增范围、外部动作或真实条件时回交。 |
| Q7：需求确认 | 普通新功能汇总简短 SDD 与任务清单，一次必要确认后连续推进；复用有效确认，明确授权的普通修复直接实施。 |
| Q8：连续推进 | 有可验证进展就继续；同类失败先诊断，无固定机械重试轮数；缺真实条件或决定时说明具体阻塞。 |
| Q9：首轮范围 | 单一实现仓、无 API 变化的修复和小功能；包括 daily 与 standard 的衔接。兼容新增 API 沿用现有流程。 |

三次用户回复均为对当轮推荐项的明确选择。本文不把这些选择转换为尚未展示的实施计划、产品正式决定或 Git 操作授权。

## 2. 与既有设计及现行规则的关系

沿用[默认直接使用技能的架构优化设计](2026-10-23-skill-first-optimization-design.md)的依赖方向：普通技能不反向申请治理资格，治理按需调用技能。该文的 accepted 状态是已有设计记录，不证明其所有安装与迁移能力均已实施。本方案不新增安装模式，不把本轮轻量化变成普通工程的新前提。

| 当前实际入口 | 本方案如何接入 |
|---|---|
| 已明确提供的独立技能入口 | 直接使用当前需求、已有验收及宿主工具；不强制创建治理身份、标准 evidence block 或运行 route。新功能的简短方案确认是对需求与范围的确认，不据此创建正式批准包。 |
| 已启用现行治理政策的 Spec / Backend 实例 | 继续消费唯一交付路径政策；daily / standard 使用原 Ticket 与原校验，已有正式任务保持 governed。 |
| 身份非法、政策或工具能力不支持 | 停止依赖该身份或能力的动作，保留现场并说明缺口；不能把异常解释成独立技能模式或通过降级放行。无关只读调查可继续。 |

入口依据来自实际安装内容、用户选择及当前身份，不因缺少某个文件猜测模式。高风险事项使用其适用的现有正式路径；普通独立工程未选择治理时，先说明需决策的范围和风险，不自动初始化治理或改写旧记录。

已启用治理时，[request_triage](../../.template-spec/process/orchestration/entry/request-triage.yaml)继续持有路线条件，[普通任务交付](../../.agents/skills/yss-product-lifecycle/references/daily-delivery.md)继续持有记录与完成语义。本文描述目标交互和工程衔接，不新增第四条路线，也不自行改变排除风险、批准或校验含义。

## 3. 方案比较与选择

| 方案 | 主要取舍 | 本轮选择 |
|---|---|---|
| Agent 编排现有技能、CLI 和工程工具 | 复用现有记录与校验；补齐一致性、任务组织及收证接线，宿主负责实际执行。 | 采用；对应已确认的自然语言入口与连续交付。 |
| CLI 新建通用执行器、任务状态库和调度器 | CLI 接管命令执行、恢复和 Agent 调度；扩大权限、协议及维护面。 | 不纳入首轮。 |
| 仅压缩说明文字 | 改动较少，但不能证明任务可实施、证据可正确登记。 | 只作为入口一致性的一部分，不作为整体交付。 |

首轮不增加外部依赖、常驻服务、全局任务发现或新日志协议。若缺少确定性的证据整理能力，优先在现有生产者旁补最小格式整理函数；不以此新增业务命令执行器。

## 4. 用户能够看到的完整路径

| 步骤 | Agent 的动作 | 用户看到的结果与暂停条件 |
|---|---|---|
| 理解需求 | 读取请求、相关代码、已有约定和验收，复用当前记录；未知事实先调查。 | 简短说明理解和下一步；只询问仍缺少的关键业务决定。 |
| 组织 SDD 和任务 | 形成目标、范围、验收与必要风险说明；列出覆盖全部验收的任务，展开当前实施项。 | 新功能集中展示一次可审阅内容。普通修复复用已有授权；不逐任务再确认。 |
| 确认与准备 | 核验当前范围、实际工程和适用路径。治理实例按原合同准备 standard 决定和输入；普通独立技能不补治理资产。 | 有效确认不重复索取；真实决定或事实缺失只阻断依赖工作。 |
| 连续实施 | 默认同一 Agent 按依赖逐项实现，执行必要行为测试，记录真实结果，更新同一任务。 | 有意义的进度、发现和范围变化；内部任务细化不制造新的人工确认。 |
| 集中质检 | 对当前完整差异核验全部本轮验收、必要测试、适用技术规则和内容复核；治理实例再完成原有完成校验。 | 已满足验收、阻断问题和未覆盖边界；失败进入范围内修复。 |
| 修复及交付 | 修复阻断问题，重验受影响内容及原协议要求的当前绑定；无阻断且本轮验收完成后交付。 | 变更结果、实际验证、剩余限制与可用回滚依据；技术完成不自动触发提交、推送或发布。 |

“末端质检”是集中验收位置，必要编译和行为测试仍随实现执行。专业技术规则按影响面加载，不推迟到最后才发现本来无法实施的前置缺口。

## 5. SDD 与任务的组织

复用现有需求、Issue、Ticket、PR 或文档，不因本方案强制新建载体。治理实例沿用一张 Ticket；standard 的一页 Spec-lite 及真实决定继续原合同。首次展示包含需求结果、验收、允许范围和任务总览，不要求每个未来任务预先列出精确代码。

任务总览回答每项验收由哪些实施动作覆盖。当前实施任务说明要改变的可观察行为、允许范围、必要依赖、验证办法和完成条件；文件路径只在已定位且必要时写实，不虚构未来接口或工具命令。后续细化不得悄悄删减已确认验收；新增需求或实质范围变化回到已有决定边界。

任务进度和技术细化放在原 Ticket 的独立章节，SDD 正文保持稳定。在 standard 中，不通过持续改写已确认的 Spec-lite 来记录进度；确需改其字节时，执行原摘要与决定规则，不能自行定义语义等价豁免或给旧回复续期。

建议的最小阅读对应如下，只作为写作约定，不新增 schema 必填字段：

| 验收 | 实施任务 | 如何验证 | 当前结果 |
|---|---|---|---|
| 名称 100 字符可保存，101 字符被拒绝 | 修正共享校验，并覆盖创建与改名 | 根 Maven Wrapper 下的对应行为测试及实际返回断言 | 准备时写待执行；仅运行后登记实际结果。 |

默认顺序实施；本轮不新增多 Agent 调度。用户明确要求或任务实际独立时仍消费已有协作边界。

## 6. 质检、真实收证和完成判断

### 6.1 职责分工

| 执行位置 | 持有职责 | 不扩大到的职责 |
|---|---|---|
| Agent 与宿主工具 | 判断影响、执行工程命令、保存原始输出、实施和修复、真实内容复核。 | 不把模型判断包装成工具实测、真人回复或独立复核。 |
| 现有记录整理能力 | 从真实调用结果整理原合同字段，计算原始字节摘要，产生对同一记录的最小更新。 | 不生成未执行结果，不凭通过文字推断退出码，不覆盖用户正文。 |
| YSS CLI | 在声明支持时准备输入、核验来源和当前候选、校验既有证据；保持现有命令语义。 | 不因本方案把只读 MCP 或 verify-daily 变成命令执行器。 |

### 6.2 收证接线

实施前核验固定 CLI 的实际能力和现有生产者。已存在格式整理或写入能力时接入；确实缺少时补最小整理函数，消费宿主真实结果并输出原协议的记录更新，不新建命令执行服务。内部函数名和位置由实施者在核对实际调用链后决定，不在此预定公共 CLI 命令。

真实执行时捕获原合同要求的 argv、cwd、exit_code、executed_at 及可读原始日志；候选绑定在调用前取得，执行后核验相关输入和差异未漂移。取消、未启动、状态未知或缺原始结果分别保留，不补成功时间或退出码。原始输出能证明的范围与执行者的内容判断分别表达。

记录整理只更新本轮持有的日志、证据段及任务结果。写入前比较原记录与当前内容；用户同时修改时保留当前文件，重新读取和合并，不能整篇覆盖。不得仅改 footer 摘要、复写旧日志中的 candidate_digest 或 api_digest 来续期。

当前[输入准备接口](../../.template-spec/process/daily-input-preparation.md)只覆盖部分无 API 的 daily 输入摘要。standard 首轮沿原字段与原校验补齐准备；不假定它已支持 prepare-inputs，也不为了复用该参数改标签或省略真实决定。若确需扩展该接口，先在模板事实源写明兼容语义，再让 CLI 消费并验证，保留旧能力探测分支。

### 6.3 完成和自动修复

完成要求包括：本轮验收全部有结果；适用工程命令实际执行且通过；当前差异符合允许范围；适用内容复核完成且无开放阻断项；治理实例的现有完成校验成功。只读查询成功、记录完整或测试命令存在都不等于任务完成。

失败时区分业务实现问题、工程环境问题、收证格式问题、输入漂移和新范围。能在授权内修复的继续处理；同一症状重复出现时先调查机制，不机械重复命令。没有新证据、可行修复或独立可推进工作时，如实报告具体阻塞和解除所需的最小输入，不用进度文字维持空转。

修复后执行受影响行为与依赖的验证；只有现行消费者支持且可证明条件未变时复用旧结论。旧日志保持原字节，候选变化后的当前绑定仍按原协议满足，不引入跨运行通过缓存。可选优化建议保留待办，不增加完成门禁。

## 7. 最小接续能力

首轮只做当前任务的接续，不建设通用恢复系统。恢复时读取原需求、有效确认、任务记录、当前差异及可读执行结果，说明已完成、仍有效、已失效和下一步。正在执行、已结束未登记、结果未知分别对账，避免重复启动同一命令或重复实现已完成动作。

使用原 Ticket 和原运行记录，不新增 checkpoint。已有修改和失败材料保留；不知道结果时先调查，不能因换会话就自动重试可能产生副作用的命令。独立技能入口仍复用原会话或已有任务材料，不因此强制安装 runtime 数据库。

## 8. 预期改动面与实施次序

此表是设计分解，不是已批准的逐文件实施计划。实施前以实际消费者重新确认范围；Skill 仅改 canonical，再用原生成器更新必要投影和锁。

| 次序 | 预期范围 | 本批交付及边界 |
|---|---|---|
| 1：入口一致 | 根入口及按需政策说明、yss-product-lifecycle 与相关参考、Spec-lite 模板、对应 Backend 消费者与帮助来源。 | 同一普通需求在入口、模板和路由中得到一致下一步；消除无政策依据的额外限制。独立技能不被重新绑回治理。 |
| 2：SDD 到任务 | 现有 Spec-lite / Ticket 写作约定、适用实施与审查技能、必要案例。 | AC 到实施及验证可追溯；总清单完整，当前任务足够执行，后续细化不反复改已确认主体。 |
| 3：收证到质检 | 现有 Agent 编排、日志及原记录生产者；确有缺口时补最小确定性整理接线。 | 真实结果可稳定登记；实际命令失败、记录冲突、输入漂移均不能被总体通过覆盖。 |
| 4：消费者收口 | 实际受影响的 CLI 文档或帮助源、模板派生、平台投影、锁及分发验证。 | 没有只有文案变轻而实际入口仍多余阻断的半套交付；不因模板普通提交自动刷新 CLI 固定来源。 |

第一批前做有界能力核对：固定使用本设计引用版本或另行明确的完整 CLI 提交，确认现有 formatter / writer / runtime 接口及 standard 准备能力。只读或记录命令不视为业务执行器。网络不可用则使用已取得的固定材料并标出源码缺口；在依赖该事实的修改前补证，不用本地旧版推断新版缺失。

仅当模板现有协议无法表达目标时才修改协议消费者；不为此整体重写治理核心。CLI 仓的任何实际修改须先读其本地入口、使用匹配基线并取得适用实施范围，不以本设计授权覆盖另一工作区。初始化、迁移、安装事务和公开发布不属于本轮设计的实现目标。

## 9. 行为验收与效果观察

| 场景 | 预期行为 |
|---|---|
| 独立技能用于普通工程 | 无需补治理身份、evidence block 或 checkpoint；真实实施与必要验证仍完成。 |
| daily 普通修复，目标及范围已明确授权 | 复用原请求直接推进，同一 Ticket 保存真实结果；不再要求阶段批准。 |
| standard 小功能，无 API 变化 | 一次展示简短 SDD 与覆盖验收的任务总览，真实决定绑定当前主体；确认后连续完成实施、质检和范围内修复。 |
| 缺验收细节 | 先查代码及现有约定；关键业务选择集中提问，明确区分提议和已确认事实。 |
| 后续任务技术细化 | 不漏掉总清单中的验收，不因任务进度更新改写已确认 Spec-lite；实质变化重新决定。 |
| 实际工程测试失败 | 保存原失败输出，修复并取得新结果；不能生成通过记录或仅重写摘要。 |
| 测试未启动、取消或结果未知 | 如实记录具体情况，不能完成；恢复先对账。 |
| 测试后再次修改代码 | 原结果按当前绑定和影响规则重新判断，补真实验证及复核。 |
| 证据回写时用户已改 Ticket | 检测冲突，保留用户内容，重新读取并合并；不整篇覆盖。 |
| 用户确认后又改变需求、范围或关键风险 | 保留原决定及已有修改，停止依赖变化的动作，展示必要差异取得决定。 |
| 发现 API 变化、高风险或已有正式绑定 | 退出首轮新增自动化范围，按原兼容 API 或正式路径继续；不改标签放行。 |
| 只完成部分验收或仍有阻断项 | 报告部分完成与剩余事项，不宣称整体交付。 |
| 请求中断后接续 | 核对已有结果，保留失败材料，不重复有效确认或不明副作用命令。 |
| 技术完成但未授权提交、推送或发布 | 交付结果，不执行相应外部动作。 |

实现验证按实际修改选择现有行为检查及直接、传递消费者；已有检查足够时直接复用。只给新增非平凡逻辑补最小行为回归，不写镜像实现的测试，不默认运行全量或恢复已退役的测试体系。内容审查和工具断言分别记录，文案匹配不代替 Agent 行为验收。

效果观察复用实际任务材料，记录进入实施前的实际耗时、人工往返、质检返修耗时及交付后漏检。没有起止时间或完整原始消息时写 unavailable；确认与执行等待分开，新增需求不计作重复澄清。少量或不可比样本只作描述，不承诺百分比收益，不建设常驻度量平台。
