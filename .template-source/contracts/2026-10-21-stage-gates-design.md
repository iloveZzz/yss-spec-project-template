# Spec 四阶段门禁设计

用户已批准本会话提出的四阶段方案，并明确要求构建执行计划。本文固化该设计及实施所需的数据边界；它是模板维护设计，不是产品批准记录，不授予实施、合并或发布权限。执行计划见 [四阶段门禁执行计划](2026-10-21-stage-gates-plan.md)。本轮只编写设计和计划。

## 1. 目标与范围

完整 Spec 正式流程最多保留四个阶段出口：Plan 确认、Spec／适用产品设计基线确认、实施准入、交付验收。阶段内检查产生 `passed / failed / not-applicable` 结果，不办理独立批准，不要求岗位会签，也不要求每项检查创建审查任务或批准文件。

只做 Spec 时在第二个出口结束。现有 daily / standard 路由和直接脚手架请求保持原有适用边界。Backend 自身的门禁数量、阶段及现行政策不在本轮重设计范围；仅适配共享 CLI 与显式交接中的新 Spec 来源读取。

全局约束：

- 新 Spec 正式流程只有四个阶段门禁；内部检查没有独立批准记录。
- 用户原始决定、授权范围、当前实施合同及实际验证继续核验，不生成或改写用户回复。
- 已有授权且业务范围、验收、契约承诺和授权边界未发生实质变化时复用有效决定；技术细化不产生新的人工暂停。
- 默认同一 Agent 自检；只有明确用户要求或项目已知外部要求才使用独立复核。
- 修复只使受影响的检查、成果绑定及下游依赖失效；未知影响先调查，不默认全量复审。
- 历史批准、原始政策和冻结资产保留原义，只读核验；迁移不补造批准，不静默套用新政策。
- CLI 是治理语义的执行来源；Node 保留内容处理及原生调用适配，不另写一套阶段裁决规则。
- 普通材料分析与轻量 handoff 按现有约定处理；正式打包只在用户明确选择时执行。
- 达到本次交付目标即停止；交付验收不自动授权提交、合并、发布或部署。
- 本轮不新增第三方依赖、不修改 CONTEXT.md 的业务语言表、不创建产品 Ticket 或阶段 checkpoint。

## 2. 当前问题

当前 Spec 注册表有 8 个门禁、13 个内部检查。两个 Plan 内部检查仍要求 `evidence.approval-record`；资产自身的 `approval` 注解又触发批准核验，导致内容、检查、审查任务和阶段批准交叉依赖。去除岗位要求后，旧路径仍比较 `record.role_id` 与 `approval.approver`。

现有 `approval3`、内嵌 `approval.schema_version: 2` 和 Plan 组合审查是不同合同，不能只修改一个字段或把 `gate.*` 重命名为 `check.*`。长期修复需要把批准归属移到阶段出口，并把内容验证与阶段批准消费分开。

参考事实源：

- `.template-spec/process/lifecycle-registry.yaml`：阶段、门禁、检查及依赖。
- `.template-spec/process/orchestration/domain/{review,planning,progression}.yaml`：批准、Plan 审查和目标停止政策。
- `scripts/lib/{plan-spec-entry,native-approval,plan-review-control}.mjs`：Node 消费路径。
- CLI `internal/governance/{kernel/policy_versions,approval/gate_policy,plan_semantic}.go`：原生政策与批准语义。

## 3. 四个阶段出口

| 门禁 ID | 用户看到的阶段 | 成果及决定 | 推进方式 |
|---|---|---|---|
| `gate.plan-approved` | Plan 确认 | 目标、范围、关键规则、必要业务边界与方案决策 | 当前真实决定或有效授权延续 |
| `gate.spec-baseline-approved` | Spec／产品设计基线确认 | Spec、验收、适用产品设计和业务 Ticket 覆盖 | 形成成果后集中确认；无 UI 影响不要求原型 |
| `gate.implementation-admitted` | 实施准入 | 技术约束、适用 API 冻结、当前 Slice 合同、仓库与允许写范围 | 授权内自动核验；新实质取舍单独提交用户决定 |
| `gate.delivery-accepted` | 交付验收 | 按本次目标验证交付、验收与必要回退依据 | 汇总实际结果，按原约定验收；用户验收未取得时如实待确认 |

工作单元仍可拆分，工作单元完成不是新增批准点。Spec 草拟和适用产品设计可连续准备，在统一基线确认前保持草稿；不能先批准不完整 Spec，再因补原型默认要求第二次确认。

新政策退役五个独立出口：`gate.product-design-approved`、`gate.backend-architecture-platform-approved`、`gate.engineering-contract-approved`、`gate.slice-contract-approved`、`gate.strategic-design-handoff-approved`。其检查或操作分别归入基线、实施准入和显式交接；历史 ID 不重新分配给别的含义。实施准入采用新 ID，避免扩大旧工程契约批准的语义。现有工作阶段和工作单元可保留；新政策显式把 Spec 与产品设计两个工作阶段归到同一个基线出口，不要求新增阶段 ID。

实施准入可随切片复算，但同一授权范围内的每个切片不新增人工审批。某切片失败只阻止该切片及依赖工作，不撤销无关切片的有效结果。

## 4. 数据归属与版本

继续使用 identity2 / Profile3 / policy2 的基础组合，在 Spec Profile 的 `required_capabilities` 和编排合同的新 `stage_gates` 部件同时声明 `stage-gates-v1`。新部件使用 `schema_version: 1`；两处声明必须一致。缺能力、单侧声明或未知版本明确返回能力／迁移错误。旧 CLI 已对未知必需能力拒绝，不依赖版本号猜测。

Backend 不声明该能力时继续原政策。共享的角色无关能力与 task3 协议继续有效；检查是否需要批准，必须由当前 Profile 的门禁模式选择，不能仅凭 `GovernanceVersion == 2` 硬编码旧 Plan 规则。

| 数据 | 新格式 | 写入和兼容边界 |
|---|---|---|
| 阶段记录 | `stage-result` v1 | 每个阶段候选一份不可变记录；重做结果写新记录，checkpoint 选择当前引用 |
| 生命周期 checkpoint | v2 | 四个门禁引用阶段记录；内部检查从记录投影，不重复维护批准状态；v1 只读兼容 |
| 领域策略、阶段决策包 | v4 | 保留业务字段、来源与版本；去除必填内嵌批准，内容状态只表达 `draft / ready / stale / blocked`；v3 按原政策读取 |
| Slice 实现合同 | 继续 v4 内容格式 | 新政策下其实际字节须被实施准入记录绑定；不由内容中的 `approved` 字样授予写资格 |
| approval3、review-bundle3 | 保留 | 继续用于旧政策和未改造的消费者；新 Spec 内部检查不生成它们 |
| 显式 Handoff v5 | 保留运输格式 | 来源政策声明新能力时，现有 `record_ref` 位置引用阶段记录，接收端核验其资产成员；不合成兼容 approval3 |

新内容 v4 与 checkpoint v2 必须先获得原生读支持，再由模板默认生成。只有启用新能力的 Spec 默认生成内容 v4；未采用新政策的实例维持原生成语义。schema 代际登记、分发别名与历史读取按现有常驻两代规则更新，不覆盖历史 schema 的含义。

### 阶段记录的最小字段

`stage-result` v1 必填 `schema_version`、`kind: stage-result`、`feature_id`、`gate_id`、`scope`、`assets`、`checks`、`outcome`、`blocking_findings`、`provenance`。`outcome` 为 `ready-for-human / approved / blocked`；`stale` 由当前性核验得出，不回写历史记录。

- `assets`：`{ref, digest}`，需要稳定身份时另含已有 `id / version`。记录自身、可变 checkpoint 和未来成果不得成为自身冻结成果，避免自引用摘要循环。
- `checks`：`{id, result, inputs, evidence, reason?}`；`inputs / evidence` 都是带摘要的引用。失败和不适用必须说明原因；不适用依据属于当前输入。条目中不允许 `approval_ref / approver / role_id / countersigner_role_ids`。
- `provenance`：实际执行工具及 `execution_ref`，可引用现有任务；自检不强制稳定 Agent、岗位、账号或会话身份。独立复核只在实际要求命中时核验既有独立来源证据。
- `authorization`：`{kind, ref, digest}`，`kind` 为 `user-decision / continuation / stage`。`approved` 时必须有当前可核验的授权来源；实施准入可引用覆盖当前操作的基线阶段授权。`ready-for-human / blocked` 不伪造该字段。
- 原用户回复与阶段候选分开存放。批准核验读取当前候选及实际回复；不能把回复写进候选后继续沿用旧摘要。

实施准入的 `assets` 包含本次需要实施的实际 Slice 合同字节。批准整体方向不能批准未形成的未来合同；新增合同只有在当前已有授权覆盖其范围、技术细化可核验且必要检查通过时，才自动生成新的实施准入结果。

技术设计、空工程准备与 Slice 编译属于已授权的准备工作，可以先形成候选。机械骨架生成须核验实际技术选择、准备授权和写范围，但不反向依赖尚需该仓库与合同才能生成的实施准入记录；准备期间不得写业务实现。直接脚手架请求仍采用既有独立入口。适用 API 冻结先核验真实约束及授权，再将当前冻结版本纳入准入成果，不能反向要求准入已经完成。

## 5. 单向执行与失败处理

```text
形成成果 → 内容检查 → 阶段决定或授权复用 → 阶段记录 → 下游消费
```

内容验证器默认只验证内容、结构、引用、术语与版本一致性，不要求当前或未来阶段已批准。下游通过独立的阶段消费模式核验该资产是否属于有效阶段记录。领域策略先形成，阶段决策包引用其当前摘要；同一 Plan 出口统一确认两者，不要求两个子批准。

失败只报告：哪个阶段、哪个必要检查、哪个成果／证据、下一步修复动作。模板或 CLI 兼容错误归类为工具缺陷，停止受影响验证；不要求业务用户增加审批或补造角色。未命中检查不生成逐项人工说明任务，必要的不适用依据由影响分析提供。

普通修改更新当前成果绑定与实际验证。原始批准继续绑定原快照，通过既有差异与有效授权延续协议判断能否覆盖当前成果；不能只改摘要，也不建立无限延续链。业务范围、验收、契约承诺或授权边界变化时重新决定。

## 6. 目标与外部动作

- `spec-approved`：第二个阶段完成且本次适用业务票结果当前即可停止；不等待实施、打包或交付验收。
- `product-design-completed`：使用第二阶段的设计覆盖结果，不再追加产品设计批准。
- `backend-deliverable`：按当前后端职责和验证结果停止，不声称全业务验收。
- `business-accepted`：交付验收阶段通过且本次验收依据完整。
- 显式交接：验证选定阶段记录、当前资产成员及不可变包，复用决定；不增加第五个门禁。旧包继续按冻结原政策核验。Backend 没有发起交接时不被迫导入。
- 合并、发布、部署继续消费已有具体动作授权；阶段完成本身不生成这些授权。

## 7. 迁移与上线顺序

先建立新格式及显式能力协商，再实现原生裁决和调用方，最后同步文档、分发与固定来源。开发阶段仅在测试候选显式启用；现行根注册表的有效出口裁剪与默认 Profile 能力切换在最终集成中一起完成。激活能力只能发生在所需消费者和 Bundle 闭包均已具备时。

旧实例的模板同步与产品状态迁移分开计划。迁移复用现有事务能力，保留输入摘要、原记录、原政策及恢复信息，写入新路径；普通 `sync` 不自动批准或迁移产品成果。复用旧决定前必须按来源政策核验，记录新旧成果范围对应关系；有缺项的新阶段保持 `blocked / ready-for-human`。无权读取或无法核验旧证据时列出缺项，不删除失败证据来放行。

试点实例未提供；`return-rate-engine` 的真实状态复验需要后续可访问的项目根。计划中的合成场景不替代该实例的复验。

## 8. 验收

1. 新 Spec 注册表只有四个有效阶段门禁，内部检查没有批准引用或角色资格要求。
2. 真实完整的 Plan 只需一份阶段记录即可进入 Spec，不需要两个专业子批准。
3. 有／无 UI 的 Spec 均在统一基线出口收敛，目标达到后停止。
4. 已授权切片自动核验准入；失效合同、越界写路径、未完成 API 冻结或失败验证阻止受影响实施。
5. 内容变化后只复验受影响依赖；实质决定变化要求重新确认；原用户回复和历史快照不变。
6. 旧批准、旧包和无新能力的 Backend 保持原义；未知能力、篡改、跨范围批准或伪造通过均拒绝。
7. 新安装、显式同步、事务恢复与显式打包使用同一原生规则，不能出现文档已精简、运行时仍要求旧子批准的分歧。
