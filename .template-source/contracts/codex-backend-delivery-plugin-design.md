# Codex Plan 到后端交付插件实施设计

本设计把主模板的生命周期能力封装为 Codex 插件，让用户从普通目录或既有代码仓开始，经独立治理项目完成 Plan、Spec、适用产品设计、工程契约、后端实现及正式交付。唯一主控是 `yss-product-lifecycle`，终点是可供前端接收的 Backend Delivery。

本文记录已确认的产品范围及实施方案，属于模板源维护设计，不是业务产品 Spec 或获准的 Slice Implementation Contract。用户已通过“OK 进行下一步实现”并显式调用 `implement` 授权 M1，随后授权 M2，并明确继续“M3：固定 CLI 初始化与治理项目版本绑定”。当前已实现 M1 准备、M2 开发构建与 M3 接入，用户进一步授权 M4 职责范围、后端终点及恢复／派发约束；M4 已修改权威生命周期合同并同步派生资产；初始化与后端终点仅在隔离工具测试中验证，尚未创建真实业务示例或执行 Git 提交。实际安装和端到端验证仍待完成。

## 1. 已确认的范围

来源为当前任务中的 grilling 问答。用户首先明确回复 Q1 B、Q2 B、Q3 A，并补充必须符合生命周期规格与合同、主控为 `yss-product-lifecycle`；随后两次“全部应用推荐”分别确认 Q4—Q6 和 Q7—Q8。此记录用于追溯范围，不代替未来具体业务项目的批准或外部动作授权。

| 决定 | 已确认内容 |
|---|---|
| Q1 | 完成真实后端实现、验证及 Backend Delivery；前端接收是下游 |
| Q2 | 支持从普通目录或既有代码仓启动，引导初始化或接管 |
| Q3 | 第一版供本人及少量熟悉 YSS 的同事试用 |
| Q4 | 插件负责适用产品设计；生产前端代码交给下游 |
| Q5 | 首个试点在本机运行和验证；不将本机通过等同于跨机器接收通过 |
| Q6 | 独立治理项目，后端代码使用登记的 `external-repository` |
| Q7 | 第一版正式验证 macOS 上的 Codex 桌面端 |
| Q8 | 新建隔离示例，以真实后端贯穿验证；过程中补齐适用平台证据 |

“设备借用申请”是建议的示例题材，业务规则、架构、Spring Boot / Java 精确组合尚未批准，应在示例自己的生命周期中决定。

## 2. 可复用能力与已知缺口

源码研究见[研究简报](../evidence/maintenance/codex-plan-to-backend-plugin/plugin-research-brief.md)和相邻证据台账。

| 现有能力 | 本次如何使用 | 边界 |
|---|---|---|
| 主模板 `yss-product-lifecycle` | 作为唯一主控，保留现有路由、合同、批准和恢复规则 | 不手工复制维护另一套生命周期 |
| `create-yss-spec` | 复用固定快照的初始化与治理文件同步能力 | 当前 `templatePlan/templateApply` 是同步 API，不能当初始化 API |
| 后端专职模板 | 参考既有后端交付边界与验证实现 | 其入口消费已批准战略，不能原样充当 Plan 起点的插件 |
| `backend-delivery` | 验证、导出可移植后端交付包 | 编译通过或 JAR 存在不等于正式交付 |
| Codex `plugin-creator` | 生成本机支持的插件清单和个人 marketplace 条目 | 清单通过不证明动态技能路由、安装或业务执行正确 |

当前 `docs/engineering/backend-platforms.json` 中 Boot 2.7/JDK 8 与 Boot 3.5/JDK 17 的两条兼容记录均为 `blocked`，平台级 `capabilities` 和 `evidence` 为空。这是本次源码读取时的状态，不断言未来状态或真实工程一定不可运行。完整示例交付必须补齐所选组合及实际命中组件的原始依赖、构建、启动、消费和审查证据；不得改状态字段冒充通过。

## 3. 建议的插件与项目结构

插件工作名建议为 `yss-backend-delivery`，暂不作公开名称、版本可用性或发布承诺。实现源码和构建脚本建议由主模板治理区持有，安装产物输出到独立目录；不在插件安装缓存中维护权威源码。

```text
主模板权威源码
  ├─ canonical Skills、生命周期注册表、合同、校验器
  └─ 插件构建与接入适配（待新增）
       ↓ 固定源版本、生成、验证
Codex 插件安装产物
  ├─ .codex-plugin/plugin.json
  ├─ skills/                  由 canonical 生成的插件投影
  ├─ scripts/                 接入、诊断和打包适配
  └─ assets/                  固定版本 CLI/模板资源及来源清单

用户工作区（与插件安装目录分开）
  ├─ demo-governance/          Plan、Spec、设计、合同、Ticket、证据
  ├─ demo-backend/             独立 Git 后端实现仓
  └─ deliveries/              已验证的交付快照
```

上图为拟建结构，不是现有路径或可直接执行的命令。先使用本机 `plugin-creator` 支持的 Codex 兼容格式，实施时核对当前官方清单格式和本机验证器；便携根清单与 `.codex-plugin` 覆盖配置如有差异，先通过真实安装测试确定组合。第一版建议使用 Skills 与本地脚本，暂不新增 MCP、远程服务、自定义 UI 或后台自动运行机制。

## 4. 主控与版本所有权

1. 插件接入入口只处理目录发现、运行依赖、项目初始化计划和主控定位，不持有业务阶段或批准权。接入完成后调用唯一 `yss-product-lifecycle`，由主控派发专项技能并验收结果。
2. 插件中的 Skills 从 `.agents/skills` 生成，锁定来源提交、内容摘要、注册表及依赖资源；不能手改插件投影。插件自身新增入口也遵守 `maintaining-skills`，不以插件格式绕开仓库技能治理。
3. 分发闭包通过合同允许的调用、技能注册表、脚本依赖、模板与 schema 引用计算；不是把所有文件复制进包。Plan、Spec、适用产品设计、工程契约、实现、审查及交付所需能力必须完整。
4. 初始化后治理项目拥有自己的固定规则版本和可审计状态。插件全局版本不同于项目固定版本时，只做诊断与迁移计划；运行应消费项目匹配版本，不同时混用两版主控或校验器。
5. 必须验证插件技能命名空间与项目本地同名技能的发现行为。设计目标是业务执行只有一个可确定的有效主控；具体绑定机制在安装试验中定稿，不能只依赖“优先使用”的提示词。
6. 不把业务产物、凭据、运行日志或批准记录写进插件目录。运行依赖单独探测并报缺项，不假设其他用户拥有当前开发机的绝对路径和私有技能。

## 5. 首次接入、继续与恢复

普通目录先只读检查，不因缺少 `yss-project.yaml` 就推断它是项目实例。接入适配走初始化/接管检查，生成具体目标目录、写入文件和冲突计划；完成必要确认及真实初始化后，业务主控才按 `project-instance` 运行。这一顺序不能通过放宽主控身份检查实现。

已有治理项目直接核对身份、版本、Context 和 checkpoint。既有代码仓默认关联或创建独立治理项目，登记代码根、分支、CI、验证命令、回滚点和允许路径；不覆盖业务源码，不重跑脚手架，不自动转换架构。多个候选治理根无法确定时，才让用户选择。

第一版建议由接入脚本通过参数数组调用包内固定版本 CLI 的公开初始化路径。`templatePlan/templateApply` 仅用于其实际支持的同步用途；若需要新初始化 API，应在 CLI 权威仓单独实现和验证。运行时不依赖 `@latest`、主模板开发目录、兄弟源码仓或随时变动的网络模板。

主控接管后从最近可信工作单元继续，保留跨会话恢复、上游摘要核验、真实批准、Context reconciliation 及 drift 重路由。新会话、重新安装插件或机器重启不能自动解除阻塞。

## 6. 从 Plan 到交付的范围控制

以下是用户可见顺序，稳定 ID、门禁、产物和状态仍由现有权威合同定义：

| 环节 | 主要结果与必须保留的边界 |
|---|---|
| Plan | 目标、范围、规则、方案与入口审阅；进入 Spec 前验证真实决定 |
| Spec | 可验收需求与适用架构输入，不提前实现代码 |
| 产品设计 | 按影响面生成或复用页面、状态、原型及批准；不得因后端终点跳过命中要求 |
| 工程契约 | 技术、数据、API 设计与批准；适用时冻结 OpenAPI |
| 实现准备 | 既有工程接入，或架构平台确认后的机械脚手架及验证 |
| Ticket 与 Slice Contract | 正式窄切片、当前合同、批准及完整 `ready-for-agent` 计算 |
| 后端实现与验证 | YSS 专项技能、行为测试、独立审查、构建、运行及部署身份等证据 |
| 后端交付 | 战略快照、当前冻结接口与后端合同、构建部署及成功/失败证据绑定，正式导出和验包 |

“后端交付后停止”需要机器约束，不能只写在入口描述。实施时应在主模板权威合同中设计受限交付范围或与之等价的配置，明确交付所有者、可执行工作单元和终止判断，再由查询、流转、恢复及派发入口共同校验。M4 将该配置实现为 `execution_scopes.plan-to-backend`，终点为 `work-unit.backend-delivery`；只终止本次后端职责，不替代业务或发布终态。

产品需求可以有 UI 影响，而本轮实现职责仅为后端。必须区分产品设计依赖、后端切片职责和下游前端待办：保留产品设计要求，不强行派发生产前端代码，也不把尚未执行的前端实现/验收标为已通过。若现有主模板就绪公式在这种组合下要求前端资产，应在权威合同中按职责澄清并补反例，不能在插件包装层跳过失败。

终点报告只表示该切片的后端可交付，列出下游尚需完成的接收和前端工作；不能宣布整个业务功能完成。生产部署、Git 提交/推送、远端创建、插件公开发布和业务发布仍分别检查授权。

## 7. 交付验收方式

隔离示例使用真实可启动的后端，覆盖至少一个成功和一个拒绝场景、持久化结果、冻结接口及本机可探测部署身份。只有当前适用的原始批准和验证证据齐备才导出。来源政策要求提交身份时先完成真实 Git 授权，不能用虚构 SHA 或测试 fixture 充当源码身份。

交付包验证以正式工具为准。在单独的临时接收项目中验证可离线读取、来源和摘要完整，并在本机环境有效期间验证适用接收检查；接收验证用例不实现生产前端，也不把其 `inputs-verified` 解释为前端合同获准。

新建工程的 DDD/MVC、Boot/Java 与 YSS 父 POM/BOM 组合在示例生命周期中确认。平台缺证据时报告阻断并补证，不能为验收演示选一个未验证组合。平台补证可能涉及外部组件仓及制品仓发布，具体变更和外部动作另按范围处理。

## 8. 实施顺序与完成条件

| 工作包 | 改动与交付 | 完成条件 |
|---|---|---|
| M1 依赖和边界设计 | 技能/资源闭包、主控版本归属、后端终点及 UI 职责合同差异 | 明确权威修改点及反例；不改变已确认产品范围 |
| M2 插件构建 | 源码到安装产物生成、来源锁、插件清单、依赖探测 | 插件结构校验通过，路径可移植，无本机私有引用 |
| M3 项目接入 | 固定 CLI 初始化、关联治理根、既有仓接入、冲突/回滚 | 从插件安装产物初始化成功；失败不破坏用户文件 |
| M4 生命周期集成 | 主控路由、职责范围、交付终点、恢复、批准与独立审查接入 | 合同查询和所有执行入口约束一致；缺批准和越界用例被阻断 |
| M5 平台与真实示例 | 补适用平台/组件证据，按实际生命周期从 Plan 到后端交付 | 实际构建、启动、契约测试、独立审查和导出/接收证据齐备 |
| M6 本机安装与试用 | 个人 marketplace、安装、新会话发现、更新与恢复操作说明 | 不依赖主模板开发目录完成试用，版本不匹配有明确恢复路径 |

M1 后才冻结实现依赖清单。M2—M4 与平台事实调查可在无依赖部分推进；M5 不能绕过平台证据阻塞。M6 的安装验证应提前做小规模试验发现命名空间问题，最终验收仍覆盖完整安装产物。

## 9. 必须覆盖的验证场景

- 正例：空目录接入；既有代码仓关联独立治理根；已批准上游复用；Plan 到真实后端交付；新会话恢复。
- 身份与路径：模板源被拒绝执行业务；未知身份不能直接写入；脏工作树不被覆盖；未登记和越界路径被阻断。
- 批准与证据：Spec 草稿、父 Ticket、未批准合同不能启动实现；篡改摘要、缺少原始用户回复、过期接收或合同均不能放行。
- 职责与终点：UI 产品设计保留；不派发生产前端实现；后端交付完成后不自动发布，不伪造全业务完成。
- 打包与版本：断开主模板开发目录后依然可用；依赖缺失明确报错；同名主控和版本不匹配不会随机选择；升级不改旧批准字节。
- 交付：合成 fixture 只验证机制；真实示例证明运行链路；验包与实际服务探测分别留证；缺部署身份不能标可接收。

插件 manifest、Skill frontmatter、引用和锁检查只证明结构。必须增加安装后实际调用、阶段流转、恢复与交付验证，才能宣布首版完整可用。

## 10. 当前状态与下一动作

产品范围 Q1—Q8 已确认，后续用户明确授权下一步实现。M1 的只读依赖规划与选定合同/Skill 版本比对已落在[准备工具](../plugins/yss-backend-delivery/README.md)，后续安装、初始化和示例业务仍按分阶段验收，不把准备报告当业务批准。

M2 构建复用本机 Codex manifest 形状，由 canonical 生成顶层诊断入口，完整源布局放在 `assets/template/`，以固定版本解析器计算模块依赖并保留治理数据家族。来源清单记录原文、转换与输出摘要，外部平台技能不打包。开发构建只提供验包、依赖诊断和包内 Plan 查询；未实现业务派发入口。

M3 以 `cli-pin.json` 固定已有 CLI 及其 committed 模板快照，完整打包原始分发文件；不修改或重建 CLI 子仓快照。`project-plan` / `project-apply` 通过真实初始化命令生成独立治理项目，或仅为匹配版本的已有实例写入绑定记录。`project-check` 对照固定 CLI 核验核心代码/合同和 Context；`query-project` 只运行项目本地查询，不消费包内较新预览规则。版本变化只报告迁移需求，不自动覆盖。后端路径关联是接入候选，不代替正式实现仓库登记。

M4 在主控权威合同新增 `execution_scopes.plan-to-backend`，注册 `work-unit.backend-delivery`；项目显式选择职责，查询、流转、实现上下文和派发共同消费。UI 产品设计继续保留，生产前端由下游承接。终点工具复验当前独立审查、真实提交身份、源文件和正式包，终点恢复不自动解锁或发布。固定 CLI 保持原字节；开发包显式携带主模板工作树覆盖层，仅新建项目可应用，原项目升级仍需独立迁移计划。

下一步 M5 为真实示例补齐平台与交付证据。实际安装后的主控发现、动态执行资源和真实交付尚未验证。涉及 Skill 变更时使用 `maintaining-skills`；涉及生命周期边界、生成语义和跨仓合同的改动按 L3 维护，完成受影响 canonical、投影、锁、CLI 快照及适用验证。正式分发使用已提交的固定来源，不能把未提交工作树当发布快照。

本设计文档本身不授予 Git 提交、推送、制品发布、插件安装或业务环境变更权限。前一轮用户手册改动继续保留，不混入插件完成证据。

## 统一调整已确认方案

用户确认名称＋主入口、实现或接入后交付、单一公开入口、显式计划后迁移。新版本 0.2.0-dev.1；保留主控及生命周期稳定 ID，内部职责标识 plan-to-backend 保持兼容。旧 M4 历史记录和包不改写。实施接口和迁移边界见 ../plugins/yss-backend-delivery/README.md。原 M1—M4 记录的能力边界以历史证据为准；新版本另验安装发现和真实交付。
