# 前后端专职 Harness 拆分方案

状态：`verified`。双输入校验、专职模板、本地初始化与生成实例接力均已实现并通过五仓校验。用户已授权提交推送；四个子仓代码已推送至 GitHub，主仓随本次交付更新真实 gitlink。

本文记录模板维护范围、已确认决定、拟议合同和实施验收清单。它不替代生命周期注册表、仓库 profile、已批准的 Slice Implementation Contract 或执行证据，也不直接放行任何产品任务。

## 1. 已确认的目标与边界

将通用研发模板拆出后端、前端两个专职模板项目，以独立 Git 仓库和真实 submodule 接入模板源。现有 `yss-harness-dev-agent` 暂留兼容，新项目优先走新链路，既有实例通过单独迁移切换。

两个专职项目分别执行，共享业务基线与跨仓切片，由统一管理方汇总最终业务验收。仓库拆分不把一个业务功能拆成两个互不关联的完成结论。

本方案讨论的是两层不同的仓库关系：

- 模板维护层：当前模板源通过 `submodules/` 管理可复用 Harness 模板，不承载具体产品的运行时代码。
- 产品实例层：由模板生成的研发项目接入独立实现仓；选择 submodule 承载运行时代码时，执行既有 `apps/backend/<project>`、`apps/frontend/<project>` 接入规则。

维护涉及 Harness、跨仓合同和分发集成，不在当前 `template-source` 创建产品 Spec、OpenAPI 或垂直切片 Ticket。当前实施命中 `lifecycle-gate`、`cross-repo-contract` 与 `core-validator`，按 L3 模板维护执行；业务 TDD 为 not-applicable，因为修改的是流程合同、确定性验证器与模板分发，使用阻断场景及生成实例集成验证。

## 3. 职责与权威资产

| 参与方 | 维护内容 | 接收与输出边界 |
|---|---|---|
| 战略设计项目 | 业务目标、责任边界、规则、Spec、页面流程、原型及视觉基线原件 | 输出已批准、可追溯的战略交接快照 |
| 统一管理方 | 已承接基线的版本引用、跨仓切片、阻塞关系、验收汇总 | 记录源资产和承接关系，不另写一份 Spec 或原型作为并列权威 |
| 后端专职项目 | 后端战术设计、API 契约、代码、接口验证与部署证据 | 接收战略与消费需求，按切片输出经过验证的真实接口交付 |
| 前端专职项目 | 前端工程设计、组件与 API 适配方案、代码、视觉与交互验证证据 | 联合接收同版战略及后端交付，输出当前切片的前端验收证据 |

统一管理方是统筹职责，不要求额外新增一种模板；具体产品接入时绑定实际管理项目和责任人。战略模板现有终点仍为战略交接，不能直接把它视为已支持下游整体验收的主控。

API 由后端维护，冻结前包含前端消费需求确认。前端不机械复刻聚合和持久化设计；有领域影响时按影响面处理，完整 DDD 战术设计不因前端独立成仓而自动触发。

## 4. 前端接收与执行条件

前端项目可以先执行只读验包、列出缺口和回交责任方。以下“输入就绪”条件全部成立后，才进入正式前端工程设计、实现计划和合同准备：

| 条件 | 校验内容 | 未满足时的处置 |
|---|---|---|
| 战略输入完整 | 战略、Spec、规则、当前切片成功与失败场景，以及适用的交互、状态矩阵、原型和视觉基线具备当前批准绑定 | 缺资产或批准回战略方；不得用空模板补齐 |
| 后端交付完整 | 冻结 API、后端代码/构建/部署身份、真实接口环境、数据准备方式、接口及契约验证证据齐备 | 缺项回后端方；仅有 OpenAPI 或构建通过不足以交接 |
| 版本匹配 | 后端交付绑定同一战略基线、切片与接口契约摘要，批准和验证针对同一组资产 | 不匹配、已知漂移或撤回时重新接收 |
| 运行条件可用 | 从前端执行环境验证指定后端版本可访问，并具备验证当前切片所需的配置及测试数据 | 网络、环境、版本或数据不满足时阻断相关任务 |
| 承接有效 | 目标词汇对账通过；规则、场景、接口和前端验收用例可追溯；相关阻塞已清除 | 冲突回对应权威方；依赖无法确定时扩大阻断范围 |

“输入就绪”允许准备前端实现资产；正式写代码另须已登记可写的实现仓、通过校验的 `frontend_implementation_plan`、已批准且当前的 Slice Implementation Contract 和既有 `ready-for-agent` 公式全部成立。这样不会出现“必须先有实现计划才能开始起草实现计划”的循环依赖。

前端提前参与只发生在上游页面与接口需求确认中，不放行前端项目在缺少两类交付时搭建页面、生成代码或执行正式实现。缺失输入不能由 Mock 冒充真实后端交付。

上述条件已接入正式阶段路由、合同编译、任务派发、恢复与验证入口，运行时重新执行校验器。现有前端视觉与交互验证要求继续复用。

## 5. 便携交接与变更回流

战略包复用现有原字节快照、manifest、逻辑摘要、批准绑定和导入收据机制。后端交付增加以下信息，并引用原战略包的身份与摘要：

- 本次交接范围、切片引用、已实现规则与成功/失败场景、已知限制和责任人。
- 冻结 OpenAPI、版本及摘要、消费需求确认、接口与契约验证结果。
- 后端代码提交、构建产物及部署版本、运行环境引用、数据准备方式和当前验证证据。
- 适用的延期项、影响范围、后续任务、验证计划与目标版本。

前端单独检出后，应能解析全部必需的业务、契约和视觉快照，不借助兄弟仓的绝对路径；快照不成为目标仓新的战略权威。真实服务通过登记的环境访问，凭据只使用环境或凭据代理引用。验包不执行包中的来源代码。

离线可验证包完整性和所选批准基线，但不能据此声称已检查未同步的源仓最新变化或真实服务当前可用。恢复执行时对约定基线、已知上游变更及指定服务版本重新核验；运行条件未知时不放行实现。

前端发现接口缺口后提交可复现业务场景；后端继续负责接回修正。影响契约时返回 Draft/Review/Freeze 及依赖合同重编译；改变业务规则则回战略方。已知变化使相关批准/计划/合同失效，依赖明确时仅阻断相关切片，未知时扩大范围。

## 6. 三种完成条件

| 结论 | 必需证据 |
|---|---|
| 后端可交接 | 当前切片 API 符合冻结契约；指定真实部署可用；业务行为、权限与失败场景验证及数据准备证据可读 |
| 前端可验收 | 已接入指定后端版本；当前切片页面、异常状态、权限体验、交互与视觉验证通过；实际 `pnpm` 命令和退出码齐备 |
| 业务切片完成 | 同一战略、契约、后端部署和前端版本组合通过端到端业务验收，由统一管理方汇总并核验所需批准 |

后端可以结束当前实现任务并继续承担缺陷和契约修正责任；整体切片必须等待前端及业务验收。发布仍独立遵守既有门禁。

## 8. 跨仓实施顺序与验收

以下是维护工作包，不是产品垂直切片 Ticket。1–5 已形成可执行实现并通过本轮校验；6 已完成远程建仓、子仓代码推送与真实 gitlink 接入。

| 顺序 | 维护范围与写入边界 | 可检查的退出条件 |
|---|---|---|
| 1 | 当前模板源：共享交接 schema、接收校验器、生命周期/合同接入及最小 Skill 引用 | 缺战略、缺后端、失配、过期、环境不可用都不能进入前端正式执行；完整输入可准备合同且不会直接获准写代码 |
| 2 | 后端专职模板：仓库 profile、角色/技能闭包、后端交付合同及验证 | 可从批准战略按业务切片产出交付；后端单独完成不能被解释为整体切片完成 |
| 3 | 前端专职模板：联合接收、工程设计、计划/合同、实现、前端验收 | 单独检出可恢复；所有入口遵守输入条件；真实服务与视觉/交互证据完成绑定 |
| 4 | 初始化与分发：目标模板选择、metadata 身份、固定快照、共享技能投影与 lock | 生成实例身份正确，后端/前端 profile 不串用，旧通用实例的 sync 不会静默改换 profile |
| 5 | 集成验证：临时战略、后端、前端实例及受控真实测试服务 | 完整接力和异常回流通过；实际命令、版本、摘要与退出码可读取 |
| 6 | 兼容与仓库接入：迁移说明、回滚、模板子仓与父仓 gitlink | 既有实例可维持原流程；新链路可用后再评估旧入口退役；提交/推送与发布分别遵守授权 |

两个公开仓库已创建：`https://github.com/iloveZzz/yss-harness-backend-agent` 与 `https://github.com/iloveZzz/yss-harness-frontend-agent`，均为 main 分支，挂载于同名 `submodules/` 路径。gitlink 已更新为包含实现代码的可获取提交，详情见[GitHub 交付记录](../evidence/maintenance/backend-frontend-split/git-delivery.md)。

新模板使用仓库内 `scripts/instantiate-harness`，无需新增 npm 包。干净提交与文件摘要共同冻结；维护测试显式允许工作树时标记非发布快照。现阶段仅支持新目录初始化，原地 sync/迁移不受支持，旧通用 CLI 保持原行为。

共享内容只修改 canonical 来源，再生成投影和分发快照。正式 submodule 通过既有 Git 接入方式形成，不能复制模板目录冒充 gitlink。Git 提交/推送逐仓计算授权；子仓可获取提交准备完成后再更新父仓 gitlink。

既有 `create-yss-harness-dev` 工作树存在本轮开始前的改动，本轮不触碰。后续分发适配先核对该改动与目标任务的关系，不重置、不覆盖。

## 9. 必须覆盖的验证场景

- 战略或后端交付缺失、损坏、批准不匹配：只能接收诊断，不能执行前端任务。
- 契约文件存在但服务不可访问、部署版本不同或测试数据缺失：阻断相关实现。
- 两类输入通过：可以准备前端计划与合同；合同未批准时仍不能写代码。
- 一个切片输入齐备，另一个仍有缺口：只允许依赖明确且条件通过的切片继续。
- 前端独立检出、工作目录改变、无兄弟仓：包内快照可解析；真实服务另行验证。
- 后端接口变更、战略规则变更、视觉基线变更和批准撤回：依赖失效正确传播，旧结果不能复用放行。
- 包校验通过但关键业务场景未通过：不能判定业务切片完成。
- 老通用实例更新：不会被自动转换为专职 profile；迁移失败有可执行回滚。

日常实施采用各受影响仓库的 `scripts/verify-template-fast`，正式候选与发布按现行验证分级执行。新增/修改 Skill 时使用 `maintaining-skills` 并验证投影、lock 与调用方；模板首次冻结及最终发布执行完整校验，CLI 分发集成未闭合不得称可发布。

新增测试覆盖交付批准绑定、便携包、缺输入阻断、服务版本与数据变化、接收说明字节漂移、专职 profile/metadata 失配、跨端派发以及生成实例接力。测试服务为独立维护测试进程，不代表真实产品后端或产品前端验收。
