## 设计包与范围

需求依据是 [最终决议](spec-skill-optimization-notes.md)。设计包包含 [T02 流程与职责](spec-profile-target-flow-design.md)、[T03 审批与状态](spec-profile-approval-state-design.md)、[T04 产品设计裁剪](spec-profile-product-design-depth.md)、[T05 tracker 适配](spec-profile-tracker-design.md)、[T06 初始化与技能就绪](spec-profile-initialization-design.md)、[T07 清理范围](spec-profile-cleanup-design.md)。

本汇总集中表达需要审阅的设计选择。它不把早期建议变为用户已批准的要求，不覆盖用户确认的非技术边界、tracker 模型或不支持自动迁移的决定。实施细节由后续计划落实到具体消费者。

## 供审阅的目标方案

1. 保留 life 作为轻量路由，原生综合与显式 to-spec 共用 life 持有的规格方法。取消新 Spec 对旧四阶段资格、领域机器包、技术/API、实现切片和独立 Handoff 的默认依赖。
2. 新建/接管默认 governed，但该安装方式只决定资源供给，不要求执行旧产品生命周期。已有新流程配置复用，旧实例由人工迁移，不自动转换。
3. 每个工程选择本地 Markdown、GitHub Issues 或 GitLab Issues 为主 tracker。远程模式以远程正文为当前内容权威，本地草稿与批准快照不作为可编辑同步源。
4. 仅实际审批动作需要真实用户批准，复用有效决定；没有明确审批要求不补固定批准节点。已发布、已批准、可实施分别判断。
5. AI 按问题和风险选择文字、流程、低保真或原型，只有实际需要的产物才创建和验证。
6. 自动检查初始化与技能缺口，已授权且无冲突时连续完成。专项按需安装和读取，当前技能 user-only 规则在实施前仍有效。
7. 下游通过规格引用消费业务要求，自行承担技术和实现职责；不固定 Backend，也不由 Spec 自动创建下游工程或 Git PR。

## 工程选择收敛建议

此前若干事项在 T06/T07 间互相引用。为避免实施计划再次悬空，建议以下选择作为设计基线接受审阅；最终代码位置和必要 schema 变更在实施计划中列明。

| 项 | 推荐选择 | 实施必须验证 |
|---|---|---|
| 新流程识别 | 使用 distribution.specWorkflow，值 matt-spec-v1；由支持它的 Bundle 与 CLI 在 init/attach 生成 | 识别绑定实际来源/安装政策；未知值拒绝受影响操作，手写标识不能替代完整性检查 |
| 核心技能 | yss-product-lifecycle、to-spec、grilling、domain-modeling、i-have-adhd；共享规格方法与 tracker 必需参考随之交付 | 计算真实引用闭包，移除旧阶段前置；若发现必要依赖缺失，更新精确清单并说明原因 |
| 按需技能 | yss-research、产品设计相关技能 | 按实际问题加载；setup 通过用户级引导或现有可发现入口复用，不要求每个项目重复安装 |
| 自动设计调用 | 本项目 yss-prototype-stage / prototype-review 改为模型可调用，按风险触发；to-spec 保持显式入口 | frontmatter、openai 元数据、注册表及投影一致；共享 Backend 行为不得被静默改变 |
| tracker 权威配置 | 沿用 issue-tracker.md 单一所有者，三种平台选择；本地默认路径可建议 .work | 新 Spec 最小 schema 与解析器一致，不继承业务票/阶段版本必填项 |
| 状态 | 内容 draft/reviewable；审批使用可读决定说明；发布记录实际定位与结果 | 不新增全局阶段状态机、不默认镜像标签，不以五态标签授权实施 |
| 远程工具 | 优先已连接的适用平台工具，不足时 gh/glab；不新建三平台原生 HTTP 引擎 | 检查工具实际支持的读取、评论、创建更新、并发及恢复能力，未支持项给出边界 |
| 发布定位 | 已有 URL/路径直接复用；新远程创建使用随机稳定标识，写入目标与恢复记录 | 有未知创建结果先查明，不按标题重建；本地简单规格不强制额外发布记录 |
| 批准内容 | 用可还原已有版本；否则仅在确有批准要求时保存实际展示内容和设计快照 | 不依赖可变 URL；不强制 commit、摘要链或机器审批包 |
| 不适用旧命令 | 新 Spec 对旧阶段/Handoff/实施命令返回明确不适用，不隐式执行旧内核 | 保留 Backend 自有命令语义和用户文件/事务保护，不以恒通过替代校验 |

这些选择是设计建议，不是已实现能力或额外业务门禁。若精确依赖或工具能力证明推荐选择不可执行，计划中必须说明替代和影响；涉及用户已确认边界的变化才重新请求决定。

### tracker 最小配置合同

建议沿用 issue-tracker.md 的 YAML frontmatter，唯一配置对象为 tracker：

| 字段 | 必需条件 | 含义 |
|---|---|---|
| platform | 始终 | local-markdown / github / gitlab |
| root | 本地模式必需；远程需保存草稿、恢复或批准材料时配置 | 工程内受保护的相对工作根，默认建议 .work，不自动覆盖已有值 |
| repository | github 必需 | 明确的 owner/repo |
| host | gitlab 必需 | 明确的实例 HTTPS 地址，包括自建实例 |
| project | gitlab 必需 | 完整项目路径，操作时可解析实际项目 ID，但不据此改写用户选择 |

不把 lifecycle_tracking_version、business_ticket_version、remote_mirror、legacy_roots 作为新 Spec 必需配置；不自动迁移旧格式。展示表格如需保留只作为派生说明，不能第二次维护配置值。凭据引用使用实际工具配置，不将密钥写入此文件。此处字段为推荐基线；schema 与消费者调整是实现任务。

### 共享 Backend 的隔离策略

先在既有 Profile 合成/生成层落实 Spec 与 Backend 的政策、参考和调用元数据差异，再重写 canonical 共享技能。保留共用方法，Profile 专属流程以明确的条件化参考或已有 overlay 生成；不直接手改派生副本，也不要求新 Spec 承担 Backend 的旧治理前提。

Backend 的现有有效树与实际调用语义作为隔离检查基线，特别包括 life 路由和原型技能 user-only 规则。对新 Spec 修改的调用权限不得无条件投影到 Backend。若现有生成器无法隔离，先增加受影响的生成能力并验证，再修改共享正文，不能以“最后跑一次测试”替代前置隔离。

这项工作与新流程标识合同一起，是实施计划的前置任务；保护 Backend 不等于为旧 Spec 建设兼容或迁移。

## 跨文档审阅重点

- 安装默认 governed 与新 Spec 不再走旧阶段内核：两者必须在入口、CLI、分发中同时落实。
- 自动引导不能依赖尚未安装的 life，宿主未暴露用户级 setup 时明确限制。
- 新实例身份真实性与旧产品资产前提分开，不能因保留身份检查再次要求 Context/Plan/checkpoint。
- 原型深度与实际验证相匹配，材料产生但关键问题阻断时不报告完成。
- tracker 的评论是来源，普通建议不自动成为规则；修改批准内容时同步纠正当前稿批准说明。
- 远程写入与业务批准复用真实授权但不互相推导；创建超时与更新竞争窗口不能假称原子安全。
- Spec 调用元数据改变后必须检查 Backend 的实际有效树，不能仅比较文件名或目录是否存在。
- 模板工作区与固定 CLI Bundle 分开核验，不把文档或模板变化当成发行已生效。

## 进入实施前的交付要求

设计获批后，T08 先编写实施计划，按模板/CLI/生成物拆分有依赖的具体任务；明确新旧识别、入口切断、最小闭包、tracker 适配、共享边界及验证。计划不包含旧实例迁移或下游实现重建。

必要验证覆盖新 governed Spec 主线、三 tracker 的操作边界、技能元数据、身份与事务保护、Backend 共享反例和固定 Bundle 装配。实际外部测试和未覆盖条件分别报告，不以设计检查替代运行结果。

本轮没有安装、远程写入、运行代码修改、提交或发行。
