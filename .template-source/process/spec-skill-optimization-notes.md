# Spec Profile 优化最终决议与待办

日期：2026-10-29。状态：需求澄清已完成，待现状诊断、方案设计与实施。

本文是本轮讨论的最终需求基线，替代此前笔记中的历史方案。记录已确认的方向、范围和后续待办，不表示运行政策或代码已经完成修改。

## 目标与范围

以 Matt Skills v1.3.1 为基线，重新设计 Spec Profile 的非技术规格流程，解决阶段、技能编排、初始化和下游协作混乱的问题。允许删除或重构旧逻辑，不以继续保留既有流程为前提。

Spec 负责问题、目标、使用者、业务规则、范围、非目标、可观察行为、异常、验收要求及适用产品设计。技术设计、API 契约、实现任务切片、实施准入、代码实现和工程验证由下游 Profile 承担，不属于本次建设范围。

目标主线为：

```text
识别目标工程与配置
  → 按需完成初始化及技能就绪
  → 澄清需求、查证事实、统一业务词汇
  → 综合 Spec，并按需补充产品设计
  → 完成适用的人工审批
  → 发布或更新所选 Issue tracker 中的规格
  → 下游通过引用消费规格及相关材料
```

这是职责主线，不要求每一步单独建阶段记录或取得批准。草稿保存、首次发布与审批的具体先后关系由设计确定，不将全部文件写入都视为正式批准。

## 已确认决定

### 1. 采用 Matt 的 tracker 模型

Spec 发布到项目选择的 Issue tracker，支持以下三种适配：

- 本地 Markdown。
- GitHub Issues。
- GitLab Issues。

三种适配承载同类规格内容，按工程配置选择。已有合法配置优先复用，缺少真实用途决定时再询问。

不建设 Markdown PR 模型，不要求本地 Markdown 自动同步远程 PR/MR，也不并行维护多份可编辑事实源。Git PR/MR 属于下游实现阶段，本次不改造其执行逻辑。

### 2. Spec 保持非技术职责

Spec 描述用户问题、业务行为和可验证结果。Matt Spec 模板中的 Implementation Decisions / Testing Decisions 不直接照搬；已知技术约束可作为来源或约束引用，技术方案及测试工程设计交给下游。

产品设计用于澄清用户任务、交互、页面流程和状态，不扩展为生产前端实现。

### 3. 下游直接消费规格

下游不固定为 Backend。通过 tracker 条目及其关联材料取得当前规格、验收、相关决定和未决项，不再设置独立交接包或固定 Spec → Backend 流程作为必经条件。

设计须明确规格修改、审批失效和下游反馈的处理方式；不得用“已发布”或某个标签推断已经获得业务批准或实现授权。下游内部工作流不在本次改造范围。

### 4. 自动衔接初始化和技能加载

用户要求在指定工程开展 Spec 工作时，在已有授权范围内自动检查并补齐必要初始化、技能和资源；已有合法配置复用，只有真实缺失决定、冲突或未覆盖的动作才回到用户。

当前初始化默认 governed。该安装选择不构成继续保留旧阶段门禁的理由；安装命名及政策组织由设计结合实际消费者确定。

优先评估复用 setup-yss-harness，避免再建重复初始化入口。区分技能选择、文件安装、宿主发现、参考读取和技能调用，逐层核验就绪状态。自动化涉及 user-only 技能时，应明确调整本项目入口与调用规则，不靠隐式调用绕过限制。

### 5. 人工确认只用于审批动作

需人工审批的动作使用真实人工批准，复用仍有效的授权或批准。普通调查、起草、检查、技能加载和内部工作步骤不新增人工门禁。

具体审批动作清单是方案设计的必需产物。每项必须说明批准对象、触发条件、批准依据、批准后允许的动作，以及什么变化会使批准失效。不得由模型、超时或 tracker 标签代替真实批准，也不得自动套用 Matt 的 ready-for-agent 作为本项目的人工审批结果。

### 6. 产品设计深度由 AI 协助判断

AI 根据用户任务、交互与状态复杂度、已有材料和未解决风险，判断所需设计深度并说明依据。可采用文字说明、流程、状态矩阵、低保真或可交互原型，不固定要求全套资产。

深度以能够澄清非技术产品行为与验收为准。无相关设计影响时不创建空原型；涉及真实业务取舍或审批动作时由用户决定。不得将产品原型自动升级为生产实现。

### 7. 不支持旧实例自动迁移

旧实例由人工自行迁移。本次不开发迁移工具、历史状态转换或为旧流程维持双轨执行，不自动修改旧实例和历史用户资产。

仍需排查本仓事实源、消费者和分发的依赖，确保清理旧逻辑后新流程一致；这属于新流程改造完整性，不属于旧实例兼容承诺。

## Matt v1.3.1 的借鉴与差异

固定研究基线：`mattpocock/skills` v1.3.1，提交 `24fe0ef7737efae15c87225755e9f6f5965e4888`。

| 方面 | 借鉴内容 | 本项目明确差异 |
|---|---|---|
| 需求澄清 | 复用已有讨论，事实由 AI 调查，业务决定由用户回答 | 已确认事项不反复询问 |
| Spec 综合 | 将已确认讨论整理为完整规格，引用既有材料 | 只负责非技术规格，不承担架构、API 或实现切片 |
| tracker | 本地 Markdown、GitHub、GitLab 的可替换适配 | 不增加 Markdown PR 或同步引擎 |
| 技能协作 | 小职责、按需调用、参考资料归属明确 | 自动初始化需求须在入口规则中显式实现 |
| 任务拆分与实现 | Spec 后由任务与实现流程继续消费 | to-tickets、implement、implement-spec、TDD 和代码审查属于下游，本次不建设 |
| PR | 实现阶段创建 Git PR，pr 技能组织正文 | Spec 创建不触发 Git PR |
| 确认与状态 | 采用简单、可读的 tracker 表达 | 必要人工审批按已明确动作设计，不直接继承自动准入标签 |

研究依据：[Matt v1.3.1 Spec/PR 调研](matt-v131-spec-pr-research.md)。上游方法是设计基线，不代表本项目已升级对应来源锁或可以忽略上述明确差异。

## 整体验收条件

1. 从新工程、已合法配置工程及新流程中断任务均能识别当前状态并确定下一步，不要求人工重复初始化。
2. 本地 Markdown、GitHub Issues、GitLab Issues 分别可创建、读取和更新规格；首次与重复执行结果可核实，失败后可识别已完成部分。
3. 规格内容覆盖目标、规则、边界、异常、非目标和验收；技术设计、API 和实现切片不会成为 Spec 起草或完成的前置条件。
4. AI 能说明产品设计深度的选择依据，无 UI 影响不生成空原型，存在关键交互风险时不会仅靠文字宣称问题已解决。
5. 必要审批由真实用户完成并绑定实际对象；普通准备工作不引入重复门禁，范围发生实质变化时仅重开受影响决定。
6. 下游能通过规格条目及引用获得当前内容、验收和未决项，无需先进入 Backend 或建立独立交接包。
7. Spec 工作不自动创建 Git PR，不要求 Markdown 与远程 PR 同步，不修改下游实现执行逻辑。
8. 当前新流程的入口、技能、政策、CLI 消费和分发保持一致；旧实例迁移由人工负责，不作为本次交付条件。
