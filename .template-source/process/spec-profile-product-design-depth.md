## 选择原则

先回答：当前尚未解决的产品问题是什么，哪种最小表达能让用户和下游准确理解行为与验收？复用已存在且适用的材料，只补当前缺口。不按功能大小、页面数量或是否有 UI 机械要求原型，也不以材料数量证明设计完成。

设计深度可以局部组合。一个功能可用文字覆盖多数规则，仅为高风险交互提供状态矩阵或原型，不要求全部页面达到同一保真度。不确定时先调查和澄清，不能自动选择最高档构建代替识别风险。

判断随新证据调整：实际检查或用户反馈表明表达不足时，只对受影响问题补充必要深度；问题被更简单方式解决时即可停止，不要求逐层升级或走完所有表达方式。

## AI 判断步骤

1. 读取用户任务、现有 Spec、已确认规则及适用产品规范，识别需要澄清的用户行为，而非提前选择技术组件。
2. 列出会影响业务结论的缺口：动作结果、角色权限、前后依赖、状态转换、异常恢复、信息优先级或必须实际体验才能判断的交互。
3. 区分事实、业务决定和表达不足：事实交研究或实际检查；业务决定按 grilling 澄清；表达不足由设计补齐。可交互原型不能替用户决定规则。
4. 选择下面最小必要产物或组合，并说明它准备回答什么问题；已有材料已解决的问题不重做。
5. 执行与产物及声明相称的实际检查，将发现回流 Spec 与验收；关键行为仍无法确定时不报告设计完成。
6. 结果放回现有规格或关联材料，简述选择依据、解决的问题、未覆盖边界和下一动作，不单独建立“深度批准”文件。

## 深度与升级条件

| 表达方式 | 通常适用 | 需要补充其他表达的信号 | 最小产物 |
|---|---|---|---|
| 文字与验收例子 | 规则和结果清晰，无需空间或操作体验来判断 | 多角色、多步骤或例外关系难以用文字准确核对 | 规则、成功及适用失败/边界例子 |
| 流程与状态说明 | 涉及顺序、权限、等待、取消、重试、返回或跨角色协作 | 信息布局或操作入口仍有歧义，或实际操作关系无法确认 | 针对受影响路径的流程或状态表 |
| 低保真页面或线框 | 信息结构、任务入口、表单关系和动作结果需要可见表达 | 需通过实际交互判断是否可理解，或视觉呈现会影响业务结论 | 必要页面、内容层级、动作与状态注释 |
| 可交互原型 | 关键问题只有通过操作才能验证，如复杂编辑、条件流程、跨步恢复或动态状态 | 模拟不足以回答原问题，或用户发现新的实质行为问题 | 可重复触发的关键场景、明确模拟范围和观察结果 |

视觉外观本身是待解决问题时，可使用静态视觉稿或原型，不要求先构建交互。纯视觉任务只验证其实际声明，不强制生成无关业务流程。具体工具和交付形式按当前需求选择，不预设生产技术栈。

没有 UI 不意味着没有产品设计：复杂角色协作或状态规则可能需要流程与状态表，但不因此生成页面原型。

## 对应检查

| 产物或声明 | 实际检查 | 不可据此宣称 |
|---|---|---|
| 文字规格 | 对照来源核查主体、条件、量词、权限、异常、恢复及 AC | 已验证页面可用性或真实实现 |
| 流程/状态 | 走查主路径及当前相关的拒绝、取消、失败、重试与退出路径，检查可达性和规则冲突 | 所有未涉及状态均已覆盖 |
| 低保真/线框 | 检查任务入口、必要信息、动作结果、权限提示及主要异常状态；与 Spec 核对 | 已完成响应式、浏览器或无障碍运行验证 |
| 静态视觉稿 | 对照适用规范和实际展示内容检查视觉层级与范围；明确只验证静态结果 | 主流程可操作或动态行为已验证 |
| 可交互原型 | 实际操作承诺的场景，检查结果、恢复路径及适用显示条件；记录工具、场景、结果和限制 | 已接入真实 API、生产组件或已达到生产质量 |
| 涉及键盘、窄屏或特定可访问性要求 | 对要求涉及的场景实际验证，失败回流修复 | 未执行的全部无障碍或多端检查通过 |

不能只凭源码看起来可行或截图存在宣称交互通过。环境无法运行时明确限制；若核心问题依赖操作验证，仍未解决，不用文字替代通过。

风险或明确验收要求决定检查范围；不强制每个产物经过同一套六轴 QA、H1/H2 归档或独立审查。具体验证工具按真实产物选择。独立复核仅在真实用户或适用外部规则明确要求时执行，默认诚实自检。

## 技能协作

life 判断当前需要并汇总结果；产品设计专项组织必要产物。domain-modeling 处理业务词义，grilling 处理缺失决定，yss-research 处理事实，i-have-adhd 辅助当前说明。

yss-design-system 在需要设计规范或视觉一致性时加载，不因存在 UI 就强制读取所有主题或 Token。prototype-review 负责已有设计中的行为、覆盖与一致性审查，不要求先有 OpenAPI、端点映射、技术组件或 Slice。

原型相关技能当前 user-only 限制仍有效。自动协作所需权限调整由 T06 明确设计，实施前不能依据本草案绕过现行调用规则。T07 应同步清理强制原型档位、固定独立审查和技术反推要求的消费者。

## 回流与停止条件

设计发现的业务规则、权限、异常或验收变化回流 Spec。需要用户作真实取舍时，按 T03 消费明确决定；产品设计本身不增加独立批准步骤。单纯工具选择或等价表达调整不重复询问。

当前范围完成意味着：提出的产品问题已有足以支持判断的表达与适用实际检查，Spec 和设计一致，关键未决问题已解决，可延期项保留影响与解决条件。关键问题仍阻断时，只报告产物已形成和具体阻断，不能报告设计完成。设计完成不意味着下游实现、技术可行性或生产验收完成。

无法解决时说明具体缺口、已尝试的方式和下一动作。用户选择延期或缩小范围必须是真实决定，AI 不自行接受关键风险。

## 验收场景

1. 简单规则调整：文字及验收例子足够，不创建页面或原型。
2. 无 UI 的多角色审批规则：按需提供流程/状态，不生成空页面，也不自动增加本系统审批节点。
3. 新表单但规则与页面模式明确：复用模式，必要时补低保真，不自动进入全套原型构建。
4. 复杂编辑与冲突恢复：原型只验证关键操作及异常，记录模拟限制，不编造 API 契约。
5. 视觉调整：仅检查实际视觉目标，不强制附带可交互流程。
6. 原型运行环境不可用：明确未验证，关键交互问题保持未解决，不写通过。
7. 设计暴露新增权限决定：先澄清并回流 Spec 与 AC，仅按实际适用要求审批。
8. 多数页面可复用、单一路径有风险：只补该路径，其他材料不重复制作。
