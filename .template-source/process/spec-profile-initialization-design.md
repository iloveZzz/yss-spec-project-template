## 目标与入口

用户指定工程并要求开展 Spec 工作，即在已有授权范围检查并完成必要配置与资源，不要求用户逐条发出 setup、ensure 和加载命令。只读咨询和审阅不触发初始化写入。

宿主先识别目标与当前可发现的技能：

```text
任务入口
  → 确认目标工程与只读/写入意图
  → 复用已发现的 life 或用户级 setup 引导
  → 检查工程、tracker、执行能力和当前任务所需技能
  → 仅补必要缺口
  → 读取实际需要的技能入口和参考
  → 交回原 Spec 任务，报告剩余能力限制
```

新工程尚无项目 life 时，用户级 setup-yss-harness 是推荐引导。若宿主连引导能力也未安装或暴露，只能明确报告缺口并按宿主支持方式引导，不能假装项目技能能自行安装自身。项目内文件存在也不证明宿主已经发现它。

不要求所有 Spec 任务先安装 CLI。已有技能和明确的合法 tracker 配置足以完成当前工作时直接继续；只有实际受管初始化、补装或当前操作需要时才准备对应执行器。CLI 版本、安装来源、目标 Profile 与 tracker 分别识别，不能从一个条件推断全部就绪。

可继续起草仅表示当前能力足以完成相应工作，不表示尚未执行的受管初始化已完成。初始化、设计验证或发布仍有缺口时分别报告部分完成与剩余限制，不能用草稿产出替代工程就绪。

本次自动衔接与最小资源策略仅作用于新 Spec 流程。setup-yss-harness 是共享能力，不全局放宽其身份、事务和文件保护，也不改变 Backend 初始化或其他安装方式的既有行为。

## 最小配置

| 配置 | 来源与选择 | 缺失处理 |
|---|---|---|
| 目标工程 | 用户指定路径及可核实上下文 | 可独立读取材料；受影响写入前明确目标，不猜相邻工程 |
| Profile | 已有合法 Spec 配置，或用户明确的新建 Spec 用途 | 新 Spec 用途已明确时无需再次询问；合法 Backend 工程不自动转换为 Spec |
| installation | 新建/接管默认 governed，复用同一新流程已有配置 | 不用切换 skills 隐藏旧流程依赖；用户显式选择独立 skills 时沿对应范围处理 |
| tracker | T05 的平台及本地根/远程完整目标 | 优先已有选择；无选择且无可确定用途时合并询问必要决定，保留用户可接受的建议 |
| 文档 | 现有入口、稳定术语及必要规格位置 | 保护用户文件；不为普通起草强制新建 Context、ADR、Plan、checkpoint 或完整目录 |
| 平台操作能力 | 连接器或已配置 gh/glab 的实际读写能力 | 按实际需求报告认证/工具缺口，不读取秘密、不自动换账户 |

CLI 可用只表示程序能力，初始化完成不表示有平台权限；检查平台只读成功也不证明写入权限。只有实际发布后才能报告该次发布成功，不执行无关外部写入来试探权限。

## 工程分流

| 现状 | 动作 |
|---|---|
| 空目录或普通未接入工程，用户要求开展 Spec 工作 | 在授权范围规划并应用新 Spec 最小初始化/接管，保护既有入口和业务文件 |
| 已按新流程合法配置的工程 | 复用身份、tracker 和已安装技能，只补当前缺口 |
| 旧流程实例 | 明确不提供自动迁移；只读诊断并由人工迁移后再接入新流程，不 sync 或改字段伪装迁移完成 |
| 身份非法、未知 schema、来源不明或配置冲突 | 保留原件并报告；不自动重建、降级或 attach 绕过 |
| 新流程中断的事务 | 查明当前事务和真实结果，按支持的恢复机制继续，不重复未知副作用 |
| 用户只要求分析或审阅 | 只读，报告缺口，不生成安装计划、下载、补装或改配置 |

新旧流程的可核验识别方式由 T07 对齐 schema、政策及消费者；不能按日期、文件夹名或关键词判断。需要显式能力标记时在实现计划说明，不能把现有合法旧实例默认当作新流程已就绪。

## 安装与读取集合

区分分发可用集合、宿主技能列表和本次实际读取集合。分发能力可多于任务需求；默认不全量加载或为简单规格补齐全部专项。

| 能力 | 角色 | 就绪策略 |
|---|---|---|
| yss-product-lifecycle | 项目 Spec 路由与连续推进 | 核心能力，缺失时由外部引导安装 |
| 共享规格综合参考 | life 所有的非技术规格方法 | 与 life 一起交付，原生路径直接读取 |
| to-spec | 用户显式综合入口 | 建议作为核心用户入口随项目提供，原生任务不隐式调用 |
| grilling / domain-modeling | 业务决定与术语澄清 | 建议作为基本可发现能力提供，当前有真实缺口才读取 |
| i-have-adhd | 当前文档表达 | 按文档任务加载必要规范，不持有流程状态 |
| yss-research | 事实调查 | 需要调查时按需确保可用，不要求每次启动研究 |
| yss-design-system / yss-prototype-stage / prototype-review | 适用产品设计 | T04 判断需要后再补齐相应能力，不因有 UI 就全装全读 |
| setup-yss-harness | 引导与缺口补齐 | 可从项目外发现；不要求作为每次任务的全流程包装器 |

以上是推荐角色分组；T07 结合实际依赖闭包确定精确分发集合。Spec 默认集合不包含 implement、to-tickets、实现合同编译器、TDD 和代码审查；保留它们在其他 Profile 或独立技能包的用途。

## 调用规则调整建议

保持 to-spec 为 user-only：显式命令使用共享方法；普通任务 life 直接消费同一参考，避免绕过权限或维护两套模板。

产品设计自动分支需要将本项目的 yss-prototype-stage 与 prototype-review 调整为适当的模型可调用能力，并同步 frontmatter、agents/openai.yaml、注册表及实际宿主投影；仅在 T04 需要时触发。名称不构成独立审查要求，默认诚实自检；真实独立要求仍按实际执行上下文满足。

setup-yss-harness 已可按任务使用，继续限于授权工程和必要安装动作，不授予业务批准。grilling、research 等沿其实际可调用边界处理；不因为路由表列出某技能就视为已经调用。

这些是待实施的显式规则变更，当前调用限制在实施前继续有效。宿主不支持自动技能调用时，报告支持边界，使用其公开的读取方式也不能绕过 user-only 限制。

## 受管补装与宿主发现

1. 先读 metadata 或宿主提供的最小技能描述，选择当前需要的能力，不加载完整治理资产作普通发现前置。
2. 需要受管资源时复用支持的 skills list/resolve/ensure，并消费真实结果与来源。已有授权、目标无冲突时保存计划并应用，不逐步重问。
3. 漂移、占用、未知来源和用户定制不自动覆盖；只阻断受影响操作，不将 ensure 变成隐式 sync 或迁移。
4. 文件就绪、运行时投影就绪与宿主发现分别报告。宿主无可靠发现证据时写未知，不称重启或刷新已经完成。
5. 受支持时，当前会话可直接读取已核验入口及其必要参考继续工作；这表示通过读取取得指导，不等于原生 slash-command 已出现。引用、调用权限继续有效。
6. 再次执行时复用已完成结果，重新检查实际相关差异；无变化不重复安装、配置或下载。

## 失败与范围控制

初始化/补装失败时，分别报告程序、工程、技能和平台的实际状态。保留用户工作及已成功的独立部分，不以整体失败自动回滚他人内容。

缺失专项时能独立完成的已授权文字准备继续，但必须说明未覆盖能力；核心需要原型验证或远程发布的任务不能靠降级草稿宣称完成。

执行器缺少所需能力时，使用已明确支持且可核实的替代入口，或报告阻断；不能伪造命令/flag。不自动提交、推送、发布发行包、创建 Git PR 或执行旧实例迁移。

## 验收场景与后续

覆盖：空目录、普通已有工程、新流程合法工程、旧实例、非法身份、缺 tracker 决定、缺核心技能、缺设计专项、宿主未刷新、CLI 缺失但当前工作无需 CLI、远程认证不足、部分事务失败、只读请求和重复执行。

每个场景分别检查真正动作、保留文件、剩余限制与是否回到原任务；不把文件存在、退出码或模型声称当成宿主发现和实际发布证据。

设计审查时的历史记录：已完成独立上下文的只读设计检查，并补齐共享 setup 的改造边界及草稿可执行与工程就绪的区分。当前为 T06 设计草案完成、待用户审阅，不表示实际初始化或用户批准。T07 必须落实新流程识别、技能调用元数据、分发闭包、旧消费者清理和 CLI 固定来源边界；不开发自动迁移。
