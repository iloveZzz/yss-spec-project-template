## 设计原则

不预设 Plan 批准、设计批准、阶段包批准等固定人工关卡。先看实际动作和已有授权，只有该动作需要人工审批且缺少有效依据时才请求确认。内部检查不会生成业务批准。

业务取舍澄清、业务审批和外部操作授权分别解释；同一条明确用户回复可以同时覆盖多个对象，无需为了字段完整重复提问。自动运行只复用真实决定，不能自行生成批准。

## 审批动作表

| 动作 | 何时需人工参与 | 消费的依据与对象 | 获得决定后允许什么 | 何时需重新确认 |
|---|---|---|---|---|
| 确定尚未确认的业务规则、范围或取舍 | 实质决定无法从已有材料确定 | 当前问题、可选项、影响的规则及验收 | 将用户选择写入规格；这是澄清，不强制额外批准一遍 | 新事实改变决定基础，或用户撤回 |
| 业务规格批准 | 用户明确要求审批，或当前项目已明确规定必须审批 | 实际展示的规格、适用设计、范围、验收及未决项 | 将该范围标为已批准，并供下游判断如何消费 | 业务范围、关键规则、验收、设计行为或已接受风险发生实质变化 |
| 接受影响规格结论的重要风险或延期 | 存在不能由 AI 自行接受的实际取舍 | 风险、后果、延期内容及适用范围 | 在明确接受范围内继续；不能将延期说成问题已解决 | 后果、范围、风险程度或延期条件改变 |
| 新增或改变配置、覆盖冲突文件 | 已有任务授权未覆盖，或存在需要用户选择的冲突 | 目标工程、具体变更与保留影响 | 执行被明确授权的配置或冲突处理 | 目标、写范围或冲突结果改变 |
| 发布或更新 GitHub/GitLab Issue | 当前任务或持续授权未覆盖对应平台、目标及动作 | 目标仓库、内容范围、创建或更新动作 | 发布或更新指定条目；不等于业务批准 | 越出平台/仓库/条目/内容范围，授权撤回或出现新的实质风险 |
| 提交、推送、合并、发布或部署 | 本次不自动引入这些动作；若实际任务要求则核验对应授权 | 具体动作、目标及范围 | 仅执行授权动作，不由规格批准推导 | 动作或范围改变 |

已经授权的初始化、技能补装、本地草稿保存、事实调查、表达修订及实际检查直接继续；不因存在上表而对每一步再问。只读请求仍不执行写入。

规格批准不是所有任务的默认必经节点：没有明确审批要求时，不为符合旧阶段模型而补造批准。决定是否需审批时要能指出用户要求或项目规则；找不到依据就不新建关卡。

上述项目规则仅指新 Spec 流程明确保留的规则、真实用户要求或适用外部制度；旧四阶段政策不因文件仍存在就自动继承。设计与清理期间发现冲突应明确报告并处理，不能自行猜批准或套用全部旧门禁。此目标规则不授权当前尚未改造的运行时跳过现行校验。

## 最小状态表达

采用三个互不冒充的事实，均记录在现有规格/tracker 中，不建立独立阶段状态文件。

| 事实 | 建议表达 | 含义与限制 |
|---|---|---|
| 内容是否可供评阅 | `draft / reviewable` | draft 可以包含未解决事项；reviewable 表示检查后能评阅，不等于批准或可实施 |
| 适用审批情况 | 文字记录“不要求审批 / 待审批 / 已批准 / 需重新审批”及实际依据 | 不要求所有条目填写一个机器批准枚举；无原始依据不写已批准 |
| 远程发布结果 | 实际 URL/编号；失败时明确“待发布”或“更新未完成” | 远程失败不改投平台，不因本地草稿存在就声称已发布 |

内容存在阻断问题时，在未决项中列清原因、影响范围及下一动作；不新增 blocked 阶段或 checkpoint。对已在下游使用的旧批准版本，应明确“旧版本批准仍仅适用于旧范围，当前修改待审”，不能覆盖原始依据后暗示两版都获批准。

不强制每个平台支持同样的原生状态。GitHub/GitLab Issue open/closed 表示平台条目状态，不直接映射业务批准；本地 Status 行也不能同时承担三种事实。若使用 Matt 五态标签，`ready-for-human` 可表达需人工处理，`ready-for-agent` 不作为实现资格，由 T05 确定是否保留及如何解释。

## 决定记录与所有权

life 负责查找、核验和报告用户决定，专项技能只提供内容与发现。记录复用当前规格、tracker 正文或评论，不新增审批包、checkpoint、角色注册或摘要链作为默认要求。

最小可读记录包括：谁在何时对什么范围作出什么决定、原始回复或评论引用、批准涉及的规格版本或当时可读快照，以及仍未覆盖的内容。当前对话无法形成持久链接时，不编造 URL；如实保留可读原文摘录及来源说明，不能把 AI 转述作为用户原话。

版本绑定优先采用已有 Git 提交、平台内容版本或保留的规格快照。并非所有本地草稿都已提交 Git；T05 必须提供无需强制 commit 的可读绑定方式。保存批准依据不触发自动提交、推送或远程评论。

版本引用必须能还原实际批准时的内容。单独的可变 Issue URL、编号或更新时间不构成版本绑定；平台不能提供可读历史版本时保留当时的可读快照，存储方式由 T05 确定，不因此新增默认摘要链或机器审批包。

若上次批准内容无法读取或无法确定范围，明确未知，只阻断依赖该批准的动作；不阻断独立调查、草稿准备或已授权修复。

## 变更处理

| 变更 | 默认动作 |
|---|---|
| 排版、措辞、引用修复，含义不变 | 自检语义后复用原决定，说明实际变化；不新增人工审批 |
| 基于已确认规则补充等价验收例子 | 检查未扩展量词、边界或权限；等价则复用，实质变化则回到决定 |
| 目标、范围、业务规则、权限、异常结果或验收改变 | 标明受影响内容；存在适用审批要求时重新审批，不重开无关决定 |
| 设计改变用户可见行为 | 回流 Spec 及 AC，按业务变化处理 |
| 仅原型工具、页面实现细节改变且产品行为不变 | 执行适用设计验证，不默认重批业务规格 |
| 远程发布失败或重复运行 | 查明实际条目与内容后恢复，不重放未知创建，也不反复索取仍有效授权 |
| 下游反馈实现困难 | 调查限制，不能直接更改业务范围；需要新取舍时澄清并处理适用批准 |
| 用户撤回批准 | 保留原记录，明确撤回范围；停止依赖该批准的后续动作 |

## 下游消费边界

Spec 返回当前规格引用、相关材料、适用决定及未决项。下游自行按其 Profile 判断技术准备和实现授权，Spec 不计算 ready-for-agent、签发 Slice 合同或触发实现。

存在真实业务 blocker 或适用审批缺失时，允许下游读取并提出问题，不能把当前稿当成已确定或已批准的执行依据。文档准备完成、远程发布成功和下游已经接手是不同事实。

## 验收场景

1. 用户已授权在指定 tracker 创建规格：生成与发布连续完成，不因内部步骤再请求授权。
2. 用户只要求草稿：本地保存后返回，不自动发布远程或标为批准。
3. 用户明确要求审阅批准：完整展示实际范围后消费真实回复，不用超时、默认选项或标签代答。
4. 同一条回复覆盖规格批准和指定平台发布：复用该回复，不拆成两轮确认。
5. 修改错别字：不重批；修改关键权限或验收：仅重新确认受影响决定及适用批准。
6. 无项目审批要求：实际自检后可报告规格已整理和发布，但不虚构已批准或已获得实施资格。
7. 远程不可用：保留明确待发布草稿，恢复时识别已有条目，不重复创建。
8. 已批准版本产生新草稿：原决定保持可读，修改稿不继承实质变化部分的批准。
