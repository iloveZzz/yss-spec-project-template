## 单一权威与适配边界

每个工程选择一个主 tracker：local-markdown、github 或 gitlab，沿用已有明确选择。缺少配置时由 setup 根据已知用途提出建议；Git remote 只提供候选仓库信息，不自动改变已配置 tracker。不能把模板预置默认值误当成用户已明确选择的远程目标。

本地模式的规格文件是权威内容；远程模式的 Issue 正文及关联讨论是权威内容。本地远程草稿是准备材料，发布后不作为第二个并行可编辑源；再次修改前读取当前 Issue 正文和评论。批准时的快照仅保留历史内容，不参与自动同步。

关联讨论是决定和事实的来源材料，普通建议不自动成为已确认业务规则。只有明确真实用户决定或有依据的事实进入当前规格；未确认评论列为待处理项，不能自动推翻已有批准范围。不同来源冲突时明确指出并处理。

不建设本地与远程内容双向同步、PR 模型或标签镜像引擎。原生 yss tracker 的 GitHub 标签镜像不承担规格发布。

## 最小配置与内容

在现有 issue-tracker.md 配置所有者下统一维护：platform、明确的 tracker 根或远程项目定位，以及必要的访问方式。不得在多个入口复制平台选择规则。最终配置格式由 T06/T07 对齐当前解析器，不能仅改文档后继续消费旧字段假设。

| 项 | local-markdown | GitHub | GitLab |
|---|---|---|---|
| 主定位 | 配置根下的功能目录与 spec.md | 完整仓库 owner/repo + Issue 编号/URL | 实例地址 + 完整项目路径 + Issue IID/URL |
| 创建 | 写入新的 spec.md | 创建 Issue | 创建 Issue |
| 读取 | 读取正文与 Comments | 获取正文、评论和实际适用审查依据 | 获取正文、讨论和实际适用审查依据 |
| 更新 | 保护用户字节并更新指定内容 | 重新读取、检查并发变更，再更新正文 | 重新读取、检查并发变更，再更新正文 |
| 状态 | 简单可读字段及决定记录 | 正文/评论，标签可选 | 正文/讨论，标签可选 |

规格使用同一内容结构：问题与目标、使用者与场景、范围及非目标、规则与可观察行为、异常与权限、非功能约束、验收、适用材料、未决项和决定引用。按规模裁剪，不包含技术设计/API/实现任务清单。

本地模式建议结构：

```text
<tracker-root>/<feature>/
├── spec.md                 规格与当前可读状态
├── design/                 仅实际需要的设计材料
├── research/               仅需要保存的研究材料
└── decisions/              仅需持久批准依据或快照时创建
```

根路径复用已配置值，未配置可建议当前默认 .work；不要求改为 Matt 的 .scratch。无需 parent-ticket、业务票集合、checkpoint、gates、api、architecture 或实现 issues 目录。

远程模式只建立实际需要的本地草稿和附件位置，不强制复制上述完整目录。需保存时建议在配置的工作根下使用同一功能目录，publication.md 保存目标与恢复信息，草稿不得声称已经远程发布。

## 定位与幂等

优先使用用户给出的路径或 URL；否则读取已有规格及发布记录。不得按标题相似自动认为是同一功能，也不得为同一规格重复创建 Issue。

首次创建前生成稳定的规格标识，并将其与目标写入本地操作记录；本地模式可采用项目内唯一功能标识，远程模式正文保留可查找的明确标记。标识格式由实现确定，不能仅用标题或时间戳充当唯一身份。操作记录只是创建/恢复辅助，不是阶段资格或新增批准。

标识和发布恢复记录不作为读取、分析或起草的资格前置；已有明确唯一定位直接复用，不要求为本地简单规格新增操作记录。仅在实际发布需要恢复信息时保存必要内容。

| 情况 | 动作 |
|---|---|
| 已有明确规格定位 | 读取后更新同一条目，不新建 |
| 新功能且不存在关联 | 授权内准备标识、创建一次，保存实际路径或远程编号 |
| 创建返回超时或回执未保存 | 先依据目标与稳定标识查询是否实际创建，查明前不重发创建 |
| 标识对应多个条目 | 报告冲突，不静默选择、合并或删除 |
| 本地路径被占用 | 比较身份与现有内容；不覆盖未知文件 |
| 正文与平台条目状态冲突 | 返回实际双方信息，解决受影响冲突，不用本地旧草稿强行覆盖 |

幂等是避免重复副作用，不意味着有未知结果时不断重试。平台无法可靠搜索标识时，保留未知和恢复信息，只有核实未创建后才再次创建。

## 保存、发布与更新顺序

1. 读取主 tracker 配置、已存在规格、评论和授权范围。
2. 在当前任务上下文或明确草稿位置综合修改；实际自检按 T02/T04 执行，审批按 T03 判断。阻断未解时只能保存或发布明确的草稿，不宣称规格完成。
3. 外部创建/更新前核实目标、内容与有效授权；操作未被覆盖时只请求该动作所需决定。
4. 更新前比较读取基线与最新正文。发现并发用户修改时保留并重新综合，不能仅用旧草稿覆盖；评论中新业务决定同样要消费。
5. 执行发布或更新，获取实际定位，再读取实际结果核对预期内容。不能仅凭进程退出 0 宣称远程字节一致。
6. 记录真实结果和未完成部分，返回主规格引用。发布成功后，本地草稿明确为已发布副本或清理可重建临时副本，不自动删除用户材料。

平台缺少原子条件更新时，读取后写入仍存在竞争窗口。实现须明确能力边界；使用可用的原生并发控制，至少执行写前复读与写后核对，不能宣称具备原子冲突保护。多人高并发等无法保证的情况停止自动覆盖并报告。

## 状态与批准内容

沿用 T03：内容 draft/reviewable、适用审批情况、发布结果分别表达。字段放在既有正文或本地 spec.md 顶部附近，不另建阶段状态机。Issue open/closed 不表示批准，ready-for-agent 也不授予实现资格；不默认要求创建全部 Matt 五态标签。

更新已批准规格且存在影响批准的实质变化时，正文与当前稿的审批说明必须在同次内容更新中一起调整，明确旧批准仅适用于原版本；不能先替换规则却仍显示当前稿已批准。旧决定和对应内容保留，不覆盖或删除。若有独立标签表达批准，须同步处理并核验；部分失败时不得报告批准状态已一致。

存在实际审批要求时，展示实际候选规格及适用设计，保存真实用户决定。原始评论引用只证明谁说了什么，不能单独证明当时正文内容。

版本依据可以是可读 Git 提交、平台可读历史版本或保留的候选快照。若平台没有可靠历史正文，先保存当次展示的正文和必要设计快照，再绑定用户回复；未经重新展示和确认的后续变化不能算入该批准。新批准不得覆盖旧版本内容。

快照包括批准实际涉及的内容：动态设计链接本身不足以还原当时设计，需引用不可变版本或保存被批准内容。存储采用本地 decisions 或明确允许的持久材料位置，记录可读范围与来源，不默认要求摘要链或 commit。远程消费者无法访问本地材料时，不能声称交付已完整；必须提供可访问的版本或在条目中明确缺口。

批准记录写入未被授权的远程位置时，不能因用户批准内容就自动发布评论。可以在已授权本地材料保留依据，另核验发布范围。

## 材料引用与下游消费

优先在规格正文保留足够理解行为与验收的内容，设计、研究按需引用。引用要能被预期下游访问；远程 Issue 不仅引用执行器临时绝对路径，本地规格不依赖即将失效的临时链接。

下游读取当前主规格及适用批准版本；规格更改时返回版本差异和受影响决定，不创建独立 Handoff。下游实现如何产生分支、任务和 PR 由其 Profile 决定。

关闭 Issue、分配人员、创建下游任务或更改下游状态不属于默认发布操作。只有明确任务需要且授权覆盖时才执行，不以“完成 Spec”自动关闭条目。

## 操作工具与错误边界

建议复用目的明确的已连接平台工具；工具不足时使用已配置的 gh/glab，优先保证身份、目标与操作可核验。GitLab 必须保留实例地址，不能假设都是 gitlab.com。凭据和权限缺失如实报告，不输出秘密、不自动换账户或改投其他平台。

本次不要求为三平台新建统一原生 HTTP 客户端；仅当已有工具确实无法满足最终场景时，在实施计划中列出缺口和必要新增能力。不调用现有 yss tracker sync 来代替正文发布。

| 失败 | 结果与恢复 |
|---|---|
| 凭据缺失/权限不足 | 保留目标和待发布草稿，说明需要的权限；不假称平台不可用后改投本地 |
| 本地已保存、远程失败 | 标明本地准备完成、远程未完成；不改主 tracker |
| 远程创建成功、回执保存失败 | 按稳定标识查询恢复定位，避免重复创建 |
| 正文更新成功、批准依据写入失败 | 分别报告真实结果，规格不能因此显示已有批准依据 |
| 读取或写后核对失败 | 保留未知，只阻断依赖该结果的后续动作 |
| 内容冲突 | 保留用户内容及本次候选，解决后再更新，不自动回滚他人修改 |

## 验收场景与状态

三平台分别验证新建、读取、更新、重复执行和内容自检。另覆盖：目标歧义、远程超时但实际成功、并发修改、部分失败、权限缺失、不可变批准内容、下游无法访问附件以及只读任务。

验收不得用 mock 成功替代真实平台可用性声明；单元检查可验证解析、定位与恢复决策，实际外部动作是否执行分别报告。

设计审查时的历史记录：已完成独立上下文的只读设计检查，并补齐讨论来源边界、更新时批准状态处理及发布恢复记录的最小作用域。当前为 T05 设计草案完成、待审阅，不表示用户批准或平台运行验证通过。T06 明确初始化配置和工具就绪；T07 将其与现有 tracker 解析、CLI、模板及分发消费者对齐，不开发旧实例迁移或同步引擎。
