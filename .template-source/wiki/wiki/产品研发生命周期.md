# 产品研发生命周期

`project-instance` 按产品研发生命周期分诊任务。主阶段以 `docs/process/lifecycle-registry.yaml` 为准，注册表当前列出 8 个：入口分诊、Discovery、Spec / 功能架构、产品设计、系统 / 数据架构与工程契约、Ticket 正式化、垂直切片实现、验证 / 发布 / 复盘。

任务开始时先读 `yss-project.yaml` 确认仓库身份（见 [[仓库身份与路由]]），再用 [[影响面分诊与流程裁剪]] 判定变更类型、影响面和最近可信阶段，然后按注册表执行命中的工作单元与 [[条件强制门禁]]。条件门禁全部按影响面强制：命中必须完成；未命中只记录 `not-applicable` 及原因，不生成空文档。产物、工作单元和证据不得统称为门禁。

新功能或较大变更默认进入 `yss-product-lifecycle` 的原生 Discovery / 需求分析工作单元（`work-unit.discovery-opportunity`、`work-unit.discovery-requirements`），再经 Spec 综合形成 [[Spec基线]]。`grill-with-docs` 与 `to-spec` 只是用户显式兼容入口，不是默认路径；Spec 基线与产品设计影响的完整判定以注册表和裁剪规则为准。[[SpecDelta]] 只记录相对既有冻结 Spec 基线的高风险行为差异；全新产品、全新模块和低风险调整不生成。

命中产品设计影响时走 [[产品设计影响与原型]]；未命中记录 `not-applicable`。API 契约变更先形成 OpenAPI 3.1 Draft，经必要的工程基线、系统 / 数据架构和设计审查后 Freeze（见 [[OpenAPI契约]]），再进入实现。无 API 影响时显式记录，不编造契约。

OpenAPI Freeze 或无 API 影响记录完成后，由生命周期原生 Ticket 正式化工作单元（`work-unit.ticket-decomposition`）拆成可独立验证的窄 [[垂直切片Ticket]]；用户显式 `to-tickets` 仅作为兼容入口，禁止只按 Adapter / Application / Domain / Infrastructure 横向拆分。每个功能先建功能父 Ticket 汇总 Spec、设计、审查、OpenAPI Freeze、阻塞项和阶段证据（见 [[Ticket与流程状态]]）。正式实现必须消费已批准、已持久化且版本当前的 [[切片实现合同]]；`yss-router` 只生成草案，不批准合同、不设置 `ready-for-agent`。

安全 / 权限不设独立生命周期资料或专属门禁。日常功能不做额外登记、`not-applicable` 或推导校验；只有需求或冻结资产明确要求改变认证、授权、租户隔离、敏感数据或合规行为时，才把该行为写入普通 Spec、API、架构、验收和测试 seam，并仅按实际 UI、API、Backend、Data、High-risk 影响触发既有门禁。普通 action 注册、沿用既有认证中间件、未变化的 `401` / `403`、一般字段、SQL / DDL / 迁移和上传 / 下载本身不构成安全 / 权限专项。`seam-deferred` 只能显式记录风险、责任人、后续 Ticket、验证计划和目标版本或发布日期。
