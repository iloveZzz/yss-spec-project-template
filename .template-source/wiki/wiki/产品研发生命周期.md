# 产品研发生命周期

`project-instance` 先按当前主控合同的唯一政策核验日常 / 正式路径；本页主阶段与批准链适用于 `governed`。当前主链从入口分诊开始，经 Plan、Spec / 功能架构、产品设计、工程契约、Ticket 正式化和垂直切片实现，最后完成验证 / 发布 / 复盘；每次恢复都核验最近可信阶段。

合格 `daily` 只维护同一 Ticket/PR，按需求验收、YSS 技术技能、实现、测试及独立审查推进，使用 `verify-daily` 核验当前差异与证据，不生成阶段 checkpoint、正式 Slice 或多级批准。已有正式任务不能降级；发现排除风险保留修改与证据并恢复最近可信正式阶段。

## 主阶段与退出依据

| 主阶段 | 主要结果与退出依据 |
|---|---|
| `stage.entry-triage` 入口分诊 | 身份合法，范围、影响面和最近可信阶段可解释 |
| `stage.plan` Plan（战略规划） | 目标、边界、规则、MVP / 非目标、优先级和交接责任明确；适用战略与决策检查通过，当前 Plan 获批 |
| `stage.spec-architecture` Spec / 功能架构 | Spec 基线与功能边界可审查 |
| `stage.product-design` 产品设计 | 命中的设计门禁通过；未命中项有原因的 `not-applicable` |
| `stage.system-data-engineering` 系统 / 数据架构与工程契约 | 后端架构与平台已确认或核验复用，适用契约冻结，脚手架证据齐全 |
| `stage.ticket-formalization` Ticket 正式化 | 切片窄、依赖清楚，验收和测试 seam 可执行 |
| `stage.vertical-slice-implementation` 垂直切片实现 | 当前批准合同规定的写路径、禁止模式、证据和验证要求满足 |
| `stage.verification-release-retrospective` 验证 / 发布 / 复盘 | 适用门禁、审查点和 Fresh Verification 完成，checkpoint 可追溯 |

结构事实以 `.template-spec/process/lifecycle-registry.yaml` 为准，见 [[条件强制门禁]]。新功能与较大变更先进入 Plan；小改动或已有工程从最近可信阶段恢复，见 [[影响面分诊与流程裁剪]]。`to-spec`、`to-tickets`、`implement` 仅为显式兼容入口。

## 从业务范围到可实现切片

正式功能首次进入 Plan 或最近可信接入阶段时，建立功能父 Ticket 汇总资产、审查、阻塞和证据。Plan 进入 Spec 前关闭业务边界、关键规则及 MVP 的阻断问题，其他未决项写责任人和解决时点；Plan 批准只允许继续 Spec。

Spec 综合同步起草业务 Ticket 集，Design 校准同一组稳定 ID。业务正式化确认 FR / AC、规则、场景和设计覆盖，保持 `ready-for-human`；它允许战略交接或技术分析，不授予实现资格。高风险变化已有冻结 Spec 时，用 [[SpecDelta]] 记录相对基线的行为差异。

存在产品设计影响时，形成交互说明、低保真、状态矩阵及 H1 / H2 原型交付物，经独立评审、交付物验证与产品设计批准进入下游，见 [[产品设计影响与原型]]。未命中时不生成空设计材料。

技术分析消费正式化业务 Ticket 及 Spec、设计和工程影响。API 变化先形成 OpenAPI 3.1 Draft，经适用专业审查后随工程契约批准冻结；无 API 影响保存可读结论。后端 Technical Design 与适用数据架构前置批准，既有工程核验接入，新工程按批准的架构和初始化合同生成机械骨架，见 [[OpenAPI契约]] 与 [[实现仓库与跨仓库契约]]。

Ticket 正式化消费冻结资产、当前实现仓库准备结果和阻塞关系，拆成贯穿受影响层的窄垂直切片。每片绑定持久化且当前的 [[切片实现合同]]，由主控批准后复算就绪，才能设置 `ready-for-agent`。合同编译器只能起草，业务票、父票或文件存在都不能代替实现批准。

## 实现、验收与恢复

实现按批准合同和公开 seam 执行 `behavior-tdd`。UI 影响切片在实现前具备还原计划，实现后补桌面 / 窄屏视觉、状态、交互、console 与 `pnpm` 证据。独立审查与本轮实际验证共同支撑交付验收，发布、推送和合并仍按外部动作授权执行。

工作单元批准或流转前核验 `context_reconciliation`；词汇缺失、冲突或摘要漂移保持阻断。`seam-deferred` 记录风险、责任人、后续 Ticket、验证计划及目标版本或发布日期。安全 / 权限变化写入普通 Spec、契约、架构、验收和 seam，按实际影响触发现有门禁。

修复后按差异和依赖定向复审，并把证据重新绑定当前候选；历史结果不能证明当前交付。发布后或阶段性完成后命中现行复盘触发条件时形成中文记录并回流权威资产，见 [[Fresh验证与独立审查]] 与 [[复盘与权威资产修订]]。
