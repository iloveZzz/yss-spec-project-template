# 条件强制门禁

生命周期按影响面触发门禁。命中必须通过，未命中写明依据与 `not-applicable` 原因，不生成空文档。当前注册表分别登记聚合门禁 `gate.*` 和内部检查 `check.*`；检查结果作为门禁输入，不能用一次批准掩盖适用检查失败。

## 当前聚合门禁

| 门禁 | 触发与聚合内容 |
|---|---|
| `gate.plan-approved` Plan 批准 | Plan 进入 Spec；汇总适用业务边界与规则、方案决策包检查，核验当前规划范围批准或有效授权延续 |
| `gate.spec-baseline-approved` Spec 基线批准 | 新功能、行为变化或范围扩大进入 Spec 基线；范围内细化复用有效授权，实质变化重新决定 |
| `gate.product-design-approved` 产品设计批准 | 存在产品设计影响；聚合独立原型评审与交付物验证，新增体验取舍由用户决定 |
| `gate.backend-architecture-platform-approved` 后端架构与平台批准 | 新建后端一次确认 `domain-driven` / `layered-mvc` 和精确 Spring Boot 版本；既有工程核验复用并记录不适用 |
| `gate.engineering-contract-approved` 工程契约批准 | 有 API、架构或工程基线影响；组合适用专业审查后统一批准，有 API 影响时冻结同一 OpenAPI 版本 |
| `gate.slice-contract-approved` 切片合同批准 | 主控批准已持久化且当前的垂直切片合同；就绪计算另行执行 |
| `gate.delivery-accepted` 交付验收 | 汇总独立审查、Fresh Verification、回滚证据及适用前端还原验证；不授予合并或发布权限 |

这些门禁分布在 [[产品研发生命周期]] 的对应主阶段。阶段、产物、工作单元与证据各有独立身份，不统称为门禁；已发布稳定 ID 不复用为其他语义。

## 内部检查的作用

`check.repository-identity-valid` 每次进入流程核验身份。Plan 的业务边界与规则、方案决策包检查由实际影响触发；产品设计检查覆盖低保真独立评审和 H1 / H2 交付物验证。工程契约检查覆盖适用 OpenAPI Draft Review、设计、架构、工程基线与冻结准备。

`check.implementation-repositories-ready` 核验命中交付面的已有工程接入或新工程准备结果。`check.slice-ready-for-agent` 复算垂直切片可直接实现的条件，合同批准本身不能代替该检查。UI 实现完成准备合并、发布或阶段完成时，`check.frontend-implementation-verified` 核验还原证据；专职前端或显式 `frontend_delivery` 的输入核验也只证明输入就绪。

自动前置核验和状态计算不新增人工批准，专业审查仍保持独立性。角色候选名单不要求全员签字；普通功能默认一个推进负责人与一个独立审查者，能力缺口、专业冲突或项目外部制度要求时再增加审查者。

## 失效与决定边界

已有批准只在同一资产版本、依据和范围保持有效时复用。实质范围、规则、验收、承诺、授权或风险接受变化，先展示差异再取得真实决定；技术载体或候选摘要变化不自动要求重复人工批准。首轮覆盖全部适用检查，修复后按受影响结论及依赖定向复审，未受影响项保留可核验的复用依据。

验收 / 契约违规、关键验证失败和证据缺失均阻断，不能改成建议绕过。历史结果、自述和未返回的审查请求不能放行当前任务。Spec、原型和 Draft 用 `ready-for-human`；只有通过适用门禁且可直接实现的窄切片用 `ready-for-agent`。详情见 [[影响面分诊与流程裁剪]]、[[Ticket与流程状态]] 和 [[Fresh验证与独立审查]]。

安全 / 权限不单独设门禁。明确改变相关业务行为时，按实际 UI、API、Backend、Data、High-risk 影响复用普通流程；SQL、迁移、上传 / 下载等载体本身不自动触发安全专项。
