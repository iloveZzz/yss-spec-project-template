# 条件强制门禁

生命周期门禁（条件强制门禁）只有影响面命中触发条件时才必须裁决；未触发时记录 `not-applicable` 及原因，不生成空文档，也不默认走全部门禁。门禁不是产物、工作单元或证据的统称；主阶段不会因增加门禁而自动增加。

注册表当前列出 14 个门禁，按 `id` 与 `name` 为：`gate.repository-identity-valid` 仓库身份校验、`gate.spec-baseline-approved` Spec 基线批准、`gate.prototype-reviewed` 原型评审、`gate.prototype-verified` 高保真原型验证、`gate.user-confirmation` 用户确认、`gate.openapi-draft-reviewed` OpenAPI Draft Review、`gate.design-reviewed` 设计审查、`gate.openapi-frozen` OpenAPI Freeze、`gate.engineering-baseline-accepted` 工程基线、`gate.architecture-reviewed` 架构审查、`gate.slice-contract-approved` Slice Implementation Contract 批准、`gate.slice-ready-for-agent` 垂直切片实现就绪、`gate.frontend-implementation-verified` 前端实现还原验证、`gate.release-ready` 发布就绪。`gate.release-ready` 还要求 `requires_gates: [gate.frontend-implementation-verified]`。数量以注册表当前列出为准。

这些门禁分布在 [[产品研发生命周期]] 的入口分诊、Spec / 功能架构、产品设计、系统 / 数据架构与工程契约、Ticket 正式化、验证 / 发布 / 复盘等阶段。[[影响面分诊与流程裁剪]] 只减少未触发的门禁，不得跳过已经命中的条件强制门禁。命中证据写入对应 `evidence.*`，并集中回写功能父 Ticket（见 [[Ticket与流程状态]]）。

安全 / 权限不设独立生命周期资料或专属门禁。日常功能不做额外登记或推导校验；只有需求或冻结资产明确改变认证、授权、租户隔离、敏感数据或合规时，才写入普通 Spec、API、架构、验收和测试 seam，并按实际 UI、API、Backend、Data、High-risk 触发上列既有门禁。SQL / DDL / 迁移、上传 / 下载由其数据或 API 影响决定路线，不自动升级为安全专项。`seam-deferred` 必须显式记录风险、责任人、后续 Ticket、验证计划和目标版本或发布日期。

只有通过必要门禁、阻塞边已清除并具备直接实现条件的 [[垂直切片Ticket]] 才能使用 `ready-for-agent`。Spec 初稿、产品设计、原型、[[OpenAPI契约]] Draft 和待冻结资产使用 `ready-for-human`。进入实现前还须由生命周期编排器批准 [[切片实现合同]]；实现者不能承担命中的独立审查，完成结论必须基于 [[Fresh验证与独立审查]]。
