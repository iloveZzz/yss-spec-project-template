# 实现仓库与跨仓库契约

运行时代码默认进入已登记的外部实现仓库，工程身份、写范围和验证必须回指实际项目。多个仓库协同交付时分别保存契约、验证与回滚证据，并明确发布顺序。

## 登记与项目边界

每个受影响实现仓库登记仓库地址、分支、代码所有者、CI、测试或构建命令、允许写路径、回滚点和 MR/PR；没有登记记录时先完成 onboarding。接入或初始化规划前运行 `scripts/preflight-delivery --input <清单> --stage prepare --json`，后续执行边界重新核验，旧报告不能放行当前动作。

用户明确选择当前 Harness 承载实现代码时，项目根必须为 `apps/backend/<project>/` 或 `apps/frontend/<project>/`。`apps/backend/`、`apps/frontend/` 只是容器；`app/backend/`、`app/frontend/` 及子路径禁止作为工程目标。允许写路径、证据路径与生成位置回指具体项目，外部仓库则登记实际项目根。

`repository_scope` 仅允许 `external-repository`、`harness-apps`、`git-submodule`。同一 monorepo 可共用仓库登记，但逐项目列出根路径和独立验证命令；不同 Git 仓库分别登记，子模块各自登记。

## 子模块写入与交付顺序

子模块必须是真实 gitlink，`git_entry_mode: 160000`，挂到具体 `apps/backend/<project>/` 或 `apps/frontend/<project>/`；不能把 gitlink 当 `harness-apps`，也不能复制实现源码冒充 submodule。登记字段与实际 Git 身份必须一致，clone、CI 和 Cloud Agent 递归检出。

空 gitlink、未初始化、detached HEAD 或强制覆盖挂载点不得当作普通目录。写入前读取 `inspectWorkingTreeScope` 对象结果，只有 `.writable === true` 才能写；先在子仓检出跟踪分支，脚手架即使收到 `--force` 也不能覆盖 gitlink。

Git 授权按仓分别计算。获授权后先子仓 commit/push，再由父仓更新 gitlink；父仓 push 使用 `git push --recurse-submodules=check`，跨仓交付顺序包含 `superproject-gitlink-update`。`.gitmodules`、gitlink 与子仓工作树不属于 CLI 受管资产，`sync` 不能创建、覆盖或删除它们。

## 实现与验证

正式切片前登记工程，再编译最小 Skill 集和当前 [[切片实现合同]]。无工程时先确认外部目标或输出目录；新后端架构按用户逐项目确认结果路由。脚手架仅在当前架构决策及已批准的 Project Scaffold Contract schema v4 下生成机械骨架，既有工程不得重选或覆盖。

前端安装、测试、type-check 与构建优先 `pnpm`；后端校验、测试与编译优先项目根 `./mvnw`。缺少工具时记录受控例外、替代命令与责任人；Ticket、合同、CI 和 Review 记录实际执行命令。独立 Reviewer 使用能够执行这些命令的运行时，审查任务只写证据，不修改实现。

模板与 CLI 共同发布前分别记录 commit、快照 hash、测试结果、独立审查结论及 rollback 路径；正式模板快照绑定 40 位不可变 commit，不能跟随浮动 `main`。CLI 不得覆盖前后端运行时代码、删除目标 `.git` 或改动 gitlink。

路径越界、证据缺失、未执行验证、`drift`、`violation` 或 `new_impacts` 时停止实现并重新路由。Git 提交、推送及实际发布仍按授权执行。切片拆分见 [[垂直切片Ticket]]，完成证据见 [[Fresh验证与独立审查]]，入口见 [[仓库身份与路由]]。
