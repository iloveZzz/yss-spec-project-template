# 模板维护流程

`template-source` 维护可复用模板、规则、工具和共享 Skill。标准路线是“影响面 → 单一事实源 → 投影 / 派生 → 分级证据”；首次编辑结束后继续完成同步与本轮验证，默认交付状态为 `implementation-ready`。

## 维护范围与事实源

先核验仓库身份，再判定受影响行为与最近可信依据。模板源不生成具体产品的 Spec、原型、OpenAPI 或垂直切片 Ticket；未涉及的产品设计和运行时工程范围写明原因。改共享 Skill 使用 `maintaining-skills`；`.agents/skills` 为权威内容，平台 root 的同名 Skill 通过工具生成，禁止分别手改，见 [[技能投影与锁定]]。

已授权范围内继续修改事实源、同步受影响投影与锁文件及分发快照，并完成适用验证。只有出现新决定、必要输入缺失或既有审批边界时暂停。提交、推送与发布按独立授权执行，维护就绪状态不授予这些动作权限。

## L1 / L2 / L3

强度只由 `.template-source/process/maintenance-intensity.yaml` 计算，未给 trigger 时默认 L2，未知 trigger 先更新策略与场景。等级由行为与错误逃逸风险决定，不能按所在目录或拆小改动规避。

| 等级 | 当前触发项 | 最低证据 |
|---|---|---|
| L1 | `textual-only`、`link-only`、`deterministic-projection` | 至少一项直接相关的实际检查；自检或显式人工 checkpoint |
| L2 | `local-rule`、`template-structure`、`non-core-validator` | 可失败的最小反例、维护者自检与本轮 Fresh Verification |
| L3 | 生命周期门禁、Ticket 状态、权限边界、生成 / 发布语义、跨仓契约、核心验证器、重要问题逃逸、整体行为变化或发布候选 | 维护者自检与本轮 Fresh Verification；正式发布另执行完整验证 |

当前 L3 trigger ID 为 `lifecycle-gate`、`ticket-state`、`permission-boundary`、`generation-semantics`、`release-semantics`、`cross-repo-contract`、`core-validator`、`historical-important-escape`、`aggregate-behavior-change`、`release-candidate`。权限边界、生命周期门禁和发布语义三项额外要求绑定对应实际拒绝场景的 counterexample。证据包含命令、实际结果、日志摘要、输入摘要和时间，不能用文字 `pass` 代替执行。

日常 L1 / L2 / L3 均不强制独立审查、候选冻结或三轴任务包。按需独立审查保持实施与审查身份独立，不能用请求代替结论。发现新影响先更新 `escalation`、合同和等级并补证据；违规与验证失败修复后按差异影响定向验证，未命中条件才可不适用。

## 验证入口与 checkpoint

内循环 `scripts/verify-template-fast` 根据 Git 影响面执行检查；未映射路径或核心核验资产变化时升级到完整验证，来源仍为当前工作树，支持 `implementation-ready`；显式 candidate / release 入口要求已提交来源。PR 用 `scripts/verify-template-candidate`，main 和正式发布前运行不可裁剪的 `scripts/verify-template`。入口名称不代表必须冻结候选，见 [[模板发布门禁与验证]]。

新维护 checkpoint 为 schema v2，记录 trigger、changed_assets、验证、review_mode、escalation 和目标状态。日常 `implementation-ready` 使用 `verification_profile: fast`、`review_round: 0`、`candidate_digest: null`，由 `scripts/verify-maintenance-checkpoint` 只读校验。L1 有 relevant-check；L2 有 counterexample、self-check、fresh-verification；L3 有 self-check、fresh-verification 及命中风险的定向反例。

维护者自检路径的 `release-ready` 使用 release profile，并绑定恰好一条 `scripts/verify-template` 的 final-release-verification。该状态仅表示维护验证就绪，外部生成器固定版本集成、兼容性和发布授权仍须分别闭合。历史 checkpoint schema v1 只读；历史结果不能放行当前交付。

显式独立审查兼容协议继续可用：候选、任务包与结论绑定同一摘要，候选字节改变使旧结论失效。采用该协议时最多两轮审查，第二轮未收敛保持 `needs-human`；普通日常流程不启用这个限制。集中 checkpoint 保留范围、依据、验证、风险、阻塞、下一步，见 [[Fresh验证与独立审查]] 与 [[复盘与权威资产修订]]。

## 仓外运行证据

维护运行输出存到当前工作区可信仓外目录，用 `maintenance:<相对路径>` 引用；验证记录必须绑定 `evidence_digest`。该引用只用于模板维护，不扩展项目实例或 Slice 的路径权限。正式规则、工具与当前阅读资产继续由仓内权威文件持有。

新 Worktree 候选输出到 `maintenance:candidates/<id>/`，目标捕获前必须不存在，经 staging 原子落盘。目录恰好包含 `candidate-manifest.yaml`、`candidate.bin`、`tracked.diff`；manifest schema v2 声明 `reference_base: bundle` 和工作区身份，stream / diff 使用包内相对引用。`candidate.bin` 沿用原字节流帧及摘要，不再生成逐文件副本；旧版本只读兼容。

高风险拒绝场景可用 `scripts/verify-maintenance-risk-scenarios --output maintenance:research/<本轮>/counterexamples` 生成实际记录，并补受影响行为的定向验证。核验只读这些记录，不执行其中命令，也不授予业务批准。
