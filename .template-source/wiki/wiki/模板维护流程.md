# 模板维护流程

`template-source` 维护可复用模板、规则、工具和共享 Skill。标准路线是“影响面 → 单一事实源 → 投影 / 派生 → 分级证据”；首次编辑结束后继续完成同步与本轮验证，默认交付状态为 `implementation-ready`。

## 维护范围与事实源

先核验仓库身份，再判定受影响行为与最近可信依据。模板源不生成具体产品的 Spec、原型、OpenAPI 或垂直切片 Ticket；未涉及的产品设计和运行时工程范围写明原因。改共享 Skill 使用 `maintaining-skills`；`.agents/skills` 为权威内容，平台 root 的同名 Skill 通过工具生成，禁止分别手改，见 [[技能投影与锁定]]。

已授权范围内继续修改事实源、同步受影响投影与锁文件及分发快照，并完成适用验证。只有出现新决定、必要输入缺失或既有审批边界时暂停。提交、推送与发布按独立授权执行，维护就绪状态不授予这些动作权限。

## L1 / L2

当前维护策略 schema v2 只定义 L1/L2。强度只由 `.template-source/process/maintenance-intensity.yaml` 计算，未给 trigger 时默认 L2，未知 trigger 先更新策略与场景。等级由行为与错误逃逸风险决定，不能按所在目录或拆小改动规避。

| 等级 | 当前触发项 | 最低证据 |
|---|---|---|
| L1 | `textual-only`、`link-only`、`deterministic-projection` | 至少一项直接相关的实际检查；自检或显式人工 checkpoint |
| L2 | 局部规则、模板结构、非核心验证器及其他具体行为影响，共 9 项 | 维护者自检与本轮 Fresh Verification；命中风险补实际反例 |

普通 L2 不强制通用反例包。当前 L2 的 9 项 trigger 是 `local-rule`、`template-structure`、`non-core-validator`、`lifecycle-gate`、`permission-boundary`、`generation-semantics`、`release-semantics`、`cross-repo-contract`、`core-validator`。权限边界、生命周期门禁和发布语义三项额外要求绑定对应实际拒绝场景的 counterexample。证据包含命令、实际结果、日志摘要、输入摘要和时间，不能用文字 `pass` 代替执行。

四项原判级标签已退役，当前记录必须按实际行为重新归类：

| 退役标签 | 当前处理 |
|---|---|
| `ticket-state` | 普通工单规则用 `local-rule`；准入、流转、放行或完成条件用 `lifecycle-gate`；执行权限改变同时用 `permission-boundary` |
| `historical-important-escape` | 历史漏检写入问题说明和回归依据，按具体影响分级并保留原缺陷回归 |
| `aggregate-behavior-change` | 选择全部实际命中的具体影响项，覆盖消费者，每项强制风险分别留真实反例 |
| `release-candidate` | 由现有目标状态、验证 profile、候选摘要和正式合同处理；修改发布放行语义才用 `release-semantics` |

不得用空 triggers 或普通标签遮蔽已识别的风险。旧两级 L2 记录携带退役标签时，当前校验拒绝；继续工作先保存原字节，再重新分析影响、更新本轮记录和受政策变化影响的证据。`--history` 使用冻结 v1 的原三级映射，不保证旧两级 L2 记录通过；仅审计时保存原政策、源码与输出，不授予当前执行资格。候选、main 集成与发布的完整覆盖合同继续适用。

日常 L1 / L2 均不强制独立审查、候选冻结或三轴任务包。按需独立审查保持实施与审查身份独立，不能用请求代替结论。发现新影响先更新 `escalation`、合同和等级并补证据；违规与验证失败修复后按差异影响定向验证，未命中条件才可不适用。

## 验证入口与 checkpoint

内循环先看 `scripts/verify-template-fast --plan`，按变化行为及直接 / 传递消费者选择必要检查；每项指出命中文件、受影响行为与能发现的具体错误，适用强制检查注明合同依据。未知路径、缺映射或非法依赖先修正计划，不自动全量；已有覆盖时不新增测试或启动环境，必要检查通过即结束，只有相关修改、失败或具体遗漏才追加。来源为当前工作树，日常报告 `limited` 与未覆盖边界，支持 `implementation-ready`。PR 候选用 `scripts/verify-template-candidate --base <完整 SHA>`；main 集成及正式发布按现行完整覆盖、baseline、资格与回退合同运行 `scripts/verify-template`。入口名称不代表必须冻结候选，见 [[模板发布门禁与验证]]。

需要维护 checkpoint 时，新记录为 schema v2，记录 trigger、changed_assets、验证、review_mode、escalation 和目标状态。日常 `implementation-ready` 使用 `verification_profile: fast`、`review_round: 0`、`candidate_digest: null`，由 `scripts/verify-maintenance-checkpoint` 只读校验。L1 有 relevant-check；L2 有 self-check、fresh-verification 及命中风险的定向反例。

维护者自检路径的 `release-ready` 使用 release profile，并绑定恰好一条 `scripts/verify-template` 的 final-release-verification。该状态仅表示维护验证就绪，固定版本统一 CLI 集成、兼容性和发布授权仍须分别闭合。冻结 `maintenance-intensity-v1.yaml` 仅供 --history 按原映射、证据与审查规则读取历史 L1/L2/L3；当前校验拒绝 L3，不改写旧批准、状态或摘要。历史 checkpoint schema v1 只读，历史结果不能放行当前交付。

显式独立审查兼容协议继续可用：候选、任务包与结论绑定同一摘要，候选字节改变使旧结论失效。采用该协议时最多两轮审查，第二轮未收敛保持 `needs-human`；普通日常流程不启用这个限制。集中 checkpoint 保留范围、依据、验证、风险、阻塞、下一步，见 [[Fresh验证与独立审查]] 与 [[复盘与权威资产修订]]。

## 仓外运行证据

唯一自动 Git 例外只消费 `advance-maintenance-iteration` 的本地 checkpoint 引用合同，不扩展提交、推送或发布授权。

维护运行输出存到当前工作区可信仓外目录，用 `maintenance:<相对路径>` 引用；验证记录必须绑定 `evidence_digest`。该引用只用于模板维护，不扩展项目实例或 Slice 的路径权限。正式规则、工具与当前阅读资产继续由仓内权威文件持有。

新 Worktree 候选输出到 `maintenance:candidates/<id>/`，目标捕获前必须不存在，经 staging 原子落盘。目录恰好包含 `candidate-manifest.yaml`、`candidate.bin`、`tracked.diff`；manifest schema v2 声明 `reference_base: bundle` 和工作区身份，stream / diff 使用包内相对引用。`candidate.bin` 沿用原字节流帧及摘要，不再生成逐文件副本；旧版本只读兼容。

高风险拒绝场景可用 `scripts/verify-maintenance-risk-scenarios --output maintenance:research/<本轮>/counterexamples` 生成实际记录，并补受影响行为的定向验证。核验只读这些记录，不执行其中命令，也不授予业务批准。
