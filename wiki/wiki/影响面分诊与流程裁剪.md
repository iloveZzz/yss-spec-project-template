# 影响面分诊与流程裁剪

`docs/process/harness-process-tailoring.md` 规定如何根据变更规模和风险选择最近可信阶段。裁剪只减少未触发的门禁，不得跳过已经命中的 [[条件强制门禁]]；未命中只记录 `not-applicable` 及原因，不生成空文档。

判定顺序：先读 `yss-project.yaml`，非法、缺失或不支持的身份直接进入迁移检查（见 [[仓库身份与路由]]）；再判断是否为模板源维护、项目实例小改动、中等变更或全新产品 / 模块；再判断 UI、API、数据、后端、前端、跨仓库和高风险影响；最后从最近可信阶段恢复，不因目录里存在某类文件就猜测阶段已通过。

裁剪矩阵的默认入口不同。模板源维护默认入口是影响面分析，必需工作是修改单一事实来源、按强度分级执行证据、必要的技能投影同步和 fresh verification / review，产品 Spec、产品设计、OpenAPI、运行时代码记 `not-applicable`（见 [[模板维护流程]]）。小改动从入口分诊进入，未触发时 Spec、架构、原型、切片可记 `not-applicable`。中等变更从最近可信的 Spec / 架构阶段恢复。全新产品 / 模块从 Discovery 进入。高风险变更从既有冻结基线进入，需要 [[SpecDelta]]、架构 / 数据 / 工程审查、契约复核、切片和回滚设计。

安全 / 权限不单独分诊。需求或冻结资产没有明确改变认证、授权、租户隔离、敏感数据或合规时，不登记、不解释 `not-applicable`、不增加门禁；明确改变时只按实际 UI、API、Backend、Data、High-risk 复用普通 [[产品研发生命周期]]，不另设专属资料。SQL / DDL / 迁移、上传 / 下载继续由其数据或 API 影响决定路线。文案、token、颜色、间距和无行为变化的孤立视觉修复属于 UI 影响，但不自动构成产品设计影响，也不强制 [[产品设计影响与原型]]。

`grill-with-docs`、`to-spec`、`to-tickets` 只是用户显式兼容入口，不是默认路径；新功能或较大变更走生命周期原生 Discovery / 需求分析与 Ticket 正式化。Spec Delta 只记录相对既有冻结 Spec 基线的高风险行为差异；全新产品、全新模块和低风险调整不生成。跨仓库变更必须绑定实现仓库、分支、CI、验证命令、发布顺序和回滚点。`seam-deferred` 必须显式记录风险、责任人、后续 Ticket、验证计划和目标版本或发布日期。

任何裁剪都要写明原因和证据。阶段证据在集中 checkpoint 回写，至少包含范围、变更文件、受影响仓库、验证命令及结果、阻塞项、人工审查点、Ticket 状态和下一步。同一独立执行者可以在一个连续工作单元内完成相邻实现动作，但不能替代独立审查者（见 [[Fresh验证与独立审查]] 与 [[Agent入口规则]]）。
