# 后端子项目用户手册

本手册面向后端负责人和交付协调者。当前 profile 是 `harness.backend-delivery`：消费批准的 Spec 或 Strategic Design Handoff，完成后端工程设计、OpenAPI Freeze、Slice Contract、实现验证和 Backend Delivery；不实现前端，也不自行宣布整个业务切片完成。

## 创建或接管项目

先从受控发行清单取得适配平台的固定 `yss` 二进制并校验 SHA-256；用实际版本记录核对发行来源。以下创建和接管示例在目标项目的父目录执行，计划保存在项目外的新文件中。

```sh
yss version --json
yss init --root ./backend-project --profile backend --project-name 设备借用 --business-domain 内部设备管理 --json
yss attach --root ./existing-project --profile backend --plan --out ./backend-attach.plan.json --json
yss attach --root ./existing-project --profile backend --apply --plan-file ./backend-attach.plan.json --json
```

`init` 直接创建项目，目标须不存在或为空；`attach` 默认只预演，审阅已保存计划后再执行应用。应用会重新核验计划摘要和当前输入，输入变化后须重新预演。生成后核对 `yss-project.yaml`、原生 `.yss.json`、根 `CONTEXT.md`、`.template-spec/process/harness-profile.yaml` 和实现仓登记；CLI 详情见[CLI 使用说明](CLI使用说明.md)。

## 第一次让 Agent 工作

```text
请先只读检查本仓身份、根 CONTEXT.md、profile、批准战略或 Spec、实现仓登记和工程基线。
说明当前可信阶段、架构身份、API 影响、缺失证据和下一步。
输入不全时只诊断并回交；当前 Slice Contract 获准前不要写代码。
```

导入成功只证明交付包已落地，不等于目标词汇对账、技术设计或合同已批准。上游规则含糊时回交战略所有者，不能在后端设计中补造业务决定。

## 本仓操作主线

`战略接收与对账 → 工程预检 → 技术设计与 API Freeze → Slice Contract → 后端实现与验证 → Backend Delivery`

1. 验证并导入战略包，完成目标仓 `CONTEXT.md`、源规则和关键场景的逐项承接。
2. 运行 `scripts/preflight-delivery --stage prepare`，核对治理身份、目标范围、实现仓和工程证据。
3. 既有 Java/Maven 工程提供 repository registration、engineering baseline、observation manifest 三份原始证据；它们必须与实际 Git、POM、源码和架构身份一致。支持 `existing-domain-driven-maven` 与 `existing-layered-mvc-maven`。
4. 使用 `yss-technical-design` 形成当前技术设计；API 有影响时完成 OpenAPI 3.1 Draft、审查和 Freeze。
5. 编译窄 Slice Contract，绑定允许路径、验证命令、回滚点和公开测试 seam。编译器不批准合同；当前批准和阻塞清除后才能实现。
6. 在登记工程中实现，后端优先使用根 `./mvnw`，保存正常、拒绝、并发、幂等、数据库和恢复场景的真实结果。
7. 绑定战略、冻结接口、合同批准、源码、构建制品、部署身份和测试数据，形成后端交付源记录。

## 预检、导出与交付边界

准备 `delivery_kind: backend-delivery` 的输入清单。导出前运行：

```sh
node scripts/preflight-delivery --input <后端预检输入.json> --stage export --json
node scripts/backend-delivery export --source-root . --delivery <交付描述相对路径> --output <新包目录> --preflight-input <后端预检输入.json> --zip
node scripts/backend-delivery verify --bundle <包目录或ZIP>
```

预检读取原始技术设计、冻结接口、Slice、批准、构建制品、部署记录和后端交付源记录，不执行其中命令。离线验包证明包内绑定和摘要，不证明服务当前可达；前端接收时仍要探测真实服务、接口和数据版本。

## 用户决定与完成标准

用户或对应负责人需要确认架构选择、API 兼容、数据与回滚、Slice 写入范围和交付风险。批准记录必须绑定当前资产；工程基线、接口、合同或源码身份变化后重新预检和批准受影响部分。

本仓完成时应同时满足：

- 上游规则与场景已在目标词汇中承接，无未裁决冲突。
- 技术设计、OpenAPI Freeze、Slice Contract 和实现仓证据当前且相互一致。
- 实际构建制品、部署和验证证据绑定同一源码与切片。
- Backend Delivery 通过本轮预检与验包，交付缺口和未覆盖风险已披露。
- 结论只写 `backend-deliverable`，不写前端或整体业务已完成。

## 同步与恢复

在项目根目录执行以下命令。`sync` 默认只预演；应用必须消费已保存的计划。

```sh
yss doctor --root . --profile backend --json
yss diff --root . --profile backend --json
yss sync --root . --profile backend --plan --out ../backend-sync.plan.json --json
yss sync --root . --profile backend --apply --plan-file ../backend-sync.plan.json --json
yss recover --root . --profile backend --json
yss recover --root . --profile backend --apply --json
yss rollback --root . --profile backend --json
yss rollback --root . --profile backend --apply --json
```

原生实例由 `.yss.json` 记录身份、来源与受管基线。已绑定插件的实例，来源升级须经对应插件的升级计划与应用流程，把身份和 binding 纳入同一事务；直接 `sync` 不能绕过绑定更新。同来源资源补装仍须保存计划后应用。

旧实例不会在 `sync` 中自动转换。先用 `doctor`、`diff` 只读检查；旧事务未完成时，先用归档版本对应的仓外固定旧执行器恢复。随后明确保存并应用同家族迁移计划：

```sh
yss migrate --root . --profile backend --plan --out ../backend-migrate.plan.json --json
yss migrate --root . --profile backend --apply --plan-file ../backend-migrate.plan.json --json
```

插件绑定实例的迁移由对应插件入口编排，不能省略绑定合同。旧 metadata 原字节作为迁移基线保留，业务方案和批准不因迁移自动获得新批准；跨家族转换拒绝。当前不支持旧 `--prune` 参数，`sync` 保留退出分发的既有文件及基线，需要清理的退役资产另行审阅和归档。

`recover` 和 `rollback` 默认只读，增加 `--apply` 才执行恢复或最近项目事务的整体回退；收据同时保护受管字节、权限、身份和 binding。后续用户修改会阻止覆盖。中断事务恢复后重新预演；完整回退后按恢复结果核对原身份，再使用对应版本维护。

职责案例见[设备借用案例](设备借用贯穿案例.md)，阶段导航见[本仓工作流](产品生命周期工作流.md)。
