# 实现计划与执行

复杂拆分、跨仓集成、跨会话续办或执行已有计划时使用。清晰的小改动直接完成。计划承接原始需求、已确认的规则与本次授权，引用原验收和采用版本。

## 编排

先按用户要求的终点梳理本次采用的来源及版本、原 FR/AC 或已有验收引用、真实工程和整体依赖。需要拆分时沿用工程票方法，按用户或调用方可观察的结果划分增量。逐项回看原验收由哪个增量或哪次集成覆盖，优先细化近期可执行的工作。

每项写清可观察结果、实际仓库及必要路径、接口或产物的提供方和使用方、解除依赖所需的结果，以及验证方法和可观察预期。前置未明时记录受影响工作和待核实事实；须一起验证的工作明确共同集成范围。短计划留在当前任务或已有工程票，独立计划沿用原件并回链，当前执行状态在已有任务或采用的 tracker 维护。

共用规则跨会话推进时，给相关增量保留本次采用的前置决定及受影响的原验收引用。前置决定或事实变动时，按实际消费者复查相关增量和验证结果。下游以真实输入版本和观察到的结果作为前提成立的依据。

## 执行

按 [写入前核对](repository-scope.md#写入前核对) 核实实际采用的确认、目标 Git 和写入授权。用实际提供物和对应版本的检查结果解除下游依赖。跨仓明确集成人，核实各方采用的真实接口。当前终点包含联调且具备相应授权时，由集成人用实际工程版本组合验证原 AC，并记录对应版本和结果。当前只做分仓或模拟验证时，报告实际结果及待联调项。

验证、隔离和评审按用户要求、工程约定和风险选择，测试优先按明确请求采用。提交、推送、部署和 tracker 写入使用各自动作的有效授权。已有并行、工作台和 PR/MR 跟进方法按当前任务使用。

## 续办

回读本次实际采用的来源版本、工作树差异、已有工作项或 PR/MR 及验证结果。保留仍有效的工作，据实更新受变化影响的步骤和验证。此前写入结果未知时，先查真实结果再决定是否重试。

技术做法变化且业务结果一致时，在原任务记录依据和影响，按授权继续。来源变化或计划偏差涉及业务行为、权限或验收时，定位原规则及受影响工作，按写入前核对复用覆盖当前范围与采用版本的有效决定和确认。依据齐备时，按授权更新受影响的步骤和验证。确有待决或缺少有效确认时，定点澄清并暂停相关写入与集成，继续有依据的独立部分。
