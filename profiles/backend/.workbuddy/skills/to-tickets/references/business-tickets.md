# 业务票

用户明确要求按业务行为组织 Ticket 时读取。业务票是业务规格的组织形式，不是完整 Spec 的额外必交付物，也不是研发接收或实现的前置。用户要求研发实现拆分时使用工程票方法，不把本分支的职责边界套到已授权研发任务上。

按完整可观察业务行为组织票据，写明业务价值、范围、原始规则/FR、验收项/AC、业务依赖与未决项，不机械一条 FR 一票。不要求实现仓、技术选型、API 冻结或构建命令；已有工程工作项就关联真实条目，不要求每张业务票再拆一层工程票。

参考项目根 `.template-spec/templates/business-ticket-template.md`，字段按真实来源填写；没有集合就省略相应字段，不虚构引用或新建集合。已有集合继续维护同一引用与覆盖情况。只摘录本票需要的规则，保留原始来源与稳定 ID，不复制完整规格或另建当前状态台账。

跨票共用的规则统一引用原始来源和稳定 ID，各票写清该规则在本票的适用条件。拆分后逐项对照本次范围内的原 AC，核对每项由哪些票承接、是否存在遗漏或冲突。只有多票结果同时满足才成立的 AC，保留共同验收的条件和可观察结果。覆盖缺口写回拆分结果或已有集合。

业务对象、概念关系、信息含义、必填/唯一性、权限与状态规则可以写；不据此生成物理表、字段存储类型、主外键、索引、DDL、迁移方案、生产 API 路径与请求响应契约、技术分层或实现切片。已有技术事实可注明来源及业务影响后引用，不能借引用扩写新的技术设计；原型模拟数据不构成生产契约。

需要产品设计时围绕流程、状态、失败与恢复校准，未决项说明影响和解除条件，不生成空原型。已有决定继续使用；只有实质改变业务范围、规则或验收才回到业务方，不能将技术缺口改写成未经确认的产品决定。

返回每票业务结果、范围、验收、业务依赖与未决项。涉及保存、更新或完成状态时，按项目根 `.template-spec/agents/issue-tracker-operations.md` 复用对应授权，并报告实际保存结果。业务票完成依据本票 AC 的实际结果，子票关闭或 PR/MR 合并不自动证明业务完成，也不自动授权关闭父票。
