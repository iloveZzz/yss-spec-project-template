# 选择技能与编写提示词

先看用户要拿到的东西。“这份周报该用哪个技能改，帮我写一句”要的是用法。“帮我把这段改成周报”要的是周报，直接使用当前工程的写作方法完成。点名某个技能做比较或调研时，交付用户所问的分析。用户明确要求先推荐再执行时，按原请求的范围继续。

## 推荐一个可以使用的入口

1. 从用户原话、已有材料和目标工程找出要交付的结果，以及提示词会发给哪个聊天。按需读工程根的 `.template-spec/agents/profile-skills.md`，重点看“用具体请求检查选择是否合理”。涉及旧称时查地图“技能改名”和实际安装版本。
2. 只读有可能改变推荐的目标 `SKILL.md`，核对它的职责、使用时机和显式调用要求。无需掌握整套目录。用户明确要求看菜单时，再按“想完成什么”分组列出当前工程可用的入口。
3. 如果用户只问“用哪个技能”，上下文里也没有目标，只问“你现在想拿到什么结果？”。已有目标但两种理解会产生不同成果时，只问一个区分问题。例如“你想给后端写一段接棒提示，还是把选定文件交进 PR/MR？”已经说明目标或渠道时直接给出推荐。

用户只说“想做个原型”且目的未明时，问“你想看页面怎么操作，还是验证一条业务规则在不同状态下会怎样？”前者在可用时推荐 `yss-design-ui`，后者推荐 `yss-prototype-logic`。想分析业务需求与验收规则时，推荐当前工程可用的 `yss-analyze-business`。已有具体选项且需要业务方拍板时，推荐“澄清业务取舍” `grilling`，把已定事实和真正待答的选择写进提示词。

已接入 YSS 且安装情况影响答案时，可用 `yss skills list --root <目标工程> --json`。`result.available` 说明当前库提供哪些名称，`result.selected` 是当前 Bundle 的选集。`result.installed` 报告工程安装状态。旧 CLI 可能把一份借用的参考文件也报成 `installed`。

遇到状态冲突、同名或旧名时，核对目标工程 `.yss/project.json`、本地入口文件，以及目标宿主清单中的启用状态和实际来源。目录名、安装记录或同名菜单项都不足以单独确认调用。用户指定工程版时，认准这个工程已启用的入口。菜单里只有个人版或另一工程的同名项时，说明差别，给符合本工程目标的普通提示词。用户接受其他来源且其职责相符时，可以给该来源的实际调用写法。目标入口已停用时，提示词直接描述任务和所选材料，避免让接收方绕道加载停用的技能正文。

按**实际接收聊天**确认可以点名的来源。排查为何未自动选中时，另查该来源在对应宿主的显式或隐式策略。例如 Codex 的 Spec 和 Backend 工程均可有可点名的项目版 `to-tickets`。共享版关闭隐式调用，Backend 版按其职责允许隐式选择。允许隐式只表示可被选择，某次采用还需读取或调用证据。具体判断按项目有效配置。

用户留在当前聊天跨工程时，切 shell 目录只改变命令的运行位置。若明确要求采用另仓可读且允许使用的方法，在普通提示词里写入已核实的目标工作树、`AGENTS.md` 与技能正文路径，让接收方先读规则再处理。要求原生点名时，按接收聊天实际启用的来源给写法。遇到外仓、同名或宿主语法问题，按需读工程根的 `.agents/skills/setup-yss-harness/references/host-compatibility.md`。

CLI 已升级而工程尚未同步时，宿主仍启用旧名就给旧名的写法，并说明升级后的路径。`result.diagnostics` 只列和当前工程有关的旧记录或路径。地图中的其他 Profile 案例可作查证线索。清单无此项而确需确认退役时，查对应版本与 Profile 的 Bundle 退役声明。已接入的目标工程确认当前 CLI 支持预览时，可用 `yss skills ensure <旧 ID> --root <目标工程> --dry-run --json` 查原因和替代项。`SKILL_RETIRED` 可以确认当前库中的退役记录，`INVALID_INPUT` 只说明当前库不提供该名称。按实际查证结果说明原因和依据，再按本次产物选目标宿主可用的入口或普通提示词。安装或同步沿用用户对该动作的授权。

| 查到的状态 | 怎样给用户一条可走的路 |
| --- | --- |
| `installed` 或 `unmanaged`（工程自行维护） | 按本地正文和宿主的实际入口给出写法，自管入口采用项目自己的版本。查询用法时保留工程文件和安装记录。 |
| `not-installed` 或只有借用资料 | 宿主没有相符的可用入口时，给一个普通中文提示词，并说明查到了什么，例如“工程只有组件参考文件”。如果工程路径上是链接，分别说明 CLI 核实的文件和宿主发现的来源。用户问安装时再给适用命令。 |
| `missing` 或 `modified` | 按需用 `yss doctor --root <目标工程> --json` 定位差异。缺入口时核对宿主并给可用写法。只缺参考或有本地定制时，读取与问题有关的部分，例如问主题时看主题资料，问职责时看本地正文。说明受影响的工作。 |
| 当前库无此项、工程未接入（`NOT_READY`）或状态仍无法核实 | 依据目标宿主可核实的入口和来源回答。若只能确认材料可读，给普通提示词，说明还有哪项可用性未知。用户指定其他接收工程时，按那个工程核对。 |

例如，当前工程缺少可调用的建图入口，可以直接发“请根据我已说明的目标，列出已定事项、开放问题和依赖，暂时说不清的留白。”

## 让用户能直接发送

默认给一个首选、一句理由、一段可复制的中文提示词。比较相邻技能时，说明哪个条件会改变首选，例如检查原型、审查 MR、修正正式页面要交付的结果各不相同。按用户要的结果写完成条件和证据，沿用原材料中已确定的规则。

改写已有提示词时，以用户这次要的结果和终点为准。保留原始现象、已有依据和限制，补一项能支持或排除判断的最小观察。原稿里的处置建议仍待验证时写成线索。用户只要可粘贴的文字时直接交付该段。

- 修复缺陷时带上原始症状和触发操作，请接收方沿同一路径复验并报告结果。用户猜测的原因标为待核实。
- 复核原型或实现时写明原验收及接收方能观察的结果。能操作的页面写入失败恢复等实际操作，访问情况未知时先核实。若只拿到静态稿或截图，请核对可见状态，并在提示词里点名待验的交互，例如“重试行为待实测”。模拟验证注明范围。备注是否保留尚未确定时，记录看到的表现并标为待定。
- 调研事实时说明要支持哪个判断，请接收方给出可追溯的来源，指出哪些结论仍缺依据。

原会话可以沿用刚讨论的目标。给新会话的提示词要独立读得懂。写明接收工程、从那里可用的材料位置、实际采用的版本或读取时点、原验收、影响本次工作的待定规则，以及要交什么、交到哪里。区分发送方读过的原件和接收方能打开的材料。接收方无权读原件时，注明来源和访问限制，在允许共享的范围内摘述足以开展工作的条款。访问情况未知就标明未知。缺少依据时，请接收方先做已知部分，并指出哪一项还缺哪条规则。

来源会变化时，把版本依据写进可转发的正文。提交或修订含有所选条款时，给接收方可回读的位置和条款号。若选中工作树改稿，填入实际读取日期或已核实的文件指纹，再摘录允许共享的验收原句和待定项。例如“我在〔实际日期〕读到〔路径〕的未提交稿，AC-3 原文为……”。这样旧稿无法取回时仍能拆票。接手时如同一路径的业务行为、角色或权限已经改变，请列明差异，按明确选定的口径交付。还有取舍时只标出受影响的部分，单纯的排版变化可继续。

同名技能按接收工程的正文和用户要的产物解释。例如给共享版 `to-tickets` 写业务拆票提示时，可请它“在对话中给出业务票草案，写明用户在什么条件下能做什么、怎样按原验收判断”。给 Backend 版拆后端实现项时，可请它“逐项写明实现结果、对应原验收、实际依赖及待定规则的影响，只在对话里列出”。把已知的工程、来源位置和版本直接写入要发送的那段话。安装、修改材料或对外发送沿用对应动作的授权。

给新聊天续办进行中的工作时，沿已有任务记录带上当前候选、旧证据所对应的版本、正在运行的检查、结果未知的操作和下一步。请接收方先核实未知操作是否生效，按当前版本复查受变化影响的结果。区分查一次状态、只读审查、跟到可合并、实际交付文件和执行合并，按用户指定的终点写入提示词。

续办提示只转述本次已知的动作授权。处理实质反馈可以包括授权内的本地修复和复验。提交、推送、平台回复、重试写入和合并各沿用实际授权。只知道账号可写或上次请求超时时，先只读核实。授权还不明确的动作列作待处理项，已授权部分继续。

用户问“怎样让它回到只读审查”，可以给“请保留工作树现场，只审查这个 MR，在对话里列出有文件位置和依据的缺陷，说明刚才已经改过什么”。问“它只给构建结果就说页面已还原，我下一句怎么说”，可以给“请在相同视口和数据下打开选定原型与正式页面，两边各操作一次失败恢复，记录实际能否重试及差异，附可复核的画面或操作记录。构建结果单列，没操作到的标明待验”。用户直接说“只审查，停下改动”或“现在就复核页面”时，由当前任务按原授权实际审查或操作并报告观察结果。

例如，用户说“方向有了，连还有哪些问题都说不全”，想知道怎么起步。目标 Spec 工程已安装 `yss-map-decisions` 时，按当前宿主的显式调用写法给提示词。以下是可直接在 Codex 中发送的示例。

> 推荐 `yss-map-decisions`。你已经有目标，可以先找出哪些决定影响后面的工作，暂时问不清的部分可以留白。
>
> `$yss-map-decisions 请为我们刚讨论的目标建立决策地图。沿用已确认的决定，列出现在能说清的问题和依赖，把尚未成形的部分留白，指出先解决哪一项。`

在 Spec 工程中，从产品目标编制规格与原型、或为已有规格写给研发的接棒提示，可用时推荐 `yss-build-spec`。用户明确点名 `to-spec` 整理已经确定的材料时，沿用已有决定。

用户只要一句给研发的接棒提示时，在当前对话写明材料位置、未决项和接收方下一动作。问如何把选定文件实际交进指定 PR/MR 时，目标宿主启用了 `yss-deliver-pr-mr` 就给其写法，提示词保留选定文件、目标 PR/MR 和接收方。只问用法即可收尾。
