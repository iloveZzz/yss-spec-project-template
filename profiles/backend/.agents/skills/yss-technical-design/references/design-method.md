# 架构、方案与详细设计

用于当前任务需要的技术判断。复用已有设计或任务说明，按复杂度展开同一份内容；简单空值修复不需要类图、架构文档或逐行说明。

## 输入与依据

从真实 Spec/需求中提取可观察行为、约束与验收，结合代码调用链、POM、数据库/接口定义和实际运行配置。产品原型用于理解业务状态与交互，不重新设计产品。业务未决项说明影响；常规实现选择由 Agent 判断。

清楚区分已确认业务约束、当前工程事实、本次技术决定及尚未验证的假设。性能/容量没有测量依据时保留假设与验证办法，不编造吞吐或时延保证。

发现来源变化、原型冲突或技术选择将改变业务结果、权限或验收时，按项目根读取 `.agents/skills/implement/references/spec-feedback.md`，定位原规则和受影响部分再澄清。业务结果不变的技术选择自行判断并记录依据，独立工作继续。

## 架构层

明确本次命中的系统与外部系统边界、模块职责、依赖方向、运行环境、技术限制及重要质量要求。已有工程优先沿用框架、数据库与版本；只有现有选择不能满足目标时才解释调整理由及影响。

DDD 用一致性和领域行为确定边界，聚合内部按需交给 `yss-tactical-design`。MVC 将用例规则和事务放在既有 Service 边界，保持 Controller/Service/Repository；安装了 DDD 技能不构成新增 Domain/Gateway 的理由。新工程依真实约束选择架构，不把脚手架默认值当需求。

## 技术方案层

说明实现当前行为所需的核心调用路径、数据模型、API 与外部集成，以及下面实际相关的决策：

- 事务范围、一致性要求、并发竞争、幂等键与重复请求的结果。
- 权限主体、输入校验、错误语义与敏感数据边界。
- 与已有接口/数据/调用方的兼容性，变更后的迁移顺序。
- 超时、重试、部分失败、补偿或人工恢复的条件；重试次数和时机来自实际约束。

候选方案存在实质差异时说明选择和代价；唯一清晰的局部方案无需凑备选项。不能借实现方便静默改写 Spec。

## 详细设计层

仅把复杂行为展开到可实现的粒度：对象职责、关键接口/签名、输入输出和异常、状态转换、数据映射、查询与索引影响。签名需由现有代码或明确的新设计支持，不能从过时索引猜测 API。

例如订单取消涉及支付竞争：明确谁可以取消、哪些状态允许、并发支付/取消如何裁决、重复取消返回什么、外部退款失败如何恢复；再确定事务与接口，而不是先列 Controller/Service/Repository 类名。

补充对应的验证要点和未决限制。单元验证不代表真实数据库锁/隔离级别已验证；设计中的恢复策略不代表已执行部署或数据修复。

## 输出与继续范围

用现有文档或当前任务说明表达行为、关键决定、影响与依据；不创建平行合同或固定批准包。只读评估可给出建议与待确认项，不能修改工程或远程建票。实现是否继续由当前用户任务决定，所有外部写入沿用对应授权。
