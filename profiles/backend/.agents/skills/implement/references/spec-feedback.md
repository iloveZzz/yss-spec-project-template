# 承接规格与回流研发发现

承接 Spec、业务票或原型，或发现来源变化与业务差异时使用。业务规则和验收沿用原 Spec；原型说明交互与模拟边界，Backend 负责技术选择、实现和实际验证，不另建一份权威规格。

## 保留同一规则的关联

读取实际材料和适用工程，在当前任务保留规则/验收来源、相关原型状态及模拟范围、本次实现或 Slice、验证结果与缺口。沿用 FR/AC、Issue 或章节链接；没有编号用已有材料名称和章节，不新建 ID、票集或追踪台账。简单任务一段说明即可。

记录可获得的 commit、Issue 更新时间或读取时点；无版本能力时说明限制。动态来源在开始依赖工作和交付前按风险复读，比较真正消费的内容，包括未提交修改；不要用旧 HEAD 代替当前材料，也不创建镜像权威。

## 发现差异时

| 发现 | 下一步 |
|---|---|
| 规则清楚，材料未变或只改排版 | 复用有效确认，直接完成已授权技术工作 |
| 仅技术选择变化，业务结果不变 | 记录依据与影响，按原授权继续，不重问已定业务问题 |
| 实现需要改变结果、权限或验收 | 指出具体原规则和影响，只暂停依赖该决定的工作，向用户澄清；独立部分继续 |
| Spec 与原型矛盾 | 保留两处来源，澄清真实分歧，不以原型能点通代替业务决定 |
| 上游改变已消费规则 | 定位受影响 Slice、接口、场景和测试，复核相关范围；不在陈旧规则上继续集成 |
| 原型成功，真实数据库或服务未运行 | 分别说明模拟结果与实际验证缺口，不改原验收含义 |

例如 Spec 允许撤回但原型禁止时，先定位规则与状态再澄清；上游收窄撤回权限时，应重看对应权限实现和拒绝场景，不要求无关功能重做。

## 回到原任务

研发发现先返回原任务。Spec 文件在当前可写范围内且决定已确认时增量修订同一规则；位于其他仓库或远程平台时准备有来源的修订建议，实际写入使用对应授权。读取材料不授权跨仓修改、评论、关闭条目或通知他人。

完成说明按原验收分别列出已实现、实际验证过、未验证和仍待决定的行为及影响；代码完成不等于业务验收通过。保留未受影响工作和用户修改，不为回流另设审批包。
