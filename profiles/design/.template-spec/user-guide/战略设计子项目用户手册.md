# 战略设计子项目用户手册

本手册面向产品经理、需求分析师和商务协作者。当前 profile 是 `harness.business-ddd-strategy-handoff`：把用户问题收敛为批准的业务边界、Spec、页面依据、业务级 Ticket 和业务方案交接包；不设计工程 API，不生成前后端工程，不实施代码。

## 创建或接管项目

先从受控发行清单取得适配平台的固定 `yss` 二进制并校验 SHA-256；用实际版本记录核对发行来源。以下创建和接管示例在目标项目的父目录执行，计划保存在项目外的新文件中。

```sh
yss version --json
yss init --root ./design-project --profile design --project-name 设备借用 --business-domain 内部设备管理 --json
yss attach --root ./existing-project --profile design --plan --out ./design-attach.plan.json --json
yss attach --root ./existing-project --profile design --apply --plan-file ./design-attach.plan.json --json
```

`init` 直接创建项目，目标须不存在或为空；`attach` 默认只预演，审阅已保存计划后再执行应用。应用会重新核验计划摘要和当前输入，输入变化后须重新预演。生成后核对 `yss-project.yaml`、原生 `.yss.json`、根 `CONTEXT.md`、`.template-spec/process/harness-profile.yaml` 和实现仓登记；CLI 详情见[CLI 使用说明](CLI使用说明.md)。

## 第一次让 Agent 工作

```text
请先只读检查本仓身份、根 CONTEXT.md、harness-profile.yaml 和现有业务资产。
说明当前可信阶段、已确认决定、待确认问题、缺失证据和下一步。
按依赖逐轮澄清，不进入技术设计、API、脚手架或代码实现。
```

Agent 应区分业务决定、可查证事实和待验证假设。业务语言先登记到根 `CONTEXT.md`；每个工作单元流转前完成当前 `context_reconciliation`。文件存在、聊天同意或历史批准都不能证明当前版本已获批准。

## 业务方案总览

总览只是导航视图，引用下列权威资产的当前状态、未决项和下一步，不复制正文，也不成为新的事实来源：

- 机会与目标：谁遇到了什么问题。
- 业务故事：事情通常怎样一步步发生。
- 业务责任区与协作：每一步由谁负责。
- 规则与例子：有哪些规则、例外。
- Spec：确认的范围、行为和验收。
- 页面验证：用哪些例子和证据证明结果正确。
- 业务级 Ticket：哪一小段可以独立交付；本仓只形成业务级范围，不创建技术切片。
- 业务方案交接：将已批准资产和待决问题交给研发团队。

## 本仓操作主线

`机会与目标 → 业务故事与责任边界 → 规则与反例 → Spec → UI 依据 → 业务级 Ticket → 批准交接`

1. 确认用户、问题、目标、限制、范围和明确非目标。
2. 用可观察行为说明正常、拒绝、边界和恢复场景；规则含糊时继续向有权用户提问。
3. 形成 Spec。存在 UI 变化时准备并批准原型；确认无 UI 变化的既有工程使用 `existing-ui-baseline`，绑定源码、构建、浏览器捕获、截图和 API 记录。
4. 由有权用户确认业务方案、页面依据和交接范围。业务级 Ticket 保持 `ready-for-human`，本仓不创建父 Ticket、垂直切片或 `ready-for-agent`。
5. 形成 Handoff v5 交接描述，绑定根词汇、规则、场景、批准和 UI 基线；把技术待决项明确交给下游。

## 导出前预检与交接

`scripts/preflight-delivery` 只读取当前原始资产，不执行清单中的命令，不生成批准或收据。导出前准备 `delivery_kind: strategic-handoff` 的输入清单，并运行：

```sh
node scripts/preflight-delivery --input <战略预检输入.json> --stage export --json
node scripts/strategic-handoff finalize --source-root . --handoff <Handoff-v5相对路径> --preflight-input <战略预检输入.json> --zip
node scripts/strategic-handoff verify --bundle <包目录或ZIP>
```

预检和验包通过只证明所读资产的身份与完整性。它们不批准下游技术设计、Slice Contract 或发布。输出包交给下游后保留版本和摘要，不手改包内文件。

## 用户决定与完成标准

用户需要明确确认目标与非目标、规则与反例、UI 分支及当前基线、业务级 Ticket 范围、交接内容和研发待决事项。批准必须绑定当前资产、依据、范围和真实回复；资产变化后重新判断受影响批准。

本仓完成时应同时满足：

- 业务方案交接包已由当前批准资产生成并通过本轮验证。
- 交接包含根词汇快照、规则/场景、UI 依据、业务 Ticket 和下游待决项。
- 没有越界生成 OpenAPI、技术 Ticket、Slice Contract 或运行时代码。
- 结论只写“战略可交接”，不写“产品完成”或“可发布”。

## 同步与恢复

在项目根目录执行以下命令。`sync` 默认只预演；应用必须消费已保存的计划。

```sh
yss doctor --root . --profile design --json
yss diff --root . --profile design --json
yss sync --root . --profile design --plan --out ../design-sync.plan.json --json
yss sync --root . --profile design --apply --plan-file ../design-sync.plan.json --json
yss recover --root . --profile design --json
yss recover --root . --profile design --apply --json
yss rollback --root . --profile design --json
yss rollback --root . --profile design --apply --json
```

原生实例由 `.yss.json` 记录身份、来源与受管基线。已绑定插件的实例，来源升级须经对应插件的升级计划与应用流程，把身份和 binding 纳入同一事务；直接 `sync` 不能绕过绑定更新。同来源资源补装仍须保存计划后应用。

旧实例不会在 `sync` 中自动转换。先用 `doctor`、`diff` 只读检查；旧事务未完成时，先用归档版本对应的仓外固定旧执行器恢复。随后明确保存并应用同家族迁移计划：

```sh
yss migrate --root . --profile design --plan --out ../design-migrate.plan.json --json
yss migrate --root . --profile design --apply --plan-file ../design-migrate.plan.json --json
```

插件绑定实例的迁移由对应插件入口编排，不能省略绑定合同。旧 metadata 原字节作为迁移基线保留，业务方案和批准不因迁移自动获得新批准；跨家族转换拒绝。当前不支持旧 `--prune` 参数，`sync` 保留退出分发的既有文件及基线，需要清理的退役资产另行审阅和归档。

`recover` 和 `rollback` 默认只读，增加 `--apply` 才执行恢复或最近项目事务的整体回退；收据同时保护受管字节、权限、身份和 binding。后续用户修改会阻止覆盖。中断事务恢复后重新预演；完整回退后按恢复结果核对原身份，再使用对应版本维护。

职责案例见[设备借用案例](设备借用贯穿案例.md)，阶段导航见[本仓工作流](产品生命周期工作流.md)。
