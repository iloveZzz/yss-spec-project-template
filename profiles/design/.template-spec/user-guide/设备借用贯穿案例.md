# 设备借用：战略设计职责案例

本文是虚构教学材料，不是已批准 Spec 或真实交付包。目标是把“员工借用设备”收敛为可交接的业务方案，不进入 API、数据库或代码设计。

## 1. 澄清业务结果

```text
请按战略设计流程澄清内部设备借用。
先确认参与者、目标、范围、申请、审批、领用和归还的可观察结果。
逐轮询问会改变业务结果的问题，不替我决定审批是否预占设备、谁能代领或超期如何处理。
```

至少覆盖：日期非法、设备不可借、无权限审批、重复审批、未批准领用、并发领用和重复归还。用户确认前都保持为待决项，不写成规则。

## 2. 形成可审阅资产

1. 把稳定业务词汇登记到根 `CONTEXT.md`，完成当前对账。
2. 形成目标、非目标、业务故事、责任边界、规则和反例。
3. 起草 Spec，使规则与验收场景对应。
4. 有 UI 变化时准备申请、审批、领用和异常恢复页面；无 UI 变化的既有工程使用经验证并批准的 `existing-ui-baseline`。
5. 形成窄业务级 Ticket，例如“已批准申请领用设备”，保持 `ready-for-human`。

用户确认的是业务结果、页面依据和交接范围，不是后端架构、工程 API 或实现许可。

## 3. 准备 Handoff v5

交接描述应绑定当前根词汇、源规则、关键场景、Spec、UI 分支、业务 Ticket、批准和研发待决项。准备 `delivery_kind: strategic-handoff` 的预检输入：

```sh
node scripts/preflight-delivery --input <战略预检输入.json> --stage export --json
node scripts/strategic-handoff finalize --source-root . --handoff <Handoff-v5相对路径> --preflight-input <战略预检输入.json> --zip
node scripts/strategic-handoff verify --bundle <包目录或ZIP>
```

预期结果是当前战略包可验证。若 UI 基线、批准、摘要或源资产发生变化，修正事实源并重新预检和导出，不手改包内摘要。

## 4. 交给下游

向下游说明：设备占用竞争、事务、幂等、数据库和 API 仍需技术设计；战略方只交付批准的业务含义。下游导入后必须重新完成目标词汇对账、规则/场景承接和本地合同批准。

本仓完成结论是“设备借用战略方案可交接”。后端实现、前端验收和整体业务发布仍由相应责任方完成。
