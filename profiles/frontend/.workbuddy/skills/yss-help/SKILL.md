# 选择技能与编写提示词

先看用户要拿到的东西。“这份周报该用哪个技能改，帮我写一句”要的是用法。“帮我把这段改成周报”要的是周报，直接使用当前工程的写作方法完成。用户若明确要求先推荐再执行，做完推荐后按原请求的范围继续。

## 推荐一个可以使用的入口

1. 从用户原话、已有材料和当前目标工程找出要交付的结果。按需读工程根的 `.template-spec/agents/profile-skills.md`，重点看“用具体请求检查选择是否合理”。涉及旧称时读取地图“技能改名”、当前注册表或 Bundle 的退役记录。例如，问怎么用 `i-have-adhd` 修改周报，在已同步的新工程推荐 `yss-write-docs` 并给新写法。目标工程尚在旧版时，说明该工程当前可调用的名称。优先采用目标工程的实际版本。
2. 只读有可能改变推荐的目标 `SKILL.md`，核对它的职责、使用时机和显式调用要求。无需掌握整套目录。用户明确要求看菜单时，再按“想完成什么”分组列出当前工程可用的入口。
3. 如果用户只问“用哪个技能”，上下文里也没有目标，只问“你现在想拿到什么结果？”。已有目标但两种理解会产生不同成果时，只问一个区分问题。例如“你想给后端写一段接棒提示，还是把选定文件交进 PR/MR？”已经说明目标或渠道时直接给出推荐。

用户只说“想做个原型”且目的未明时，问“你想看页面怎么操作，还是验证一条业务规则在不同状态下会怎样？”前者在可用时推荐 `yss-design-ui`，后者推荐 `yss-prototype-logic`。想分析业务需求与验收规则时，推荐当前工程可用的 `yss-analyze-business`。已有具体选项且需要业务方拍板时，推荐“澄清业务取舍” `grilling`，把已定事实和真正待答的选择写进提示词。

已接入 YSS 且安装情况影响答案时，可用 `yss skills list --root <目标工程> --json`。`result.available` 列出当前 CLI 为该 Profile 提供的技能，`result.installed` 只报告这些名称的本地状态。

CLI 已升级而工程尚未同步时，列表可能省略工程仍在用的旧名。核对目标工程 `.yss/project.json` 的 `managed` 路径，再看目标宿主的项目技能菜单或会话清单。若宿主仍启用旧名，按旧名给当前可用的提示词，同时说明升级后的名称。若某个平台的副本缺失或入口被禁用，按该宿主实际可用的入口回答。

| 查到的状态 | 怎样给用户一条可走的路 |
| --- | --- |
| 已安装 | 按目标工程正文给出写法。`modified` 时先读本地修订。显式技能提示用户按本宿主支持的入口点名。 |
| 在库中但未安装 | 说明可按需补装。`missing` 表示文件缺失，`not-installed` 表示未安装。给一段当前会话能用的普通提示词。用户询问安装时再给具体命令。 |
| 当前库无此项 | 改用已确认可用的方法或普通提示词。若用户已经指定另一个接收工程，可说明该工程经核实的入口。 |
| 无法核实 | 依据当前会话列出的技能、可读文件和已有材料回答，说明哪项可用性尚不清楚。能读到文件只证明材料可读。 |

例如，当前工程缺少可调用的建图入口，可以直接发“请根据我已说明的目标，列出已定事项、开放问题和依赖，暂时说不清的留白。”

## 让用户能直接发送

默认给一个首选、一句理由、一段可复制的中文提示词。把用户已提供的材料、限制、交付结果写进去，未知信息保留原状。可以沿用已有正式入口或经核实的新名称。只问用法时，给出提示词即可收尾。安装、修改材料或对外发送依照用户对具体动作的授权。

例如，用户说“方向有了，连还有哪些问题都说不全”，想知道怎么起步。目标 Spec 工程已安装 `wayfinder` 时，按当前宿主的显式调用写法给提示词。以下是可直接在 Codex 中发送的示例。

> 推荐 `wayfinder`。你已经有目标，可以先找出哪些决定影响后面的工作，暂时问不清的部分可以留白。
>
> `$wayfinder 请为我们刚讨论的目标建立决策地图。沿用已确认的决定，列出现在能说清的问题和依赖，把尚未成形的部分留白，指出先解决哪一项。`

在 Spec 工程中，从产品目标编制规格与原型、或为已有规格写给研发的接棒提示，推荐 `yss-build-spec`。用户明确点名 `to-spec` 整理已经确定的材料时，沿用已有决定。

用户仅想把已有材料交给接收方时，把材料位置、未决项和接收方下一动作带进提示词。明确要求通过 PR/MR 交付选定文件时，才推荐现有的 `handoff` 交付方法。
