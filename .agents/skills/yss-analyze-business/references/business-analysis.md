# 业务分析方法

从当前问题选择适用维度，不要求每项生成文件。以“谁在什么条件下做什么，得到什么可观察结果”组织结论。

| 维度 | 要回答的问题 |
|---|---|
| 问题与场景 | 谁遇到什么问题，已有流程哪里不足，期望结果是什么，证据在哪里 |
| 目标与范围 | 包含什么、不包含什么，优先级依据是什么，哪些目标互相冲突 |
| 概念与责任 | 角色、业务对象、信息来源、规则提供方/使用方与交接责任如何划分 |
| 规则与权限 | 什么触发动作，前提和例外是什么，谁能执行、能看哪些数据，结果如何可见 |
| 状态与恢复 | 成功、拒绝、取消、失败、重试、并发冲突或恢复会怎样，哪些动作不合法 |
| 方案取舍 | 哪些方案确实解决同一问题，各自收益、代价和限制是什么，何时重新考虑 |
| 业务质量 | 哪些质量要求已有依据，观察口径是什么，未知数值由谁决定 |
| 验收缺口 | 哪些结果还无法判断，应调查、澄清还是通过原型体验 |

综合目标时保留来源中的对象、范围和确定程度，不因某个环节已有功能或更容易测量就缩小业务目标。细化指标、统计起止事件或目标值属于建议时，明确标为建议或待确认；来源已明确的口径直接沿用，不重复询问。

存在真实方案取舍时，区分“功能按约定工作”与“原业务问题得到改善”：说明预期改善、支持判断的现有证据，以及什么观察会促使重新考虑方案。功能验收通过不证明业务效果；未知基线、指标、负责人和时点保持未知，不为普通需求强制增加 KPI 表或实验报告。

需要关联解释角色、状态、权限或变更时，使用 [图解表达](../../yss-write-docs/references/visual-explanation.md)。业务分析负责转换的角色、触发、条件、目标状态与拒绝结果；未决信息保持可见，图解只选择表达，不替代业务决定。

用具体故事和反例检查边界：权限变化后能否继续、部分成功后重试什么、取消是否保留原数据、重复动作是否重复产生业务结果。只讨论当前影响的场景，不把技术幂等或事务方案提前定为实现要求。

多条规则共同决定结果时，检查条件重叠、遗漏的结果、动作顺序和优先关系，按当前风险选取组合。把有依据的结果落实到原 FR/AC，说明哪几条已确认规则共同支持它。

例如，已确认“仅当前负责人能撤回待处理事项”和“转交只改变负责人”，可推得这样的反例。甲打开待处理事项，转交给乙已生效，甲在旧页面撤回，系统拒绝，事项仍为待处理，负责人仍是乙。如果材料只写“按负责人权限控制”，判权时点和拒绝后保留的数据都待核实。请求可能排队时，可用“甲提交撤回，随后转交生效，系统最后才处理撤回”区分按提交还是按处理时的身份判权。若另有条款允许原负责人撤回，指出冲突及受影响的验收。转交与撤回同时发生时谁优先，上述规则均未决定。

业务依赖方向与 HTTP/消息方向分开表达，不从表结构反推业务边界。核对已知实现与期望行为时标明差异，不把尚未部署的代码当作现状。

来源、假设和决定分别记录。重要未决项写清影响与解决条件，未知责任人/时点就保留未知；不能编造限制使规格看似完整。多份材料冲突先定位来源与版本，实质业务取舍交回用户。

生成或更新需求时，对影响本次范围的关键决定当场使用项目根 `.agents/skills/grilling/SKILL.md` 澄清，说明影响与建议，不只把问题堆在文末 OQ。可调查事实自行查；等待仅暂停依赖该答复的范围，其余工作继续。沿用已有 FR/AC/OQ 和工作台问题 ID，复用真实答复，用户补充改变结论时重新核对受影响规则。

工作台仅回写与当前问题摘要、适用范围相符且仍待采纳的实际答复。沿同一 Spec 的规则与 AC 更新相关交互和原型，核对一致后才解决问题并绑定真实答复 ID。已采纳且一致的结果直接引用，失效答复保留原文供复查。有效延期只更新原因、影响、排除范围及复查日期及时区或条件。按保存时的时区，到复查日当天即须复查，包括尚未首次回写的安排。条件是否触发须核实。本次必经路径还有未决项时，暂缓相应范围的确认。提醒限于当前聊天和工作台打开或刷新时。

工作台延期回写须在原问题同时写入 `status: "deferred"`、说明延期依据的非空 `resolution` 和本次真实延期答复 ID 对应的 `appliedDecisionId`，缺一仍是待回写。登记、续办与答复沿用已核实的工作台数据目录，不改用默认库重复登记。

分析结果回到当前 Spec，保持规则、状态和验收一致；无需另建 Plan、ADR 或集合。只有确有难逆转且需要解释的真实取舍，且用户授权记录时，才维护决策说明。

涉及对象或字段时，在同一 Spec 说明业务含义、归属、关系、必填、有效值、默认、唯一性及保存后可修改条件；唯一性需有范围和编辑时的自身排除规则，默认需区分建议与强制。涉及多角色时分别说明可见数据、操作前提、允许与拒绝结果，不能只写按钮隐藏或禁用。简单关系可用短段落，复杂条件再用规格中的对应表格；未知列未决，不补造技术模型。

按角色任务串起起点、跨页动作、结果和返回/失败分支；AC 给出实际初始角色、状态、代表数据、操作及可观察结果和不变项。已有规则或较长场景用具体引用复用，局部修订只更新受影响内容。改变行为时一并核对相关检查记录：保留旧观察并标明其适用的旧规则或版本，新行为未复查就明确未验证；不把历史通过沿用为新规则的结果。
