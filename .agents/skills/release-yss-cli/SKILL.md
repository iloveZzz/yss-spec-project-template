# YSS CLI 构建与发布

将用户确认的新版本从固定源码交付为可下载、可校验、已验证安装的 GitHub Release，适用于后续任意符合当前仓库合同的版本。默认平台为 `windows/amd64` 和 `darwin/arm64`；用户明确指定其他范围时先核验其当前发行合同。仅安装或升级已有 CLI 使用 `setup-yss-harness`；创建、修改本技能不触发实际发版。

## 输入与授权

从当前请求和仓库事实确定 CLI 仓库、模板来源、GitHub 目标、平台及操作范围。每次新版本任务必须依次完成 **查询最新正式 Release → 生成新版本号建议 → 用户明确确认版本号 → 构建、验收和发布**，不能把示例版本或以前的发版授权当作本次目标。

### 新版本确认门槛

先读 [版本查询与确认](references/version-selection.md)，从目标 GitHub 仓库查询最新正式 Release 并核验其身份。依据该版本及本次变化建议新版本号，展示当前版本、建议版本、递增理由、目标仓库及平台，请用户明确确认。首次请求中附带的版本号只是候选；除非已存在绑定本次查询基线的有效确认，仍须先展示建议并取得确认。

确认前只做只读调查、版本建议和记录，不修改版本/来源、不为该版本提交推送、不构建或运行发行验收、不创建 tag/Release。沉默、定时触发、技能调用、历史成功或以前对 1.3.7 等版本的授权都不是本次版本确认。确认后在已授权动作范围连续推进；同仓库、同版本、同基线及同平台的有效确认可复用。查询基线或目标发生实质变化时重新展示差异并确认，不按时间机械重复询问。

“最新代码”指确认后开始准备时从已核验 remote/default branch 获取并固定的已提交源码；固定后发生的新提交另行记录，不在构建中途切换来源。

- “构建/试打包”只产生候选与证据，不创建远端 tag 或 Release。版本准备仍保持真实 `working-tree` 状态，不能伪装 committed；正式构建所需提交若未获授权，准备可审阅差异后再取得授权。
- “构建并发布”确定动作范围，不能替代上述版本确认；版本已确认且仓库、来源和平台明确后，覆盖该版本必要的更新、提交、推送、tag 和正式 Release。复用当前会话已有有效授权，不重复确认同一范围；仓库要求的外部审批仍需满足。
- 发布不包含用户全局 CLI 覆盖、业务工程同步、npm 发布或无关源码修改。真实缺项先做可完成的准备；缺权限、平台 runner 或证据时准确说明阻断，不放宽检查。
- 读取各仓当前 `AGENTS.md`、发布说明和固定来源合同，记录 HEAD、分支、index、文件状态、待保护字节/权限。存在本地差异或并发工作时在隔离 checkout/worktree 完成；不 reset、clean、stash、强推或夹带改动。证据与构建输出放在源码仓外。

## 执行路径

1. **查询并确认版本。** 完成上述版本门槛，再核验目标 tag、正式 Release 和资产。用户明确重验已发布版本或补平台时，查询最新正式 Release 作为背景，按该既有版本核验，不擅自改成新版本发布；普通重试不重新发布、不移动 tag、不覆盖资产。只有用户明确补充平台或修复发行资产时才走发布参考中的补发路径。网络/鉴权失败不等于版本不存在。
2. **固定输入并构建。** 按 [构建与逐平台验收](references/build-and-qualification.md) 更新所需模板来源、技能锁、Bundle 和版本。发布任务从最终 clean committed CLI SHA 构建两平台；仅构建候选时，若当前构建器支持，可固定工作树输入摘要并真实标记 `working-tree`，不擅自提交，也不赋予正式发行资格。构建统一使用 `CGO_ENABLED=0`，源码、构建工具和验证工具的提交或工作树状态分别记录。
3. **完成当前发行资格。** 在各平台真实运行与其声明范围相符的检查，保留命令、实际退出、原始日志和摘要。候选通过安装检查后装配正式包；稳定字段由受审装配器产生。不能将交叉编译、历史通过记录或日常 `limited` 检查称为当前发行资格。
4. **发布并回读。** 按 [GitHub 发布与恢复](references/publish-and-recover.md) 交付正式 tag/Release、两平台归档、校验与资格证据；回读远端摘要、公开下载字节并验证两平台正式包的在线安装与回滚。CI 状态单独记录。
5. **交付结果。** 返回两平台直接下载链接、源 SHA、校验文件、逐平台实际资格、CI、未覆盖项和证据位置。源码或门禁失败、上传部分成功、发布后验证失败均如实报告；不得只因 Release 对象存在宣布完成。

仅在当前仓缺少发行工具、需要 Windows 分发适配或处理 1.3.x 兼容问题时读取 [已验证工具与历史边界](references/tool-lineage.md)。历史提交是可核验的实现参考，不是未来版本的默认来源或永久门禁。

## 关键不变量

- 两个平台绑定同一最终 CLI SHA、版本、source-lock 和四 Profile 来源；完整 SHA 不能用短 SHA、分支名或 `latest` 代替。
- Windows 安装资格与 Mac 的较广原生资格分别呈现。当前合同要求更多覆盖时补齐；不能因历史 Windows 只验安装而降级新合同。
- 所有归档清单的 `releaseGateSha256` 必须与共同 `checksums.json` 一致，且独立固定的资格索引与 required platforms 相符。不能只向校验文件追加 Windows 条目。
- 证据复用只适用于源码、二进制、工具、参数、环境和输入仍相符的范围；改变受影响输入后重验。保留首次失败/超时和修复后的记录，不覆盖失败历史。
- 不把 `stableReady`、`nativeRuntimeVerified` 或 `runtimeVerification` 当作人工开关。只有当前合同认可的真实证据及校验器才能产生发行资格。

调用示例：`使用 $release-yss-cli 查询最新正式版本，建议下一个版本号，等我确认后构建并发布 Windows x64 和 Mac ARM64。` 示例不预设任何版本号。
