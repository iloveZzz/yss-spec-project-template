# MVC Service 用例实现

沿用现有 Server、Service、Repository 模块与包名。Server 的 Controller 负责 HTTP、认证授权接线、输入校验与 DTO 转换，Service 负责用例规则、事务和幂等协调，Repository 负责持久化。通过 `yss-application` 维护 Service，用 `yss-repository`、`yss-web-controller` 处理相应边界。

## 事务入口

- 先定位 Controller、定时任务或消息消费者实际调用的 Service 方法，明确需要原子提交的写入、事务管理器与数据源。Repository 参与该事务，业务提交边界由 Service 决定。
- Spring 默认代理模式下，事务方法须经代理调用。检查同类自调用、非受代理管理的实例、异常被吞掉及异步线程切换，不能仅凭 `@Transactional` 存在认定事务生效。需要拆分时沿用已有 Bean 职责，或使用工程已有的编程式事务方式。
- 按实际异常类型确定回滚规则。用中途失败检查多次写入是否整体回滚，读取和纯计算按需要选择事务。

## 并发与重复提交

- 从当前业务与接口约定明确幂等键的作用域、请求内容、有效期，以及处理中、成功和失败后的重复请求结果。涉及租户或用户隔离时保留对应授权与键范围，规则未知时定点澄清。
- 查后再写存在并发窗口。沿用业务唯一约束或持久化幂等键，使请求占用、业务写入与结果记录按所需原子性提交。仅进程内锁或客户端禁用按钮无法覆盖多实例并发与重试。
- 相同键与相同请求按约定返回已有结果或处理中状态，避免重复写入。同键不同内容按约定报告冲突，不能静默复用另一请求结果。数据库唯一冲突只在确认对应约束后转为重复请求处理，其他数据库错误保留原有错误处理。
- 唯一冲突可能使当前事务不可继续使用。读取已提交结果或重试须在可用的事务边界执行，不能在已标记回滚的事务中继续提交。失败重试遵循已有可重试条件与次数，不能把所有异常都自动重放。

## 提交后副作用

- 消息、缓存失效、审计和外部调用按实际一致性要求安排。事务内发送外部请求可能无法随数据库回滚，提交后回调或内存异步队列也存在进程崩溃丢失窗口。
- 数据库已提交后副作用失败时，先区分已完成的业务写入与待恢复副作用，避免重跑整个用例造成重复。需要崩溃后恢复投递时，复用工程已有持久投递记录或同事务 Outbox，再按幂等消费规则重试，具体保证以真实实现为准。
- 只按需求补足恢复路径，覆盖回滚不发布、提交后失败、进程恢复和重复消费等命中场景。

## 模型转换与验证

- HTTP Request/Response 与内部 Service 输入输出的转换归 Server，PO 转换归 Repository。沿用现有模型和 MapStruct 约定，避免 HTTP DTO、PO 穿透内部边界。
- 业务规则留在 Service，不为 MVC 增设 Domain/Gateway、Application Query Port 或空转换层。已有查询按当前 Service/Repository 结构维护，分页和排序保留组件约定及列白名单。
- 从真实用例入口检查代理、回滚、并发重复提交、返回结果和恢复行为。按风险选择工程已有检查，优先根 `./mvnw`，实际数据库方言和组件行为需要对应运行证据。
