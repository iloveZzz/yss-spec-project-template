# 版本查询、建议与确认

每次新版本构建/发布先执行本协议。它确认具体版本，不扩大用户原有的构建、提交或发布动作授权；仅确认版本的回复不能将“只构建候选”变成正式发布。

## 查询当前版本

从目标 remote 和用户指令核验 GitHub `owner/repo`。通过连接器或只读命令查询：

```sh
gh repo view "$repo" --json nameWithOwner,defaultBranchRef,url
gh api "repos/$repo/releases/latest"
```

记录仓库、Release ID/URL、tag、发布时间、draft/prerelease、tag peeled 完整 SHA 和查询时间。排除草稿及预发布，不用本机二进制、main 的版本常量、最大 tag 字符串或技能内历史样例替代最新正式 Release。GitHub 指定的 latest 与其他正式版排序有矛盾时展示事实并核验仓库发布约定。

404 时进一步核验仓库访问权限和正式 Release 列表；无正式版本才走首次发布建议，网络/权限故障不能推断“尚未发布”。查询失败时保留诊断，停在版本查询，不自行采用旧缓存版本开始构建。

## 生成建议

- 先消费仓库版本规则。通常将 `vMAJOR.MINOR.PATCH` 解析为数字：修复/维护建议递增 PATCH，明确兼容新能力建议 MINOR，不兼容变化按当前合同评估 MAJOR。没有变化分类事实时将 PATCH 作为待确认建议，明确其依据待核验，不能自行扩大版本语义。
- 若用户提供目标版本，将它纳入建议并与最新正式版比较，核查对应 tag/Release 是否被占用。已占用的版本转只读幂等核验，不提出覆盖或移动 tag。
- 首次发布或非标准版本格式按仓库规则给出候选；没有规则时把该缺项交给用户决定，不猜已有版本。所有具体数字只来自本轮查询和当前请求，不内置默认发布版本。

展示一条明确的确认问题，例如：“目标仓库的最新正式版是 `<当前版本>`；本次建议 `<新版本>`（理由：`<本次变化>`），分发 Windows x64 和 Mac ARM64。是否确认以 `<新版本>` 执行本次已请求的构建/发布？”使用宿主的用户输入能力；必须等到明确回复，超时或无回复不放行。

## 绑定确认与进入执行

在仓外发布记录中保存：查询快照（仓库、Release ID/tag/SHA 或已核验的无正式版状态）、建议及理由、用户明确确认的版本、平台、原始回复引用和已授权动作。不要为了填记录伪造回复或审批。

- 首次命令“发布 X.Y.Z”表达候选目标，不能省略最新查询和建议展示后的确认；已在同一任务完成这一步且依据不变时复用有效回复。
- 进入实际构建前重新核验最新正式基线和目标占用状态。基线变化使版本建议过期时，展示新建议并重新确认；不得静默改成下一个数字或继续覆盖已占用版本。
- 确认后只构建该版本。用户改版本或改变会影响建议的版本承诺时，停止受影响执行、保留已生成证据，重新绑定确认；旧构建不能改标签后冒充新版本。
- 既有正式版的只读重验或明确补平台不产生新版本号，保留原 tag/SHA；若补发需要改变生产源码，则转入新版本查询与确认流程。

确认完成后才进入构建参考的来源准备、版本更新、提交、原生构建、门禁和发布。任何门禁成功都不能代替用户的版本确认。
