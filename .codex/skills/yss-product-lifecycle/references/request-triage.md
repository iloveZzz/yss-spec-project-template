# 请求分诊协议

判断规则由 `orchestration-contract.yaml.request_triage` 定义，本文解释应用方式。分诊成功以理解用户目标并采取正确首个动作为准；技能名称命中只是中间结果。

## 理解与澄清

把当前表达与已有对话合起来理解：用户针对什么，希望得到什么结果，当前请求允许做到哪里。短句可以足够明确；长描述也可能缺少目标。只保留影响决策的事实、假设和未知项，不要求用户填固定表单。

出现不同解释时，比较它们是否改变交付目标、修改范围或外部动作。若共同下一步都是已授权的可逆调查，先调查；否则先解释具体缺口并提问。能够自行读取的代码、日志和已回答问题先自行核查，不把取证工作转交用户。工具不可访问时如实说明，不假设证据内容。

例如“页面有问题”且没有上下文，可问“是哪一个页面，执行什么操作后出现了什么现象？”；若页面和错误已在上下文中，直接排查。用户只知道“系统慢”时，帮助缩小到操作、发生时间和影响范围；仍无法定位时给有限指引并保留未决项。无需让用户选择技能名或阶段。

## 从理解到动作

“帮我修复”“开始实施”等明确行动请求可选择有界执行；“只讨论”“不要改文件”限制当前范围。“继续”只恢复已明确且仍有效的动作，不扩展授权。仅“能否优化”可能是评估请求，应结合上下文判断；不得用关键词匹配替代理解。

模式选择不代替仓库身份、实现合同、用户决定或 Git/发布授权检查。排查授权不自动包含修改；实现缺少前置条件时说明具体阻塞并推进可独立开展的授权工作。用户请求简单咨询时直接回答，不创建流程产物。

“排查慢接口，并评估是否重构”包含两个目标：先取得性能证据，再评估重构；不能把评估自动升级为重构实施。将每个目标的下一动作和依赖带入任务包，返回时逐项验收。复杂请求只需向用户简述理解和下一步，不强制每次确认复述。

## 纠错与验收

用户纠正后，停止依赖旧理解的后续动作，报告更新后的目标与已执行情况，保留仍有效证据。已有修改要说明范围并协商处理，不擅自清理工作树；影响变化沿既有 stale/reroute 规则处理。

核验输出是否回答原问题、是否遗漏诉求、未决项是否被误报为已解决，再执行适用工作流证据检查。专项执行成功不等于用户目标已满足。找不到可执行工作但仍有未决项时，明确待补信息或门禁，不能宣布完成。

## 场景评估

使用 [分诊场景集](request-triage-scenarios.yaml) 回放时向执行者提供 input 和 context，保留其原始回答、动作及调用轨迹，再按 expected 和 forbidden 评分。固定技能版本、模型与运行条件，逐维度记录通过数和适用样本数；没有轨迹的案例标为未执行。模拟案例与真实误判样本分开统计，真实样本需脱敏。

静态合同测试只证明规则可查询、投影一致和边界未被改写，不证明自然语言分诊准确率。第一轮可用模拟场景作维护者桌面推演，但不得冒充独立模型回放或数字命中率。后续真实案例用于修订场景，禁止把一次误判泛化成所有请求的强制问卷。
