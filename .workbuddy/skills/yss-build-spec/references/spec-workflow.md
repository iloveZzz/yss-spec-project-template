# 非技术规格与完整交付

读取当前目标、来源、已确认决定及既有规格；存在 Context 时沿用稳定词汇，缺失不阻断综合，不自动创建 Context、ADR 或计划。普通查询仅回答问题；局部改稿仅修订受影响范围。

综合目标时保留来源中的对象、范围和确定程度，不因某个环节已有功能或更容易测量就缩小业务目标。细化指标、统计起止事件或目标值属于建议时，明确标为建议或待确认；来源已明确的口径直接沿用，不重复询问。

事实缺口使用 `.agents/skills/yss-research/SKILL.md`，业务分析使用 `.agents/skills/yss-analyze-business/SKILL.md`，真实取舍与词义问题分别使用 `.agents/skills/grilling/SKILL.md` 和 `.agents/skills/domain-modeling/SKILL.md`。可调查事实先调查；复用有效确认，多个来源冲突不静默改范围。

## 保存位置与命名

沿用用户指定位置和项目已有约定。无约定的新需求使用 `key = YYYY-MM-DD-<topic>`：首次创建产物时核实当地日期，后续保持不变；topic 使用具体需求的英文 kebab-case，优先复用 Context 的业务标识，如 `2026-11-14-user-batch-import`。

```text
docs/spec/<key>/<key>-spec.md
docs/spec/<key>/<key>-interaction.md
prototypes/<key>/
```

主文件与分文件交互说明共用同一 key；确有独立产品设计说明才新增 `<key>-design.md`，不增加必交付物。交互已合并到主文件时不强拆。原型只有新建独立工程时采用上述目录；已有共享原型继续增量维护，关联真实入口，不复制整套应用。文档 H1 使用清晰中文业务标题。

先查用户指定的材料、现有主规格及相关验收。按本次业务范围、已确认规则和是否可独立验收判断归属，复用用户已明确的归属。Spec 已交付、更新日期变化或多个需求共用原型工程时，仍按这些业务依据判断。

在第一次写入受影响的规格、交互说明、原型或工作台记录前，先向用户发一条可见消息。说清“沿用《已有 Spec 标题》”或“新建《拟建 Spec 标题》”，并给一条业务依据。衍生需求在这条消息里指出关联的原规格。仅需修订指定原型且查无关联 Spec 时，在这条消息中说明查阅结果和本次采用的修改依据。归属或修改范围明确时，发出消息后同轮继续。

查完材料仍有会改变归属的业务选择时，先只问决定范围的一问。受该选择影响的草稿、OQ 等文件内容及工作台记录都等到用户答复后，先发归属说明再写入。仅查询、索取研发接棒提示或交付已有材料时，按对应请求处理。

同一需求的补充、澄清和修错沿用原 key、文件及 FR/AC/OQ 编号。独立可验收的新范围另建具体 topic。新需求源自已有 Spec 时，在新正文写明两者的业务关系并链接原主规格。本地链接从新正文所在目录解析，按实际路径核对目标。没有原规格来源的独立需求按自身范围起草。

例如，向用户说明“新建《联系人批量导入》，关联《联系人列表》。导入有独立入口、处理结果和验收条件。” 新正文可写“从 `[联系人列表](../2026-11-12-contact-list/2026-11-12-contact-list-spec.md)` 的批量导入入口衍生，导入结果独立验收”，用项目实际路径替换示例链接。

同日同 topic 已存在时先读内容。属同一需求则复用，不同范围细化 topic，保留现有文件并避免随机后缀。日期不随修订更新，状态和版本放正文、既有元数据及 Git，不用 `v2`、`final`、`最新版`、`已确认` 命名。旧 `docs/spec/user-management/spec.md`、`interaction.md` 继续使用，局部修订不触发迁移。

`key` 不是工作台 Spec ID。明确要求改名已登记文件时，先沿用原数据目录核实 specId 与新路径是否被启用或停用记录占用；安全改名并同步正文相对链接、项目相对 resources、个人资源及受影响原型入口，再通过原 Spec 的“主规格相对路径”编辑保存，最后登记新路径并核对返回仍为原 ID。不能先登记新路径制造第二条记录，停用也不会释放占用。保持原问题、答复和历史；路径也参与产物摘要，纯改名后仍需重新核对确认，不改写旧确认。文件与工作台修改不是跨目录事务，失败时修复同一记录并说明当前路径，不创建补偿 Spec，也不覆盖并发改动。

## 主 Spec、澄清与确认

同一需求维护一个主 Spec，正文是业务规则的权威来源，交互说明、原型和补充材料通过主 Spec 关联；工作台只索引这些真实产物、问题和个人答复，不复制另一份规格。草稿保存后即可查看，登记或确认不是起草、修改与查看的前置。旧文件没有明确内容状态或真实确认记录时保持未知，不能从文件名、成熟外观或 `Content: ready` 猜测已确认。

生成或更新 Spec 时，先查当前材料和已有答复。Agent 当场使用 grilling 澄清影响本次范围的关键业务选择，提出可直接作答的问题，给出影响和建议。事实自行调查。可先完成不依赖该答案的内容，并在当轮会话中向用户提问。未决项保留稳定 OQ/问题 ID，记录事实缺口或业务决定、影响、建议、是否阻塞及受影响范围。等待只暂停依赖该问题的工作，其余部分继续；不会因此增加逐阶段审批。

用户可在当前聊天答复，也可在工作台答复、补充或延期。只把针对当前问题版本、仍有效且尚待采纳的业务答复落实到原 FR/AC/OQ、交互说明和相关原型。逐项核对结果后，在原问题记录解决依据，用 `appliedDecisionId` 引用实际答复 ID。沿用历史原文时，用户须针对当前问题明确保存，哪怕逐字相同也使用此次保存所得的新 ID。打开表单、填入旧文或取消编辑后，旧记录仍仅供复查。整份 Spec 的内容确认另按用户实际答复处理。

保留原问题编号及答复历史。新补充改变结论时，重新检查受影响范围。可调查事实用实际证据解决。聊天答复沿用原始来源，核实适用于当前问题后，用所装 CLI 支持的 `workbench respond` 保存并取得真实 ID。接口不支持时说明尚待关联，已有有效答复无须重问。

延期不等于解决：记录原因、影响、明确排除的范围，以及复查日期或条件，保留延期状态。范围内的 `open`、`deferred` 和尚未回写一致的答复均待处理。仅当用户明确将整个受影响范围排除出本次交付时，才可继续确认剩余范围。到期或满足复查条件时重新处理，不从沉默推断延期继续有效。提醒限于当前聊天和工作台打开/刷新时，不承诺后台通知。

范围内问题已回写和解决，必需产物及检查齐备后，才将内容标为 `ready`。另按用户的实际答复核对两项确认：

- **业务规格与验收**：核对用户明确确认的业务范围、规则及验收版本。
- **原型与交互说明**：核对用户明确确认的设计范围、原型及交互版本。有 UI 时，核心交互应可操作，纯展示可用高保真静态稿。无 UI 时确认实际业务逻辑或状态原型。交互说明可以与正文合用文件。

每项保留适用范围、可还原的采用材料版本和用户原始答复出处。采用 Git 提交时注明对应文件和提交。采用工作树版本时核对实际内容，用可回读的快照或文件内容依据标识。一次答复明确覆盖两项时复用同一答复。工作台联合确认须核对该记录的实际范围、材料与摘要确实覆盖两项。内容状态、预览链接、文件名和审批标签本身不能证明确认。沿用已有任务、用户答复或确认记录，无需另建确认包；使用工作台时先固定并展示实际采用材料，确认后将答复留在工作台或原任务。交接摘要引用该答复，避免将确认答复或材料摘要回填到同一摘要覆盖的文件，使有效确认失效。

正文、交互或原型实质变更时核对并重新确认受影响范围，旧确认仍对应原范围及版本。摘要变化先对照实际差异，沿工作台版本规则处理。草稿、分析、查看和明确的工程接入可继续。

### 复查改变的业务前提

关键问题依赖原 FR、AC 或前置 OQ 的决定时，在原题的影响中引用依据，并写清改变答案的条件。例如「只在 FR-12 允许转交后沿用旧页资格时，决定资格保留期限」。

正文规则改动、前置决定被替换或准备回写答复时，沿原出处核对实际受影响的问题、条款和验收。权限、时点、结果或适用范围发生实质变化时，在已授权的规格修订中同步更新正文与受影响的原题。保留原 OQ ID，在题意或影响写入变化后的事实和待核实范围。整份 Spec 的重新确认与单题的适用性分别核对。排版、技术等义调整和无关问题继续沿用有效答复。

回写前用所装 CLI 的工作台请求或页面复读当前答复及历史。只改正文或只保存前置题的新答复时，下游题摘要可能不变，仍须根据原出处核对适用性。单纯采纳当前答复时沿用回写字段规则。此次只需核对独立问题时，保留该题的原状态、答复和对应条款，待其写入授权明确时再采用其决定。

已有明确裁决时引用出处，真实取舍仍存时才提问。若原前提取消，使整条分支不再适用，在原 Spec 记录依据及影响。该题没有当前有效答复时将源问题保持为 `open`，工作台据实显示待复查，原答复留在历史。确需保存新决定时沿实际授权取得答复 ID。

## 工作台登记与续办

仅获委托修订指定原型时，规格流程的写入范围限于该原型，已有工作台登记可作为查阅依据。工作台登记或进展回写有另行有效授权时，按该授权的范围接续。

阶段进展及目标按项目根 `.template-spec/agents/workbench-progress.md` 接续。工作台、日常 Codex/终端和 PR/MR/CI 沿同一 dataDir、specId、实际 Spec 摘要及目标版本上报，复用真实任务与原验收。生成或更新产物后沿既有登记接口保存当前材料，随后核对摘要和进度；关键需求、业务验收及最终交付的确认关联用户实际决定、范围版本与证据摘要。

在获授权的工作台操作中，当前 CLI 支持登记时，在主 Spec 或关联材料保存/更新后自动登记同一主 Spec，无需再次确认；用户明确不使用工作台时遵从该选择。先查看 `yss version`、`yss workbench --help` 和对应子命令帮助；以下接口只适用于帮助实际列出它们的 CLI，模板更新不会使旧版获得新命令：

先从当前会话启动信息、已有续办文本等核实工作台数据目录。使用自定义目录时，以下所有命令统一使用 `yss workbench --data-dir <已核实的绝对路径> ...`；只有确认使用默认目录时才省略。已有目录不可改用默认目录重新登记，可查事实自行核实，不要求用户重复提供。

```sh
yss workbench register --root <项目绝对路径> --source <主Spec的项目相对路径> --json
yss workbench request --spec-id <实际登记返回的ID> --json
yss workbench respond --spec-id <实际ID> --question-id <原问题ID> --question-digest <当前问题摘要> --kind answer --answer '<用户实际答复>' --json
```

`register` 读取主 Spec 的一个 `<!-- yss-spec {JSON} -->` 元数据块，复用该项目和主文件的登记；附属材料放在 `resources`，不再各登记为独立 Spec。JSON 使用 `schemaVersion: 1`、`scope`、`contentStatus: "draft" | "ready"`、`resources` 和 `questions`。无状态时按草稿处理，不能由登记成功推导确认。资源含 `kind`（`supplement`/`prototype`/`interaction`/`other`）、`label`、`targetType`（`local`/`web`）、`target`（项目内相对路径或 HTTP(S) URL）；只填实际存在且可核对的材料。当前工作台无法锁定 web 资源版本，确认前须将相应资源项替换为已核验的项目内本地快照，使用 `targetType: "local"`；原链接可保留在正文来源中，同时保留 web 资源项仍会阻塞确认。问题含 `id`、`title`、`kind`（`research`/`decision`）、`impact`、`recommendation`、`blocking`、`affectedScope`、`status`（`open`/`resolved`/`deferred`）、`resolution` 和可空的 `appliedDecisionId`。正文中的问题详情与该索引保持一致，未决与延期不得改成 resolved 来获得 ready。

正文链接相对所在文档，`resources.target` 相对项目根，两者不混用；只有实际构建后才把原型资源指向 `dist/index.html`。支持新命名识别的 CLI 只将同目录同 key、无自身元数据且被主文档明确本地引用的 `<key>-interaction.md`（kind=interaction）或 `<key>-design.md`（kind=supplement/other）归主；有效自身元数据始终代表独立 Spec，其他参考文件不因被引用而归并。旧 `spec.md + interaction.md` 的无元数据推断保留。新命名归并须核验实际程序行为，不能仅凭相同命令帮助或模板更新推断旧二进制支持；兼容性未核实时只显式登记主路径，说明附件发现/归并尚未验证。

`request` 只读取续办上下文。终端 `request --json` 从 `result.text` 取文本，`respond --json` 保存成功后从 `result.responseId` 取真实答复 ID。工作台页面的 `GET /api/specs/<specId>/request` 在响应对象的 `text` 返回全文。工作台内 Pi 接收续办文本，使用 `ask_spec_question` 时从该工具的答复文本取得真实 ID。多行或含引号的答复使用宿主结构化参数或安全传参。

读取全文先定位当前问题数组。用每项的 `question.id` 找原问题，`digest` 对应当前摘要，`response.id` 标识该项的答复。分列历史原文的格式在当前数组内仅保留有效 `response`，并标明待回写、已回写、待复查或待答用途。历史区保留原文、原 ID 和复查原因，供追溯。页面复制的有效答复只覆盖所选内容。

已发布的 CLI 3.14.0（`74f3f5c`）把最近答复放在同一个问题数组，即使它已经失效。逐项核对同一 Spec 和问题的身份、`response.questionDigest` 与当前 `digest`、`state` 及实际适用范围。`open` 保留未决，`needsReview` 和 `overdue` 只供复查。即使是 `pendingWriteback`，也要核对延期的排除范围、日期和条件。问题变更、范围不符、被替换、已到期或已触发复查的记录只作历史。原数组无法还原的历史注明未知。回写前对照原问题的 `appliedDecisionId`、状态、`resolution` 和实际 FR/AC。已采纳且条款一致时直接引用，即使再次续办也跳过该次写入。建议、原型模拟和未保存的编辑均不能作为用户决定。

延期使用 `respond --kind defer`，按实际帮助传 `--reason`、`--impact`、`--excluded-scope`，并提供 `--review-at YYYY-MM-DD` 和当地 `--review-utc-offset-minutes`（中国为 `480`），或提供 `--review-when` 条件。按该安排保存的 `reviewUtcOffsetMinutes` 计算当地日期，到 `reviewAt` 当天及以后即待复查，包括旧版仍列为 `pendingWriteback` 的延期。旧记录有复查日期而无法核实保存时区时，保留原文并列为待复查。对 `reviewWhen` 查证实际触发事实，尚未核实时保留原条件并说明待核实。若已触发，按授权在原问题的 `impact` 补充事实和依据，将问题重开为 `open`。已采纳延期的原 `appliedDecisionId` 保留供追溯。续期需要当前版本的新安排与真实保存 ID。

有效延期只回写安排。保留 `reason`、`impact`、`excludedScope` 和原复查日期及时区或条件，在原问题写入 `status: "deferred"`、说明延期依据的非空 `resolution`，并以 `appliedDecisionId` 引用本次真实延期答复 ID。三项缺一仍待回写。再次登记后核对主 Spec、资源、问题及内容状态，再报告实际结果。

登记失败不等于内容丢失：保留已保存产物，明确失败步骤、主文件位置和具体错误；修复路径、元数据或 CLI 能力后重试同一主文件，不另建重复 Spec。不支持新接口时仍交付可读文件和查看方式，明确工作台尚未登记或更新；不能称登记、回写关联或确认已完成。

### 进度答复

用户问“做到哪了”或“现在需要我确认什么”时，先说明自用户上一条相关消息以来会影响判断的变化。再用现有问题和答复记录列出仍需用户决定的事项，说明各选项对范围、规则或验收的影响，并给出有依据的建议。已有确认和适用的答复直接引用。当前无需用户决定时，直接说明。无法核实上次状态时，说明当前能核实的范围。

纯进度询问只读取材料、问题及答复，直接在会话回答。进度上报和登记刷新只用于本次授权执行的工作。已有其他写入任务时，其工作仍按原有授权开展。用户随询问一并给出业务答复或明确要求修改时，按相应方法处理。

## 完整产品 Spec 的三类内容

1. **业务规格**：按 `.template-spec/templates/spec-template.md` 或当前适用结构说明问题、目标、角色场景、范围、规则、权限、状态异常、非目标、业务质量约束、可观察验收、重要来源和决定。量词、数值、边界保持来源一致；未知值列未决项。
2. **高保真交互原型**：有 UI 的需求用 `.agents/skills/yss-design-ui/SKILL.md` 表达用户如何完成任务；核心操作/状态变化可实际操作，纯展示可交高保真静态设计。低保真草稿可支持探索，不能单独称为完整交付。无 UI 使用 `.agents/skills/yss-prototype-logic/SKILL.md` 的业务逻辑或状态原型，不虚构页面，不以文字声明“原型不适用”省略它。
3. **交互说明**：规则和 AC 与页面/状态的对应、查看/运行方法、入口与退出、动作结果、校验与权限、失败/恢复、模拟范围、实际检查和未覆盖项。可与规格共用文件，不强制三个文件或额外包。

按任务选择适用原型形式，按风险选择覆盖范围和必要状态；完整有 UI 交付的高保真要求不以风险低为由省略。限定规则试验可辅助，但不替代产品 UI 原型。原型框架、演示代码和模拟数据不构成生产技术选型或契约，技术架构、接口、数据库和实现切片留给研发。

业务规格可以描述概念对象与关系、信息含义、值域、必填/唯一性、权限和状态；不能据此设计物理表、存储类型、主外键、索引、DDL、迁移方案、生产 API 路径/请求响应结构或分层实现任务。既有技术约束只注明来源和业务影响，不借引用补造决策。研究、来源与必要概念说明支持同一份规格，不增加必交付包。

采用增强规格结构时，先明确本次范围和采用材料的版本/读取时点；业务信息、角色数据范围及完整任务按实际复杂度使用短段落或对应表格，未知列未决，不要求简单需求填空表。AC 关联同一规则、初始角色/数据、操作、结果及不变项；交互说明定位实际场景、进入与重置方式。先列范围内任务和页面，再选择状态与验证深度，制作覆盖不能替代实际验证。

从讨论写回原 Spec 时，保留会改变结果的限定词。在原 FR 写清谁能在何种状态和时点操作，在对应 AC 用一个反例说明拒绝结果及仍保留的数据。权限条件说明谁有资格操作，承诺执行成功还需相应依据。不变项按动作核对，转交时对其他数据的保证只适用于转交。

以负责人转交为例，逐项核对原材料是否确定了「当前」「待处理」和「只改变负责人」。原文只说「按负责人权限控制」时，在受影响的 FR/AC 标明未定的判定时点和失败结果。作者可仅凭原条款核对这一例，再按下文「交接提示」引用已有编号。

贯通写法可按需查看 `.agents/skills/yss-design-ui/assets/spec-delivery-example/README.md`；它只提供教学输入、Spec、原型与说明的对应，不提供真实产品事实。局部改稿只更新受影响规则/AC/页面及采用版本，不自动补建完整产物。

业务票仅在用户明确要求拆票时作为规格的组织形式输出，保留原 FR/AC，不是第四类交付物；普通 Spec 完成不自动拆票。“确认 Spec”“准备交给研发”不授权技术设计。用户明确要求技术设计或开发时作为研发任务按授权承接，分别说明成果与缺口，不以 profile 标签拒绝或新增阶段审批。

角色、条件、状态、交互或变更关系需要关联阅读时，按 [图解表达](../../yss-write-docs/references/visual-explanation.md) 选择必要图表，放在相关规则附近并引用其章节或编号；已有文字足够就复用。图文冲突先核对来源，未知条件保留未决项，不用图示补造业务决定。

### 分批编制

多个场景共用权限、状态或业务决定时，先在当前任务中列出场景、对应的原 FR/AC、原型入口或状态及阻塞项，再按能完整演示的业务结果分批编制。同一目标沿用主 Spec 和已有 FR/AC/OQ 编号。

关键业务决定按上文的 grilling 方法澄清。未决项只暂停依赖该决定的部分，继续编制独立场景。核对整个交付范围的成功、拒绝与恢复路径，并检查跨批共用规则在规格、原型和交互说明中的一致性。仅受委托修订指定原型时，修改限于指定范围。

## 交接提示

已登记 Spec 沿用原数据目录和 Spec ID，附采用材料、参与工程及版本、原验收和本次完成终点。采用工作台决定前核对数据目录、Spec ID、工程根与主文件；只有当前工程材料可核实时，明确工作台记录的缺口。已有进度目标时，按项目根 `.template-spec/agents/workbench-progress.md` 核对产物摘要 `specDigest` 和目标版本 `goalVersion`。工作台普通续办文本的「来源摘要」只覆盖主文件。接收方核对最新事实后在原授权范围内续办，产物更新继续登记同一主 Spec。

新会话接手或续办中发现关联材料更新时，逐一对照主 Spec、相关原型和交互说明的可读内容、当前采用的版本以及现有记录能观察到的版本。已登记的材料按[工作台续办指引](../../../../.template-spec/agents/workbench-progress.md#交接与-agent-续办请求)查现有摘要和材料变更记录。主文件相同也要检查相关材料。说明变更的材料及差异、受影响的 FR/AC 和需复查的结论，沿用仍有效的答复 ID、采用依据、确认范围及独立验收。

只能读取旧版时，说明实际读到的路径和版本。现有线索能证明有新版时，指出已观察到的版本差异或变更项，并明确新版内容中仍待核实的部分。只有读到新版内容才能报告其具体行为。材料取舍按已有确认与用户答复处理，实际冲突只暂缓受影响的工作。

完整 Spec 交付、用户表示准备交接或单独索取提示词时，结合实际材料给出交接要点和可复制提示词。引用规格、原型和交互说明的位置及版本或读取时点，指出已确认范围、原验收、模拟边界和实际验证。分别说明自己读到了什么、接收方能否访问，未核实的访问情况注明未知。材料不全时交代缺口及影响，交接有依据的部分。目标工程或材料地址缺失时使用明确占位项。普通查询、局部修订和探索草稿按本次请求交付。

接收方是前端实现任务时，按 [原型交给前端](../../../../.agents/skills/prototype-review/references/frontend-handoff.md#原型交给前端) 说明体验承诺、关键场景复验依据和演示边界，复用已有的检查记录。

交接权限变化、判定时点或失败后保留的数据时，先定位原 Spec 的 FR、AC 或稳定小节，再按接收方能读到的材料决定写多深。

- 接收方能读到完整反例时，给出具体条款和它裁决的场景，接收方据此即可判断。
- 原条款可读且事实足够，但未写反例时，引用条款后用一句话说明谁在何时、什么条件下做了什么、结果如何、哪些数据保留，并标明这是从哪几条已确认规则推得的结果。
- 发送方读过、接收方无法读取时，写明来源位置及采用版本、访问限制和已确认范围，在允许共享的范围内摘述同样的最短反例。
- 事实不足或条款冲突时，列清缺失的时点、失败结果或优先关系，指明影响哪些 FR/AC。可查事实自行核实，真正的业务取舍回到原问题，有依据的部分继续。

负责人转交后的撤回示例见项目根 `.agents/skills/yss-analyze-business/references/business-analysis.md`。若同一用语在不同场景下含义不同，交代谁负责裁决、谁使用结果。Frontend 接手可见状态、可用操作和错误反馈，纯文案修改按原范围完成。Backend 沿用实际架构和原验收，MVC 保持既有分层，DDD 涉及建模时才核实一致性与事务边界。

交接摘要分别列「业务规格与验收」「原型与交互说明」两项的适用范围、采用材料及版本、用户确认依据。材料或确认缺失、版本不匹配或范围内仍有未决项时，指出欠项、影响范围与最小补齐动作，注明材料供评审，并提示暂停相关研发写入。只有用户已明确排除整个受影响范围时，才把未决项视为本次交接范围外。已有确认只复用其有效部分。

提示词以用户明确的分析、设计或开发要求为准；仅说准备交接时，先读取材料和目标工程，分析影响与待决问题，暂不修改生产代码。原型模拟不构成生产契约，生成提示不自动启动研发或授权提交、推送、部署及对外发送。

上下文明确采用 PR/MR 协作，或用户希望以可审阅文件变更交付时，说明可使用 `yss-deliver-pr-mr` 及其用途；只询问如何准备时提供说明，不调用技能或写入 PR/MR。仅分享链接或提示词、没有 PR/MR 需求依据时不主动推荐。用户明确请求执行 PR/MR 交付即可表达意图，无需点名技能；按宿主支持的方式调用 `yss-deliver-pr-mr`，不能调用时读取并遵循其方法，按授权处理并说明能力限制。其他指定渠道按实际能力和授权处理。渠道或目标不明确时先整理内容并说明缺口，不默认创建或更新 PR/MR，也不向他人发送消息。

例如，用户要把已确认的退款规则交给后端、退款例外尚未决定，可给出这段接棒提示。用实际材料位置替换方括号：

> 请读[退款规格位置及版本]的[权限条款及拒绝路径 AC]和[对应原型位置]，按已确认的验收分析后端影响。退款例外仍待业务方决定，请指出受影响的行为，已有验证沿用材料中的记录。

## 综合与检查

### Spec 正文审查

完整 Spec 的正文和验收成稿后，在标记就绪、提交用户确认或作为本轮完整成果交接前，默认执行一次正文审查。正文形成后即可开始，原型可以并行制作。实质修订按差异核对改动条款、关联验收和受影响的既有规则。探索稿、纯文案或排版调整、仅修订原型、仅索取交接提示按各自请求处理。单独委托正文审查时，按指定范围只读检查，返回发现和待澄清问题。

先定位主 Spec 候选版本和审查范围，读取本次采用的原始需求、有效业务决定、正文规则和相关验收。候选版本、范围和依据都仍适用时，复用已有可核对的审查结论。来源缺失时指出哪条承诺无法判断，继续检查有依据的部分。

1. **双向核对来源与范围。** 从本次适用的已确认要求查正文和验收是否遗漏，再从会改变业务结果的条款反查依据，核对范围、条件、数值和例外。能从已确认规则明确推导的结果写清依据。检查待定或已排除的内容是否被写成承诺。
2. **按风险检查规则组合。** 选择能区分业务结果的具体反例，检查权限或状态跨时点变化、动作顺序、条件重叠和失败恢复等适用组合。定位冲突或遗漏的条款及验收。结果有两种合理解释时，说明各自影响，交由用户裁决。
3. **检查关键规则是否可验收。** 定位每项关键规则对应的验收场景，按现行规则从给定前提和操作推演结果，核对预期的可观察结果及不变项，找出修订后仍沿用旧预期的验收。覆盖有影响的成功、拒绝、边界和恢复路径。已有场景可直接引用，一个场景可覆盖多条规则。

在现有会话或交付摘要中记录审查范围、候选版本或读取时点、发现和未验证项。每项发现写明原 FR、AC、OQ 或章节、依据、触发条件、影响和建议。

权限、状态或恢复行为的高风险争议会影响验收时，在该发现中补一条可重放的反例。引用原 FR/AC 或章节及产物版本，写明角色、初始状态和数据、按顺序执行的动作、预期结果及应保留的数据、实际观察到的结果。说明结论依据的是正文推演、实际操作还是模拟，以及模拟覆盖的范围。预期未获裁决时列出各解释对应的结果。无法重放时记录已核实的部分和具体未验证的动作或结果。

编制或修订时，依据明确的修正限于本次授权可写的条款、验收和关联产物，随后定点复查。范围外的修正列为建议。关键业务选择沿原问题按[澄清与确认方法](#主-spec澄清与确认)处理。关键规则或验收因未决问题、依据缺失仍无法判定时，暂缓受影响范围的就绪与确认，继续独立部分。建议性意见随摘要交付，就绪与用户确认沿用现有范围和版本规则。

### 产物复核与后续发现

交接后的研发发现沿原 FR/AC 或章节回到同一规则，保留材料版本或读取时点、相关原型状态与模拟范围、实现关联及实际验证缺口；没有编号不新建 ID。动态来源在开始依赖工作和交付前按风险复读，只检查本次消费内容的实质变化。仅排版或技术选择变化且业务结果不变时继续原工作；涉及业务结果、权限或验收时定位差异并定点澄清，独立工作可继续。

Spec 与原型冲突时保留两处实际来源，不把原型可操作当作业务决定；模拟成功也不证明真实服务已验证。已确认修订在本次可写范围内增量更新原规格，其他仓库或远程材料先准备修订建议，实际写入仍使用对应授权；交接不自动评论、关闭条目或通知他人。

从正式前端接收原型或交互修订时，按 [正式前端回写原型](../../../../.agents/skills/prototype-review/references/frontend-handoff.md#正式前端回写原型) 核对采用版本、实际复验和变更依据。沿用同一主 Spec 和仍有效的确认。按授权回写已确认变更，业务规则或验收确有变化时更新原 FR/AC，并复查受影响条款与采用材料。仅委托修订指定原型时，写入限于该原型。

设计发现回写同一份规则与 AC，避免第二规格。按 `.agents/skills/prototype-review/references/review-method.md` 检查实际产物及承诺路径，覆盖影响任务的成功、拒绝、边界、状态变化和恢复。静态图不证明交互，代码存在不证明运行，Agent 自检不等于真实用户研究。

缺工具时继续完成独立内容并记录具体未验证项；关键规则未定、必需原型缺失或所需验证未执行，仍是未完整交付。非关键延期项说明影响和解决条件。使用 `.agents/skills/yss-write-docs/SKILL.md` 改善表达，不改变事实。

保存/发布遵循 [tracker 操作](spec-tracker.md)。没有 tracker 时继续授权的本地或对话草稿；实际发布前确认目标与权限。按 [用户决定](user-decisions.md) 复用授权，不额外增加阶段确认；有真实审批要求才记录实际展示内容与用户回复，中途可按授权保存或发布明确草稿，不暗示已批准。返回主规格与原型引用、实际结果及下游限制，不自动创建 PR、关闭 Issue 或启动研发。
