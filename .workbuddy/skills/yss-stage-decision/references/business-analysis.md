# 业务分析方法

从当前问题选择适用维度，不要求每项生成文件。以“谁在什么条件下做什么，得到什么可观察结果”组织结论。

| 维度 | 要回答的问题 |
|---|---|
| 问题与场景 | 谁遇到什么问题，已有流程哪里不足，期望结果是什么，证据在哪里 |
| 目标与范围 | 包含什么、不包含什么，优先级依据是什么，哪些目标互相冲突 |
| 概念与责任 | 角色、业务对象、信息来源、规则提供方/使用方与交接责任如何划分 |
| 规则与权限 | 什么触发动作，前提和例外是什么，谁能执行、能看哪些数据，结果如何可见 |
| 状态与恢复 | 成功、拒绝、取消、失败、重试、并发冲突或恢复会怎样，哪些动作不合法 |
| 方案取舍 | 哪些方案确实解决同一问题，各自收益、代价和限制是什么，何时重新考虑 |
| 业务质量 | 哪些质量要求已有依据，观察口径是什么，未知数值由谁决定 |
| 验收缺口 | 哪些结果还无法判断，应调查、澄清还是通过原型体验 |

需要关联解释角色、状态、权限或变更时，使用 [图解表达](../../i-have-adhd/references/visual-explanation.md)。业务分析负责转换的角色、触发、条件、目标状态与拒绝结果；未决信息保持可见，图解只选择表达，不替代业务决定。

用具体故事和反例检查边界：权限变化后能否继续、部分成功后重试什么、取消是否保留原数据、重复动作是否重复产生业务结果。只讨论当前影响的场景，不把技术幂等或事务方案提前定为实现要求。

业务依赖方向与 HTTP/消息方向分开表达，不从表结构反推业务边界。核对已知实现与期望行为时标明差异，不把尚未部署的代码当作现状。

来源、假设和决定分别记录。重要未决项写清影响与解决条件，未知责任人/时点就保留未知；不能编造限制使规格看似完整。多份材料冲突先定位来源与版本，实质业务取舍交回用户。

分析结果回到当前 Spec，保持规则、状态和验收一致；无需另建 Plan、ADR 或集合。只有确有难逆转且需要解释的真实取舍，且用户授权记录时，才维护决策说明。

涉及对象或字段时，在同一 Spec 说明业务含义、归属、关系、必填、有效值、默认、唯一性及保存后可修改条件；唯一性需有范围和编辑时的自身排除规则，默认需区分建议与强制。涉及多角色时分别说明可见数据、操作前提、允许与拒绝结果，不能只写按钮隐藏或禁用。简单关系可用短段落，复杂条件再用规格中的对应表格；未知列未决，不补造技术模型。

按角色任务串起起点、跨页动作、结果和返回/失败分支；AC 给出实际初始角色、状态、代表数据、操作及可观察结果和不变项。已有规则或较长场景用具体引用复用，局部修订只更新受影响内容。
