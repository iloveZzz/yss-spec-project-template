# 按业务行为拆票

仅用户明确要求拆票或显式调用时使用。业务票是业务规格的组织形式，不是完整 Spec 的第四类必交付物；“确认 Spec”“继续完善规格”“准备交给研发”不自动触发拆票。复用已确认讨论、Spec、现有票、稳定 ID 和产品设计，不重新访谈或生成平行票集。

按完整可观察业务行为组织票据，写明业务价值、范围、原始规则/FR、验收项/AC、业务依赖与未决项，不机械一条 FR 一票。不要求实现仓、技术选型、API 冻结或构建命令，也不要求先拆业务票才能交给研发。

参考 `.template-spec/templates/business-ticket-template.md`，字段按真实来源填写；没有集合就不填写虚构引用或新建集合。已有集合继续维护同一引用与覆盖情况。

业务对象、概念关系、信息含义、必填/唯一性、权限与状态规则可以写；不据此生成物理表、字段存储类型、主外键、索引、DDL、迁移方案、生产 API 路径与请求响应契约、技术分层或实现切片。已有技术事实可注明来源及业务影响后引用，不能借引用扩写新的技术设计；原型模拟数据不构成生产契约。

需要产品设计时围绕流程、状态、失败与恢复校准，未决项说明影响和解除条件，不生成空原型。用户明确要求技术设计或研发拆分时，识别为研发任务并按授权使用适用研发能力；本技能保持业务票职责，不以 profile 标签拒绝已授权的研发请求。

tracker 沿用明确配置和对应操作授权。远程父子/阻塞关系使用真实 ID，支持时用原生关系，无能力才用文本；已存在原生关系不维护另一套阻塞清单。完整读取相关分页与实际状态，未知状态不当成已解决。普通分析仅在对话给出拆分；只有授权保存/发布才修改条目。

返回每票业务结果、范围、验收、依赖、未决项和实际保存状态。实质改变范围/规则/验收时明确缺少的业务决定；等义细化复用已有授权，不新增审批节点，不强制主控回交、关闭父票或宣布功能完成。
