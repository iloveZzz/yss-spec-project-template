# 按请求组织业务票或工程票

仅用户明确要求拆票或显式调用时使用。“确认 Spec”“继续完善规格”“准备交给研发”不自动触发拆票；明确的实现请求直接使用 `implement` 或适用研发能力，不要求先建票。复用已确认讨论、Spec、现有票、稳定 ID 和产品设计，不重新访谈或生成平行票集。

Ticket 指待完成的工作项，Issue 是承载工作项的一种方式。按用户已有 tracker 和材料组织，保留规则的原始来源；文件来源仍以原文件为准，Issue 本身是来源时才以其正文为准。采用 tracker 时，当前执行状态在该 tracker 维护，工作项引用来源与实际进展，不复制另一份规则或状态台账。

按用户要求的结果和原始输入选择分支，不能仅凭当前 Profile、安装位置或输入来自 Spec 判定职责：

| 本次要求 | 按需读取 |
| --- | --- |
| 组织业务行为、业务范围和验收，产出业务票 | [业务票](references/business-tickets.md) |
| 把需求、Spec、设计或 Issue 拆成实际工程可实现的增量，产出前端或其他工程票 | [工程票](references/engineering-tickets.md) |

同时要求两类时分别保留业务验收与工程执行边界，关联真实条目，不强制建立父子两层结构。只有分支差异实质影响范围且现有上下文无法判断时才澄清；已明确的研发拆分请求不因 Profile 标签被降为业务票。

已授权的 `implement`、前端应用等研发任务需要组织可验收增量时，可按项目根直接读取 `.agents/skills/to-tickets/references/engineering-tickets.md`。读取方法不调用拆票入口，不要求新增 Ticket、父票或拆票阶段，也不自动启动其他仓库的实现。

接收、恢复、读取或写入 tracker 工作项时，读取项目根的 `.template-spec/agents/issue-tracker-operations.md`，按共享方法定位目标、处理关系与执行对应授权。普通拆分分析在对话给出结果；保存或发布使用已有对应授权。

返回每票结果、范围、来源与验收、依赖、未决项和实际保存状态；工程票补充真实执行位置与完成终点。实质改变范围、规则或验收时说明缺少的业务决定，等义细化沿已有授权继续，不新增审批节点。
